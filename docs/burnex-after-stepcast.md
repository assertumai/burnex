# Burnex после форка stepcast: функционал доработок

Период: от импорта stepcast (`ce98cf5b`, 2026-09-28) до `develop` на 2026-10-28.
Описание собрано по `docs/`, `user_docs/`, `archived.md`, коммитам и выборочно сверено с `src/`.

## 1. Движок пайплайнов

### `skip_exit_code` — код выхода «пропущено»
- Командный шаг (`run` / `script` / `uses`) может сообщить «делать нечего», не роняя прогон: процесс выходит с объявленным кодом, шаг и его работа получают статус `skipped`.
- Объявляется на пайплайне, работе (в теле или в месте подключения) или шаге; действует ближайшее объявление. Значение — целое 1..255, по умолчанию не задано. На шаге `agent` и шаге плагина это ошибка разбора.
- Код проверяется до `expect`, `output_schema` и judge. Пропуск считается последней попыткой, оставшиеся `attempts` не тратятся, остальные шаги работы не выполняются.
- Прогон, где есть только успехи и пропуски, получает `success`; `fail_fast` не срабатывает.
- `burnex lint` отклоняет `expect: exit_code`, совпадающий с кодом пропуска.
- Источник: `docs/pipeline-format.md` — «Skip exit code».

### Shadow-режим
- Запуск: `burnex run … --shadow` или `POST /api/run` с `shadow: true`. Режим пишется в `run.json` (`mode`), `resume` продолжает в том же режиме.
- Каждый непрозрачный шаг (`agent` / `run` / `script` / `uses`) обязан объявить `external`, иначе прогон отклоняется до старта. Шаг с `external: true` не исполняется: движок пишет запись действия, и шаг считается успешным.
- Плагин с `external: true` в контракте выполняет внешнее действие только через точку действия движка; в shadow-режиме это действие записывается.
- В запись попадают файлы `action-<n>.json` и событие `step.action`; из `env:` записываются только имена переменных. Предикаты (`cmd` / `script` / `judge`) исполняются как обычно.
- Назначение: прогнать сценарий «насухо» и проверить, какие внешние действия он совершил бы.

### `on_fail.analyze` — анализ причины сбоя
- Если шаг завершился `failed` после последней попытки, агент вызывается ровно один раз. Ответ пишется в `analysis.md`, статус шага не меняется: анализ только советует.
- Ключи: `analyze`, `model`, `model_tier`, `effort`, `prompt`, `external`.
- Агент выбирается так же, как для шага `agent`: блок `on_fail` выступает отдельным уровнем; при `agent_policy: fallback` значение `analyze` — только запасное.
- Анализ идёт в свежей сессии без MCP, таймаут фиксирован (600 с). В промпт передаются хвосты stdout/stderr по 16 КБ. Исход: `written`, `failed`, `skipped` или `shadowed`.

### `on: always` при пропущенных зависимостях
- Работа с `on: always` исполняется при любом исходе зависимостей, в том числе если все они пропущены (по условию, из-за `fail_fast` или по `skip_exit_code`). Условие `if` по-прежнему проверяется.
- Это ломающее изменение: прежнее поведение возвращается явным условием по статусам зависимостей.

### Выходные значения работы (`outputs`)
- Шаг `run` получает в `BURNEX_JOB_OUTPUTS` путь к файлу и дописывает туда строки `key=value`.
- Зависимые работы с прямым `needs` получают значения как переменные `NEEDS_<JOB>_<KEY>`.
- Ограничения:
  - ключ — `^[A-Za-z_][A-Za-z0-9_]{0,63}$`;
  - значение — до 4096 байт;
  - на работу — не больше 32 значений;
  - имя, похожее на секрет, отклоняется.
- Список `outputs: [...]` сам запись не ограничивает. Если объявленный ключ так и не опубликован, работа падает, а `lint` проверяет `$NEEDS_*` по объявленному набору.

### Объявляемая оболочка для строкового `run` (`shell`)
- По умолчанию строка исполняется через `sh -c` (`cmd.exe /c` на Windows). `shell` задаёт префикс argv: команда запускается как `[...shell, command]`.
- Действует ближайшее объявление: шаг → работа → пайплайн. Пустой список отклоняется `lint`. Списочную форму `run` ключ не затрагивает.

### Переопределение env на один прогон
- `burnex run --env KEY=VALUE` (флаг можно повторять) или поле `env` в `POST /api/run`.
- Меняются только ключи, уже объявленные в верхнеуровневом `env:` пайплайна. Необъявленный ключ или многострочное значение отклоняются; подстановки в значении не раскрываются.
- Переопределения сохраняются в `run.json` (`env_overrides`), `burnex resume` берёт их оттуда.

### Шаг `review-set` — ревью набором агентов
- Входы: `set` (обязателен), `strategy` / `strategy_file`, `out`, `prompt`, `permissions`, `secret` и другие.
- Стратегия — именованная из `review.strategies` конфигурации или файл. В ней задаются `reviewers` (с гейтом `scope`), шаблон `per_repo` и `aggregator`.
- Модели задаются через `model` или `tier` (взаимоисключающие): `max` / `deep` / `balance` / `fast` / `mini` плюс собственные `model_tiers`.
- Ревьюеры работают параллельно. Агрегатор запускается, только если успешных ревьюеров больше одного; если он упал, итог — объединение находок, и шаг не падает.
- Находки уровня CRITICAL/MAJOR, затрагивающие несколько репозиториев, публикуются во все названные MR.
- Источник: `docs/review-set.md`.

### Исполнение шагов в контейнере
- Ключ `isolation: host | container` на шаге или работе. Действует ближайшее: шаг → работа → `defaults.isolation` → `host`. Плагины и `decision` ключ не принимают.
- Глобальная секция `container`: `runtime: podman | apple` (значения по умолчанию нет), `image`, `base_image`, тома, `cpus`, `memory`. В проектной конфигурации секция запрещена.
- Окружение проверяется перед стартом, откат на хост не делается никогда. Агент с непустым `mcp` в контейнере отклоняется.
- Пути монтируются один в один, каждая попытка агента идёт в свежей сессии.
- Команды: `burnex container status | build | login`.

### Циклы по группам работ (`loops`)
- Цикл объявляет набор работ, которые повторяются проходами: `jobs`, `while`, `max_iterations` (обязателен), `cost`, `wallclock`. В `while` доступны только участники цикла и `loop.*`.
- На границе прохода выносится вердикт: `done`, `exhausted` или `canceled`. При `exhausted` прогон получает `failed`, при исчерпании `cost` — `budget_exceeded`.
- Переменные: `BURNEX_LOOP`, `BURNEX_LOOP_ITERATION`, `BURNEX_LOOP_ITERATION_MAX`.
- `lint` выдаёт ошибки на:
  - неизвестного или повторного участника;
  - работу, входящую в два цикла;
  - `needs: all`;
  - работу вне цикла, стоящую на пути между участниками.

  Предупреждает, если не задан `cost`, и о ловушке с пропущенным участником.
- `resume --from` разрешён только на точке входа цикла; незавершённый цикл переигрывается с первого прохода. Проходы видны в ленте прогона CLI.

### Повторы работы целиком (`attempts` на работе)
- `attempts: { max: N }` перезапускает упавшую работу с первого шага. Значение ограничено `limits.attempts`; повторы отдельных шагов этим ключом не задаются.
- Не повторяются:
  - пропуск;
  - превышение бюджета;
  - отмена;
  - `backend_rate_limited` и `backend_unauthenticated`.

  Рабочая директория между попытками не откатывается.
- Переменные `BURNEX_JOB_ATTEMPT` и `BURNEX_JOB_ATTEMPT_MAX`. Бюджет работы покрывает все её попытки, зависимые видят только финальный исход.
- `lint` запрещает `max > 1` внутри `session_group`. При resume работа считается единым целым.

### Возобновление завершённого прогона с выбранной работы
- `burnex resume <run> --from <job | job/step> [--set k=v]` создаёт новый прогон с `resumed_from`. Шаги выше точки `--from` переиспользуются по совпадающему ключу.
- В дашборде у работы на графе есть кнопка **Resume from this job**. У идущего прогона кнопки нет; отказ (нет секрета, не прошла предстартовая проверка) показывается прямо на кнопке.

## 2. Учётные данные

### Сервис `credentials` и секреты по имени
- Секрет объявляется в верхнем ключе `secrets:` пайплайна:
  - имя — `^[a-z][a-z0-9_-]{0,63}$`;
  - `provider`;
  - `env` — по умолчанию имя в верхнем регистре с заменой `-` на `_`; префикс `BURNEX_*` запрещён.
- Шаг получает секреты через `secrets: [имя]`.
- Значение доступно только тому, кто его объявил: процессу шага `run` / `script` / `uses`, плагинному шагу, MCP-серверу, workspace. **Агенту секрет не передаётся никогда.**
- Секреты разрешаются до создания каталога прогона. Значение короче 8 символов отклоняется. В логах и `prompt.txt` значения маскируются.
- Встроенные провайдеры: `env-file`, `glab`, `keychain`. Свой провайдер подключается как вклад плагина по контракту `burnex/pipeline`.

### Провайдер `glab`
- Параметр `host` обязателен. Токен берётся командой `glab auth status -t --hostname <host>`; формы без хоста нет, поэтому токен чужого хоста подхватиться не может.
- Пустой, замаскированный (`*`) или слишком короткий токен отклоняется с подсказкой `glab auth login --hostname <host>`.

### Провайдер `keychain`
- Читает токен из связки ключей macOS: `security find-generic-password -a <account> -s <service> -w`, таймаут 5 с. Не на macOS прогон отклоняется до старта.
- Для бэкендов отдельно есть `backends.<id>.credentials.<VAR>`. Ключ задаётся только в `~/.burnex/config.yml`, значение попадает только в окружение процесса CLI; в контейнере такой ключ отклоняется.
- Экран Settings → Keychain (`/keychain`).

### Подстановка `${env.*}` не раскрывает секреты
- Подставляется только объявленный `env` (работа / include / пайплайн); окружение машины не читается. Необъявленное имя — отказ работы.
- Выражение остаётся литералом, если имя — переменная секрета, попадает под `env_deny` или значение содержит значение секрета.
- Переменная с секретом убирается из окружения остальных шагов (событие `env.withheld`).

## 3. Бэкенды агентов и выбор модели

### Новые бэкенды
Подключаются строкой в `plugins:` глобального конфига (`burnex/backends/cursor`, `burnex/backends/copilot`, `burnex/backends/antigravity`) или через Settings → Agents. Выбираются через `agent:` или `defaults.agent`.

| Бэкенд | Имя бэкенда | Модель по умолчанию | Что умеет | Ограничения |
|---|---|---|---|---|
| Cursor | `cursor-agent` | `composer-2.5-fast` | сессии (`--resume`), список моделей, `permissions.mode` → `--sandbox` | нет MCP, `output_schema`, `strict`, reference trees |
| GitHub Copilot CLI | `copilot` | `claude-sonnet-4.5` | запуск с `--allow-all` | нет сессий, usage и списка моделей; на живом CLI не проверен (`backend-copilot-live: postponed`) |
| Google Antigravity | `antigravity` (CLI `agy`) | `gemini-3.8-flash-high` | сессии | оплата квотой: показывается оценка, а не деньги |

Ни один из трёх не принимает effort: effort из настроек отбрасывается с событием `backend.degraded`, а effort в документе пайплайна отклоняет прогон.

### Каталог моделей и цены
- Цены лежат в `src/builtin/prices/model-prices.json` и поставляются с пакетом.
- Стоимость берётся из отчёта CLI (`reported`); если её нет — оценка по каталогу (`catalog`); у Antigravity — `quota`.
- Модель без цены не проверяется против `budget.cost`.

### Уровни (tiers) и порядок выбора модели
- Встроенные уровни: `max`, `deep`, `balance`, `fast`, `mini`; свои задаются по маске `^[a-z][a-z0-9_-]*$`.
- Модель ищется по уровням шаг → работа → пайплайн; на каждом явный `model` сильнее `model_tier`. Tier, которого нет у агента, считается незаданным. Дальше по цепочке: `backends.<agent>.default_model` → `defaults.model` → встроенная модель.
- Effort ищется по тем же уровням (учитывается effort самого tier, если модель дал он), затем `default_effort`, затем `defaults.effort`.
- Встроенные пайплайны указывают уровни (`deep`, `balance`), а не конкретные модели.

### Агент и уровень на шаг и на весь пайплайн
- Ключи конфига `step_agents` и `pipeline_agents`; их записывает экран Pipelines.
- `pipeline_agents` действует только на шаги, где ни шаг, ни работа не объявляют `agent` / `model`.
- Итог проверяется командой `burnex config --pipeline <p>`.

### Выбор пользователя против выбора пайплайна (`agent_policy`)
- `force` (по умолчанию): приоритет растёт в порядке пользователь → пайплайн → работа → шаг, то есть документ пайплайна сильнее.
- `fallback`: пайплайн → пользователь → работа → шаг, то есть выбор пользователя сильнее. Чужая для бэкенда `model` из документа отбрасывается в пользу tier, затем `default_model`.

## 4. Демон и эксплуатация

### Сервис триггеров в демоне
- Демон раз в минуту опрашивает источники триггеров: `schedule` (`trigger-schedule`) и `gitlab-comment`. Запуск идёт тем же путём, что `POST /api/run`.
- Лимиты: `ui.triggers.max_concurrent_runs` (10) и `max_concurrent_agent_jobs` (4). Расписания отключаются через `disable trigger-schedule`.

### Расписания
- Объявляются в `triggers.schedule` файла пайплайна или в `ui.triggers.schedules` домашнего конфига (repo / branch / pipeline). Есть экран расписаний в дашборде.
- На каждый пайплайн одновременно живёт не больше одного прогона.
- `max_catchup_hours` (по умолчанию 2; `0` — только текущая минута): после сна или выключения запускается один пропущенный момент.
- `keep_awake`: `caffeinate` держит машину бодрствующей во время прогона, `pmset schedule wakeorpoweron` будит её за 120 с до момента. Нужный сниппет sudoers Burnex только предлагает, но не устанавливает.
- `require_network`: перед запуском проверяются DNS и TCP до хоста `origin`; если сети нет, момент пропускается.

### Автозапуск через launchd
- `burnex up --install` создаёт `~/Library/LaunchAgents/com.burnex.daemon.plist` (`RunAtLoad`, `KeepAlive`) и переносит в него `PATH` и `SSH_AUTH_SOCK` текущей оболочки.
- `burnex down` выгружает агента, `burnex down --uninstall` удаляет plist. После обновления `--install` нужно повторить.

### Установщик и мастер настройки
- `install.sh` требует Node 22. Раскладывает релизы в `~/.burnex/releases/<v>` и ставит `~/.local/bin/burnex`; по умолчанию берёт последний тег `v*`, поддерживает `--ref` и `--repo`.
- `burnex setup` проходит этапы node, git, glab, backends, glab-auth, token-scopes (нужен скоуп `api`). Поддерживает `--host` и `--json`. Записывает только `defaults.agent` и строку в `plugins`; в неинтерактивном режиме ничего не пишет.
- Первая интерактивная команда один раз запускает `burnex setup`. Первый `burnex up` до настройки открывает экран Integrations.

### Самообновление и поставка через npm
- `burnex update` действует по способу установки из `~/.burnex/install.json`:
  - `managed` — последний тег `v*`;
  - `checkout` — сборка как есть;
  - `npm` — `npm install -g burnex@latest`, реестр переопределяется через `BURNEX_NPM_REGISTRY`.

  После обновления демон перезапускается.
- Burnex публикуется как npm-пакет в Artifactory по тегу `vX.Y.Z` (ручной джоб `publish` в CI).

## 5. Очередь backlog и self-improve loop

### Блокировка очереди
- Все, кто пишет в `backlog.md` / `archived.md` (`pick`, `finish`, `settle`, `merge-lanes`, демон дашборда), работают по схеме «lock → read → edit → write → release».
- Lock-файл: `<git common dir>/burnex-backlog.lock`, а вне git — `.backlog.lock` рядом с очередью. Внутри JSON `{pid, host, command, acquired_at}`, файл создаётся с `O_EXCL`.
- Попытка повторяется каждые 50 мс; через 10 с ожидания команда выходит с кодом 2.
- Брошенный lock (тот же host, процесс мёртв) снимается; lock с чужого host не трогается. `list` lock не берёт.

### Новые поля пункта и статус `postponed`
- `needs` — slug'и зависимостей. Пункт свободен, только когда все зависимости `done`. Неизвестный slug или цикл зависимостей — код 2.
- `goal` — один целевой документ; `details` — список файлов или каталогов с материалами (принято хранить их в `backlog/<slug>/`). Пункт с отсутствующим путём `pick` пропускает, `pick --only` падает.
- `claimed_by` (`run:<id>` или `dispatch:<id>`, ставится через `pick --owner`) — владелец взятого пункта. Пункт с владельцем считается зависшим не по возрасту (`--stale-hours`), а по живости владельца: процесс прогона или `state.json` диспетчера. `finish --owner` с чужим владельцем ничего не меняет.
- `postponed` — пункт не берётся в работу, не занимает группу и не удовлетворяет `needs`. На доске у него своя колонка «Postponed».

### Команды
- `burnex backlog add <slug> --title --why --done-when [--group] [--needs] [--goal] [--details] [--status todo|postponed] [--after slug]` добавляет пункт под lock'ом. Все проверки выполняются до записи.
- `burnex backlog show <slug> [--owner] [--run-dir]` выводит взятый диспетчером пункт без правки очереди; с `--run-dir` пишет `item-a.json`.
- В коммиты `merge-lanes` и `settle` попадает только правка блоков своих пунктов. Чужие блоки очереди остаются байт в байт.

### Сведение на вершину ветки: `burnex merge-lanes --onto <branch>`
- Дорожки прогона сливаются на текущую вершину ветки, а не на стартовый коммит. Поэтому несколько прогонов от одной базы сводятся друг за другом.
- Работает под merge lock (`<git common dir>/burnex-merge.lock`), публикация идёт через `git update-ref` с проверкой старого значения. При расхождении исход — `publication_conflict`.
- Если основная копия грязная вне файлов очереди, сведение ждёт без ошибки и раз в 10 минут пишет события `merge.dirty_waiting` / `merge.dirty_resolved`.
- `--check` (по умолчанию `project.check`) задаёт проверку. `--keep-claim` оставляет неслитый пункт в `in_progress` для повторной попытки. С `nested_repos` режим не работает.

### Автономная петля
- `caffeinate -i sh scripts/self-improve-loop.sh` гоняет `.burnex/pipelines/self-improve.yml` итерация за итерацией. Перед каждой итерацией движок собирается из `HEAD` в отдельном worktree; `npm ci` выполняется только при смене lockfile.
- Петля останавливается, когда прогон ничего не закоммитил, когда упала сборка или когда исчерпан `MAX_RUNS` (по умолчанию 20). Грязная рабочая копия петлю не останавливает.
- `goal` и `details` пункта попадают в контекст агентских работ петли (propose / plan / implement / review) через запись контекста `item_refs`.
- Заготовки под будущего диспетчера:
  - `improve-item.yml` — прогон одного уже взятого пункта;
  - `resolve.yml` — повторная попытка неслитого пункта по пакету свидетельств.

  Самой команды `burnex dispatch` пока нет: это целевая архитектура из `docs/dispatcher-target.md`.

### Board и Backlog — проектный плагин
- Экраны Board (`/scrum`) и Backlog (`/backlog`) и их API вынесены из ядра в `.burnex/plugins/backlog/`.
- Колонки доски хранятся в `.burnex/board.yml`, пункты меню — в `.burnex/routes.yml`.
- Без `npm run build` (включает `build:plugins`) экранов нет.

## 6. Пакеты и маркетплейс

### Пакеты
- Пакет — один каталог: `<project>/.burnex/packages/<name>/` (слой проекта) или `~/.burnex/packages/<name>/` (домашний слой). Имя — kebab-slug; `burnex` зарезервировано.
- Манифест `package.yml` (строгая схема):
  - обязательные поля: `version: 1`, `kind: package`, `name` (совпадает с именем каталога), `description`, `package_version` (semver);
  - необязательные: `owner`, `private`, `plugins`, `integrations`, `pipeline_agents` (значения по умолчанию);
  - `needs: { backends, mcp, secrets, packages }`.
- Что приносит пакет:
  - `pipelines/*.yml` — запуск `burnex run <package>:<name>`; такие пайплайны видны на экране Pipelines и в запуске прогона;
  - `steps/<name>/step.yml` и `scripts/`;
  - `plugins/` — каталожные плагины подключаются сами, `.mjs` — строкой в `plugins:`; поддерживаются серверная и браузерная половины;
  - `widgets/<id>.tsx` — адресуются по голому id;
  - `dashboards/<id>.yml`;
  - `routes.yml` — маршруты в таблице меню.
- Порядок поиска: свободный каталог проекта → пакеты проекта → свободный каталог home → пакеты home → встроенное. Пакет проекта целиком затеняет одноимённый пакет home. Дубликат плагина, виджета или дашборда в одном слое — ошибка загрузки.
- Серверная половина плагина импортирует только `burnex/plugin`, `burnex/pipeline` и `burnex/ui-plugin` и поставляется собранным ESM. `burnex/ui-plugin` даёт хелперы HTTP-обработчиков (`sendJson`, `readBody`, `isLocalOrigin` и др.) и типы экранов.
- Сломанный пакет падает отдельно, остальные загружаются.
- CLI:
  - `burnex package list [--json]` — имя, слой, версия, каталог и причина поломки;
  - `burnex package new <name> [--home]` — создаёт заготовку с версией 0.1.0.
- Пример: `examples/packages/hello/` — пайплайн, виджет и плагин с обеими половинами.

### Маркетплейс
- Каталог — git-репозиторий из `marketplace.repo` (только в `~/.burnex/config.yml`). Он клонируется в `~/.burnex/marketplace/catalog` и читается с `main`. Демон делает fetch при первом обращении и затем раз в минуту.
- Экраны: What's New, Agents (`skill`, агентский `plugin`, `mcp`, `extension`) и Burnex (`package`). Вид `package` заменил прежние pipeline, burnex plugin и integration. Экраны открываются с последним известным каталогом и перерисовываются, только если свежий ответ отличается.
- Установленность читается с самой машины:
  - skill и MCP — по местам назначения всех агентов (home и проекты);
  - extension и агентский plugin — командой `check` записи;
  - package — по `~/.burnex/marketplace/installed.json`.

  Результат кешируется на 5 минут.
- Значки проверки: **Verified** — запись на `main`. Для своей записи на ревью — **In review**, **Changes requested** или **Closed**.
- Установка: `burnex marketplace install <entry> [--home | --project <root>] [--layer] [--agents] [--replace] [--proceed] [--yes]`.
  - Для пакета сначала проверяются `needs`; для каждой недостающей зависимости называется способ её закрыть. `--proceed` ставит пакет, несмотря на недостающее.
  - Пакет ставится одним каталогом: Update заменяет каталог, Remove удаляет.
  - Копию, изменённую после установки, Burnex перезаписывает только по запросу; карточка показывает расхождение.
  - Всё, что запускает команды, требует `--yes`.
- Публикация: `burnex marketplace publish <package dir> [--dry-run]`.
  - Owner, версия и описание берутся из `package.yml`. Уже существующая версия отклоняется, `private: true` не публикуется.
  - Публикацию блокируют значение секрета в файлах, импорт серверной половины за пределы пакета и отсутствующий файл из `plugin.json`.
  - Карточка показывает, что пакет приносит и что ему нужно.

- `docs/config.md`, раздел «Deferred: Secrets»: утверждает, что отдельной сущности секретов нет, а сервис `credentials` уже есть. Похоже, раздел устарел.
