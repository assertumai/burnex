# Burnex: пять моделей навигации

Открыть `burnex-navigation.html` в браузере. Это автономный кликабельный
макет: сеть запрещена Content Security Policy, API демона не вызывается,
состояние хранится только в памяти страницы. Сборка приложения и перезапуск
демона не нужны. Можно открыть конкретную концепцию фрагментом `#1` … `#5`.

Исходники макета: `index.html`, `styles.css`, `prototype.js`. Автономный файл
собирается командой `node docs/design/navigation-2026-11-10/package.mjs`.

## Основание

Разбор текущих исходников, а не аудит живой страницы: доступ к интерфейсу
на localhost через браузер в этой сессии не удался. Наличие процесса на
127.0.0.1:7717 проверено без изменения его состояния. Рабочие данные не
считывались; все карточки, числа, ошибки и сценарии в макете демонстрационные.

Прочитаны `src/builtin/routes.yml`, `ui/src/plugins/shell.tsx`,
`ui/src/pages/Home.tsx`, `Scrum.tsx`, `Decisions.tsx`, `Proposals.tsx`,
`ui/src/api.ts`, `src/parts/ui/grouping.ts` и описание продукта в README.

Наблюдения по коду:

- Decisions и Proposals входят в `extend` в маршрутах, но в `Work` на главной.
  Действия человека сложно найти по их назначению.
- Backlog и Scrum — два представления очереди, но поданы как разные разделы.
- Настройки исполнения и устройство самой витрины конкурируют с ежедневной работой.
- Сценарий, прогон и задача должны иметь разные названия и объяснимые связи.
- Меню расширяемое. Реализация не должна заменять реестр маршрутов статическим списком.

## Сравнение

| № | Модель | Принцип | Выигрыш | Компромисс |
|---|---|---|---|---|
| 1 | По этапам | Обзор → планировать → выполнять → проверить | Объясняет весь процесс и следующий шаг | Настройки на втором уровне |
| 2 | Центр внимания | Состояние → причина → контекст → действие | Ускоряет работу оператора параллельных прогонов | Пустая очередь хуже знакомит с продуктом |
| 3 | Вокруг задачи | Очередь → задача → связанный прогон | Сохраняет намерение пользователя | Не все прогоны связаны с задачей |
| 4 | Вокруг сценария | Каталог → сценарий → запуски | Показывает повторяемую автоматизацию | Очередь задач менее заметна |
| 5 | Карта возможностей | Намерение → функция → объект | Помогает обнаружить возможности | Больше чтения перед действием |

Одна палитра, типографика и набор демонстрационных сущностей намеренно
использованы во всех пяти вариантах. Отличаются основной объект, первый
экран, группировка меню, плотность и путь пользователя.

**Рекомендация: начать с №1.** Основная цель — понятность возможностей
burnex, а не только скорость наблюдения. Взять из №2 заметный вход в
ожидания человека, из №5 — короткие пояснения возможностей. Это гипотеза,
не подтверждённый пользовательскими исследованиями результат.

## Карта существующих экранов для варианта №1

| Сейчас | Предлагаемая точка входа | Смысл / ограничение |
|---|---|---|
| Home `/` | Обзор работы | Состояние и следующий шаг |
| Backlog `/backlog` | Планировать → Задачи → Список | Та же очередь |
| Scrum `/scrum` | Планировать → Задачи → Доска | То же редактирование задач |
| Pipelines `/pipelines` | Выполнять → Сценарии | План, а не выполнение |
| Runs `/runs` | Выполнять → Все прогоны | Конкретные запуски |
| Run `/runs/:projectKey/:runId` | Карточка прогона | Шаги, вывод и состояние |
| Decisions `/decisions` | Проверить → Решения | Ожидающие шаги человека |
| Proposals `/proposals` | Проверить → Предложения | Diff конфигурации `.burnex`, не любое ревью кода |
| Usage `/usage/:period?` | Настроить → Расходы; ссылка из прогона | Источник цены и неполнота данных сохраняются |
| Agents `/agents/:tab?` | Настроить → Агенты и модели | Default, backends, tiers, policy |
| Secrets `/secrets` | Настроить → Секреты | Только имена и доступность |
| Schedule `/schedule` | Настроить → Расписание; вход из сценария | Просмотр, не новый редактор |
| System `/system` | Настроить → Состояние системы | Не смешивать с наблюдением за прогоном |
| Packages `/packages` | Расширения → Пакеты | Состав и ошибки ресурсов |
| Widgets `/widgets` | Расширения → Виджеты | Установленные компоненты |
| Routes `/routes` | Расширения → Маршруты | Адреса и композиция меню |
| Cleanup `/cleanup` | Настроить → Хранилище прогонов | Сохранить предпросмотр очистки |
| Пользовательские маршруты | Собственные группы / Расширения | Не терять динамические вклады |

Это информационная архитектура, а не обещание готовности всех вторичных
экранов макета: для настроек и расширений показаны входы и поясняющие панели.
Основные рабочие пути кликабельны: задача, сценарий, прогон, ожидание,
предложение, ошибка, форма запуска, список/доска, поиск по задачам.

## Граница изменений без backend

Возможны новые подписи, группировка меню, объединение представлений очереди,
карточки сценариев, клиентская сводка внимания и контекстные переходы.
Существующие маршруты, параметры и действия API следует сохранить.
Каркас должен продолжать использовать реестр экранов/слоты, а ссылки —
разрешаться через текущий механизм целей маршрутов.

Прогоны группируются по `projectKey` и `pipelineFile`, как в `grouping.ts`;
совпадение названия не является надёжной связью. Для варианта №3 нельзя
выводить историю задачи из совпадений названий. Показывать только явную
связь, а при её отсутствии — «Связь неизвестна» и вход во все прогоны.
Полная история задачи, новые правила уведомлений, редактор расписаний и
новые серверные сущности находятся вне этого макета.

## Как выбрать по понятности

Дать 5–7 людям, не знающим структуру меню, одинаковые задания. Менять порядок
вариантов между участниками, чтобы знакомство с первым не исказило сравнение.

1. Найти очередь и подготовить запуск конкретной задачи.
2. Объяснить разницу между задачей, сценарием и прогоном.
3. Найти место, где движку нужен ответ; отличить ожидание от ошибки.
4. Найти предложенную агентом правку конфигурации и понять её эффект.
5. Найти выбор модели, расходы и расписание.

Фиксировать первый выбранный раздел, завершение без подсказки, неверные
переходы и время. После задания просить пересказать назначение функции.
Выбирать по успешности и правильному пониманию; скорость и субъективная
симпатия — дополнительные критерии. Цифры эффективности заранее не выдумывать.

## Проверка и эксплуатация

Исходный код приложения, конфигурация демона и каталог `dist` не изменены.
Макет не содержит fetch, WebSocket, EventSource или submit-форм.
Кнопки принятия/отклонения только показывают уведомления; новая задача
добавляется в память страницы. После перезагрузки всё сбрасывается.
В CSP отдельно запрещены соединения и отправка форм; автономный скрипт
разрешён своим SHA-256, внешние зависимости отсутствуют.

Проверены синтаксис JS, сборка автономного файла и переходы с DOM-заглушкой.
Визуальная проверка в браузере в этой сессии недоступна; её нельзя считать
выполненной. Перед внедрением нужны проверка desktop/mobile и реальные
пользовательские задания. Само внедрение в рабочую витрину не выполнялось.
