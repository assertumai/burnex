# Установка и обновление

Как поставить, обновить и откатить burnex, как вести разработку из рабочего дерева и где что лежит.

## Установка

Одной командой, без клонирования руками:

```bash
curl -fsSL https://raw.githubusercontent.com/assertumai/burnex/main/scripts/install.sh | bash
```

Скрипт берёт последний тег `vX.Y.Z`, собирает его и раскладывает релиз в
`~/.burnex/releases/<версия>`; ссылка `current` указывает на действующий
релиз, а лаунчер `~/.local/bin/burnex` — на `current`. Нужны `git`, `npm` и
Node ≥ 22. Если `~/.local/bin` не в `PATH`, скрипт печатает строку
`export PATH=…` и профиль не правит.

- `--ref <ссылка>` — тег, ветка или sha вместо последнего тега. Пока в
  репозитории нет тегов, скрипту без `--ref` нечего ставить:
  `… | bash -s -- --ref main`.
- `--repo <адрес или путь>` — другой репозиторий (форк, `git@…`, локальный путь).
- `--force` — заменить чужой файл на месте лаунчера (например, `npm link`).
- `BURNEX_HOME` (по умолчанию `~/.burnex`) и `BURNEX_BIN_DIR` (по
  умолчанию `~/.local/bin`) переносят каталог релизов и лаунчер.

Сбой на любом шаге оставляет прежний `current` нетронутым. Скрипт пишет
паспорт установки `~/.burnex/install.json`, по которому `burnex update`
знает, чем обновлять.

### Обновление

```bash
burnex update              # последний тег; --ref <ссылка> — другая версия
burnex update --no-restart # не перезапускать демон витрины
```

`update` обновляет тем способом, каким движок поставлен:

- **managed** (через `install.sh`) — запускает `install.sh` из
  `releases/current` с теми же `BURNEX_HOME` и `BURNEX_BIN_DIR`, что
  при установке; ничего не делает, только если установлен ровно этот тег
  (сборка ветки или sha обновляется всегда);
- **checkout** (рабочее дерево с `npm link`) — `git pull --ff-only`, `npm ci`,
  `npm run build`; при незакоммиченных правках отказывает до любых шагов;
  с `--ref` вместо `pull` — `git fetch` и `git checkout <ref>`, а ветка затем
  догоняется `git pull --ff-only`. Тег или sha отцепляют HEAD: следующий
  `update` без `--ref` откажет с подсказкой назвать ветку
  (`burnex update --ref main`);
- **npm** — `npm install -g <пакет>@<ссылка или latest>`.

Способ берётся из паспорта, а без него выводится из места установки;
выбранный способ и каждая команда печатаются. Команда не читает конфигурацию
и работает, когда она сломана. После успешного обновления демон витрины
перезапускается: агент launchd — через `launchctl kickstart -k`, отсоединённый
демон — остановкой и `burnex up` новой версии в его каталоге проекта; не
поднятый демон не поднимается. Демон, поднятый прежней версией (в записи
`ui.pid` нет каталога), не трогается: `burnex update` просит перезапустить
его самому — `burnex down && burnex up`.

### Откат релиза

Прежние релизы остаются в `~/.burnex/releases/`; откат — переключение ссылки:

```bash
ln -sfn ~/.burnex/releases/<прежняя> ~/.burnex/releases/current
```

Порядок выпуска версии — [docs/release.md](release.md).

### Разработка: `npm link`

Пакет объявляет бинарник `burnex`, но сборка сама по себе не выкладывает его
на `PATH` — до установки команду зовут полным путём (`node dist/src/bin.js`), а
`burnex up` отвечает `command not found`.

Разработка ведётся по симлинку: он указывает прямо в рабочее дерево, поэтому
правки видны сразу после пересборки, без переустановки.

```bash
npm install && npm run build && npm link
```

`npm link` создаёт симлинк в глобальном каталоге npm (`$(npm prefix -g)/bin/stepcast`),
ведущий на `dist/src/bin.js` этого репозитория. Следствия, о которых стоит
знать заранее:

- **После правки исходников нужен `npm run build`.** Симлинк ведёт на
  собранный файл, а не на исходник, и без пересборки команда продолжит
  работать по прошлой сборке.
- **Каталог репозитория нельзя переносить или удалять** — симлинк повиснет, и
  `stepcast` перестанет запускаться.
- **Если `$(npm prefix -g)/bin` не в `PATH`,** линковка ничего не изменит:
  проверьте `npm prefix -g` и добавьте его `bin` в `PATH`.

Откат:

```bash
npm unlink -g stepcast
```

Демон витрины в автозапуск не прописывается: после перезагрузки машины
`burnex up` нужно вызвать заново.

Витрина, которую отдаёт `burnex up`, сама по себе исходники на React и
TypeScript в `ui/`; `npm run build` уже собирает её (`vite build` в
`dist/ui-web/index.html`) вместе с кодом на Node — отдельного шага не нужно.
При правке самой витрины удобнее `npm run dev:ui`: он поднимает dev-сервер
Vite с горячей перезагрузкой и проксирует `/api` на уже запущенный демон
(`burnex up` в другом терминале), не заставляя пересобирать `dist/ui-web`
на каждое изменение.

## Где что лежит

| | |
|---|---|
| Бинарник | `burnex` (на `PATH` после установки или `npm link`) |
| Пайплайн | `burnex.yml` или `.burnex/pipelines/*.yml` |
| Работы | `.burnex/jobs/*.yml` |
| Переиспользуемые шаги | `.burnex/steps/<имя>/step.yml` |
| Пакеты | `.burnex/packages/<имя>/package.yml` и `~/.burnex/packages/<имя>/` — [docs/packages.md](packages.md) |
| Конфиг | `~/.burnex/config.yml` и `.burnex/config.yml` |
| Прогоны | `~/.burnex/runs/<project>/<run>/` |
| Переменные | `BURNEX_*` (переходно читаются и `STEPCAST_*`) |
