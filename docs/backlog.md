# Очередь улучшений (`backlog.md`) и команда `burnex backlog`

Очередь — список пунктов, которые предстоит сделать, в одном файле
Markdown. Ведёт её человек в обычном редакторе; `burnex backlog`
разбирает, отбирает и правит файл, не зная ничего о проекте, в котором он
лежит, — ни конфигурации, ни `.stepcast/`, ни каталога прогона. Заводится
очередь в любом репозитории созданием файла в этом формате — второй
документ не нужен.

## Формат файла

Файл состоит из преамбулы и пунктов.

Преамбула — всё до первого заголовка второго уровня. Она не разбирается:
в ней можно писать что угодно, включая таблицы и строки вида
«ключ: значение» — движок в неё не заглядывает. Огороженный блок кода
(тремя обратными кавычками либо `~~~`) в преамбуле пропускается целиком,
так что пример пункта, приведённый во вводном тексте, пунктом очереди не
становится.

Пункт начинается с заголовка второго уровня, слаг которого — kebab-case
(строчные латинские буквы, цифры и дефис, без пробелов и заглавных букв):

```markdown
## slug-of-the-item

status: todo
title: Короткое название
why: Зачем это нужно
done_when: По чему признаётся выполненным
```

Под заголовком — плоские поля вида `ключ: значение`, по одному на
физическую строку; значение не переносится на следующую строку. Пустые
строки внутри пункта пропускаются. Строка, которая не разбирается ни как
следующий заголовок, ни как поле, ни как пустая строка, — отказ разбора.

Обязательные поля: `status`, `title`, `why`, `done_when`.

| Поле | Значение |
|---|---|
| `status` | слово из строчных латинских букв, цифр и `_`; смысл движок знает у `todo`, `in_progress`, `done`, `failed` |
| `title` | одна строка о том, что делается |
| `why` | зачем это нужно |
| `done_when` | по чему признаётся выполненным |

Необязательные поля: `group`, `track`, `started_at`, `claimed_by`, `reason`, `repos`, `needs`, `goal`, `details`.

| Поле | Значение |
|---|---|
| `group` | слаг смежности; по умолчанию действующая группа равна слагу самого пункта |
| `track` | вес пункта — метка, по которой пайплайн выбирает цепочку работ |
| `started_at` | ISO 8601, проставляется командой `pick` при взятии в работу |
| `claimed_by` | владелец взятого пункта вида `run:<id прогона>`; поле движка, как `started_at`: проставляется командой `pick --owner` и снимается `pick` без него; в запись `list`/`pick` не входит |
| `reason` | причина отказа; проставляется командой `finish` при `--status failed` |
| `repos` | репозитории, которых касается пункт, — перечень каталогов через запятую (`.` называет корень дерева); по умолчанию корень |
| `needs` | слаги пунктов, которые должны быть `done` до того, как этот станет свободным, — перечень через запятую; по умолчанию зависимостей нет |
| `goal` | путь файла с целью пункта от каталога очереди; по умолчанию пусто |
| `details` | пути файлов с подробностями от каталога очереди — перечень через запятую; по умолчанию пусто |

Значение `track` — слаг в kebab-case; значение другой формы — отказ разбора,
называющий пункт и значение. Проверяется **форма, а не словарь**: какие слова
что означают, решает пайплайн, читающий выдачу, а перечень допустимых в движке
запретил бы репозиторию назвать свои веса своими словами. Пункт без поля даёт
пустую метку, а не слово по умолчанию: слово было бы тем же навязанным
словарём.

Цена этого выбора названа прямо: опечатка (`expres` вместо `express`) — не
отказ разбора, а несовпадение с меткой, которую ищет ветка пайплайна. Пункт
пойдёт цепочкой по умолчанию — той, что пайплайн назначил непомеченным. В
петле этого репозитория умолчание — полная цепочка, то есть опечатка стоит
денег, а не качества.

Что именно облегчается, очередь не знает и знать не должна: она несёт метку, а
цепочку под неё выбирает пайплайн. В петле саморазвития этого репозитория
(`.stepcast/pipelines/self-improve.yml`) облегчённая ветка снимает планирование
и ревью, оставляя описание изменения, реализацию и объявленную проверку.
**Разметка — весь критерий:** снятое ревью ничем другим не заменено, и пункт,
названный простым по ошибке, доедет до коммита без второго мнения. Работы
облегчённой ветки обязаны сказать об ошибке разметки вслух, а не подгонять
работу под неё; такой заход завершается отказом дорожки, и пункт возвращается
человеку с `failed` — перевести его в полный вес правкой поля и есть
исправление.

Значение `repos` — перечень имён через запятую (`repos: backend` либо
`repos: ., backend`): каждое имя — относительный путь без сегмента `..`, без
символов шаблона глоба и без абсолютной формы; пустое значение, пустой
элемент перечня и повтор имени — отказ разбора. Разбор не проверяет, что
названный каталог объявлен составом `nested_repos` — очередь не знает
устройства проекта, это проверяет `burnex project repos` (см. ниже).
Пункт без поля означает корень — ровно то же, что `repos: .`.

Значение `needs` — перечень слагов через запятую (`needs: alpha, beta`):
каждый элемент — слаг в kebab-case; пустое значение, пустой элемент и повтор
слага — отказ разбора, называющий пункт и поле. Форму проверяет разбор, а
связи — `list` и `pick` (см. «Зависимости пунктов» ниже).

### Материалы пункта: `goal` и `details`

`goal` — один файл с целью пункта, `details` — перечень файлов с подробностями
(`details: backlog/an-item/a.md, backlog/an-item/b.md`). Пути отсчитываются от
**каталога файла очереди**, а не от каталога, откуда позвана команда; принятое
место — `backlog/<слаг>/`. Форма та же, что у имён в `repos`: не абсолютный
путь, без сегмента `..`, без `*` и `?` — путь называет один файл, а не
глоб. Пустое значение, пустой элемент и повтор в `details` — отказ разбора,
называющий пункт и поле. Запись пункта (`list`, `item-<дорожка>.json`) несёт
пути как написаны: `goal` — строка (пустая без поля), `details` — перечень.

Существование файлов проверяет только `pick`, под тем же замком, что и отбор:
пункт с отсутствующим (или названным каталогом) путём **пропускается** — как
ждущий `needs`, до проверки группы, так что группу он не занимает и пункт той
же группы ниже берётся вместо него. На каждый пропущенный пункт в поток
ошибок уходит строка со слагом и первым отсутствующим путём; стандартный вывод
остаётся JSON. `pick --only` на такой пункт — отказ с кодом `2` и перечнем всех
отсутствующих путей, очередь не меняется (проверка идёт после «не найден»,
«не свободен» и «ждёт зависимостей»). `list`, `finish` и `settle` файлов не
проверяют: удалённый материал одного пункта не должен ломать просмотр очереди
и проставление исхода.

Запись контекста [`item_refs`](pipeline-format.md#запись-item_refs) подаёт эти
файлы работам петли. Она разрешает пути от рабочей директории шага, поэтому
совпадает с якорем очереди только когда **очередь лежит в корне рабочего
дерева** (так в этой петле: `slots` зовёт `backlog pick` без `--file`, из
корня); при иной раскладке шаг откажет, не найдя файл.

Разбор `reason` не требует даже при `status: failed`: очередь, у которой
пункт помечен отказом без причины, читается дальше — терять на этом всю
очередь было бы хуже, чем недосчитаться объяснения. Обязателен ключ
`--reason` у самой команды `finish`, а не поле у разбора.

Поле, не входящее ни в один из этих списков, разбором принимается и
переживает любую правку файла — команда переписывает и дописывает только
названные ей поля, остальные строки пункта не трогает.

Слаг пункта обязан быть уникален в пределах файла — повторный слаг делает
неоднозначным и отбор, и проставление исхода, и это отказ разбора.

## Файл `archived.md`

Пункты, доведённые до исхода (`done` либо `failed`), со временем делают
`backlog.md` нечитаемым — открытая работа тонет в решённом. `archived.md`,
рядом с `backlog.md` в корне того же проекта, хранит историю таких пунктов в
том же формате. `burnex backlog` этого файла не знает вовсе: перенос
пункта из `backlog.md` в `archived.md` делает человек вручную, тем же
редактированием, каким ведётся сама очередь.

Экран «Очередь» витрины читает у каждого проекта оба файла и показывает их
пункты одним списком: сперва пункты `backlog.md` в его порядке, затем пункты
`archived.md` в его порядке, — с именем файла-источника у каждого пункта.
Отсутствие `archived.md` не ошибка, тем же приёмом, каким уже не ошибка
отсутствие `backlog.md`.

Статус вне этих четырёх (`postponed`, `review`) — не ошибка разбора: очередь
вправе завести своё состояние. Для движка такой пункт просто не свободен —
отбор его не берёт, пока статус не вернут в `todo`.

## Доска витрины (`/scrum`)

Экран «Доска» показывает очередь одного проекта колонками. Встроенных четыре:
три — состояния формата (`todo`, `in_progress`, `done`), четвёртая — архив, то
есть файл `archived.md`. Пункт со статусом `failed` показывается в колонке
«Сделано» с меткой отказа: отказ — исход, а не место в работе.

Пункт со статусом, под который колонки нет, доску не ломает и в чужую колонку
не подкладывается: над доской появляется полоса «статус … на доске без
колонки» с кнопкой «Добавить колонку». Диалог спрашивает название колонки и
место — между какими соседями её поставить. Раскладка целиком пишется в
`.stepcast/board.yml` проекта (маршрут `POST /api/board/columns`):

```yaml
columns:
  - id: todo
  - id: postponed
    title: Отложено
  - id: in_progress
  - id: done
  - id: archive
```

Встроенные колонки в файле обязаны быть все, имена колонок — статусы той же
формы, что в очереди. Отсутствие файла — встроенная раскладка; сломанный файл
показывается отказом рядом с очередью, а доска встаёт встроенными колонками.
Заведённая колонка принимает карточки наравне с `todo` и `done`: бросок
проставляет пункту её статус.

Щелчок по карточке открывает справа от доски панель деталей: поля `title`,
`why`, `done_when`, `group`, `track`, `repos` и `needs` правятся прямо там и
сохраняются маршрутом `POST /api/backlog/item`. Пустое значение
необязательного поля убирает само поле. Под полем `needs` панель перечисляет
зависимости: слаг, статус из пунктов проекта (`backlog.md` и `archived.md`,
очередь приоритетнее) и отметку — «met» у `done`, «waiting» у любого другого
статуса, «not in the queue» у слага, которого нет ни в одном файле. Перед
записью маршрут проверяет граф зависимостей так же, как `list` и `pick`:
неизвестный слаг и цикл — ответ `400` с `error` и `at`, файл не меняется.
Статус в панели не правится — его
задаёт колонка; `started_at`, `claimed_by` и `reason` показаны, но принадлежат
движку — их пишут `backlog pick` и `backlog finish`.

Владелец взятого пункта виден и там, и на экране «Backlog»: у `in_progress` рядом с
моментом взятия — ссылка на прогон, когда `claimed_by` имеет вид `run:<id>`, иначе
строка как записана; у пункта без `claimed_by` ничего нет. Занятая блокировка
очереди (см. «Блокировка очереди») показана предупреждением в разделе проекта на
«Backlog» и над колонками «Scrum»: команда, pid, машина, момент и возраст владельца,
а для брошенной и чужой машины — пояснение, что делать. Блокировка моложе секунды не
показывается — обычная запись держит её миллисекунды. Отказ записи доской по
блокировке (`409`) выводится текстом ответа демона.

Карточки перетаскиваются. Перенос между колонками правит `status` пункта,
перестановка внутри колонки — его место в файле, а перенос в архив и обратно
переносит пункт между `backlog.md` и `archived.md`, не трогая проставленный
исход. Пишет файлы сам демон, маршрутом `POST /api/backlog/move`, и отвечает
результатом: отказ виден на доске, а не теряется.

Колонка «В работе» — единственная, в которую доска не пишет. Бросок на неё
открывает выбор пайплайна, и в работу пункт берёт уже запуск:

```
burnex run <пайплайн> --input item=<слаг>
```

Пайплайн доезжает до пункта тем же путём, каким получает любой вход: объявляет
`inputs.item`, передаёт его работе, раздающей слоты, а та зовёт `backlog pick
--only "<слаг>"`. Пайплайн, не объявивший входа `item`, в диалоге не
предлагается: запуск взял бы не этот пункт, а очередной свободный, и молчаливая
подмена хуже отсутствия кнопки.

## Отбор пункта в работу

Свободен для взятия пункт со статусом `todo`, а также пункт
`in_progress`, взятый раньше объявленного порога давности (по умолчанию
шесть часов): такой пункт считается зависшим — прогон, который его взял,
оборвался по сигналу, крашу или бюджету, и ждать больше нечего. Пункт
`in_progress` без поля `started_at` либо с значением, не разбираемым как
дата, тоже считается зависшим и свободен. Пункты `done` и `failed`
свободными не бывают никогда.

Пункт `in_progress` с владельцем (`claimed_by: run:<id>`) судит не возраст, а
прогон-владелец. Жив ли он, определяют по журналу прогонов проекта: каталог
прогона есть, состояние `running`, процесс из манифеста существует. Мёртвый
владелец освобождает пункт сразу, при любом `started_at`; живой удерживает
пункт и его группу, даже когда пункт старше порога. Прогон, продолженный
командой `resume`, ведёт ту же работу: мёртвый владелец, чей потомок по
`resumed_from` жив, тоже считается живым. Когда о владельце судить нечем —
каталога прогона нет (прогон шёл на другой машине либо убран уборкой), форма
владельца не `run:<id>` или конфигурация проекта не читается (в последнем
случае `pick` пишет предупреждение в stderr), — пункт зависает по прежнему
порогу давности, как пункт без владельца. Конфигурация проекта нужна `pick`
только когда в очереди есть `in_progress` с `claimed_by`.

Открытое состояние одно — `todo`. Отбор берёт сперва зависшие `in_progress`
(начатое не вытесняется новым), затем `todo` сверху вниз по строкам файла:
порядок строк и есть весь приоритет.

Отбор выдаёт не больше запрошенного числа пунктов, по одному на действующую
группу. Действующая
группа пункта — значение его поля `group`, а если поля нет — слаг самого
пункта. Группа, в которой есть незавершённый и не зависший пункт
`in_progress`, целиком пропускается — независимо от того, выше или ниже
места отбора этот пункт стоит; группа, выбранная в этом же отборе,
становится занятой до его конца. Других правил приоритета, кроме состояния,
порядка строк и зависимостей (`needs`, см. ниже), нет. Если свободных пунктов меньше, чем
запрошено, отбор отдаёт сколько есть — это не отказ.

### Зависимости пунктов

Пункт с `needs` свободен, только если у каждой названной зависимости статус
ровно `done`. `todo`, `in_progress`, `failed`, `postponed` и любой другой
статус зависимость не выполняют. Правило одно для `todo` и для зависшего
`in_progress`. Ждущий пункт отбор пропускает до проверки группы и группу не
занимает: пункт той же группы ниже берётся вместо него. Пункт `postponed`
группу тоже не занимает — группу держит только свежий `in_progress`. Порядка
по графу нет: приоритет остаётся порядком строк, зависимость лишь делает
пункт несвободным.

Статус слага берётся из файла очереди, а если слага там нет — из соседнего
`archived.md` в том же каталоге; слаг в обоих файлах считается по файлу
очереди. Архив читается без lock'а и только когда хоть один пункт очереди
объявил `needs`; нет файла — архив пуст. Собственные `needs` архивных пунктов
не проверяются.

`list` и `pick` (под lock'ом, до отбора) проверяют связи и отказывают кодом
`2`: на слаг, которого нет ни в очереди, ни в архиве (сообщение называет пункт
и слаг), на цикл (сообщение называет путь вида `a → b → a`; самоссылка —
тоже цикл) и на архив, который не разбирается (сообщение называет файл
архива). `pick --only` на ждущий пункт отказывает кодом `2` сообщением
`пункт «x» ждёт зависимостей: y (todo), z (postponed)`, очередь при этом не
меняется. `finish`, `settle` и `merge-lanes` граф не проверяют: они проставляют
исход по слагу, и битая зависимость постороннего пункта не должна стоить
отметки `done` влитой работе.

## Автономная петля

`scripts/self-improve-loop.sh` ведёт заходы `.stepcast/pipelines/self-improve.yml`
один за другим без человека:

```
caffeinate -i bash scripts/self-improve-loop.sh
```

`caffeinate -i` нужен на macOS: без него машина уснёт посреди ночи. Скрипт
берёт ветку, на которой стоит копия (`git symbolic-ref --short HEAD`), и на
каждой итерации запускает `run .stepcast/pipelines/self-improve.yml --input
onto=<ветка>`.

Переменные:

- `MAX_RUNS` — потолок итераций, по умолчанию `20`.
- `BURNEX_LOOP_ENGINE_DIR` (переходно — `STEPCAST_LOOP_ENGINE_DIR`) — каталог
  worktree движка; относительный путь считается от текущего каталога.

Имя ветки должно укладываться в `[A-Za-z0-9._/-]`: оно подставляется в
команды `sh -c` работ `slots` и `merge` без экранирования, и ветку с `$`, `;`
или кавычками скрипт отклоняет на старте.

**Движок.** Каждая итерация идёт на движке, собранном из последнего коммита
ветки, а не из рабочего дерева копии. Поэтому улучшение, сведённое итерацией
N, работает уже в итерации N+1, а незакоммиченные правки человека в движок не
попадают. Собирается он в постоянном worktree: по умолчанию
`<git common dir>/stepcast-loop-engine`, то есть внутри `.git`, где его не
видят ни `git status`, ни ESLint, ни tsc копии. Перед итерацией worktree
переключается на вершину ветки (`checkout --detach --force`, `git clean` не
зовётся), `dist/` стирается и собирается заново `npm run build`: `dist/` в
`.gitignore`, `checkout` его не трогает, а tsc не чистит осиротевший `.js`
переехавшего исходника. Каталог движка, удалённый руками, git помнит как
worktree; скрипт перед созданием зовёт `git worktree prune`, и следующий
запуск пересоздаёт его сам. `npm ci` выполняется, только когда
sha256 `package-lock.json` разошёлся с записанным в
`.stepcast-loop-lock.sha`, файла нет или нет `node_modules`; отпечаток
пишется после успешного `npm ci`. Отпечатку нужен `shasum` либо `sha256sum`.

**Остановка.** Петля останавливается в трёх случаях, и каждый печатает
`self-improve-loop: остановка — <причина>` с числом выполненных итераций:

| Причина | Код выхода |
|---|---|
| исчерпан `MAX_RUNS` | `0` |
| прогон ничего не закоммитил (вершина ветки не сдвинулась) | `0`, если код прогона `0`, иначе код прогона |
| упала подготовка worktree, `npm ci` или сборка; вершина ветки не читается (ветку удалили или переименовали посреди петли) | `1` |
| отказ на старте: отделённый HEAD, имя ветки вне `[A-Za-z0-9._/-]`, неверный `MAX_RUNS`, нет sha256 | `2` |

Условие «ничего не закоммитил» смотрит на вершину ветки, а не на код прогона:
заход, у которого дорожка свелась, а `finalize` отметил что-то красным,
ветку сдвинул, и петля идёт дальше. Пустая очередь даёт этот же исход и
считается нормальным концом. Правки очереди, которые `pick` оставляет
незакоммиченными, вершину не двигают.

**Вход `onto`.** С непустым `onto` работа `slots` не проверяет чистоту
копии, а `merge` зовёт `merge-lanes --onto <ветка>`: сведение накладывает
дорожки на текущую вершину ветки и само ждёт чистой копии под lock'ом.
Поэтому грязная копия петлю не останавливает: человек, правящий копию ночью,
задерживает сведение, а не роняет итерацию. Ожидание видно событиями
`merge.dirty_waiting` в журнале прогона и кончается, когда копию закоммитили
или откатили. Работа `merge` объявлена `budget_exempt`, так что `wallclock`
пайплайна верхней границей этого ожидания не служит. Без `onto` (ручной
заход, заход с доски) пайплайн ведёт себя как прежде.

Ограничения:

- один экземпляр скрипта на копию: отдельной блокировки у скрипта нет;
- составной прогон (`project.nested_repos`) `--onto` отклоняет, и скрипт на
  таком репозитории упадёт первой же итерацией;
- пункт, не доехавший до сведения, получает `failed`, как и в ручном заходе:
  автоматического повтора нет.

## Команда `burnex backlog`

```
burnex backlog list                                     [--file backlog.md]
burnex backlog pick    [--slots N | --lanes a,b] [--only слаг] [--owner run:<id>] [--stale-hours 6] [--run-dir путь] [--file backlog.md]
burnex backlog finish  <slug> --status done|failed [--reason …] [--owner run:<id>] [--file backlog.md]
burnex backlog settle  --run-dir путь                                      [--file backlog.md]
burnex backlog add     <slug> --title … --why … --done-when … [--group …] [--track …] [--needs a,b] [--goal путь] [--details пути] [--status todo|postponed] [--after слаг] [--file backlog.md]
burnex backlog show    <slug> [--run-dir путь]                             [--file backlog.md]
```

Файл очереди — единственный вход команды: `--file`, по умолчанию
`backlog.md` в текущем рабочем каталоге. Пайплайн и `.stepcast/` команде не
нужны — `burnex backlog list` работает в пустом каталоге, где кроме файла
очереди ничего нет, как и `pick` по очереди без владельцев. Конфигурация
проекта (корень журнала прогонов) читается лишь там, где нужно судить о
владельце: `pick` при `in_progress` с `claimed_by`, `finish --owner` и
`settle`. Отсутствующий или нечитаемый файл, а
также файл, не разбирающийся по формату выше, — отказ с кодом `2` и
путём к файлу в сообщении.

### `list`

Печатает разобранную очередь в стандартный вывод одним документом JSON —
массивом записей в порядке их следования в файле. Каждая запись несёт
`slug`, `title`, `why`, `done_when`, действующую `group`, объявленный `track`
(пустая строка, когда поля нет), `repos` — перечень названных репозиториев, пустой, когда пункт поле не
заполнил, `needs` — перечень слагов зависимостей, тоже пустой без поля, `goal` —
путь файла цели (пустая строка без поля) и `details` — перечень путей подробностей.
Файл при этом не правится.

### `pick`

Отбирает свободные пункты по правилам выше, проставляет каждому
выбранному `status: in_progress` и `started_at` текущим моментом в ISO
8601 — одной и той же меткой для всех пунктов, взятых за этот вызов, — и
печатает выбранное в стандартный вывод.

Порог давности задаётся ключом `--stale-hours` (по умолчанию `6`) и действует
для пунктов без владельца или с владельцем, о котором судить нечем.

Ключ `--owner run:<id прогона>` записывает выбранным пунктам `claimed_by` вместе
с `status` и `started_at`; пайплайн передаёт `run:$(basename "$BURNEX_RUN_DIR")`.
Идентификатор — непустой, без пробелов и `/`; иная форма — отказ с кодом `2`
до захвата очереди, файл не меняется. `pick` без `--owner` снимает `claimed_by`
у отобранного пункта: иначе пункт, отобранный у мёртвого прогона, хранил бы
мёртвого владельца и тут же снова считался бы зависшим.

Ключ `--only <слаг>` берёт именно названный пункт вместо первого свободного по
очерёдности: так очередь берёт в работу пункт, выбранный человеком на доске
витрины. Правило группы при этом остаётся в силе — занятость считается по всей
очереди, и пункт, чья группа занята идущей работой, не отбирается. Неизвестный
слаг и пункт, который не свободен (`done`, `failed`, свежий `in_progress`), —
отказ с кодом `2` и названной причиной, а не пустая выдача: опечатка в слаге не
должна выглядеть как «свободных пунктов нет». Пункт с отсутствующими
материалами (`goal`/`details`) пропускается, а при `--only` — тот же отказ с
кодом `2`: см. «Материалы пункта».

У выдачи две формы, и они не смешиваются: `--slots` вместе с `--lanes` —
отказ с кодом `2`, а не молчаливый выбор одной из них.

- `--slots N` (по умолчанию `N = 1`) — массив записей, до `N` штук.
- `--lanes a,b` — объект дорожек: имена дорожек, через запятую, попарно
  различные слаги в kebab-case. Отбирается не больше пунктов, чем названо
  дорожек, каждая названная дорожка присутствует в ответе всегда, даже
  если ей не хватило свободного пункта — тогда `filled: false`, `item:
  null`, а `slug`/`title`/`group`/`track` — пустые строки. Заполненная
  дорожка несёт `filled: true` и запись пункта в `item`.

  Вес пункта дублируется у дорожки плоским полем `track` рядом со слагом и
  заголовком: условие `if` пайплайна читает его без захода внутрь `item`.

При `--run-dir <каталог>` каждая заполненная дорожка дополнительно
записывается отдельным файлом `item-<дорожка>.json` в этот каталог —
незаполненная дорожка файла не получает. Каталог создаётся, если его нет, и
готовится до правки очереди: недоступный путь — отказ с кодом `2` и
нетронутая очередь, а не взятые пункты без файлов дорожек. Относительный
путь, как и у `--file`, разрешается от текущего рабочего каталога.

Свободных пунктов не нашлось — не отказ: команда завершается кодом `0`,
`--slots` печатает пустой массив, `--lanes` — дорожки с `filled: false`, а
файл очереди остаётся неизменным.

Пустой перечень дорожек, повтор имени в нём или имя не в kebab-case —
отказ с кодом `2`.

**Параллельные `pick` не исключают друг друга.** Два одновременных прогона
петли на одной очереди могут прочитать файл до того, как другой его перепишет,
и раздать один и тот же пункт дважды. Блокировки файла нет; сегодня заход у
петли ровно один, и до второго это не проверить.

**У `pick` нет прежних форм `--now`, `--out` и голого объекта одного пункта.**
Часы теперь только внутренние (текущий момент проставляется командой, а не
приходит ключом — он был нужен исключительно старым тестам скрипта, которые
переписаны на прямые вызовы ядра); печать в отдельный файл через `--out`
снята — тот же результат печатается в стандартный вывод, и вызывающему
достаточно его перенаправить; `--slots` без числа теперь тоже даёт массив
(из одной записи), а не одиночный объект. Внешнего вызывающего этих форм в
репозитории не осталось: `--lanes` объявляется в `slots.yml`, а `finish`
зовут два скрипта петли — обе замены уже сделаны.

### `finish`

```
burnex backlog finish <slug> --status done
burnex backlog finish <slug> --status failed --reason "почему"
```

Проставляет названному пункту исход. `--status` принимает только `done`
или `failed` — другое значение отклоняется. При `failed` ключ `--reason`
обязателен и не может быть пустым; при `done` он не нужен.

Причина приходит как есть — обычно это кусок чужого вывода, — а поле
очереди однострочно, поэтому текст сводится в одну строку (переводы строк и
отступы становятся пробелами) и урезается по длине. Полностью он остаётся в
логе шага, который его собрал; в очереди нужна опознаваемая фраза, а не
протокол.

Пункт, которому исход уже проставлен (`status` уже `done` либо `failed`),
остаётся нетронутым, а команда завершается кодом `0`: повторный вызов
`finish` не должен состязаться за последнее слово — первый проставленный
исход и есть окончательный. Слаг, которого в очереди нет, — отказ с кодом
`2`, называющий этот слаг.

С `--owner run:<id>` исход проставляется от имени прогона: пункт, чей
`claimed_by` — другой прогон, остаётся нетронутым (его забрал другой заход), в
stderr печатается слаг и владелец, а команда завершается кодом `0`, как при уже
проставленном исходе. Своим считается пункт, взятый этим же прогоном либо его
предком по `resumed_from` (продолжение дописывает исход работы источника);
пункт без `claimed_by` правится. Сперва проверяется уже проставленный исход,
затем владелец.

### `add`

```
burnex backlog add <slug> --title "…" --why "…" --done-when "…" [--after <slug>]
```

Заводит пункт, чтобы агент петли, нашедший кандидата, мог записать его, не
правя файл руками. `--title`, `--why` и `--done-when` обязательны; `--group`,
`--track`, `--needs`, `--goal` и `--details` необязательны и имеют ту же форму,
что поля одноимённого пункта. `--status` принимает `todo` (по умолчанию) или
`postponed`; исход и работу проставляет петля, не автор. Пункт встаёт сразу за
пунктом `--after`, а без ключа — в конец файла; остальной текст файла не
меняется.

Цикл «прочитать → проверить → записать» идёт под lock'ом очереди, и все
проверки предшествуют записи: слаг в kebab-case и свободный как в
`backlog.md`, так и в `archived.md`; значения непустые и однострочные; форма
полей — как у разбора; каждый слаг `needs` называет пункт очереди или архива,
цикла нет; файлы `goal` и `details` существуют; `--after` называет пункт
`backlog.md`. Любой отказ — код `2` с причиной, файл очереди не тронут.

### `show`

```
burnex backlog show <slug> [--run-dir <каталог>]
```

Печатает запись пункта `backlog.md` в той форме, что и элемент вывода `list`.
С `--run-dir` та же запись пишется ещё и в `item-a.json` этого каталога
(создаётся при необходимости): так диспетчер читает взятый пункт, не листая
всю очередь. Очередь не правится и не блокируется. Слаг, которого нет в
`backlog.md`, — отказ с кодом `2`, и `item-a.json` при этом не создаётся.

### `settle`

```
burnex backlog settle --run-dir <каталог> [--file backlog.md]
```

Закрывает заход: каждому пункту, взятому в этот прогон и оставшемуся без
исхода, проставляет `failed` с единой причиной «заход до сведения дорожки не
дошёл». Взятые пункты определяются по файлам `item-<дорожка>.json` каталога
`--run-dir` — тем самым, которые пишет `pick --lanes --run-dir`; других
файлов каталога прогона команде не нужно.

Исход проставляется от имени прогона `run:<имя каталога --run-dir>`: пункт,
перехваченный другим прогоном, `settle` пропускает — печатает строку о пропуске,
исхода не проставляет и в число закрытых не считает. Так же ведёт себя
`merge-lanes` от имени `run:<id прогона>`: пункт чужого владельца не получает
ни `done`, ни `failed`, сведение идёт дальше. Результат дорожки такого
пункта не накладывается и не коммитится: его работу ведёт новый владелец, и
второй коммит той же работы повторил бы её либо упёрся в конфликт. Дорожка
получает исход `foreign_owner` с владельцем в причине. Если пункт забрали,
пока шла проверка после наложения, наложенное снимается тем же откатом, что и
после красной проверки, а в очереди остаётся запись нового владельца.

Различимые причины несведения (негодная дорожка, конфликт, красная проверка,
остановка на более ранней с названным основанием — конфликт наложения либо
неподтверждённый откат) проставляет сведение дорожек (`burnex merge-lanes`);
`settle` остаётся ровно для случая, когда до дорожки дело не дошло вовсе —
отмена по сигналу, остановка по бюджету, гибель шага.

**`settle` коммитит свою правку очереди**, если хоть один пункт проставила —
адресно, в том репозитории, где файл очереди лежит (`project.nested_repos`
находит его тем же правилом, что и `merge-lanes`), сообщением `backlog: исходы
дорожек прогона <короткий id прогона>`. Коммит адресован файлу, а не индексу:
`settle` отвечает за очередь и не подметает в коммит посторонние правки
рабочего дерева. Правок нет, файл не отслеживается этим репозиторием
(игнорируется либо никогда не был закоммичен) или лежит вне репозитория git
вовсе — коммита нет, и вывод команды это называет. Отметка исхода дорожки
обязана пережить восстановление дерева при `resume` — незакоммиченной она
исчезает при первом же таком восстановлении, а коммит `merge-lanes` для
работ, до которых заход не дошёл, никогда не появляется вовсе.

Файл очереди не обязан лежать в корне дерева запуска — при объявленном
`project.nested_repos` (см. [«Вложенные репозитории»](config.md#вложенные-репозитории))
он может лежать и внутри объявленного вложенного репозитория. Коммитов у
сведённой дорожки столько, сколько репозиториев она затронула, — по одному в
каждом, с одним и тем же сообщением `<слаг>: <заголовок>`, — а репозиторий, в
чьём рабочем дереве лежит сам файл очереди, коммитится последним: в нём же
лежит отметка `done`, и она не имеет права появиться раньше того, что
отмечает. Дорожка, затронувшая только тот репозиторий, где лежит очередь (в
том числе однорепозиторное сведение без объявленного состава), даёт ровно
один коммит — вклад и правку очереди он несёт вместе. Этот коммит остаётся
заботой `merge-lanes` — коммит `settle` покрывает только те пункты, до
сведения которых заход не дошёл. Подробности — в
[«Сведение дорожек»](run-layout.md#сведение-дорожек-stepcast-merge-lanes).

Пункт, которому исход уже проставлен (`done` либо `failed`), остаётся
нетронутым — `settle` закрывает заход, а не переписывает его результат.
Каталога без файлов `item-*.json` — не отказ: команда завершается кодом `0`,
сообщая, что проставлять нечего, а очередь не правится. `--run-dir` без
значения либо на несуществующий каталог — отказ с кодом `2`, а файл дорожки
без слага — отказ с кодом `2`, называющий этот файл. На каждый помеченный
пункт печатается строка со слагом, дорожкой и причиной.

## Команда `burnex project repos`

```
burnex backlog pick --lanes a,b --run-dir путь | burnex project repos [--file путь]
```

Дополняет документ дорожек — ответ `pick --lanes` — объявлениями того
репозитория, который назвал пункт каждой заполненной дорожки: каталог
репозитория, его команда проверки и его практика спецификации (каталог
документов изменения, файл правил, имя инструмента, команда, которой петля
их гейтит). В отличие от
`backlog`, эта команда конфигурацию проекта читает — секцию `project` и
объявленный ею состав вложенных репозиториев (`.stepcast/config.yml`, см.
`docs/config.md`) — и потому не заведена подкомандой `backlog`: очередь не
должна зависеть от устройства проекта.

Документ приходит со стандартного ввода либо из файла, названного `--file`
(тогда стандартный ввод не читается вовсе). Печатается тот же документ:
незаполненные дорожки, порядок дорожек и записи пунктов не меняются,
единственное добавление — блок `repo` у заполненной дорожки:

```json
"repo": {
  "dir": "backend",
  "check": "./gradlew check",
  "spec": {
    "dir": "backend/docs/changes",
    "rules": "backend/docs/spec-rules.md",
    "tool": "openspec",
    "check": "make spec-check"
  }
}
```

Пути практики спецификации в блоке склеены от корня рабочего дерева
(`backend/docs/changes`) — так каждый потребитель получает готовое значение,
не склеивая его самостоятельно. У корня (пункт не назвал репозиторий либо
назвал `.`) `dir` равен `.`, а пути практики — без приставки
(`openspec/changes`), то есть ровно то же, что и до этой команды. Команда
ничего не правит: ни очередь, ни конфигурацию, ни рабочее дерево.

Отказывает кодом `2`, если: названный каталог не объявлен составом и не
`.` (называет пункт, имя и перечень объявленных каталогов); пункт назвал
больше одного репозитория (дорожка ведёт один репозиторий); у названного
репозитория (включая корень) не хватает `check` либо одного из
`spec.dir`/`spec.rules`/`spec.tool`/`spec.check` (называет репозиторий,
недостающий ключ и `.stepcast/config.yml` — место, где его объявляют); стандартный ввод пуст
или не разбирается как JSON. Пустой либо неразбираемый ввод — намеренно тот
же отказ, что и у неполного документа: так отказ `pick` доезжает до этой
команды ненулевым кодом второго звена конвейера, не полагаясь на
`set -o pipefail`.

## Коды возврата

`0` — успех, включая пустую выдачу `pick`, когда свободных пунктов нет, и
`settle`, когда проставлять нечего. `2` — ошибка конфигурации: файла нет,
файл не разбирается, каталог `--run-dir` не подготовить или не найден, ключ
бессмыслен (в том числе некорректный перечень дорожек, `--lanes` вместе с
`--slots`, `--stale-hours` не положительное число, `failed` без причины),
слаг не найден в очереди у `finish`, файл `item-<дорожка>.json` без слага у
`settle`. Отказ ожидания lock'а очереди (см. «Блокировка очереди») — тоже `2`.

## Блокировка очереди

Атомарная подмена файла защищает читателя от половины файла, но не писателя от
писателя: между чтением и записью соседний процесс успевает записать своё. Поэтому
каждый цикл «прочитать → поправить → записать» над `backlog.md` и `archived.md` —
`backlog pick`, `finish`, `settle`, `add`, `merge-lanes` и перенос или правка на доске —
идёт под lock-файлом очереди.

**Где лежит.** `stepcast-backlog.lock` в общем каталоге git
(`git rev-parse --git-common-dir`, считается от каталога файла очереди): основная
копия, дерево дорожки и интеграционное дерево `merge-lanes` делят один lock, а в
рабочем дереве он не появляется. Вне репозитория git — `.backlog.lock` рядом с
файлом очереди. `backlog.md` и `archived.md` одного каталога делят один lock.

**Что в нём записано.** JSON `{pid, host, command, acquired_at}`: номер процесса,
имя машины, писатель (`backlog pick`, `backlog finish`, `backlog settle`,
`backlog add`, `merge-lanes`, `ui scrum move`, `ui scrum edit`) и время захвата ISO 8601.

**Ожидание.** Занятый lock опрашивается каждые 50 мс; через 10 с писатель
отказывает с кодом `2`, называя путь lock-файла и владельца, и файлы очереди не
трогает. Доска на тот же отказ отвечает `409` с тем же объяснением, а демон тем
временем обслуживает остальные запросы. Интервал и предел флагами не меняются.

**Брошенный lock.** Lock своей машины (тот же `host`), чей процесс умер или взят до
загрузки системы, ожидающий писатель снимает сам, не дожидаясь предела. Lock другой
машины не снимается автоматически никогда, как и lock с нечитаемым содержимым:
живость чужого процесса не проверить. Если владелец мёртв на другой машине (или
имя машины сменилось), удалите lock-файл руками — путь назван в сообщении об
отказе.

**Читатели.** `backlog list` и чтение очереди демоном lock не берут и не ждут;
они видят либо прежний файл, либо новый целиком.

**`merge-lanes`.** Под lock'ом идут все его правки очереди: исходы пунктов, откат
дерева (`git reset --hard` переписывает и файл очереди) вместе с записью снимка, а в
изолированной публикации — возврат живых файлов в checkout, сама публикация
результата (очередь со `status: done` из коммита) и её аварийный возврат. Перед
публикацией живые файлы сверяются заново уже под lock'ом: правка соседа, успевшая
после подготовки публикации, даёт `publication_conflict`, а не теряется. Подготовка
публикации (одноразовое дерево, перенос локальных слоёв) и проверка дорожки идут до
захвата: держать lock на их время значило бы ронять любой соседний `pick` по
пределу ожидания.

**`merge-lanes --onto`.** Режим сведения на вершину ветки держит поверх этого lock'а
свой `stepcast-merge.lock` и берёт lock очереди только внутри него (см.
[«Сведение дорожек»](run-layout.md#сведение-дорожек-stepcast-merge-lanes)). В коммит
дорожки из файла очереди попадает только блок `## <слаг>` её пункта — с `done` — поверх
версии вершины ветки; чужие незакоммиченные `in_progress` и `claimed_by` в коммит не
уходят и в живом файле сохраняются. С ключом `--keep-claim` пункт несведённой
дорожки не получает `failed`: он остаётся `in_progress` со своим `claimed_by`, причина
записана в `merge-<дорожка>.json`, а повторный `merge-lanes --onto` того же прогона
сводит дорожку заново.

**Ограничение.** `merge-lanes` после красной проверки возвращает файл очереди к
снимку, снятому до наложения дорожки. Откат и запись снимка идут под lock'ом, но
снимок возвращает файл целиком и затирает правки соседей, сделанные между снимком и
откатом, — то есть за время наложения и проверки.

## Схема формата в чужом репозитории

Формат пункта и форма ответа `pick --lanes` публикуются пакетом схемами
`schema/backlog.schema.json` и `schema/backlog-slots.schema.json` —
порождёнными из тех же моделей, которыми команда проверяет разбор. Работа
пайплайна, проверяющая выход `pick --lanes` ключом `output.schema`, называет
схему ссылкой `burnex:backlog-slots` — движок разрешает её сам, от
собственного расположения, независимо от того, откуда пакет установлен
(`node_modules`, ссылка, исходники) и есть ли рядом с работой каталог `schema/`
вовсе. Указывать путь `node_modules/stepcast/schema/` вручную не нужно. В этом
репозитории (stepcast и есть проект) работа `slots` ссылается той же формой —
`burnex:backlog-slots` — на тот же файл в дереве исходников.

## Правка файла

Правка не переписывает файл заново — она атомарна (обрыв записи не
оставляет файл в промежуточном состоянии) и точечна: существующее поле
переписывается на своей строке, новое поле дописывается сразу за
последним полем своего пункта. Строки остальных пунктов, преамбула и
порядок пунктов в файле остаются посимвольно неизменными. `backlog add`
вставляет новый пункт целым блоком — за названным пунктом либо в конец, — не
переписывая соседей.

**Преамбула `backlog.md` этого репозитория продолжает дублировать формат.**
Нормативное описание — `docs/backlog.md`, но вводный текст самого файла
очереди (таблица полей, правило группы, правило шести часов) не сокращён:
файл вне границы правок агентских работ петли, а `pick` переписывает его в
том же прогоне, что сделало бы правку диффом поверх этого игрой без нужды.
Расхождение не остаётся незамеченным — тест движка разбирает `backlog.md`
этого репозитория как есть и падает при несовпадении с моделью.
