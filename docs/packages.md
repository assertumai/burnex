# Пакеты

Пакет — каталог, который переносит практику целиком: пайплайны, переиспользуемые
шаги, скрипты, плагины, виджеты, дашборды и маршруты витрины лежат в одном
месте, с именем, версией и описанием потребностей. Движок знает, что это одно
целое, и ищет его ресурсы теми же именами, что и ресурсы свободных каталогов
`.stepcast/` — имя пакета в ссылку на шаг, скрипт, виджет или дашборд не входит.

Слово «пакет» здесь — каталог пользователя. Пакет движка, который ставят через
npm, в коде и документах называется «поставкой» (`stepcast:<имя>` — пайплайн
поставки).

Образец — [`examples/packages/hello/`](../examples/packages/hello).

## Раскладка

```
<проект>/.stepcast/packages/<имя>/     слой пакетов проекта (в git)
~/.stepcast/packages/<имя>/            слой пакетов home
    package.yml                        манифест — обязателен
    pipelines/<имя>.yml                пайплайны
    steps/<имя>/step.yml               переиспользуемые шаги (uses:)
    scripts/                           скрипты (script:)
    plugins/<id>/plugin.json           каталожные плагины
    widgets/<id>.tsx                   виджеты витрины
    dashboards/<id>.yml                дашборды витрины
    routes.yml                         маршруты витрины
```

Каждый подкаталог необязателен: пакет с одним `widgets/clock.tsx` — законный
пакет. Ресурс пакета проверяется той же схемой и теми же правилами, что и
одноимённый ресурс свободного каталога.

Слой пакетов home лежит рядом с глобальным конфигом: `packages/` в каталоге,
где лежит `config.yml` (по умолчанию `~/.stepcast/packages/`), а не жёстко в
домашнем каталоге. Сборка с подставным путём конфигурации — запасное ядро
демона — остаётся без пользовательских пакетов, как и без пользовательских
плагинов.

Каталога `packages/` может не быть вовсе. Проект без пакетов ведёт себя так же,
как до их появления.

Пакет без `package.yml` — не пропущенный молча каталог, а **сломанный пакет** с
причиной «нет манифеста».

## Манифест `package.yml`

```yaml
version: 1
kind: package
name: hello
description: Образец пакета
package_version: 0.1.0
needs:                       # необязателен
  packages: [tools]
  backends: [claude]
  mcp: [github]
  secrets: [GITHUB_TOKEN]
```

- `version: 1`, `kind: package`, `name`, `description`, `package_version` —
  обязательны. Любой ключ, которого нет в схеме, — отказ: поля маркетплейса
  (`owner`, `private` и подобные) в манифест не входят;
- `name` — kebab-slug (`^[a-z0-9]+(-[a-z0-9]+)*$`) и **совпадает с именем
  каталога**. Имена `stepcast` и `builtin` зарезервированы: первое занято
  адресом поставки, второе — ключом встроенных виджетов в адресе модуля
  витрины;
- `description` — непустая строка; `package_version` — semver
  (`MAJOR.MINOR.PATCH`, необязательные пре-релиз и сборка: `1.2.3-rc.1+b5`);
- `needs` — строгий объект из четырёх необязательных списков непустых уникальных
  строк. Проверка `needs` справочная: она называет недостающее в
  `stepcast package list`, но статус пакета не меняет и пакет не отключает.

Схема публикуется файлом [`schema/package.schema.json`](../schema/package.schema.json),
который порождает `npm run schema` из той же модели, какой манифест проверяется.
Отказ называет файл и место нарушения.

## Порядок поиска

Ресурс, найденный по имени, разрешается в первом слое по порядку:

1. свободный каталог проекта (`<проект>/.stepcast/…`);
2. пакеты проекта;
3. свободный каталог home (`~/.stepcast/…`);
4. пакеты home;
5. встроенное.

Вид ресурса получает пакетные слои на своих местах, но недостающие свободные
слои у него не появляются: виджеты не читаются из свободного home, у дашбордов
нет встроенного слоя, у плагинов встроенное — строки дерева, а не каталог.
Свободный каталог законно перекрывает пакет своего корня: так проект подменяет
шаг из пакета, не правя пакет.

Маршруты складываются в обратную сторону — встроенное ← пакеты home ← home ←
пакеты проекта ← проект, — по `id`, по листьям: строка верхнего слоя перекрывает
строку нижнего. Для плагинов тот же порядок даёт дерево: операции подаются в
порядке встроенное → пакеты home → свободный home → ключ и патч home → пакеты
проекта → свободный проект → ключ и патч проекта, и позднее объявление `id`
заменяет раннее.

Слой и пакет найденного ресурса видны там, где виден слой: в происхождении шага
`uses` (журнал прогона, `pipeline.lock.yml`), в строке `stepcast plugins`
(`package hello (project)`), в перечнях витрины и в `stepcast package list`.

## Затенение пакета — целиком

Пакет проекта `hello` затеняет пакет home `hello` **целиком**: ни один ресурс
пакета home не участвует в поиске, даже тот, которого в пакете проекта нет.
Иначе обновлённый пакет проекта, в котором шаг переименовали, продолжал бы
тянуть старый шаг из копии home — смесь двух версий, которую никто не
собирал. Сломанный пакет проекта затеняет одноимённый пакет home тоже: молча
подставить копию home вместо сломанной значило бы скрыть поломку.

Затенённый пакет виден в `stepcast package list` со статусом «затенён».

## Конфликт внутри слоя

Два пакета одного слоя, приносящие ресурс одного вида с одним именем (шаг
`lint`, виджет `clock`, дашборд `ops`, плагин `board`, маршрут с `id: ops`), —
ошибка, называющая ресурс и оба пакета. Отказывает именно этот ресурс: он не
разрешается ни в один из пакетов и **не проваливается в нижний слой**, потому
что провал дал бы молчаливую подмену. Остальные ресурсы обоих пакетов работают.
Побеждает не «первый по алфавиту» — исход тогда зависел бы от имени каталога, а
не от намерения автора.

Как отказ выглядит по видам:

| Ресурс | Отказ |
|---|---|
| шаг `uses`, скрипт `script` | значение `ScriptUnresolved` с причиной `resource_conflict`; `stepcast lint` называет его вместе с прочими промахами |
| плагин | строка дерева с заведомым отказом, заменяющая строку нижнего слоя; `stepcast plugins` называет оба пакета |
| виджет | запись в перечне виджетов с полем `error`, файл не отдаётся |
| дашборд | запись в `failures` состава дашбордов |
| маршрут | строка исключается из обоих пакетов и попадает в `packageFailures` ответа `GET /api/routes` с именами обоих пакетов; прочие маршруты всех слоёв действуют, а строку с этим `id` может объявить слой выше |

Одинаковые имена в разных слоях конфликтом не считаются: их разводит порядок
поиска. Пайплайны конфликтовать не могут — адрес несёт имя пакета.

## Сломанный пакет

Пакет с нечитаемым, не разбирающимся или не прошедшим схему манифестом исключён
из поиска целиком, с причиной в `stepcast package list` и в промахах, где
действовал бы его ресурс: промах шага или скрипта называет искомые каталоги и
сломанные пакеты с их причинами. Поломка одного пакета не мешает загрузке других
пакетов, свободных каталогов и встроенного. Команды, не обращающиеся к его
ресурсам, из-за него не падают.

## Адрес пайплайна `<пакет>:<имя>`

```bash
stepcast run hello:greet
stepcast lint hello:greet
```

Цель вида `^[a-z0-9]+(-[a-z0-9]+)*:[A-Za-z0-9_-]+$`, кроме `stepcast:`,
разрешается в `pipelines/<имя>.yml` (или `.yaml`) пакета: сначала проекта, затем
home, с учётом затенения. Три отказа — «пакет не найден», «пакет сломан: причина»
и «в пакете нет пайплайна» — перечисляют, что есть.

- `stepcast:<имя>` по-прежнему означает пайплайн поставки движка;
- всё, что под форму не подходит, — путь от каталога запуска: `./foo:bar.yml`,
  любой путь с `/`, имя с расширением остаются путями. Голое имя файла вида
  `foo:bar` (без `./`, без расширения) прочитается как адрес — для такого файла
  пишите `./foo:bar`;
- слои шагов и скриптов пайплайна пакета ищутся от каталога запуска, а не от
  каталога пакета: пайплайн пакета home, запущенный в проекте, работает с этим
  проектом — ради этого им и делятся. Побочное следствие: шаг пакета ссылается
  на скрипт по имени, и проект может перекрыть это имя своим файлом;
- журнал прогона (`run.json`) записывает адрес так, как он был назван
  (`pipeline_address`), рядом с разрешённым путём файла (`pipeline_file`).
  `stepcast resume` идёт по разрешённому пути и адрес заново не разрешает — пакет
  можно переименовать или убрать, прогон всё равно возобновится, пока файл
  пайплайна на месте. Журнал прежней версии без этого поля читается как прежде.

## Плагины пакетов

Пакет приносит только **каталожные** плагины (`plugins/<id>/plugin.json`).
Одиночные `.mjs`, подключаемые строкой `plugins:`, пакет не приносит. Каталог
плагина пакета, названный идентификатором встроенной строки, отказывает так же,
как свободный каталог: встроенная строка остаётся действующей.

Манифест прогона записывает пакет-источник плагина (поле `package` в `plugins`),
а `stepcast diff` показывает смену источника, включая пакет.

Браузерная половина плагина пакета отдаётся по адресу `/plugins/<id>.js`, но в
поток событий витрины не входит, как и браузерная половина любого каталога вне
свободного слоя home: чтобы витрина подхватила правку, её перезагружают.

## Витрина

- Экран «Pipelines» показывает пайплайны исправных пакетов с адресом
  `<пакет>:<имя>` и источником; запуск с экрана передаёт `stepcast run` адрес, а
  не путь файла — путь пакета home лежит вне проекта. Прогон по адресу пакета
  привязывается к карточке этого пайплайна;
- виджеты, дашборды и маршруты пакетов входят в составы по порядку поиска, и
  источник каждого назван. Проверка реального пути виджета идёт относительно
  `widgets/` пакета: символическая ссылка из пакета наружу отказывает;
- витрина **не пишет в каталог пакета**. Правка дашборда пакета сохраняется
  копией в `.stepcast/dashboards/` проекта и затеняет пакетный — ту же семантику
  уже даёт правка дашборда home из проекта. Файл пакета остаётся как был;
- появление, удаление пакета и правка его файлов (в том числе `package.yml`,
  делающая пакет сломанным) отражаются в составах демона без перезапуска.
  `GET /api/packages` отдаёт ту же сводку, что и `stepcast package list --json`.

## Команды

```bash
stepcast package list [--json]
stepcast package new <имя> [--home]
```

`list` печатает по строке на каждый найденный каталог пакета обоих слоёв: имя,
слой, `package_version`, каталог, приносимые виды ресурсов (подкаталоги, где есть
хоть один ресурс) и статус — `действует`, `сломан: <причина>` или `затенён
пакетом проекта`. Под строкой — незакрытые `needs`: `packages` сверяются по
найденным пакетам, `backends` — по зарегистрированным бэкендам (только если
состав плагинов собран), `mcp` и `secrets` печатаются как объявлены, без
проверки. `--json` отдаёт ту же модель.

Команда ядерная и не зависит от состава плагинов: она работает и тогда, когда
пакет или плагин сломал состав, — для того и нужна, чтобы увидеть сломанный пакет.

`new` заводит `package.yml` с `package_version: 0.1.0` и описанием-заглушкой в
`.stepcast/packages/<имя>/` (с `--home` — в слое home). Имя проверяется схемой и
резервом; существующий каталог не перезаписывается. Пустые подкаталоги не
создаются — пустой каталог в git не живёт, а раскладка описана выше.

## Чего пакеты не делают

Установка, обновление, удаление и публикация пакетов, каталог-репозиторий и
проверка `needs` с отказом в установке — отдельная работа (маркетплейс); строгая
схема манифеста отвергает его поля до тех пор. Вложенные пакеты и запись из
витрины в пакет не поддерживаются.
