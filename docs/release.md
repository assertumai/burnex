# Выпуск версии

Версия выходит двумя путями из одного тега: `install.sh` ставит движок по тегу
`vX.Y.Z`, `npm publish` публикует пакет с той же версией. Порядок ниже.

## Порядок выпуска

1. Дерево чистое, `npm run check` зелёный, ветка — та, что выпускается.
2. `npm version X.Y.Z` — поднимает `version` в `package.json` и
   `package-lock.json`, делает коммит и ставит тег `vX.Y.Z` одним шагом.
   Править версию руками и тегировать отдельно не нужно: именно так тег и
   версия расходятся.
3. `git push --follow-tags` — отправляет коммит и тег.
4. `npm publish` — из чекаута этого тега (`git checkout vX.Y.Z`). `prepack`
   сам запускает `npm run build`, так что забытая сборка в реестр не уедет;
   `files` в `package.json` перечисляет поставку (`dist`, `schema`,
   `src/builtin`), `publishConfig.access` держит пакет публичным.

## Тег и версия обязаны совпадать

По тегу ставит `install.sh`, по версии — npm. Если тег `v0.3.0` указывает на
коммит с `"version": "0.4.0"`, получатся две разные «0.3.0». Поэтому
`install.sh` при установке тега `vX.Y.Z` сверяет его с `version` собранного
`package.json` и отказывает, называя обе версии.

## Занятое имя

Если имя `stepcast` в реестре npm занято, пакет выпускается под scope:
меняется `name` в `package.json` (например, `@assertumai/stepcast`), а
способ установки `npm` в паспорте (`install.json`) называет это же имя —
`burnex update` ставит `npm install -g <name>@<ссылка>`.

## Переход со stepcast

Проект переименован из Stepcast в Burnex по частям; этот раздел собирает, что
уже переименовано и что ещё носит прежнее имя.

- **Бинарник.** Пакет объявляет `burnex` и псевдоним `stepcast`; псевдоним
  снимается последним шагом перехода.
- **Переменные окружения.** Движок выставляет шагам и дочерним процессам
  `BURNEX_*` и, один выпуск, те же значения под `STEPCAST_*`. Свои настройки
  (`BURNEX_HOME`, `BURNEX_BIN_DIR`, `BURNEX_RELEASES_DIR`,
  `BURNEX_LOOP_ENGINE_DIR`, `BURNEX_TEST_KEEP`, `BURNEX_UI_TEST_OUT`) движок,
  `install.sh` и `scripts/self-improve-loop.sh` читают по новому имени, при его
  отсутствии — по старому; движок при этом предупреждает в stderr один раз за
  процесс. Правило одно и собрано в `src/kernel/env-names.ts`. Чтение
  `STEPCAST_*` и двойники в окружении шага снимаются в первом выпуске после
  того, в котором появились `BURNEX_*`; пайплайны к тому выпуску должны
  читать только `BURNEX_*`.
- **Пакет npm и адреса поставки.** Пакет называется `burnex`, его подпути —
  `burnex/plugin`, `burnex/pipeline`, `burnex/step`, `burnex/backends/<имя>`;
  адрес поставки — `burnex:<имя>` (схема, обёртка, пайплайн, встроенная строка
  состава); общие модули витрины — `@burnex/slots` и `@burnex/ui`. Прежние
  `stepcast/<подпуть>` и `stepcast:<имя>` в `plugins:`, `wrapper`, `schema`,
  `output_schema` и у `burnex run` читаются как свои тот же один выпуск, а
  `@stepcast/slots` и `@stepcast/ui` ведут на те же переходники карты имён
  страницы; в сообщениях и документации пишутся только новые имена. Правило
  собрано в `src/kernel/package-name.ts`. Паспорт установки способом `npm`,
  записанный до переименования, называет пакет `stepcast` — `burnex update`
  такой установки ставит прежнее имя; поправьте `package` в `install.json`.
- **Пока прежнее имя:** каталоги `.stepcast/` и `~/.stepcast`, `stepcast.yml`,
  лаунчер `stepcast`, идентификаторы кода, адрес репозитория — пункты
  группы `rename-burnex` очереди.

## Откат релиза

Каждая версия лежит в своём каталоге `~/.stepcast/releases/<имя>`, а
`current` — ссылка на один из них. Откат — переключение ссылки обратно:

```sh
ln -sfn ~/.stepcast/releases/<прежняя> ~/.stepcast/releases/current
```

Старые релизы не удаляются сами (уборка — отдельный пункт). После отката
перезапустите витрину: `burnex down && burnex up` в каталоге проекта, а
агент launchd — `launchctl kickstart -k gui/$(id -u)/ai.stepcast.daemon`.

## Экран System

Витрина показывает здоровье установки на `/system` (группа меню `system`).
Открытие экрана — чтение без сети и без новых проб: диск, `launchctl print` и
память демона.

**Что показано и откуда.**

- *Engine* — версия из `package.json` корня движка, способ установки из
  паспорта `~/.stepcast/install.json` (без паспорта — выведенный по пути, как у
  `burnex update`; движок в каталоге релизов без паспорта показывает причину
  словами `resolveInstallMethod`). Для `managed` — ссылка, версия, время
  установки и имя релиза, на который смотрит `current`.
- *Daemon* — pid, время подъёма, порт, корень проекта и путь входа берутся у
  самого процесса, а не из `ui.pid`: у демона под launchd записи нет. «Запущен
  агентом» выставляется, когда `launchctl print gui/<uid>/ai.stepcast.daemon`
  сообщает pid этого процесса; переменные окружения не читаются.
- *Autostart* — переключатель включён, когда plist есть и агент загружен.
  Отдельными строками показаны «plist есть, агент не загружен» (после
  `burnex down`) и «агент смотрит в конкретный релиз, а не в `current`».
  Вне macOS переключатель неактивен с причиной.
- *Backends* — по `backends.<id>` действующей конфигурации: команда (найдена с
  полным путём или нет — поиск идёт по `PATH` окружения шага, с
  `backends.<id>.env`), подключён ли адаптер, удержанный демоном исход пробы
  моделей (кнопка «Check» перечисляет заново, как `?refresh=1` на «Agents») и
  последний отказ `backend.refused` каждого класса из 20 новейших прогонов
  каждого проекта. Событие бэкенда не называет, поэтому он берётся из
  `usage.json` прогона по тем же `job`/`step`/`attempt`; отказ без такой
  попытки показан отдельной строкой «без бэкенда» и никому не приписан.
- *Models without price* — модели, которые называет конфигурация
  (`default_model`, `model_tiers.*`, `defaults.model` бэкенда `defaults.agent`)
  для бэкенда, не сообщающего цену, если каталога цен они не знают; рядом дата
  каталога. Правило то же, что у предупреждения `budget.cost_unpriced`.

**Авторизация бэкенда видна только по отказу прогона.** Отдельной пробы нет:
вызов модели стоит денег и лимита. Отказ аутентификации появляется после
первого прогона, который на него наткнулся.

**Проверка обновления** — `GET /api/system/update`, единственный маршрут
экрана с сетью, по кнопке «Check for updates». Решает та же функция, что и в
`burnex update`, поэтому «обновлять нечего» и отказы совпадают с командой:

| Способ | Что спрашивается | Исходы |
| --- | --- | --- |
| `managed` | `git ls-remote --tags` репозитория из паспорта, последний строгий тег | `available`, `up-to-date`, `no-tags` |
| `checkout` | `git status --porcelain`, `symbolic-ref`, `git fetch`, `rev-list --count HEAD..@{u}` | `available` с числом коммитов, `up-to-date`, `blocked` (грязное дерево, отцеплённый HEAD) |
| `npm` | `npm view <пакет> version`, сравнение по semver | `available`, `up-to-date` (и когда установленная версия новее `latest` реестра) |

Отказ сети или команды, а также проверка, не уложившаяся в 20 с, — `unknown` с
причиной. Предел общий на всю проверку, а не на команду: четыре команды
`checkout` делят те же 20 с. Команды идут асинхронно — пока ждётся сеть,
витрина отвечает на остальные запросы; одновременные запросы ждут одну
проверку. Сама `burnex update` в терминале предела не ставит. Исход демон удерживает 10 минут; `?refresh=1` проверяет заново (кнопка
экрана всегда просит заново). «Update» активна при `available` и `unknown`,
неактивна при `up-to-date`, `blocked`, `no-tags` и когда способ установки не
определён.

**«Update»** не вызывает обновление внутри демона: оно перезапускает самого
демона. `POST /api/system/update` порождает отсоединённый (в своей сессии)
`burnex update` той же точки входа в корне проекта демона; вывод дописывается
в `~/.stepcast/update.log`. Ответ — `202` с путём журнала. Экран раз в секунду
до 60 с спрашивает `GET /api/system` и ждёт другой pid. Пока отвечает прежний
демон, экран смотрит и `GET /api/system/log?kind=update`: поле `run` несёт
исход процесса, порождённого этим демоном (`running`, `exitCode`). Вышедший
процесс при прежнем pid значит, что перезапуска не будет — «обновлять нечего»,
отказ или сбой, — и экран сразу показывает код выхода с хвостом журнала, а не
ждёт таймаута. По таймауту — хвост журнала и команда для терминала. Пока
порождённый процесс жив, повторное нажатие получает `409`.

**Переключатель автозапуска** (только macOS): «включить» порождает
`burnex up --install`, «выключить» — `burnex down --uninstall`, а затем
`burnex up` одной оболочечной строкой, чтобы витрина вернулась. Оба
перезапускают демон; вывод — в `~/.stepcast/autostart.log`. Вне macOS
`POST /api/system/autostart` отвечает `409` с причиной «работает только на
macOS» и ничего не порождает. Изменяющие маршруты отвергают запрос с чужим
`Origin`.

## Открытый вопрос: первый тег

Пока в репозитории нет ни одного тега `vX.Y.Z`, `install.sh` без `--ref`
ставить нечего и отказывает. Нужен ли первый тег до слияния, решает человек
при выпуске; до тех пор установка идёт с явной ссылкой:

```sh
curl -fsSL https://raw.githubusercontent.com/assertumai/stepcast/main/scripts/install.sh | bash -s -- --ref main
```
