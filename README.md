# Burnex

Движок пайплайнов для разработки с ИИ-агентами. Прежнее имя проекта —
Stepcast: переменные `STEPCAST_*`, подпути `stepcast/…`, адреса
`stepcast:<имя>`, каталоги `.stepcast/` и `~/.stepcast` один выпуск читаются
наравне с новыми
([docs/release.md](docs/release.md), «Переход со stepcast»).

Агент — это тип шага, а не оркестратор. Топология работ, условия перехода,
бюджеты, повторы и проверка результата описаны декларативно и исполняются
движком. Модель не решает, что делать дальше — она делает то, что поручил
текущий шаг, и отдаёт результат, который проверяется контрактом.

## Статус

Ранний. Пайплайн из нескольких работ с агентскими шагами исполняется целиком,
но часть объявленного формата движок отклоняет с ошибкой — линт назовёт,
чего не хватает. Windows не проверяется: убийство дерева процессов
реализовано через группу процессов POSIX.

Движок применён к собственной разработке: петля саморазвития
[`.burnex/pipelines/self-improve.yml`](.burnex/pipelines/self-improve.yml)
берёт очередное улучшение из [очереди](backlog.md), заводит под него
OpenSpec-изменение, реализует до зелёной сборки, ревьюит отдельной сессией и
коммитит — по коммиту на улучшение. Первые пункты очереди нужны в первую
очередь ей самой.

- [Формат пайплайна](docs/pipeline-format.md) — работы, шаги, сессии, контекст
- [Прогон](docs/run-layout.md) — рабочее дерево, состояние, resume, дифф, расход
- [Конфигурация](docs/config.md) — глобальная и проектная, политика
- [Память репозитория](docs/knowledge.md) — контракт источника, встроенная раскладка, работа вне пайплайна
- [Плагины](docs/plugins.md) — свои бэкенды, предикаты и команды без правки движка
- [Целевая архитектура](docs/microkernel-target.md) — ядро-регистратор, строки состава, порядок работ
- [Тестирование](docs/testing.md) — песочница временных файлов, уборка, замер утечки
- [Запускаемый пример](examples/minimal/burnex.yml)

## Как это выглядит

```yaml
version: 1
kind: pipeline
name: fix-tests

jobs:
  fix:
    until: { max_iterations: 3, check: [{ cmd: npm test }] }
    steps:
      - id: repair
        agent: claude
        prompt: file:./prompts/fix-tests.md
        expect: [{ changed_only: ["src/**", "test/**"] }]

  verify:
    needs: [fix]
    steps:
      - id: lint
        run: [npm, run, lint]
        expect: [{ exit_code: 0 }]
```

```bash
npm install && npm run build
node dist/src/bin.js run examples/minimal/burnex.yml --input topic=сессии
```

## Установка

Одной командой, без клонирования руками:

```bash
curl -fsSL https://raw.githubusercontent.com/assertumai/burnex/main/scripts/install.sh | bash
```

Скрипт берёт последний тег `vX.Y.Z`, собирает его и раскладывает релиз в
`~/.burnex/releases/<версия>`; ссылка `current` указывает на действующий
релиз, а лаунчер `~/.local/bin/burnex` — на `current`. Нужны `git`, `npm` и
Node ≥ 22. Если `~/.local/bin` не в `PATH`, скрипт печатает строку
`export PATH=…` и профиль не правит.

- `--ref <ссылка>` — тег, ветка или sha вместо последнего тега. Пока в
  репозитории нет тегов, скрипту без `--ref` нечего ставить:
  `… | bash -s -- --ref main`.
- `--repo <адрес или путь>` — другой репозиторий (форк, `git@…`, локальный путь).
- `--force` — заменить чужой файл на месте лаунчера (например, `npm link`).
- `BURNEX_HOME` (по умолчанию `~/.burnex`) и `BURNEX_BIN_DIR` (по
  умолчанию `~/.local/bin`) переносят каталог релизов и лаунчер.

Сбой на любом шаге оставляет прежний `current` нетронутым. Скрипт пишет
паспорт установки `~/.burnex/install.json`, по которому `burnex update`
знает, чем обновлять.

### Обновление

```bash
burnex update              # последний тег; --ref <ссылка> — другая версия
burnex update --no-restart # не перезапускать демон витрины
```

`update` обновляет тем способом, каким движок поставлен:

- **managed** (через `install.sh`) — запускает `install.sh` из
  `releases/current` с теми же `BURNEX_HOME` и `BURNEX_BIN_DIR`, что
  при установке; ничего не делает, только если установлен ровно этот тег
  (сборка ветки или sha обновляется всегда);
- **checkout** (рабочее дерево с `npm link`) — `git pull --ff-only`, `npm ci`,
  `npm run build`; при незакоммиченных правках отказывает до любых шагов;
  с `--ref` вместо `pull` — `git fetch` и `git checkout <ref>`, а ветка затем
  догоняется `git pull --ff-only`. Тег или sha отцепляют HEAD: следующий
  `update` без `--ref` откажет с подсказкой назвать ветку
  (`burnex update --ref main`);
- **npm** — `npm install -g <пакет>@<ссылка или latest>`.

Способ берётся из паспорта, а без него выводится из места установки;
выбранный способ и каждая команда печатаются. Команда не читает конфигурацию
и работает, когда она сломана. После успешного обновления демон витрины
перезапускается: агент launchd — через `launchctl kickstart -k`, отсоединённый
демон — остановкой и `burnex up` новой версии в его каталоге проекта; не
поднятый демон не поднимается. Демон, поднятый прежней версией (в записи
`ui.pid` нет каталога), не трогается: `burnex update` просит перезапустить
его самому — `burnex down && burnex up`.

### Откат релиза

Прежние релизы остаются в `~/.burnex/releases/`; откат — переключение ссылки:

```bash
ln -sfn ~/.burnex/releases/<прежняя> ~/.burnex/releases/current
```

Порядок выпуска версии — [docs/release.md](docs/release.md).

### Разработка: `npm link`

Пакет объявляет бинарник `burnex`, но сборка сама по себе не выкладывает его
на `PATH` — до установки команду зовут полным путём (`node dist/src/bin.js`), а
`burnex up` отвечает `command not found`.

Разработка ведётся по симлинку: он указывает прямо в рабочее дерево, поэтому
правки видны сразу после пересборки, без переустановки.

```bash
npm install && npm run build && npm link
```

`npm link` создаёт симлинк в глобальном каталоге npm (`$(npm prefix -g)/bin/stepcast`),
ведущий на `dist/src/bin.js` этого репозитория. Следствия, о которых стоит
знать заранее:

- **После правки исходников нужен `npm run build`.** Симлинк ведёт на
  собранный файл, а не на исходник, и без пересборки команда продолжит
  работать по прошлой сборке.
- **Каталог репозитория нельзя переносить или удалять** — симлинк повиснет, и
  `stepcast` перестанет запускаться.
- **Если `$(npm prefix -g)/bin` не в `PATH`,** линковка ничего не изменит:
  проверьте `npm prefix -g` и добавьте его `bin` в `PATH`.

Откат:

```bash
npm unlink -g stepcast
```

Демон витрины в автозапуск не прописывается: после перезагрузки машины
`burnex up` нужно вызвать заново.

Витрина, которую отдаёт `burnex up`, сама по себе исходники на React и
TypeScript в `ui/`; `npm run build` уже собирает её (`vite build` в
`dist/ui-web/index.html`) вместе с кодом на Node — отдельного шага не нужно.
При правке самой витрины удобнее `npm run dev:ui`: он поднимает dev-сервер
Vite с горячей перезагрузкой и проксирует `/api` на уже запущенный демон
(`burnex up` в другом терминале), не заставляя пересобирать `dist/ui-web`
на каждое изменение.

## Принципы

**Управление потоком детерминировано.** Порядок работ, ветвления и реакция на
отказ вычисляются движком из объявленного графа, а не выводятся моделью по ходу
дела.

**Результат шага проверяется контрактом.** У каждого шага объявлен `expect`.
Жёстким гейтом становятся только проверки, которые дешевле и надёжнее самой
работы: код возврата, схема, зелёные тесты. Оценка агентом-судьёй доступна, но
по умолчанию совещательная.

**Работы обмениваются файлами, шаги внутри работы — диалогом.** Каждая работа
производит один структурированный JSON, и он автоматически попадает в контекст
последующих агентских работ. Внутри работы агентские шаги по умолчанию идут в
общей сессии: перекладывать через диск то, что обсуждалось шаг назад, незачем.

**Повторы ограничены бюджетом и числом попыток.** Проверок того, что попытка
чем-то отличается от предыдущей, нет. Каждая попытка записывается отдельно,
поэтому шаг, стабильно проходящий не с первого раза, виден как диагноз промпта
или спеки.

**Работа не знает о пайплайне.** Она описывает только то, что делает, свой
бюджет и условие сходимости, и выносится в отдельный файл. Зависимости, условия
и окружение живут на месте подключения — поэтому одна работа переиспользуется в
разных пайплайнах без изменений.

**Ошибки ловятся до запуска.** `burnex lint` проверяет структуру статически:
циклы, недостижимые работы, неразрешимые ссылки, цикл без предела, подстановку
данных модели в командную строку. Отрабатывает до того, как потрачен первый
токен.

**Редактор проверяет то же, что движок.** `burnex schema` печатает в проект
JSON Schema его документов, знающую предикаты объявленных плагинов; `stepcast
lint` предупреждает, если записанная схема устарела.

**Непонятного поведения не бывает.** `burnex config` показывает происхождение
каждой настройки, `burnex context` — что именно увидит шаг, `burnex status` —
почему шаг признан невалидным. Кеш и политика, про которые непонятно, откуда
они взялись, обходятся дороже, чем их отсутствие.

**Происходящее видно целиком.** `burnex up` поднимает локальную витрину:
один демон наблюдает за прогонами всех проектов сразу, подхватывает новые по
мере появления и показывает их живьём — вход и выход каждой работы, файлы
журнала, разрез контекста агентских шагов. Останавливается `burnex down`.
Экспериментально: свой виджет — файл `.tsx` в `.burnex/widgets/` проекта —
демон компилирует и показывает на экране «Виджеты», заменяя на лету по
правке файла (см. [`docs/widgets.md`](docs/widgets.md)).

## Раскладка

| | |
|---|---|
| Бинарник | `burnex` (на `PATH` после `npm link`, см. [Установку](#установка)) |
| Пайплайн | `burnex.yml` или `.burnex/pipelines/*.yml` |
| Работы | `.burnex/jobs/*.yml` |
| Переиспользуемые шаги | `.burnex/steps/<имя>/step.yml` |
| Пакеты | `.burnex/packages/<имя>/package.yml` и `~/.burnex/packages/<имя>/` — [docs/packages.md](docs/packages.md) |
| Конфиг | `~/.burnex/config.yml` и `.burnex/config.yml` |
| Прогоны | `~/.burnex/runs/<project>/<run>/` |
| Переменные | `BURNEX_*` (переходно читаются и `STEPCAST_*`) |
