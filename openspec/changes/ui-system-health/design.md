## Context

Сведения о здоровье установки есть в движке, но разбросаны:

- **Версия и способ установки** — `package.json` корня движка
  (`enginePackageRoot()`), паспорт `~/.stepcast/install.json`
  (`src/parts/install/manifest.ts`) и вывод способа без паспорта
  (`resolveInstallMethod`, `src/parts/install/infer.ts`).
- **Доступное обновление** — вычисляется только внутри `runUpdateCommand`
  (`src/parts/install/commands/update.ts`): `git ls-remote` + `pickLatestTag`
  для `managed`, `git status`/`symbolic-ref` для `checkout`; решение «уже
  стоит» — в `planUpdate` (`src/parts/install/plan.ts`). Перезапуск демона
  после обновления — `restartDaemon` (`src/parts/install/restart.ts`):
  `launchctl kickstart -k` у агента, иначе остановка и `up` в `cwd` из
  `ui.pid`.
- **Демон** — запись `~/.stepcast/ui.pid` (`pid`, `port`, `started_at`,
  `cwd`) пишет только отсоединённый `up`; демон под launchd запускается как
  `up --foreground` и записи не имеет.
- **Автозапуск** — `src/parts/ui/daemon/launchd.ts`: постоянные метка и путь
  plist, `installAgent`/`unloadAgent`/`removeAgent`; `LaunchdHost.launchctl`
  возвращает код и `stderr`, но не `stdout`.
- **Бэкенды** — `readSettings` (`src/parts/ui/settings.ts`) даёт состав
  `backends.<id>` действующей конфигурации демона (`command`, `enabled`,
  `available` — адаптер в реестре); `discoverModels`
  (`src/parts/pipeline/backend/models.ts`) пробует перечисление моделей и
  удерживает исход на время жизни демона (`not_installed`, `timeout`,
  `failed`, …). Неустранимый отказ бэкенда пишется событием `backend.refused`
  (`class: unauthenticated | rate_limit`) в `events.ndjson` прогона.
- **Модели без цены** — правило есть только в раннере
  (`warnAboutUnpricedCalls`, `src/parts/pipeline/run/runner.ts`): бэкенд не
  сообщает цену (`capabilities.reportsCost !== true`) и модель не названа либо
  её нет в каталоге (`PriceCatalog.find(adapter.name, model)`).

## Goals / Non-Goals

**Goals:**

- Один экран отвечает: какая версия работает, как она поставлена и есть ли
  новее; жив ли демон, с каких пор и кем запущен; стоит ли автозапуск; какие
  бэкенды не найдутся или уже отказывали; на каких моделях `budget.cost`
  слеп.
- «Обновить» и «запускать при входе» идут ровно теми путями, что CLI, — не
  второй реализацией.
- `GET /api/system` отвечает быстро и без сети.

**Non-Goals:**

- Проба авторизации бэкенда отдельным вызовом модели (стоит денег и лимита).
- Откат релиза, выбор версии (`--ref`) и уборка старых релизов с экрана.
- Автозапуск вне macOS (systemd и т. п.).
- Правка каталога цен с витрины.
- Группа меню «Конфигурация» — пункт `ui-nav-config-group`.

## Decisions

### Решение 1. Сведения о демоне — от самого процесса

`createUiServer` получает и кладёт в окружение API сведения о себе: `pid`
(`process.pid`), время подъёма (момент старта сервера), порт, корень проекта
(`projectRoot`), путь входа (`process.argv[1]`) и признак «под launchd».
Последний — `launchctl print gui/<uid>/ai.stepcast.daemon` с разбором строки
`pid = N` и сравнением с `process.pid`: метка агента постоянна, а
`XPC_SERVICE_NAME` — догадка по окружению, которое плагин или оболочка могут
переопределить. Для этого `LaunchdHost.launchctl` дополняется `stdout`
(аддитивно; прежние вызовы его не читают).

*Альтернатива* — читать `ui.pid`. Отвергнута: у демона под launchd записи
нет, а у отсоединённого она может принадлежать другому живому демону на
другом порту.

### Решение 2. Состояние автозапуска

`autostart` в ответе:

- не macOS — `{ supported: false, reason }` теми же словами, что
  `requireMacos`;
- macOS — `{ supported: true, plist: boolean, loaded: boolean, thisDaemon:
  boolean, entry?: string, entryStable?: boolean }`, где `loaded` — код
  `launchctl print` равен 0, `entry` — второй элемент `ProgramArguments`
  plist, `entryStable` — путь проходит через `current` (то же правило
  `STABLE_ENTRY`, что в `restartDaemon`, выносится в общую константу).

Переключатель экрана включён, если `plist && loaded`. Состояния «plist есть,
агент не загружен» (после `stepcast down`) и «путь входа в конкретный релиз»
показываются отдельной строкой с командой-подсказкой.

### Решение 3. Действия — отсоединённые команды CLI, не код в демоне

`POST /api/system/update` и `POST /api/system/autostart` не вызывают
`runUpdateCommand`/`installAgent` внутри процесса демона: оба действия
перезапускают сам демон, и обработчик запроса не переживает собственного
`kickstart -k` или `SIGTERM`. Вместо этого демон порождает отсоединённый
процесс той же точки входа, по образцу `launchRun` (`src/parts/ui/runLaunch.ts`):

- «Обновить» — `stepcast update`;
- «запускать при входе» включить — `stepcast up --install`;
- выключить — `stepcast down --uninstall`, затем `stepcast up` (одной
  оболочечной строкой `sh -c '… && …'` с теми же аргументами argv).

Рабочий каталог — корень проекта демона: `up --install` записывает его в
`WorkingDirectory` plist, а `up` поднимает демон там, где он был. Окружение —
окружение демона (у демона под launchd это `PATH` и `SSH_AUTH_SOCK` из plist,
то есть те же, что запишет новый plist). Вывод — дозаписью в
`~/.stepcast/update.log` и `~/.stepcast/autostart.log` соответственно.
Порождение — внедряемая функция окружения API (`launchMaintenance`), как
`launchRun`: тесты проверяют argv и `cwd`, не порождая процессов.

Процесс порождается с `detached: true` (новая сессия, `setsid`): launchd по
умолчанию убивает группу процессов задания при её выходе, а отсоединённый
ребёнок в эту группу не входит и переживает `bootout`/`kickstart -k` демона.
Это проверяется вручную на живом демоне (tasks 5.2).

Пока порождённый процесс жив, повторный `POST` любого из двух маршрутов
отвечает `409` с причиной: два обновления или обновление и переустановка
агента наперегонки ломают друг другу `current` и plist. Знание о ребёнке
живёт в памяти демона — после перезапуска удерживать нечего.

Ответ `POST` — `202 { log }`. Экран после него опрашивает `GET /api/system`
раз в секунду до 60 с: ответ с другим `pid` значит, что демон вернулся;
прежний pid и вышедший процесс обслуживания (`run` в `GET /api/system/log`:
код выхода, который демон помнит о своём ребёнке) — что перезапуска не будет,
и экран показывает исход сразу; таймаут — экран показывает хвост журнала (`GET /api/system/log?kind=update|autostart`,
последние 200 строк) и команду для терминала.

*Альтернатива* — переиспользовать `restartDaemon` в процессе демона после
обновления на месте. Отвергнута: остановка самого себя посреди ответа, а у
отсоединённого демона ещё и некому поднять новый.

### Решение 4. Проверка обновления — общая функция и удержание

Из `runUpdateCommand` выносится `checkUpdate(manifest, host)` рядом с
`planUpdate`: те же `capture`-вызовы и то же правило «уже стоит». Исход:

- `managed` — `{ status: 'available', current: ref, latest: tag }` |
  `'up-to-date'` | `'no-tags'`;
- `checkout` — `git fetch` вышестоящей ветки и `git rev-list --count
  HEAD..@{u}`: `available` с числом коммитов | `up-to-date`; грязное дерево и
  отцеплённый HEAD — `blocked` с той же причиной, что откажет `update`;
- `npm` — `npm view <package> version` против версии пакета по semver:
  установленная версия новее `latest` — `up-to-date`, а не предложение отката;
- отказ сети или команды — `unknown` с причиной.

`runUpdateCommand` использует ту же функцию для своего «обновлять нечего»,
чтобы экран и команда не разошлись. Проверка — только по
`GET /api/system/update`, асинхронно (демон не стоит на `spawnSync`) и с
пределом 20 с на всю проверку — каждая команда получает остаток; команда
`update` в терминале предела не ставит. Исход удерживается демоном на 10 минут; `?refresh=1` обходит
удержание. Кнопка «Обновить» активна при `available` и при `unknown` (решает
человек), неактивна при `up-to-date` и `blocked`; при отказе способа
установки (нет паспорта в каталоге релизов) — неактивна с причиной от
`resolveInstallMethod`.

### Решение 5. Бэкенды: команда, удержанная проба, последний отказ

Состав — `readSettings(...).backends`, тот же, что на «Agents», включая
синтетическую карточку `codex`. По каждому:

- **команда** — поиск исполняемого файла так, как его найдёт `spawn`: путь со
  `/` проверяется как есть, иначе — по каталогам `PATH` окружения, которое
  получит шаг (`buildStepEnv` с `backends.<id>.env`). Исход `found` с полным
  путём или `missing`;
- **проба моделей** — удержанный `discoverModels` исход без запуска новой
  (новая функция `heldModelDiscovery(name, command)` читает кеш модуля);
  нет удержанного — `not-probed`. Кнопка «Проверить» строки вызывает
  существующий `GET /api/models?refresh=1` и перечитывает экран;
- **последний отказ** — по каждому проекту из `listProjects(runsRoot)` не
  более 20 новейших прогонов (`listRunsByKey`), в каждом — события
  `backend.refused` из `events.ndjson`. Событие бэкенда не называет, поэтому
  бэкенд берётся из сводки расхода прогона (`usage.json`, попытка с теми же
  `job`/`step`/`attempt`, поле `backend`). Не нашлась попытка — отказ
  показывается отдельной строкой «бэкенд не установлен» с прогоном и шагом, а
  не приписывается угаданному бэкенду. Поле `backend` в само событие не
  добавляется: схема событий строгая, и новое поле сделало бы журналы новой
  версии нечитаемыми для старого движка (`journal-reader-version-skew`).
  Самый поздний отказ каждого класса по бэкенду: время, проект, прогон,
  работа/шаг, код состояния, сообщение. Читается при каждом запросе, без
  удержания: прогонов мало, а свежий отказ обязан появиться без перезапуска
  демона.

Авторизация как отдельная проба не делается (Non-Goals); экран под таблицей
так и пишет: «отказ аутентификации виден после первого прогона, который на
него наткнулся».

### Решение 6. Модели без цены — общий предикат

Из `warnAboutUnpricedCalls` выносится `isUnpricedCall(adapter, model,
catalog)` (в `budget/priceCatalog.ts`); раннер и витрина зовут его оба.
Витрина перебирает бэкенды с адаптером в реестре и модели, которые им
называет конфигурация: `default_model`, модели `model_tiers`, `defaults.model`
для бэкенда `defaults.agent`. Бэкенд без названной модели даёт строку
«модель по умолчанию CLI». Каждая строка — бэкенд, модель, где названа
(`backends.claude.model_tiers.fast` и т. п.). Рядом — дата каталога
(`asOf`). Модели из документов пайплайнов не перебираются: это предупреждение
прогона, и оно остаётся там.

### Решение 7. Экран и маршрут

Строка `screen-system` (`src/parts/ui/screens/system/{declaration,server}.ts`)
регистрирует экран и пять маршрутов: `GET /api/system`,
`GET /api/system/update`, `POST /api/system/update`,
`POST /api/system/autostart`, `GET /api/system/log`. Маршрут `/system`,
`nav: { order: 10, group: system }` — после «Schedule» (9). Свёртка ответа —
`src/parts/ui/system.ts`, системные вызовы — через внедряемого хозяина (как
`UpdateHost` и `LaunchdHost`), тест не трогает ни git, ни npm, ни launchd.

## Risks / Trade-offs

- [launchd убьёт отсоединённого ребёнка вместе с заданием] → Ребёнок в своей
  сессии; ручная проверка на живом демоне в tasks. Если не переживёт — экран
  по таймауту показывает журнал и команду для терминала, демон не остаётся
  в полуобновлённом виде дольше, чем при сбое `stepcast update` в терминале.
- [Витрина недоступна на время обновления] → Экран предупреждает перед
  действием и сам дожидается возвращения демона.
- [Нажатие «Обновить» с чужой страницы] → Изменяющие маршруты под
  `sameOrigin`, как `DELETE` прогонов и `POST /api/run`.
- [Чтение `events.ndjson` на каждый запрос] → Не более 20 прогонов на
  проект, построчный разбор с остановкой поиска по классу, найденному для
  всех бэкендов.
- [`checkout`-проверка делает `git fetch` в чекауте движка] → Только по явной
  кнопке «Проверить обновления»; `fetch` не меняет рабочее дерево.
