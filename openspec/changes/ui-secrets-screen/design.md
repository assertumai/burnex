## Context

Секрет объявляется двумя путями: верхний ключ `secrets:` документа пайплайна
(`docs/pipeline-format.md`, «Секреты») и `backends.<id>.credentials`
глобальной конфигурации (`docs/config.md`, «Учётные данные бэкенда»). Оба
разрешаются одной функцией `resolveTarget` (`src/parts/pipeline/run/secrets.ts`):
провайдер зарегистрирован → параметры проходят его JSON-схему → `resolve` не
бросил → строка, непустая, не короче 8 символов, без перевода строки. Значение
живёт только в памяти прогона, окружении шага и маскировщике журнала.

Провайдеры — сервис `secretProviders` реестра проекта: встроенные `env-file`
и `keychain` (строка `secret-providers`) плюс вклады плагинов. Реестр проекта
витрина уже поднимает в `projectSection` (`src/parts/ui/pipelines.ts`) для
`GET /api/pipelines` — с проектной конфигурацией и кешем ядер `kernelCache`.

Отказ провайдера сейчас — любое исключение; движок различает только стадии
(не зарегистрирован / схема / `resolve` бросил / значение негодно).

## Goals / Non-Goals

**Goals:**

- Ответить на экране: какие секреты ждут известные пайплайны и бэкенды, каким
  провайдером и разрешаются ли они здесь и сейчас.
- Ни одного байта значения в ответе API, на экране и в журнале демона —
  проверяется тестом, а не обещанием.
- Статус экрана и отказ запуска не расходятся: одна проба на оба пути.

**Non-Goals:**

- Ввод, правка, ротация значений; запись в связку ключей или `.env`.
- Правка объявлений `secrets:` и `credentials` с витрины.
- Группа меню «Конфигурация» — отдельный пункт `ui-nav-config-group`.
- Показ секретов в карточке пайплайна или шага на «Pipelines».

## Decisions

### Решение 1. Статус — настоящая проба тем же путём, что и запуск

`resolveTarget` разделяется на `probeTarget`, возвращающую исход
`{ ok: true, value } | { ok: false, status, error }`, и прежнюю обёртку,
бросающую `error`. Витрина зовёт `probeTarget` и сразу отбрасывает `value`:
обработчик API получает от неё только `status` и текст причины.

*Альтернатива* — «сухая» проверка (зарегистрирован ли провайдер, проходят ли
параметры схему) без вызова `resolve`. Отвергнута: вопрос пользователя —
«упадёт ли мой прогон на секрете», а на него отвечает только вызов провайдера
(нет файла, нет ключа, нет записи в связке). Вторая ветка проверок к тому же
разошлась бы с запуском на первой правке — ровно то, от чего
`secrets-keychain-provider` (решение 3) свёл секреты и учётные данные в один
путь.

### Решение 2. Три статуса и их границы

- `resolved` — все проверки запуска пройдены.
- `provider-unavailable` — провайдер не зарегистрирован в реестре проекта,
  бросил `SecretProviderUnavailableError` либо не ответил за срок пробы
  (Решение 4).

Конфигурация или плагины проекта, которые не загрузились, статуса записям не
дают: без конфигурации и реестра пайплайны не раскрыть, так что записей нет
вовсе. Проект показан строкой ошибки с файлом, местом и подсказкой, как на
«Pipelines», и пустыми списками.
- `not-found` — провайдер работал, но годного значения для этого объявления
  нет: параметры не прошли схему, `resolve` бросил иное исключение, значение
  пусто, короче порога или с переводом строки.

Причина — текст той же `StepcastError`, что увидел бы запуск (с `at`). Тексты
встроенных провайдеров значений не содержат по построению (`keychain` не
включает вывод `security`, `env-file` называет файл и ключ).

`SecretProviderUnavailableError` — новый экспорт поверхности
`stepcast/pipeline`, аддитивный: плагин, который о нём не знает, работает как
раньше, его отказы — `not-found`. Встроенный `keychain` бросает его для «не
macOS», таймаута/отмены и `ENOENT`; код 44 («записи нет») и прочие коды
возврата — обычный `Error`. Сообщения не меняются, запуск по-прежнему
показывает их как «Секрет … не разрешён: …».

*Альтернатива* — разбирать текст сообщения. Отвергнута: хрупко и не работает
для плагинов.

### Решение 3. Что перечисляется

По каждому проекту из `listProjects(runsRoot)`, как в `buildPipelines`:

- **Провайдеры**: имена сервиса `secretProviders` реестра проекта и владелец
  вклада (`builtin` или имя плагина), как его называет реестр.
- **Секреты пайплайнов**: объявления `pipeline.secrets` каждого раскрытого
  пайплайна проекта. Запись — по паре «имя + объявление»: одинаковое
  объявление в нескольких пайплайнах — одна запись со списком
  `usedBy: [{ pipeline, steps: [...] }]`; одно имя с разными объявлениями —
  разные записи. Объявленный, но никем не названный секрет помечен `unused` и
  пробуется так же: экран отвечает «что будет, если его назовут».
- **Учётные данные бэкендов**: `config.backends.<id>.credentials` проекта, с
  `at: backends.<id>.credentials.<VAR>` и признаком, используется ли бэкенд
  хоть одним пайплайном проекта (`backendsInUse`).
- **Параметры** объявления (`file`, `key`, `service`, `account`, …)
  показываются: это не значение, они уже лежат в `pipeline.lock.yml`.

Пайплайн, который не раскрылся, в ответ попадает строкой ошибки с
`error`, файлом, местом и подсказкой, как на «Pipelines», — без секретов.

### Решение 4. Когда пробовать

Проба идёт на каждый `GET /api/secrets`, без кеша статусов: кеш значений
запрещён Целями, а кеш статуса устаревает тихо (разблокированная связка
ключей не отразилась бы). Пробы одного проекта — параллельно
(`Promise.all`), проекты — последовательно, как в `buildPipelines`. Время
ответа — время самого медленного провайдера, и сверху его ограничивает срок
проб проекта (10 с): `keychain` укладывается в свои 5 с, а плагинный
провайдер без таймаута (сетевой vault) иначе держал бы запрос бесконечно.
Проба ждёт провайдера не дольше сигнала, даже если провайдер сигнал не
слушает; не уложившаяся проба — `provider-unavailable`. Сигнал срабатывает и
при закрытии соединения клиентом. Запуск этой гонкой не пользуется.
Экран грузит API по открытию и по кнопке «Проверить снова», не по потоку
событий.

### Решение 5. Гарантия «без значений» — структурой и тестом

Ответ собирается из явного типа `SecretView` без поля для значения;
`probeTarget` возвращает значение только своему вызывающему, и свёртка
витрины его не читает дальше проверки `ok`. Тест кладёт в `.env` временного
проекта значение-маркер и проверяет, что тело ответа `GET /api/secrets` его не
содержит ни целиком, ни в `JSON.stringify` любого поля; тот же маркер
проверяется в разметке экрана на фикстуре ответа.

### Решение 6. Экран и маршрут

Строка `screen-secrets` (`src/parts/ui/screens/secrets/{declaration,server}.ts`)
регистрирует экран и `GET /api/secrets`. Маршрут в `src/builtin/routes.yml`:
`/secrets`, `nav: { order: 8, group: system }` — после «Agents» (7), до
расширений. Браузерная половина: `ui/src/pages/Secrets.tsx` — по проекту
полоса провайдеров и таблица «имя · env · провайдер · параметры · где
используется · статус · причина»; бейджи статусов — существующие классы
темы.

## Risks / Trade-offs

- [Открытие экрана поднимает системный диалог доступа к связке ключей] →
  Тот же вызов, что делает запуск, с тем же таймаутом 5 с; описано в
  `docs/config.md`. «Always Allow» убирает диалог и для прогонов.
- [Плагинный провайдер вставит значение в текст исключения] → Такое же
  поведение уже есть у отказа запуска; контракт `SecretProviderContribution`
  дополняется требованием не включать значение в сообщение. Встроенные
  провайдеры проверены тестом.
- [Медленные провайдеры делают ответ долгим] → Параллельные пробы в проекте;
  экран показывает индикатор загрузки, а не пустую таблицу.
- [Пробы ходят в сеть у плагинных провайдеров (vault и т. п.)] → Принято:
  это и есть вопрос «разрешается ли». Явный запуск по кнопке, не по таймеру.
