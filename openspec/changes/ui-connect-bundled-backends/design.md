## Context

Сейчас подключение поставляемого бэкенда из витрины — частный случай Codex в
трёх местах:

- `readSettings` (`src/parts/ui/settings.ts`) импортирует модуль
  `../backends/codex/index.js` и, если бэкенда `codex` нет в разрешённой
  конфигурации, дописывает в список синтетическую карточку
  `{ name: 'codex', available: false, defaultModel: <умолчание плагина> }`;
  если `backends.codex` в файле есть, а адаптера нет, — подставляет то же
  умолчание модели;
- `SettingsPatchSchema` принимает `connectCodex: z.literal(true)`, а
  `writeSettings` по нему дописывает `stepcast/backends/codex` в `plugins:`
  глобального файла и разрешает `agent: 'codex'` при неподключённом адаптере;
- `ui/src/pages/Agents.tsx` держит состояние `connectCodex`, рисует чекбокс
  «Connect Codex» только на карточке `codex` и разрешает её в выборе агента по
  умолчанию, пока чекбокс отмечен.

Плагины `stepcast/backends/cursor` (бэкенд `cursor-agent`, имя плагина
`cursor`) и `stepcast/backends/copilot` (бэкенд и плагин `copilot`) устроены
так же, как Codex: модуль с `definePipelinePlugin`, `defaults.command`,
подпуть в `package.json` `exports`. У них нет `default_model`. Встроенный
`claude` живёт строкой (`src/parts/backends/claude/row.ts`) и всегда в реестре.

Список из `readSettings` читают ещё экран «System» (`src/parts/ui/system.ts`,
`adapter: backend.available`) и `GET /api/models` (`src/parts/ui/models.ts`) —
оба уже переживают неподключённый `codex`.

Изменение опирается на `ui-agents-settings-merge`: вкладка Backends экрана
«Agents» уже есть, отдельного экрана «Settings» нет.

## Goals / Non-Goals

**Goals:**

- вкладка Backends показывает каждый бэкенд каждого поставляемого плагина,
  подключён он или нет, и у неподключённого — одно действие подключения;
- одна обобщённая форма правки (`connect: [<имя бэкенда>]`) вместо частного
  флага, при этом `connectCodex: true` продолжает работать как раньше;
- новый адаптер, добавленный в пакет подпутём `./backends/*`, не может молча
  выпасть из витрины.

**Non-Goals:**

- отключение плагина из витрины (удаление строки из `plugins:`) — отдельная
  тема со своими вопросами (что делать с `defaults.agent`, `pipeline_agents`);
- подключение сторонних плагинов бэкендов по произвольному спецификатору;
- установка или авторизация CLI агента — витрина лишь объявляет адаптер,
  как и сейчас для Codex;
- правка проектного `.stepcast/config.yml` и слоя `plugins.patch.yml`.

## Decisions

### Решение 1. Каталог поставляемых бэкендов — статический перечень в `src/parts/backends/bundled.ts`

Модуль экспортирует упорядоченный перечень записей
`{ specifier: 'stepcast/backends/<x>', plugin: <default export модуля> }`
для `codex`, `cursor`, `copilot` — в этом порядке. Имена бэкендов и их
умолчания (`command`, `default_model`) читаются из `plugin.backends`, а не
переписываются руками. `settings.ts` перестаёт импортировать модуль Codex
напрямую и работает только с каталогом.

Файл лежит рядом с каталогами плагинов, но не внутри них: правило
`no-restricted-imports` из `eslint.config.js` применяется к
`src/parts/backends/{codex,cursor,copilot}/**`, а каталог — часть движка,
который знает о поставке, а не вклад плагина.

Тест сверяет набор `specifier` каталога с подпутями `./backends/*` поля
`exports` в `package.json` (`./backends/codex` ↔ `stepcast/backends/codex`).
Добавленный в пакет четвёртый адаптер без записи в каталоге роняет тест.

*Альтернативы.* Обход `src/parts/backends/*` во время работы — отвергнут:
в него попадает `claude`, который не подключается, а в `dist/` и в тестовой
сборке раскладка другая. Чтение `exports` из `package.json` демоном с
динамическим `import()` — отвергнуто: путь к `package.json` у живого демона
(`~/.stepcast/releases/current`) и у тестов разный, а ошибка импорта
превратилась бы в отказ чтения настроек. Статический перечень плюс сверочный
тест даёт ту же полноту без этих рисков.

### Решение 2. `connect` называет бэкенды, а не плагины и не спецификаторы

`SettingsPatch.connect` — массив имён бэкендов (`codex`, `cursor-agent`,
`copilot`), то есть тех же имён, что `BackendView.name`, `agent` и ключи
`backends`. Сервер находит по имени запись каталога и дописывает её
`specifier`.

*Альтернативы.* Имя плагина (`cursor`) — разошлось бы с именем карточки
(`cursor-agent`), и клиенту пришлось бы знать соответствие. Спецификатор
(`stepcast/backends/cursor`) — переносит в API путь пакета и даёт клиенту
повод слать произвольный модуль; проверять его всё равно пришлось бы по
каталогу.

### Решение 3. `BackendView.plugin` — чем бэкенд подключается

Новое поле `plugin: string | undefined` несёт спецификатор каталога для
бэкенда, у которого нет адаптера в реестре и который подключается из витрины;
у подключённых и у неподключаемых (бэкенд в `backends:` без какого-либо
плагина) — `undefined`. Клиент показывает действие подключения ровно при
`!available && plugin !== undefined`, без знания имён.

Порядок списка: сначала бэкенды разрешённой конфигурации в прежнем порядке,
затем недостающие бэкенды каталога в порядке каталога. Для недостающего:
`command` — `defaults.command` плагина (иначе имя бэкенда), `enabled: true`,
`defaultModel` — `defaults.default_model` плагина (у Cursor и Copilot его нет —
`undefined`), источник модели — `plugin:<имя плагина>`, tier пусты. Для
бэкенда, который есть в `backends:` файла, но без адаптера, сохраняется
нынешнее правило Codex, обобщённое на весь каталог: пустая модель
дополняется умолчанием плагина, а `plugin` заполняется.

### Решение 4. Проверка и запись `connect`

До записи, вместе с остальными проверками `writeSettings`:

- каждое имя из `connect` обязано быть бэкендом каталога, иначе отказ
  `Agent <имя> cannot be connected from the dashboard` и файл не трогается;
- `connectCodex: true` нормализуется в `connect ∪ {"codex"}`; оба поля можно
  прислать вместе, повтор имени не ошибка;
- `agent` с `available: false` принимается, только если его имя есть в
  нормализованном `connect` и спецификатор ещё не объявлен в `plugins:`
  глобального файла. Если спецификатор уже объявлен, а адаптера всё равно
  нет (плагин снят патчем дерева плагинов или не загрузился), дописывать
  нечего, и выбор такого агента получает прежний отказ
  `Agent <имя> is not connected…` — иначе витрина записала бы в умолчание
  агента, которого следующий прогон не найдёт.

Запись внутри `editGlobalConfig`: для каждого спецификатора, которого ещё нет
в `plugins:` (точное совпадение строки), — `addIn(['plugins'], specifier)`,
создавая последовательность при её отсутствии, как сейчас для Codex.
Комментарии файла сохраняются тем же документом `yaml`. Кеш ядра демона
пересобирается по смене объявлений (решение 6 `ui-agents-settings-merge`), и
ответ `writeSettings` уже показывает бэкенд с `available: true`.

### Решение 5. Витрина: отметка подключения в общей форме, а не мгновенная кнопка

Состояние `connectCodex: boolean` в `Agents.tsx` заменяется множеством
`connect: Set<string>`. Каждая карточка с `!available && plugin` получает
чекбокс «Connect <имя>» с подсказкой, что адаптер поставляется со Stepcast, а
CLI (`<command>`) нужно установить и авторизовать отдельно. Отметка делает
форму «грязной», разрешает этот бэкенд в выборе агента на вкладке Default и
уходит в `saveSettings` полем `connect` (непустым — только тогда); после
ответа множество сбрасывается, как сейчас флаг.

*Альтернатива.* Кнопка, которая сразу шлёт `PUT /api/settings`, — отвергнута:
экран держит один черновик и одну кнопку сохранения, а мгновенная запись
либо теряла бы несохранённые правки tier, либо записывала бы их без явного
сохранения.

## Risks / Trade-offs

- [Неподключённые `cursor-agent` и `copilot` появятся на «System» и в ответе
  `/api/models`] → это тот же путь, что уже проходит неподключённый `codex`:
  «System» помечает `adapter: false`, `/api/models` отдаёт отказ перечисления.
  Тест экрана «System» проверяется на новый состав, при необходимости
  ожидания в нём обновляются, а не поведение.
- [Пользователь, которому Cursor и Copilot не нужны, видит две лишние
  карточки] → карточка помечена «plugin not connected» и ничего не делает без
  явной отметки; это ровно то, чего пункт и добивается — бэкенд виден. Скрытие
  карточек не вводится.
- [Каталог разойдётся с `exports`] → сверочный тест (решение 1).
- [Спецификатор объявлен в `plugins:` иной строкой — относительным путём или
  через `plugins.patch.yml`] → такой бэкенд уже в реестре и `available: true`,
  карточки-заглушки нет, `connect` для него не предлагается. Если же адаптер
  при этом не загрузился, повторного дописывания не будет только при точном
  совпадении строки; иначе в `plugins:` окажется вторая строка того же модуля
  — загрузчик сообщит об этом своей ошибкой, и витрина покажет её в строке
  отказа сборки состава.

## Migration Plan

Форма ответа `GET /api/settings` только расширяется (`plugin`), формы запроса —
тоже (`connect`); `connectCodex` остаётся. Старый клиент витрины, присланный
вместе со старым релизом, продолжает работать с новым демоном. Откат — откат
коммита; файлы пользователя не меняют формата.
