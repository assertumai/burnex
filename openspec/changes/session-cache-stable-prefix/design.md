## Context

Как работает кеш промпта у Anthropic. Кеш хранит начало запроса в порядке
«инструменты → системный промпт → сообщения». Если в этом начале что-то
изменилось, всё, что идёт после изменения, записывается в кеш заново. Запись
при сроке жизни 1 час (так работает Claude Code) стоит ×2 от обычного входа,
чтение — ×0,1, то есть промах в 20 раз дороже попадания.

Как ходят агенты ревью. Каждый ход — отдельный запуск CLI: продолжение сессии
через `--resume`, форк или новая сессия. Схема ответа передаётся флагом
`--json-schema`, а Claude Code превращает её в инструмент `StructuredOutput`.
Отсюда два случая, когда кеш ломается:

- у имплементатора схемы нет, а у его форка-защитника она есть;
- ревьюер отвечает сначала по схеме находок, а затем по схеме возражения.

Каждый такой ход заново пишет в кеш всю историю сессии. Замер и эксперимент
описаны в proposal.

## Goals / Non-Goals

**Goals:**
- в цепочке сессий (шаг → его продолжения и форки) начало запроса не
  меняется, и каждый ход читает историю из кеша;
- окружение пользователя можно явно отключить агентам пайплайна, но по
  умолчанию оно не трогается.

**Non-Goals:**
- свой MCP-канал ответа (решение 5);
- общая сессия защитника (`review-defend-shared-session`, пересматривается
  отдельно);
- те же правки для других бэкендов без замера.

## Decisions

### 1. Возможность `schemaInPrefix`, а не «текст везде»

Адаптер объявляет необязательный флаг `schemaInPrefix?: boolean`: «нативная
схема — часть начала запроса». Помощник `callSchemaMode(capabilities)`
возвращает режим для агентского вызова:

- `'text'`, если `structuredOutput && schemaFromText && schemaInPrefix &&
  sessions`;
- иначе — то, что возвращает `structuredOutputMode`.

`structuredOutputMode` по-прежнему отвечает на вопрос «может ли бэкенд вообще
дать схему». Его спрашивают предстарт, линт и выбор защитника, и для них
ничего не меняется.

Почему флаг адаптера. Ломает ли нативная схема кеш, зависит от того, как CLI
её передаёт. Замер есть только для Claude. Codex передаёт схему как формат
ответа, а не как инструмент, и Antigravity без замера не трогаем: им флаг не
объявляется, поведение остаётся прежним.

### 2. Правило — «бэкенд с сессиями», а не «вызов, который продолжат»

Защитнику и раунду нужно, чтобы вся цепочка шла без инструмента
`StructuredOutput`, включая первый вызов. Иначе кеш сломает уже исчезновение
инструмента: имплементатор с `output_schema` шёл бы с ним, а защитник без
него. Заранее узнать, продолжат ли сессию, можно только анализом пайплайна:
`session: shared`, `implementer:`, раунды, повторы. Правило «агентский вызов
на бэкенде с включёнными сессиями» проще и даёт ту же согласованность.

Цена правила: одиночный шаг с `output_schema`, который никто не продолжит,
тоже уходит в текст и теряет нативную гарантию формы ответа. Судья — не
агентский вызов (`judgePass.ts`): его сессия всегда новая, и он остаётся на
нативной схеме.

### 3. `user_mcp` — опция конфигурации, исполняет адаптер

Ключ `backends.<id>.user_mcp: boolean`, по умолчанию `true`. Это желание
пользователя, а не возможность бэкенда, поэтому он устроен иначе, чем
`mcp` или `strict_permissions`. Адаптер объявляет, умеет ли он его исполнить
(`isolateUserMcp?: boolean`). Если `user_mcp: false` стоит у бэкенда, который
это не умеет, и бэкенд используется в пайплайне, прогон останавливается до
старта (`requireUserMcpIsolation`), тем же приёмом, что `requireMcpSupport`.
Молча проигнорированная явная опция дала бы ложное ощущение изоляции.

Что делает Claude при `user_mcp: false`:

- добавляет `--strict-mcp-config`, если его ещё нет. Серверы, объявленные
  шагом, остаются: они идут через `--mcp-config`;
- кладёт в окружение процесса `ENABLE_CLAUDEAI_MCP_SERVERS=false`. Если
  `backends.claude.env` задаёт эту переменную явно, побеждает значение
  пользователя.

`--setting-sources` не трогается. В эксперименте отключение пользовательских
настроек выигрыша не дало, а права поменяло бы.

### 4. Без изменения журнала

Формат ответа участников не меняется. Схема в тексте видна в `prompt.txt`, а
её провал — предикат `output_schema`, который уже есть. `JOURNAL_FORMAT` не
растёт.

### 5. MCP-канал ответа отложен

Рассматривался свой stdio MCP-сервер движка с инструментами вроде
`submit_defense`, объявленный при создании сессии. По токенам он не выгоден:

- схема весит около 250 токенов, это 10–15% одного сообщения и меньше 0,5%
  истории, которую ход читает из кеша;
- определение инструмента читается из кеша при каждом запросе сессии,
  включая сотни запросов имплементатора.

Плюсы MCP-канала:

- проверка ответа внутри хода, без повторного запуска CLI;
- структура приходит готовой, JSON не нужно искать в тексте.

Минусы:

- нет у Antigravity, у Cursor есть только через файл в рабочем дереве;
- инструмент нужно объявлять с первого хода имплементатора;
- в движке появляется новая часть.

Условие возврата к нему: по журналам больше 5% ходов со схемой в тексте
уходят в повтор из-за предиката `output_schema`.

## Risks / Trade-offs

- **Модель может ответить не JSON.** Тогда нужен лишний повтор.
  → Повтор с текстом ошибки уже есть; в живых прогонах эксперимента все 15
  ходов прошли с первой попытки.
- **Codex и Antigravity не изучены.** → Без замера их не трогаем.
- **Число из эксперимента получено на крошечной задаче.** → На реальных
  задачах промах растёт вместе с историей, так что эффект должен быть больше.
