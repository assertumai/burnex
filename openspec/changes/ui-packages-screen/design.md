## Context

Указатель пакетов (`buildPackageIndex`, `src/parts/packages/index.ts`) находит
каталоги пакетов двух слоёв — проекта (`<проект>/.stepcast/packages`) и home
(`packages/` рядом с глобальным `config.yml`), — проверяет манифест и помечает
затенение. Сводка `summarizePackages` (`src/parts/packages/summary.ts`) — одна
модель на `stepcast package list`, его `--json` и `GET /api/packages`: имя,
слой, каталог, статус `ok | broken | shadowed`, причина, версия, описание,
`provides` (виды, где есть хоть один ресурс) и `unmetNeeds`. Наблюдатель демона
(`src/parts/ui/daemon/watcher.ts`) держит её как `currentPackages()` и
пересобирает по сдвигу отпечатка пакетов.

Отказы ресурсов пакета сейчас разнесены по составам, каждый в своём месте:

| Вид | Где отказ виден |
|---|---|
| виджет | запись `currentWidgets()` с полем `error` и `source.package` (в том числе конфликт двух пакетов) |
| дашборд | `currentDashboards().failures` — `DashboardFailure` с `package`, `file`, `reason` |
| маршрут | `currentRoutes().failures` — `RoutePackageFailure` с `packages`, `file`, `message` |
| плагин | итог строки дерева `RowOutcome` в `currentDaemonKernel().outcomes` |
| шаг, скрипт | только при поиске: `ScriptUnresolved` с `resource_conflict`, `stepcast lint` |
| пайплайн | конфликтовать не может — адрес несёт имя пакета |

Экран «Маршруты» показывает только третью строку таблицы.

## Goals / Non-Goals

**Goals:**

- Один экран отвечает: какие пакеты есть в каждом слое, что каждый приносит
  поимённо, действует ли он, а если нет или если отказал его ресурс — почему.
- Модель состава одна для CLI и витрины — расходиться им негде.
- Отказ, который уже вычислен составом, экран не пересчитывает своими
  правилами, а берёт из состава.

**Non-Goals:**

- Установка, обновление, удаление пакетов; создание пакета с витрины
  (`stepcast package new`) — маркетплейс, отдельная работа.
- Запись в каталог пакета — витрина его не пишет (`docs/packages.md`).
- Проверка схемой каждого `step.yml` и пайплайна пакета: это делает
  `stepcast lint` при использовании; экран показывает имена.
- Пакеты прочих проектов корня прогонов: наблюдатель знает один `projectRoot`,
  как и `GET /api/packages` сегодня.
- Группа меню «Конфигурация» — пункт `ui-nav-config-group`.

## Decisions

### Решение 1. Состав — поле общей модели, отказы — только в ответе демона

`contents` — факт файловой системы (имена в подкаталогах пакета), его видит и
CLI без собранного состава плагинов, поэтому он входит в `PackageSummary`.
`problems` — факт действующих составов демона (скомпилированный виджет,
собранный дашборд, дерево плагинов); CLI их не собирает, поэтому `problems`
лежит в ответе `GET /api/packages` рядом с `packages`, а не внутри сводки.
Так обещание «`GET /api/packages` отдаёт ту же сводку, что и `stepcast package
list --json`» остаётся верным для поля `packages`.

`contents` — объект с ключами видов в порядке `ResourceKind`; каждый — список
имён по алфавиту, пустой вид опущен:

- `pipelines` — `listPackagePipelineNames`;
- `steps` — каталоги `steps/<имя>/` с `step.yml`;
- `scripts` — файлы верхнего уровня `scripts/`;
- `plugins` — каталоги `plugins/<id>/`;
- `widgets` — `widgets/<id>.tsx`;
- `dashboards` — `dashboards/<id>.yml`;
- `routes` — `id` строк `routes.yml`; файл, который не читается или не
  разбирается, даёт пустой список, а причина приходит в `problems` от состава
  маршрутов.

Правило «где есть хоть один ресурс» для `provides` выводится из `contents`, а
не из второго обхода: `provides` — ключи `contents`. Исключение одно —
`routes`: `provides` называет вид при наличии файла `routes.yml`, как сейчас,
даже когда файл не разобрался; сохраняется ради совместимости вывода
`package list`.

Сломанный пакет `contents` несёт тоже: что лежит в каталоге, видно, хоть оно и
не участвует в поиске. Экран помечает такой состав как неучаствующий; так же —
состав затенённого пакета.

*Альтернатива* — отдельный `GET /api/packages/:name` с составом. Отвергнута:
пакетов единицы, ресурсов десятки, а второй запрос дал бы экрану два снимка
разного возраста.

### Решение 2. Конфликт `id` — одна чистая функция над составом

`packageConflicts(summaries)` в `src/parts/packages/summary.ts` (над сводками с `contents`): для
каждого слоя и вида, кроме `pipelines`, имя, которое есть у двух и более
**действующих** пакетов слоя (`status: ok`), — конфликт с перечнем пакетов и
текстом `describeConflict`. Сломанный и затенённый пакет в поиске не участвуют
и конфликта не дают — так же, как в `lookupInPackages`. Плагин с именем
встроенной строки (`reservedPluginIds`, у демона — `daemonBuiltinRowIds()`)
конфликта не даёт: `packagePluginOperations` даёт такому каталогу отказ в каждом
пакете отдельно, без `supersede`, и функция повторяет это правило.

Для шагов и скриптов это единственный источник: их конфликт иначе виден только
при поиске. Для виджетов, дашбордов, маршрутов и плагинов составы находят тот
же конфликт сами; чтобы не показывать его дважды, из составов в `problems`
идут только записи, называющие **один** пакет (отказ файла), а конфликты — из
`packageConflicts`. Тест сверяет, что множество конфликтов функции совпадает с
конфликтами составов для этих четырёх видов: расхождение правил ловится
тестом, а не пользователем.

*Альтернатива* — брать конфликты из составов, а для шагов и скриптов писать
свою проверку. Отвергнута: четыре формы записи конфликта сводились бы к одной
раздельно, и шаги со скриптами всё равно требовали бы своей функции.

### Решение 3. Форма записи `problems`

```ts
interface PackageProblem {
  readonly layer: 'project' | 'home';
  readonly packages: readonly string[];   // один — отказ файла, два и более — конфликт
  readonly kind: ResourceKind;
  readonly id?: string;                   // имя ресурса; нет у нечитаемого routes.yml целиком
  readonly file?: string;
  readonly message: string;               // текст движка без перевода
}
```

Сведение — `buildPackageProblems(watcher, kernel)` в `src/parts/ui/packages.ts`:
виджеты пакетов с `error`, `DashboardFailure` с `package`,
`RoutePackageFailure` с одним пакетом, отказавшие `RowOutcome` строк, чей
источник — пакет (поле `package` манифеста плагинов), и `packageConflicts`.
Порядок — слой проекта, затем home; внутри — по пакету, виду, `id`.

Отказ плагина, который сам является конфликтом двух пакетов, узнаётся по
явному признаку `conflict` в заведомом отказе строки
(`packagePluginConflict`, `src/parts/packages/plugins.ts`), а не по ключу
«слой + вид + `id`» и не по тексту. Поэтому любой другой отказ плагина остаётся
отдельной записью. У дашбордов отказ с `id`, конфликтующим в слое пакетов, —
это сам конфликт: `buildDashboards` на конфликте файлы не разбирает, и другой
причины для этого `id` у состава нет.

Ядро демона берётся `currentDaemonKernel` — единственной точкой получения
(`src/parts/ui/daemon/kernel.ts`). Если ядро не собралось, отказы плагинов не
добавляются, а ответ несёт `pluginsError` с причиной: экран пишет «состав
плагинов не собран», и остальное показывается.

### Решение 4. Экран, строка и маршрут

Строка `ui-packages` (только API) заменяется экранной `screen-packages` с
объявлением экрана и тем же обработчиком — как у прочих экранов
(`src/parts/ui/screens/<имя>/{declaration,server}.ts`). Двух строк, владеющих
одним путём API, быть не может, а экран без своей строки не объявить.

Маршрут `/packages`, `nav: { group: extend, order: 3 }` — рядом с «Widgets»
(`order: 2`): пакеты — это расширение витрины и пайплайнов, не настройка
системы.

Экран:

- секции «Project» и «Home» в порядке поиска; пустой слой — строка «нет
  пакетов» с путём каталога слоя (`projectPackagesDir`, `homePackagesDir`),
  чтобы было ясно, куда класть;
- карточка пакета: имя, `package_version`, описание, путь каталога, бейдж
  статуса; у сломанного — причина, у затенённого — «затенён пакетом проекта»;
- состав по видам строками «вид: имена»; пайплайны подписаны адресом
  `<пакет>:<имя>`; у сломанного и затенённого состав приглушён с подписью «не
  участвует в поиске»;
- `unmetNeeds` — справочно, тем же словом, что `package list`;
- отказы пакета — список под карточкой; конфликт виден у каждого из пакетов и
  называет второй;
- кнопка «Обновить» перечитывает `GET /api/packages`; наблюдатель пересобирает
  сводку сам, так что повторный запрос видит новые пакеты без перезапуска.

Предупреждение `packageFailures` на «Маршруты» остаётся и получает ссылку на
`/packages`.

## Risks / Trade-offs

- [Чтение `routes.yml` в сводке] → `stepcast package list` начинает разбирать
  YAML маршрутов. Ошибка разбора не бросается: список пуст, `provides` прежний.
- [Удаление идентификатора `ui-packages`] → патч, отключавший строку по `id`,
  перестанет совпадать. Строка появилась недавно и встроена; в
  `docs/packages.md` записать новое имя.
- [Сбор `problems` трогает ядро демона на каждый запрос] → `currentDaemonKernel`
  кеширует ядро по дереву, совпавшее дерево ничего не пересобирает.
