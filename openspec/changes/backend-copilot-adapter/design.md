## Context

Контракт бэкенда-плагина (`src/parts/pipeline/backend/types.ts`) прошли два
внешних адаптера, Codex и Cursor (`src/parts/backends/{codex,cursor}/`). Оба
разбирают потоковый JSON: каждая строка stdout — запись, и запись сама
говорит, что она такое. Cursor вдобавок добавил в ядро различение effort
документа и настроек (`requireEffortSupport` по `effortOrigins`) и
предстартовую проверку `output_schema` агентского шага. Обе правки здесь
переиспользуются без изменений.

У GitHub Copilot CLI (`copilot`, пакет npm `@github/copilot`) неинтерактивный
режим `-p` печатает простой текст ответа. С `-s` это только ответ, без
статистики. Отсюда всё, чего у адаптера нет: идентификатора сессии в выводе,
расхода, вызовов инструментов, структурированного вывода. Адаптер burnex
устроен так же («без сессий, usage и списка моделей»), но запущен ни разу не
был.

Что держит текст шага сейчас (`run/exec/agentStep.ts`, `handleLine`): каждое
событие `result` с `text` **перезаписывает** текст попытки. `parseLine`
вызывается построчно, без состояния: экземпляр адаптера один на прогон и
обслуживает одновременные шаги (комментарий к `init.sessionId` в
`types.ts`). Значит, адаптер текстового CLI не может ни копить строки у себя,
ни отдать весь ответ одним событием.

CLI `copilot` в среде, где заводится изменение, не установлен, а сети нет.
Флаги взяты из документации GitHub Copilot CLI и из описания burnex. Их
сверка по `--help` живой установки — задача 1.1, а живой прогон — признак
выполненности.

## Goals / Non-Goals

**Goals:**
- Бэкенд `copilot` плагином `stepcast/backends/copilot`: агентский шаг,
  который правит рабочее дерево и отдаёт весь текст ответа.
- Минимальная правка ядра, которая годится любому текстовому CLI, а не только
  Copilot.
- Честные возможности: всё, чего нет, отклоняется или деградирует уже
  существующими проверками движка.
- Живой прогон шага, записанный в этом документе.

**Non-Goals:**
- Сессии. В интерактивном режиме у CLI есть `--resume`/`--continue`, но `-p`
  идентификатора не печатает, а `--continue` продолжает «последнюю» сессию
  каталога. При двух одновременных шагах это гонка, а не продолжение.
- Расход из статистики, которую CLI печатает без `-s`: формат не
  документирован как машинный, а разбор человекочитаемой сводки сломается
  при первом обновлении.
- Перевод `permissions.allow`/`deny` в `--allow-tool`/`--deny-tool`: синтаксис
  шаблонов (`shell(git push)`) не совпадает с объявлением stepcast, и перевод
  без живой сверки обещал бы границу, которой может не быть.
- Перечень моделей и карточка в витрине настроек.
- Потоковый JSON, если окажется, что новая версия CLI его даёт. Это отдельный
  пункт; в документации тогда записывается, что он есть.

## Decisions

### 1. Событие `text` в ядре вместо состояния в адаптере

В `BackendEvent` добавляется вид `{ readonly kind: 'text'; readonly text:
string }`. В `agentStep.ts` для попытки заводится массив `pieces`: `text` его
пополняет, `result` с `text` задаёт итоговый текст как прежде. После выхода
процесса текст попытки равен `text`, если `result` его дал, иначе
`pieces.join('\n')` с отсечёнными пустыми строками по краям (ведущими и
завершающими), иначе
`undefined`, если кусков не было.

*Альтернативы:*
- Копить строки в замыкании адаптера и сбрасывать в `launch()`. Отклонена:
  при `concurrency: 2` два шага делят экземпляр, и их строки перемешались бы.
- Обёртка-скрипт: адаптер запускает `node wrap.js copilot …`, а обёртка
  собирает stdout и печатает одну JSON-запись. Отклонена: лишний процесс
  между движком и CLI ломает отмену и детектор тишины (сигнал и вывод идут
  через посредника), а молчание до самого конца делает тишину неотличимой от
  зависания.
- Изменить семантику `result.text` на «дописать». Отклонена: Claude, Codex и
  Cursor отдают несколько `result`, и для них «последний побеждает» —
  правильное поведение.

Судья (`judgePass.ts`) событие `text` не читает: бэкенд без
структурированного вывода судьёй стать не может, его отклоняет линт и
предстартовая проверка.

### 2. Запуск

`[command, '--allow-all', '--no-color', '-s', ...('--model' m), <промпт>]`.

- `--allow-all` разрешает все инструменты, пути и URL. Без этого флага
  неинтерактивный запуск ждёт подтверждений, которых некому дать. Если
  установленная версия этого флага не знает, по `--help` берутся его части
  (`--allow-all-tools`, `--allow-all-paths`), и решение записывается в README
  фикстур.
- `--no-color` и `-s`: в stdout только текст ответа, без ANSI-кодов и
  сводки. Требование спеки о `stdout.log` без ANSI выполняется самим CLI, а
  не очисткой.
- Промпт: stdin, если `copilot -p` читает его из stdin (сверяется в 1.1).
  Иначе слитный аргумент `--prompt=<промпт>`, а не пара `-p <промпт>`: в
  слитной форме промпт, начатый с `-`, разборщик флагов принять за флаг не
  может. Linux ограничивает один аргумент 128 KiB (`MAX_ARG_STRLEN`), поэтому
  `launch()` в этой форме проверяет байтовую длину всего аргумента — с
  префиксом `--prompt=` и завершающим NUL — и отказывает
  `StepcastError` с подсказкой сократить контекст шага. Иначе отказ
  проявился бы как `spawn E2BIG` без имени бэкенда.
- Рабочий каталог задаёт движок процессом. `--add-dir` не передаётся: доступ
  ограничен деревом шага.

### 3. Возможности и их следствия

| Возможность | Значение | Что делает движок |
|---|---|---|
| `sessions` | `false` | `session: shared` → `per_step` с предупреждением |
| `sessionIdSource` | `'backend'` | движок не заводит UUID, `step.json` без сессии |
| `structuredOutput` | `false` | `output_schema` и судья отклоняются до старта |
| `strictPermissions` | `false` | `enforce: strict` отклоняется до старта |
| `mcp` | `false` | непустой `mcp` отклоняется до старта |
| `effort` | `false` | effort документа отклоняется, настроек → `backend.degraded` |
| `reportsCost` | `false` | предупреждение о шаге без цены (существующее) |

`sessionIdSource: 'backend'` при выключенных сессиях выбран намеренно. При
`'engine'` движок завёл бы идентификатор сам (`sessions.acquire`) и записал бы
в `step.json` сессию, которой у CLI нет. Позже `resume` пошёл бы её
продолжать.

Флаги конфигурации (`structured_output`, `mcp`, …) адаптер не читает, как и
Cursor: включить ими возможность, которой у CLI нет, значило бы пообещать её
молча.

### 4. Доступ — отказ, а не тихое «всё можно»

Пооперационных списков и режимов песочницы адаптер не переводит. Любое
`permissions.mode`, непустые `allow`/`deny` в действующем объявлении
(`effectivePermissions` шага поверх `backends.copilot.permissions`) дают
`StepcastError` из `launch()`. Ошибка называет `copilot`, ключ и причину:
запуск идёт с `--allow-all`. `enforce: strict` раньше отклоняет предстартовая
проверка, но `launch()` его тоже отклоняет — на случай вызова в обход.

### 5. Разбор строки

`parseLine(line)` → `{ kind: 'text', text: line.replace(/\r$/, '') }` для любой
строки, пустой в том числе. `unparsed` и `ignored` адаптер не отдаёт: формы,
которую можно не распознать, у текста нет. Хвостовую строку без перевода
строки движок уже передаёт в `handleLine` после выхода процесса.

Отказ не классифицируется. Только stdout доходит до `parseLine`, а stdout —
это ответ агента, и совпадение по словам дало бы ложный `rate_limit`, который
останавливает прогон. Отказ CLI (не залогинен, лимит) завершает процесс
ненулевым кодом, и попытка проваливается обычным путём. Текст ошибки остаётся
в `stderr.log`. Это записывается в «Чего не хватило».

### 6. Живой прогон

`examples/copilot/stepcast.yml`: один агентский шаг, который создаёт файл в
рабочем дереве и отвечает двумя абзацами, и проверка `file_exists`. Прогон на
установленном (`npm i -g @github/copilot`) и залогиненном CLI с конфигурацией
`plugins: [stepcast/backends/copilot]`. В раздел ниже записываются
`copilot --version`, команда `stepcast run`, статус шага, выдержка из
`step.json` (текст обоих абзацев) и все расхождения с решениями 2 и 5.

## Живой прогон

**Не выполнен.** На 2026-10-30 в среде, где реализовывалось изменение,
`copilot` не установлен (`which copilot` ничего не находит), а сети для
`npm i -g @github/copilot` и входа через `/login` нет. Поэтому
`copilot --version`, `stepcast run examples/copilot/stepcast.yml`, статус шага и
выдержка из `step.json` не сняты, наблюдение о тишине до ответа и расхождения с
решениями 2 и 5 (слитный `--prompt=`, `--allow-all`, `-s`) не получены. Флаги и
`test/fixtures/copilot/answer.txt` составлены по документации
(`test/fixtures/copilot/README.md`); исполнение шага проверено только на
подменённом `copilot` (`test/copilot-adapter.test.ts`). Пример
`examples/copilot/` готов к прогону: порядок — в его `README.md`. Задача 7.2
остаётся неотмеченной, изменение к архивации не готово.

## Risks / Trade-offs

- [Флаги взяты из документации, а не сверены] → задача 1.1 сверяет `--help`
  до написания адаптера, а живой прогон не даёт архивировать изменение с
  неверными флагами.
- [`--allow-all` даёт агенту выполнять любые команды и ходить в сеть] → то же,
  что у Codex и Cursor в неинтерактивном режиме. Граница — изоляция рабочего
  дерева шага, и `docs/config.md` называет это прямо.
- [Предел 128 KiB на аргумент, если stdin не поддерживается] → громкий отказ
  с подсказкой, а не `E2BIG`. Длинный контекст на этом бэкенде не пройдёт, и
  документация это называет.
- [Новое событие ядра] → необязательное для адаптеров. Существующие адаптеры
  его не отдают, и их поведение тест не меняет. Плагин, написанный под
  старый контракт, продолжает работать.
- [Детектор тишины: `-s` молчит до ответа] → CLI печатает ответ в конце,
  так что долгий шаг может молчать дольше `defaults.stall_timeout`. Живой
  прогон покажет, так ли это. Если так, в `docs/config.md` появится совет
  поднять `defaults.stall_timeout` для пайплайнов на `copilot`, а умолчание
  вклада не меняется.
- [Токен GitHub в окружении шага] → `COPILOT_GITHUB_TOKEN`, `GH_TOKEN`,
  `GITHUB_TOKEN` перечисляются в `docs/config.md` рядом с `env_deny` и
  `backends.copilot.credentials`.
