## Why

Сегодня движок ставится только из чекаута: `npm install && npm run build &&
npm link`, а каталог репозитория после этого нельзя ни перенести, ни удалить.
Отдать stepcast коллеге или поставить на вторую машину одной командой нельзя,
обновление — ручные `git pull` и `npm run build`, после которых ещё надо
вспомнить перезапустить демон витрины. Раскладка релизов по
`~/.stepcast/releases/<версия>` с переключаемой ссылкой `current` уже есть
(`scripts/release-local.sh`), но собирает она только текущее рабочее дерево и
о версиях ничего не знает.

## What Changes

- **`scripts/install.sh`** в репозитории — установка одной командой
  (`curl -fsSL …/scripts/install.sh | bash`). Проверяет `git`, `npm` и Node ≥ 22;
  берёт последний тег `v*` репозитория (по `git ls-remote`, сравнение версий,
  а не строк), либо ссылку из `--ref <тег|ветка|sha>`; репозиторий — по
  умолчанию `https://github.com/assertumai/stepcast.git`, иначе `--repo <url|путь>`.
  Мелко клонирует ссылку во временный каталог, собирает (`npm ci`,
  `npm run build`), раскладывает поставку в `~/.stepcast/releases/<версия>`
  (тот же состав, что у `release-local.sh`, плюс сам `install.sh`), ставит
  зависимости релиза `npm ci --omit=dev`, атомарно переключает `current` и
  ставит лаунчер `~/.local/bin/stepcast` — симлинк на
  `~/.stepcast/releases/current/dist/src/bin.js`. Записывает
  `~/.stepcast/install.json` со способом `managed`. Повторный запуск той же
  версии пересобирает её начисто; прежние релизы не удаляются.
  Каталоги переопределяются `STEPCAST_HOME` и `STEPCAST_BIN_DIR` — ради проверки
  и нестандартных раскладок. Если `~/.local/bin` не на `PATH`, скрипт так и
  говорит и печатает строку для профиля оболочки.
- **`~/.stepcast/install.json`** — паспорт установки: `method`
  (`managed` | `checkout` | `npm`) и поля способа (`repo`, `ref`, `version`,
  `releases_dir` у `managed`; `dir` у `checkout`; `package` у `npm`).
  Разбирается схемой zod; неизвестный способ и битый файл — ошибка с причиной,
  а не догадка. Нет файла — способ выводится из того, откуда исполняется
  движок (`node_modules` → `npm`, git-дерево → `checkout`); не выводится —
  отказ с подсказкой поставить через `install.sh`.
- **`stepcast update [--ref <ссылка>]`** — новая независимая от конфигурации
  команда. По паспорту:
  - `managed` — запускает `install.sh` из текущего релиза с `--repo` из
    паспорта и `--ref` из флага или последним тегом; та же версия, что уже
    стоит, — «обновлений нет», без пересборки;
  - `checkout` — отказ при грязном дереве, иначе `git pull --ff-only` (или
    `git checkout <ref>` при флаге), `npm ci`, `npm run build`;
  - `npm` — `npm install -g <package>@<ref|latest>`.

  После успешного обновления перезапускает демон витрины, если он был поднят:
  агент launchd — `launchctl kickstart -k`, отсоединённый демон — остановка и
  `stepcast up` новой версии в каталоге, где демон был поднят. Не поднятый
  демон не поднимается.
- **Каталог демона запоминается**: запись `~/.stepcast/ui.pid` получает поле
  `cwd`; старая запись без него читается как прежде, а `update` тогда не
  перезапускает демон, а печатает, где его поднять.
- **Устойчивый путь входа демона**: при установке `managed` и `up --install`, и
  отсоединённый `up` запускают демон по `…/releases/current/dist/src/bin.js`, а
  не по разрешённому пути конкретного релиза, — иначе агент launchd после
  обновления продолжал бы поднимать старую версию.
- **Поставка через npm**: `package.json` получает `prepack` со сборкой,
  `repository` и `publishConfig`; `docs/release.md` описывает выпуск — версия в
  `package.json`, коммит, тег `vX.Y.Z`, `npm publish` с этого тега — и почему
  тег обязан совпадать с версией пакета. Автоматической публикации из CI это
  изменение не заводит.
- **README** — установка через `install.sh` первой, `npm link` остаётся как путь
  разработки; раздел про `stepcast update`.

Решение: `install.sh` — единственное место, которое знает раскладку релиза;
`stepcast update` в режиме `managed` не повторяет её на TypeScript, а вызывает
скрипт, а `release-local.sh` переходит на общую раскладку, оставаясь
инструментом разработки, который паспорт установки не меняет.

## Capabilities

### New Capabilities

- `engine-install`: установка движка скриптом, паспорт установки и команда
  `stepcast update` с перезапуском демона.

### Modified Capabilities

- `ui-daemon`: запись демона хранит каталог, в котором он поднят, и при
  установке `managed` демон запускается по устойчивому пути `current`.

## Impact

- Новые: `scripts/install.sh`, `docs/release.md`,
  `src/parts/install/` (паспорт, выбор способа, план обновления, перезапуск
  демона — порождение процессов через внедряемую функцию),
  `src/parts/install/commands/update.ts`; строка `update` в
  `src/parts/cli/rows.ts`.
- Правка: `src/parts/ui/daemon/daemon.ts` (поле `cwd`),
  `src/parts/ui/commands/up.ts` (путь входа), `scripts/release-local.sh`,
  `package.json`, `README.md`, `docs/config.md` (перечень независимых команд).
- Тесты: разбор `install.json`, вывод способа без паспорта, план обновления и
  перезапуска с подменой процессов; чтение записи демона без `cwd`.
- Новых зависимостей нет. Публикация в npm требует свободного имени пакета и
  прав в реестре — это шаг человека, а не кода.
