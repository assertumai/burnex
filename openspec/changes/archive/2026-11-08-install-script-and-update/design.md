## Context

Движок сейчас живёт в двух видах: рабочее дерево с `npm link` (разработка) и
релиз, собранный `scripts/release-local.sh` в
`~/.stepcast/releases/<ts>-<sha>` с переключаемой ссылкой `current`, на
которую смотрит глобальный `stepcast`. Второй вид уже даёт главное — релиз не
зависит от дальнейших правок дерева, переключение атомарно (`ln -sfn`), —
но собирается только из локального чекаута и о версиях не знает.

Демон витрины (`stepcast up`) запускает себя по `binPath()` — пути, вычисленному
из `import.meta.url`. Node разрешает симлинки главного модуля, поэтому путь
указывает в конкретный релиз (`releases/<v>/dist/src/bin.js`), а не в `current`.
Агент launchd (`up --install`) кладёт этот путь в `ProgramArguments`. Запись
демона `~/.stepcast/ui.pid` хранит `pid`, `port`, `started_at` — каталога, в
котором демон поднят (он же корень проекта), в ней нет.

Корни поставки движок уже находит независимо от места установки
(`enginePackageRoot`, переносимые ссылки `stepcast-package:` в ключах шагов), так
что смена каталога релиза ключи шагов не ломает.

## Goals / Non-Goals

**Goals:**

- Поставить движок на чистую машину одной командой, с выбором версии и
  источника.
- Обновлять установленный движок одной командой, тем же способом, каким он
  поставлен, с перезапуском демона.
- Описать выпуск версии и публикацию npm-пакета по тегу.

**Non-Goals:**

- Уборка старых релизов (`releases/*`) — откат на прежний релиз как раз ими и
  делается; уборка — отдельный пункт.
- Публикация из CI, подпись релизов, бинарные сборки без Node.
- Windows: скрипт — bash, лаунчер — симлинк.
- Самообновление в фоне и проверка новых версий при каждом запуске.

## Decisions

### Решение 1. Раскладку релиза знает один `install.sh`

`install.sh` клонирует ссылку, собирает и раскладывает её. `stepcast update` в
режиме `managed` не переписывает это на TypeScript, а запускает `install.sh`,
лежащий в текущем релизе (скрипт копируется в релиз при раскладке).
`release-local.sh` переходит на ту же функцию раскладки: скрипт
`install.sh --from-dir <дерево>` (только для разработки) раскладывает уже
собранное дерево без клонирования. Отвергнуто: держать раскладку в двух
скриптах — они уже сейчас пришлось бы править парой при каждом новом каталоге
поставки (`package.json` `files`).

Скрипт сначала клонирует и собирает во временном каталоге, раскладывает в
`releases/<версия>.tmp-<pid>`, ставит зависимости и только потом переносит
каталог на место и переключает `current`. Сбой на любом шаге оставляет
прежний `current` нетронутым.

### Решение 2. Имя релиза — версия, а не время

Тег `vX.Y.Z` даёт релиз `releases/X.Y.Z`. Ссылка, не являющаяся тегом `v*`
(ветка, sha), даёт `releases/<ссылка>-<короткий sha>` — двух сборок одного
имени с разным содержимым не бывает. `release-local.sh` сохраняет своё имя
`<ts>-<sha>[-dirty]`. Повтор той же версии пересобирает каталог заново, а не
доверяет старому: частично разложенный релиз от прерванной установки иначе
жил бы вечно.

### Решение 3. Последний тег — по версии

`git ls-remote --tags --refs <repo> 'v*'`, отбор строгих `vX.Y.Z` (пре-релизы
`vX.Y.Z-…` пропускаются, если не названы `--ref` явно), сортировка
`sort -t. -k1,1n -k2,2n -k3,3n` после снятия `v`. Тегов нет — отказ с
подсказкой `--ref main`. `git ls-remote` работает и по пути к локальному
репозиторию, что делает `--repo <путь>` пригодным для проверки без сети.

### Решение 4. Лаунчер — симлинк в `~/.local/bin`

`~/.local/bin/stepcast` → `<releases>/current/dist/src/bin.js` (у `bin.js`
бит исполнения ставится при раскладке, как сегодня в `release-local.sh`).
Каталог не требует прав администратора и есть в `PATH` большинства
современных профилей; если его там нет, скрипт печатает строку `export PATH=…`
и не правит профиль сам. Существующий файл на месте лаунчера, не являющийся
симлинком в `releases`, скрипт не перезаписывает без `--force`: это может быть
чужой `stepcast` (например, `npm link`).

### Решение 5. Паспорт установки `~/.stepcast/install.json`

```json
{ "method": "managed", "repo": "https://…/stepcast.git", "ref": "v0.3.0",
  "version": "0.3.0", "releases_dir": "/Users/…/.stepcast/releases",
  "installed_at": "2026-10-30T…Z" }
{ "method": "checkout", "dir": "/Users/…/develop/stepcast" }
{ "method": "npm", "package": "stepcast" }
```

Схема — дискриминированное объединение zod по `method`; лишние ключи
допускаются (более новый `install.sh` может дописать поле, старый движок не
должен от этого падать). Пишет паспорт только `install.sh` (`managed`);
`checkout` и `npm` либо заданы файлом вручную, либо выводятся из пути
`enginePackageRoot()`: сегмент `node_modules` → `npm` с именем из
`package.json`; корень внутри git-дерева → `checkout` с этим корнем; корень
внутри `releases_dir` без паспорта → отказ (паспорт потерян, источник
неизвестен). Выведенный способ печатается — человек видит, что сейчас будет.

Модуль паспорта — чистые функции (`parseInstallManifest`,
`inferInstallMethod(root, probes)`), без чтения диска внутри разбора: именно
их покрывают тесты, названные пунктом.

### Решение 6. `stepcast update` — строка независимая от конфигурации

Команда обязана работать, когда конфигурация проекта сломана или её нет
вовсе: обновление движка — частый способ сломанное починить. Поэтому строка
`update` объявляется `independent`, как `down` и `init`, и не читает ни
конфигурации, ни реестра вкладов. Флаги: `--ref <ссылка>` (для `npm` —
версия или dist-tag), `--no-restart`.

План обновления строится чистой функцией из паспорта и флагов в список
команд (`{ cmd, args, cwd }`); исполнитель — внедряемый, как `launchctl` в
`launchd.ts`. Вывод каждой команды идёт в терминал как есть.

Для `checkout` грязное дерево (`git status --porcelain` непуст) — отказ:
`git pull` поверх незакоммиченных правок либо упадёт посреди, либо смешает
их с чужими. Для `managed` «обновлений нет» определяется сравнением целевой
версии с `version` паспорта до запуска скрипта.

### Решение 7. Перезапуск демона

После успешного обновления (и без `--no-restart`):

1. загружен агент launchd (`launchctl print gui/<uid>/ai.stepcast.daemon`
   успешен) → `launchctl kickstart -k gui/<uid>/ai.stepcast.daemon`;
2. иначе жив отсоединённый демон из `ui.pid` → `stopDaemon`, затем
   `stepcast up` **новой** версии (лаунчер или `bin.js` нового корня) с
   `cwd` записи;
3. иначе ничего: не поднятый демон не поднимается.

Запись без `cwd` (поднята прежней версией) — демон останавливать нельзя,
поднять обратно будет негде: команда печатает «перезапустите витрину:
`stepcast down && stepcast up` в каталоге проекта» и завершается успехом.

### Решение 8. Устойчивый путь входа при `managed`

Чтобы `kickstart -k` поднял новую версию, `ProgramArguments` агента должны
смотреть в `current`, а не в разрешённый релиз. `up` выбирает путь входа так:
если корень исполняемого движка лежит в `releases_dir` паспорта `managed`, —
`<releases_dir>/current/dist/src/bin.js`; иначе — прежний `binPath()`. Тот же
путь получает отсоединённый демон. Уже установленный агент старого вида
исправляется повторным `up --install`; `update` это и подсказывает, когда
путь в plist не ведёт в `current`.

### Решение 9. npm-пакет

`package.json`: `prepack: npm run build` (публикация собирает `dist` сама,
забытая сборка не уезжает в реестр), `repository`, `publishConfig.access:
public`. `files` уже перечисляет поставку. `docs/release.md` — порядок:
`npm version X.Y.Z` (коммит и тег `vX.Y.Z` одним шагом), `git push --follow-tags`,
`npm publish` из чекаута этого тега. Тег и версия обязаны совпадать: по тегу
ставит `install.sh`, по версии — npm, и расхождение дало бы две разные «0.3.0».
`install.sh` проверяет это при установке тега `vX.Y.Z` и отказывает при
несовпадении.

## Risks / Trade-offs

- [Сборка на машине пользователя тянет dev-зависимости (vite, typescript) и
  идёт минуту-две] → приемлемо для первой версии; готовые архивы релизов —
  отдельный пункт.
- [Имя `stepcast` в npm может быть занято] → имя пакета — поле паспорта и
  `package.json`; при занятом имени выпуск идёт под scope, документ это
  оговаривает.
- [`update` в `managed` исполняет `install.sh` старого релиза] → он клонирует
  целевую ссылку и раскладывает её; если раскладка в новой версии поменялась,
  новый скрипт попадает в релиз и будет использован со следующего
  обновления. Скрипт держится обратно совместимым по флагам.
- [`kickstart -k` рвёт идущие в демоне запуски] → обновление — явное действие
  человека; `--no-restart` оставляет старый демон работать.
- [Приватный репозиторий] → `--repo git@github.com:…` — клонирование идёт
  обычным `git` с ключами пользователя.

## Migration Plan

Установки `npm link` продолжают работать: `update` выводит `checkout`.
Глобальный `stepcast`, поставленный симлинком на `releases/current` вручную
(как у автора), продолжает работать; паспорта у него нет, и `update`
отказывает с подсказкой поставить через `install.sh`. Откат релиза —
`ln -sfn ~/.stepcast/releases/<прежняя> ~/.stepcast/releases/current`,
описан в `docs/release.md`.
