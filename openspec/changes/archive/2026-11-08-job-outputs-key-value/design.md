## Context

Работа передаёт результат вниз по графу сегодня двумя механизмами:

- **Структурированный выход** (`output.from`, `output_schema`): JSON из stdout шага, проверенный схемой; читается подстановкой `${jobs.<работа>.output...}` и блоком `context_upstream`.
- **Данные работы** (`data:` + `stepcast data set|merge`): строковые ключи в `jobs/<работа>/data.json`; движок принимает в состояние прогона только объявленные ключи (`foldJobData` в `run/runner.ts`), линт сверяет `${jobs.<работа>.data.<ключ>}` с объявлением производителя (`checkJobDataSubstitutions` в `domain/lint.ts`).

Оба раскрываются в поле документа до запуска процесса. Командному шагу, которому надо прочитать значение у себя в оболочке, приходится либо подставлять его в `env:` шага, либо звать `stepcast data`. Пункт очереди просит ход Burnex: файл `key=value` и переменные `NEEDS_<JOB>_<KEY>` у прямых зависимых, с объявлением `outputs:`, которое запись не ограничивает, но обязывает опубликовать объявленное.

Окружение шага собирает `buildStepEnv` (`run/exec/env.ts`) слоями: процесс → `env_files` → pipeline → job → backend → step → `injected` (переменные `STEPCAST_*`, неперекрываемые) → `env_deny` (кроме `STEPCAST_*`) → вычёркивание чужих секретов → названные секреты.

## Goals / Non-Goals

**Goals:**
- Шаг `run` публикует строки дописыванием в файл, без подкоманд движка и схем.
- Прямой зависимый читает их как обычные переменные окружения.
- Ошибки формы и «объявил, но не опубликовал» ловятся детерминированно и называются; ссылки `$NEEDS_*` проверяются до захода.

**Non-Goals:**
- Подстановка `${jobs.<работа>.outputs.<ключ>}` в поля документа и в `if` — для этого есть данные работы.
- Публикация выходов шагами `script`, `agent`, `uses`: у `script` свой контракт выхода, агент пишет данные через `stepcast data`. Переменная `STEPCAST_JOB_OUTPUTS` им не выдаётся.
- Многострочные значения и экранирование (heredoc-формы GitHub `name<<EOF`).
- Передача через транзитивные зависимости.

## Decisions

### 1. Отдельный механизм рядом с `data`, а не расширение `data`

`data` — fail-closed: необъявленный ключ роняет работу, потому что эти ключи попадают в `${...}` и `if`, и подсунутое агентом значение меняет решения петли (`job-data-write-scope`). Пункт же прямо требует обратного для `outputs`: необъявленный ключ работу не ограничивает. Смешать два правила в одном хранилище нельзя — пришлось бы различать ключи по происхождению. Выходы живут в своём файле, в своём поле записи и в своём пространстве имён (переменные окружения, а не `${...}`), поэтому мягкое правило не ослабляет `data`.

Отвергнуто: «выходы — это данные, публикуемые без `stepcast data`». Тогда либо `data` теряет fail-closed, либо `outputs` его получает вопреки пункту.

### 2. Один файл на работу, очищается в начале исполнения работы

`jobs/<работа>/outputs.env` в каталоге прогона. Все шаги `run` работы дописывают в один файл — так второй шаг может опубликовать то, что посчитал первый, а набор выходов — свойство работы, как и в Burnex. Движок создаёт пустой файл в начале каждого исполнения работы (первая попытка, перезапуск `attempts`, новый проход `loops`): перезапуск с первого шага не должен видеть выходы упавшей попытки. Повтор шага (`retry` шага) и итерации `until` файл не чистят — они продолжают ту же попытку работы; повтор ключа даёт последнее значение.

Отвергнуто: файл на шаг. Тогда «последнее значение» пришлось бы определять между шагами, а путь менялся бы от шага к шагу без пользы.

### 3. Разбор после каждого шага `run`, а не только в конце работы

Тем же местом, что `foldJobData`: после каждого исполненного шага `run` движок читает файл и проверяет его целиком. Нарушение — работа падает без повторных попыток (файл остался, повтор упёрся бы в то же самое), причина называет работу, ключ и правило. Раннее чтение даёт ошибку на том шаге, который её внёс, а не в конце работы.

Формат строки: всё до первого `=` — ключ, остальное — значение буквально (без снятия кавычек и без пробельной обрезки, в отличие от `parseEnvFile`: значение — данные, а не конфигурация). Пустые строки пропускаются; непустая строка без `=` — нарушение. Значение длиной больше 4096 байт UTF-8 — нарушение. Перевод строки в значении невозможен по построению; `\r` в конце строки срезается (Windows-скрипты).

### 4. «Похоже на секрет» — по действующему `env_deny`, применённому к итоговой переменной

Проверяется имя `NEEDS_<JOB>_<KEY>` теми же шаблонами и тем же сравнением (`compileNameGlob`), что вычёркивают переменные из окружения шага. Одно правило вместо второго списка: что пайплайн считает учётными данными в окружении, то же он отказывается передавать выходом. Встроенное умолчание (`*_TOKEN`, `*_SECRET`, `*_PASSWORD`, `*_KEY`, `*_CREDENTIALS`, …) покрывает типичные имена; пайплайн, сузивший или расширивший `env_deny`, получает ровно своё правило. Побочный выигрыш: принятая переменная никогда не будет вычеркнута `env_deny` у потребителя — отказ происходит у производителя, где его видно.

Дополнительно отклоняется ключ, чья итоговая переменная совпадает с переменной объявленного секрета пайплайна (`secrets.<имя>.env`).

Отвергнуто: собственный жёсткий список подстрок (`token`, `secret`, `key`…). Он разошёлся бы с `env_deny` и отклонял бы `cache_key` там, где пайплайн его явно разрешил.

### 5. Имя переменной: `<JOB>` нормализуется, `<KEY>` — как записан

Идентификаторы работ содержат дефисы (`implement-a`), переменной нужен `[A-Za-z0-9_]`: `<JOB>` = верхний регистр, всё вне `[A-Za-z0-9_]` → `_`. Ключ уже удовлетворяет форме переменной и сохраняется как записан — так `sha` и `SHA` остаются разными ключами без правила о регистровых коллизиях. Две прямые зависимости одной работы, сводящиеся к одному `<JOB>` (`build-a` и `build_a`), — ошибка линта; во время исполнения при такой коллизии (если линт обойдён) действует ошибка конфигурации до старта, а не тихое перекрытие.

### 6. Переменные `NEEDS_*` — в слое `injected`

`NEEDS_*` кладутся в `injected` и потому не перекрываются `env:` работы или шага: значение пришло от другой работы, и собственное объявление потребителя не должно его молча подменять. Они проходят мимо `env_deny` по решению 4 (производитель уже отклонил похожие имена). Выдаются всем шагам работы-потребителя и их проверкам (`grant: 'check'`), любого вида: агент тоже читает окружение.

«Прямой `needs`» — работа названа в `needs` потребителя или потребитель объявил `needs: all`. Выходы производителя, не завершившегося успехом (упал, пропущен, отменён — при `on: always`/`on: failure` потребитель всё равно исполняется), не передаются: частично опубликованное упавшей работой — не результат.

### 7. Хранение и возобновление

Принятые выходы складываются в запись работы `status.json` полем `outputs` (объект «ключ — строка»; поле необязательно — прогоны прежней версии читаются). Источник для потребителей — запись работы в памяти движка, а не файл: шаг, имеющий доступ к каталогу прогона, не должен менять уже принятое после завершения производителя. Запись каждого шага `run` несёт поле `outputs` — ключи, которые внёс именно он (новые или с изменённым значением). Возобновление переносит выходы только переиспользованных шагов, повторяя их записи по порядку: перенос всей записи работы оставил бы ключ шага, который теперь исполняется заново и больше его не публикует, — он ушёл бы зависимым и закрыл бы проверку объявленного ключа, которого в новом прогоне никто не опубликовал. Предел 32 ключей считается по объединённому набору работы, а не по файлу; объявленные ключи у работы с `until` проверяются после сошедшейся итерации.

### 8. Линт

- Набор `outputs:` проверяется: форма имени (то же регулярное выражение), повторы, не больше 32, похожесть на секрет по решению 4.
- В тексте команд шагов `run` (строка и элементы списка) и предикатов `cmd` работы ищутся `$NEEDS_<…>` и `${NEEDS_<…>}`. Имя разбирается так: среди прямых зависимостей ищутся те, чей `<JOB>` с последующим `_` — префикс имени после `NEEDS_`, а остаток — объявленный ими ключ. Ни одной зависимости с таким префиксом — ошибка «не прямая зависимость»; префикс есть, ключ не объявлен — ошибка с перечнем объявленных; подходят две зависимости (`build` с ключом `docs_sha` и `build-docs` с ключом `sha`) — ошибка неоднозначности. Упоминание необъявленного ключа — ошибка именно потому, что статически его существование доказать нечем; пайплайн, полагающийся на необъявленный ключ, объявляет его.

Во время исполнения два производителя, давшие потребителю одну и ту же переменную, роняют потребителя до первого шага с причиной, называющей обоих: тихое перекрытие одного выхода другим недопустимо.

### 9. Shadow-режим

Шаг `run` с `external: true` в shadow-режиме не исполняется (`shadow-run-mode`) и ничего не публикует. Отказ на неопубликованном объявленном ключе не применяется к работе, у которой хотя бы один шаг завершён с причиной `shadow`: иначе каждый прогон насухо падал бы на работе, чей выход по построению не мог появиться. Зависимые получают только то, что опубликовали исполненные шаги.

## Risks / Trade-offs

- [Скрипт пишет в файл значение с секретом под безобидным именем] → механизм проверяет только имена; значения в журнал попадают (поле `outputs` в `status.json`). Документация называет это прямо: для секретов — `secrets:`, не выходы.
- [Неуспешная работа уже опубликовала часть выходов, потребитель с `on: always` ждёт их] → переменных нет; скрипт потребителя обязан проверять пустоту. Это осознанно: полуопубликованное не выдаётся за результат.
- [Линт не видит упоминаний в скриптах-файлах, которые зовёт `run`] → проверка сверяет только текст документа; ссылка из внешнего скрипта на необъявленный ключ во время исполнения даёт пустую переменную. Цена статичности, та же, что у любого окружения.
- [Коллизия нормализованных имён работ] → ошибка линта и до старта, а не тихое перекрытие.

## Migration Plan

Добавочное изменение: ключ `outputs` необязателен, без него работа ведёт себя как прежде, лишь получает `STEPCAST_JOB_OUTPUTS` в шагах `run`. Поле `outputs` в `status.json` необязательно. Откат — удаление ключа из документов.
