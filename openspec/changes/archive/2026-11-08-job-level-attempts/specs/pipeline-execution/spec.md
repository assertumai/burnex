## ADDED Requirements

### Requirement: Упавшая работа перезапускается с первого шага

Работа с `attempts.max` больше 1, завершившаяся отказом с повторяемой причиной, SHALL исполняться заново с первого шага, пока число попыток не достигнет `attempts.max`.
Перед новой попыткой система MUST откатить в рабочем дереве пути, изменённые
предыдущей попыткой, к состоянию на начало работы и MUST сбросить данные
работы, опубликованные предыдущей попыткой. Сессии новой попытки MUST
начинаться заново. Счёт попыток шагов и итераций `until` MUST начинаться
заново в каждой попытке работы. Если откат не удался, новая попытка MUST NOT
начинаться: работа получает исход последней попытки, а неудача отката пишется
в журнал как учётная.

#### Scenario: Успех со второй попытки работы

- **WHEN** работа объявляет `attempts: { max: 2 }`, в первой попытке первый шаг прошёл, а второй не прошёл `expect` после исчерпания своих попыток
- **THEN** работа исполняется ещё раз начиная с первого шага
- **AND** первый шаг второй попытки видит дерево без правок первой попытки
- **AND** при успехе второй попытки работа получает статус `success`

#### Scenario: Исчерпание попыток работы

- **WHEN** все `attempts.max` попыток работы завершились отказом
- **THEN** работа получает статус `failed` с причиной последней попытки

#### Scenario: Новая попытка начинает новую сессию

- **WHEN** агентский шаг с `session: default` исполнялся в первой попытке работы, а работа перезапускается
- **THEN** этот шаг во второй попытке начинает новый диалог, а не продолжает прежний

#### Scenario: Данные упавшей попытки не публикуются

- **WHEN** первая попытка опубликовала `jobs.<id>.data.summary` и упала, а вторая попытка ключ не публикует
- **THEN** после успеха работы `jobs.<id>.data.summary` отсутствует

#### Scenario: Откат невозможен

- **WHEN** работа объявляет `attempts: { max: 3 }`, первая попытка упала, а якорь начала работы восстановить нельзя
- **THEN** вторая попытка не начинается, работа получает исход первой попытки
- **AND** `events.ndjson` содержит запись `bookkeeping.failed` об откате дерева

### Requirement: Повторяются только отказы, которые повтор может исправить

Новая попытка работы SHALL начинаться только при статусе `failed` с причиной `expect_failed`, `timeout`, `spawn_failed` или `until_not_met`.
Пропуск, успех и исходы `budget_exceeded`, `canceled`, `backend_rate_limited`,
`backend_unauthenticated` MUST NOT повторяться. Отказы, которые повтор
заведомо воспроизвёл бы, — противоречие плану возобновления и необъявленный
ключ данных работы, — MUST NOT повторяться. Отказ подготовки рабочей
директории, раскрытия отложенных подстановок и переноса живых файлов MUST NOT
повторяться.

#### Scenario: Отмена не повторяется

- **WHEN** работа с `attempts: { max: 3 }` отменена во время первой попытки
- **THEN** вторая попытка не начинается, работа получает статус `canceled`

#### Scenario: Превышение бюджета не повторяется

- **WHEN** шаг работы с `attempts: { max: 3 }` завершился `budget_exceeded`
- **THEN** вторая попытка не начинается

#### Scenario: Отказ бэкенда не повторяется

- **WHEN** шаг работы с `attempts: { max: 3 }` завершился причиной `backend_rate_limited` или `backend_unauthenticated`
- **THEN** вторая попытка не начинается, работа получает эту причину

#### Scenario: Пропуск не повторяется

- **WHEN** командный шаг работы с `attempts: { max: 3 }` вышел объявленным `skip_exit_code`
- **THEN** работа получает статус `skipped`, а вторая попытка не начинается

#### Scenario: Цикл, не сошедшийся за предел итераций, повторяется

- **WHEN** работа с `attempts: { max: 2 }` и `until` исчерпала итерации с причиной `until_not_met`
- **THEN** начинается вторая попытка работы с первой итерации на откаченном дереве

### Requirement: Бюджет и время работы покрывают все её попытки

Бюджет работы и потолок её времени SHALL считаться по всем попыткам работы вместе, а не по каждой отдельно.
Перед новой попыткой система MUST проверить бюджеты работы и прогона, и при
исчерпанном бюджете работа MUST завершаться `budget_exceeded` без новой
попытки. Расход каждой попытки работы MUST учитываться отдельно и не
сливаться с расходом другой попытки того же шага.

#### Scenario: Бюджет исчерпан первой попыткой

- **WHEN** работа объявляет `attempts: { max: 3 }` и `budget.tokens: 100k`, а к концу первой попытки, упавшей на `expect`, расход работы достиг потолка
- **THEN** вторая попытка не начинается, работа получает статус `budget_exceeded`

#### Scenario: Расход попыток виден раздельно

- **WHEN** работа прошла со второй попытки
- **THEN** сводка расхода содержит расход шагов каждой попытки работы отдельно, а итог работы равен их сумме

### Requirement: Зависимые видят финальный исход работы

Планировщик, условия `on` и `if`, подстановка `jobs.<id>.status`, остановка `fail_fast` и код возврата прогона SHALL видеть только финальный исход работы с попытками.
Отказ промежуточной попытки MUST NOT запускать работы с `on: failure` и MUST
NOT останавливать прогон. Пока работа не исчерпала попытки, её статус в
состоянии прогона MUST оставаться `running`.

#### Scenario: Промежуточный отказ не запускает обработчик отказа

- **WHEN** работа `build` объявляет `attempts: { max: 2 }`, её первая попытка упала, вторая прошла, а работа `notify` зависит от неё с `on: failure`
- **THEN** `notify` пропускается, а `build` имеет статус `success`

#### Scenario: Fail-fast ждёт последней попытки

- **WHEN** пайплайн исполняется с `fail_fast`, а первая попытка работы с `attempts: { max: 2 }` упала
- **THEN** прогон не останавливается, пока не завершится вторая попытка

### Requirement: Попытки работы записываются в журнал

Каждая попытка работы с `attempts.max` больше 1 SHALL записываться отдельно: каталоги её шагов лежат под уровнем `attempt-<n>` каталога шагов работы, над уровнем итерации.
Начало и конец попытки MUST отмечаться событиями `job.attempt.started` и
`job.attempt.finished` с номером попытки и её исходом. Запись работы в
состоянии прогона MUST содержать число использованных попыток, а записи её
шагов — записи последней попытки. У работы без `attempts` раскладка журнала и
запись работы MUST NOT меняться.

#### Scenario: Раскладка двух попыток

- **WHEN** работа `impl` с `attempts: { max: 2 }` и шагом `write` прошла со второй попытки
- **THEN** журнал содержит `jobs/impl/steps/attempt-1/01-write` и `jobs/impl/steps/attempt-2/01-write`
- **AND** `events.ndjson` содержит по паре `job.attempt.started` и `job.attempt.finished` на каждую попытку
- **AND** запись работы в состоянии прогона содержит `attempts: 2`

#### Scenario: Работа без попыток

- **WHEN** работа не объявляет `attempts`
- **THEN** каталоги её шагов лежат по прежней раскладке, без уровня `attempt-<n>`, а событий попыток работы нет
