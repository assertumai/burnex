## Context

Механика запуска с витрины уже есть: `POST /api/run` (`src/parts/ui/runLaunch/row.ts`)
проверяет проект и пайплайн по тем же обходам, что витрина, и порождает
`stepcast run` списком argv (`src/parts/ui/runLaunch.ts`). Поля `env` и `shadow`
маршрут принимает со времён `shadow-run-mode`, но `launchRun` в `ui/src/api.ts`
их не знает, а форма на «Scrum» («Start work», `ui/src/pages/Scrum.tsx`) шлёт
только `project`, `pipeline` и `inputs.item`. На «Runs» диалога запуска нет.

Проверки, которые решают судьбу прогона, живут в дочернем процессе: ключ env
должен быть объявлен в верхнеуровневом `env:` (`validateEnvOverrides`), а для
shadow-режима каждый встроенный шаг должен нести `external`
(`assertShadowDeclarations`). Маршрут отвечает 202 до них, и отказ дочернего
процесса витрина не видит — прогона просто не появляется.

Выбора агента на один прогон нет нигде: агента меняют `defaults.agent`,
`pipeline_agents` и `step_agents` в файлах конфигурации. Слой флага в
`resolveConfig` уже существует и используется `stepcast config --agent`.

Манифест shadow-прогона несёт `mode: shadow` (`run-journal`, «Манифест прогона
называет режим»), но `RunOverview` (`src/parts/ui/overview.ts`) его не
переносит. Образец пометки — `TriggerBadge` в `ui/src/pages/Runs.tsx`
(`ui-schedule-view`).

## Goals / Non-Goals

**Goals:**

- Одна форма запуска на «Scrum» и «Runs»: входы, env, shadow, агент.
- Ошибки, которые иначе случились бы молча в дочернем процессе после 202,
  форма ловит до отправки: необъявленный ключ env, неготовый к shadow пайплайн,
  неизвестный агент.
- Shadow-прогон различим в списке и на странице прогона.

**Non-Goals:**

- Выбор модели, tier и effort на один прогон: запись выбора уже есть на экране
  Pipelines, а модель, чужая выбранному агенту, решается существующим путём
  `defaults.agent` (умолчательная модель бэкенда).
- Доставка отказа дочернего `stepcast run` на витрину после 202 — отдельная
  задача; здесь предстартовые проверки дублируются в форме.
- Запуск по расписанию из формы: `scheduled` объявляет сервис, не форма.

## Decisions

### 1. Агент прогона — слой флага над `defaults.agent`, а не «силовая» замена

`stepcast run --agent <имя>` разрешает конфигурацию заново с
`flags: { 'defaults.agent': имя }` (вместе с умолчаниями плагинов из реестра,
как `runConfigCommand`). Тем самым выбор действует там, где сейчас действует
`defaults.agent`: на агентских шагах, чей агент пришёл из слоя `config`. Шаг,
которому агента назвали шаг или работа документа либо запись
`pipeline_agents`/`step_agents`, остаётся при своём — порядок слоёв и
`agent_policy` не меняются. Отсюда следствие для агента корня документа: под
`force` он сильнее флага, под `fallback` слабее — ровно как слабее он там
`defaults.agent` из файла (RANK в `document/agentChoice.ts`). Отдельный слой
«сильнее любого документа при любой политике» был бы третьим порядком слоёв,
от которого отказывается альтернатива ниже.

Альтернатива — заменить агента всех агентских шагов прогона. Отвергнута: явный
агент шага в документе — часто требование шага (модель, инструменты), и
замена без согласования с моделью документа ломала бы прогон неочевидно; кроме
того, это третий порядок слоёв рядом с `force`/`fallback`.

Чтобы выбор не был невидимым, форма показывает, сколько агентских шагов
выбранного пайплайна он затронет: шаги, у которых `agentOrigin.layer` в
`GET /api/pipelines` равен `config`, а при `agentPolicy: fallback` ещё и
`pipeline`. Пайплайн без таких шагов получает
подсказку «выбор агента этот пайплайн не меняет», поле при этом не прячется.

Неизвестное имя агента — отказ `run` до создания каталога прогона, как отказ
`--env`; текст отказа перечисляет известных агентов.

### 2. `agent_override` в манифесте, `resume` наследует

Ключ манифеста `agent_override: <имя>` пишется только при флаге. `resume` берёт
его из исходного манифеста, собственного флага у `resume` нет — тот же контракт,
что у `env_overrides` и `mode`: возобновлённый прогон должен исполнять те же
шаги тем же агентом. Страница прогона показывает переопределённого агента в
шапке рядом с бейджем режима.

### 3. Предстартовые проверки — в представлении пайплайна

`PipelineView` в `GET /api/pipelines` получает:

- `envNames: string[]` — ключи верхнеуровневого `env:` раскрытого пайплайна
  (только имена: значения могут содержать `${secrets.*}`, и витрине они не
  нужны);
- `shadow: { ready: true } | { ready: false, steps: string[] }` — результат
  проверки, которую выполняет `assertShadowDeclarations`, вынесенной в функцию,
  возвращающую перечень адресов `<работа>.<шаг>` без `external` вместо броска.
  `assertShadowDeclarations` вызывает её и бросает, как прежде: формулировка
  отказа CLI не меняется.

Список агентов для поля выбора — `backends` уже существующего
`GET /api/settings` (экран «Agents»), с признаком `available`: недоступный
бэкенд показывается выключенным. Отдельного маршрута не заводится.

### 4. Правила env в форме — копия схемы демона, а не общий модуль

Регулярное выражение имени, длина 500 и запрет перевода строки повторяются в
модуле формы; тест формы сверяет их на тех же примерах, что тест схемы демона
(`test/run-launch.test.ts`). Импорт зод-схемы демона в бандл витрины потянул бы
серверный модуль в браузер. Строка env вводится как `KEY=VALUE`; разбор делит
по первому `=`, пустое значение допустимо, повтор ключа — ошибка строки.

### 5. Один компонент диалога, два входа

Компонент `RunLaunchDialog` принимает необязательный предвыбор (проект, пункт
очереди). На «Scrum» предвыбор — проект доски и пункт; пайплайн, объявивший
вход `item`, выбирается первым, как сейчас. На «Runs» проект выбирается в
форме; входы пайплайна показываются полями по `PipelineView.inputs`.

### 6. `mode` в обзоре и бейдж

`RunOverview.mode?: 'shadow'` переносится из манифеста тем же местом, что
`trigger`. `ShadowBadge` рядом с `TriggerBadge` в строке списка и в шапке
`RunDetail`; подсказка объясняет, что внешние действия записаны, а не
совершены. Фильтра по режиму не добавляется.

## Risks / Trade-offs

- [Повторное разрешение конфигурации в `run`] → только при флаге `--agent`;
  без флага используется конфигурация точки входа, как сейчас.
- [Правила env в двух местах] → тест сверки на общих примерах; расхождение
  ловится тестом, а не пользователем.
- [Представление пайплайна стало толще] → два небольших поля, считаются при
  том же раскрытии, что уже выполняется для экрана Pipelines.
- [Выбор агента не затрагивает шаги с явным агентом] → форма показывает число
  затронутых шагов; справка `--agent` называет порядок слоёв.
