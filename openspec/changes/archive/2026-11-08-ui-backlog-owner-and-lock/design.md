## Context

Владелец пункта и блокировка очереди появились в движке двумя изменениями:

- `backlog-claimed-by-owner`: `backlog pick --owner run:<id>` пишет пункту
  `claimed_by`; разбор строки — `parseRunOwner` в
  `src/parts/pipeline/domain/backlog/owner.ts` (форма `run:<id>`, id без
  пробелов и `/`; иная форма — владелец, о котором судить нечем).
- `backlog-queue-lock`: каждый цикл «прочитать → поправить → записать» очереди
  идёт под lock-файлом `backlogLockPath(file)` — `stepcast-backlog.lock` в общем
  каталоге git (вне git — `.backlog.lock` рядом с файлом). Владелец в файле —
  JSON `{pid, host, command, acquired_at}`, читается `readOwner`
  (`src/parts/pipeline/domain/lockfile.ts`), брошенность — `isAbandoned` (та же
  машина, процесса нет). Ожидание писателя — до 10 с, потом
  `BacklogLockTimeoutError`, а маршруты доски (`POST /api/backlog/move`,
  `POST /api/backlog/item`, `src/parts/ui/screens/scrum/server.ts`) отвечают на
  него `409` с текстом ошибки, называющим владельца.

Витрина собирает вид очереди в `buildBacklog` (`src/parts/ui/backlog.ts`) и шлёт
его живым потоком событием `backlog`; кадр пересобирается, только когда меняется
отпечаток очереди в `src/parts/ui/daemon/watcher.ts` (stat `backlog.md`,
`archived.md`, `.stepcast/board.yml`). Экран «Backlog» (`ui/src/pages/Backlog.tsx`)
только читает; правят очередь «Scrum» — перенос карточки и панель деталей, —
и оба пути уже выводят `error` ответа через `json()` (`ui/src/api.ts`).

## Goals / Non-Goals

**Goals:**

- По пункту `in_progress` видно, какой прогон его держит, и туда можно перейти.
- Занятая блокировка очереди видна до попытки правки, с владельцем и возрастом.
- Отказ записи из-за блокировки читается текстом демона, а не «Daemon responded 409».

**Non-Goals:**

- Суждение о живости владельца-прогона (`runOwnerJudge`) на экране: оно читает
  манифесты прогонов проекта, а вид очереди строится без них. Ссылка на прогон
  уже ведёт туда, где его состояние видно.
- Снятие блокировки из витрины. Чужую машину демон проверить не может, а
  брошенный lock своей машины снимает следующий писатель сам.
- Изменение формата очереди, CLI, маршрутов записи или текста `409`.

## Decisions

### 1. Разбор владельца — на стороне демона, тем же `parseRunOwner`

`toItemView` кладёт в вид `claimedBy` (строку как есть) и `ownerRunId`
(`parseRunOwner(claimedBy)`, если разобралось). Браузер правило формы не
повторяет: модуль движка в бандл витрины не входит, а второе правило разошлось бы
с первым при первой правке. Строка как есть нужна для владельца иной формы —
его показываем текстом, а не прячем.

Альтернатива — отдавать только `claimedBy` и разбирать в браузере — отвергнута по
той же причине расхождения правил.

### 2. Владелец показан у `in_progress`, в той же ячейке, что «picked up»

На «Backlog» колонка «Picked up / reason» становится «Picked up / owner /
reason»: у `in_progress` — момент взятия и владелец. Ссылка — `TargetLink` на
`RUN_TARGET` с `projectKey` раздела и `runId` из `ownerRunId`: тот же вид, что у
предложений (`Proposals.tsx`), и при выключенном маршруте страницы прогона
место называет причину, а не пропадает. У пунктов других статусов владелец не
показывается: `claimed_by` по договору движка — признак взятого пункта, а
`finish` прочих статусов к нему не обращается. Панель деталей «Scrum», где
`docs/backlog.md` уже обещает `claimed_by`, показывает владельца тем же
компонентом рядом с «picked up».

### 3. Состояние блокировки — поле вида проекта, а не отдельный маршрут

`BacklogProjectView.lock`:

```ts
type BacklogLockView =
  | { readonly state: 'free' }
  | { readonly state: 'held'; readonly command: string; readonly pid: number;
      readonly host: string; readonly acquiredAt: string; readonly abandoned: boolean }
  | { readonly state: 'unreadable' };
```

Путь — `backlogLockPath(join(project.path, 'backlog.md'))`, владелец —
`readOwner`, брошенность — `isAbandoned`. Блокировка — свойство очереди проекта,
и экран, который показывает очередь, получает её тем же кадром; отдельный запрос
давал бы кадры, где пункты и блокировка из разных моментов.

### 4. Путь lock'а кэшируется по пути проекта

`backlogLockPath` порождает `git rev-parse --git-common-dir`. Отпечаток считается
каждый такт (раз в секунду) по каждому проекту, и процесс git на проект в
секунду — лишняя нагрузка. Общий каталог git проекта за жизнь демона не
меняется, поэтому путь запоминается в карте модуля `src/parts/ui/backlog.ts` по
`project.path` и служит и сборке вида, и отпечатку.

Навсегда запоминается только путь в общем каталоге git. Запасной
`.backlog.lock` рядом с файлом (git не ответил: проект ещё не репозиторий,
git недоступен или сбоил) перепроверяется не чаще раза в
`LOCK_PATH_RETRY_MS` (30 с). Иначе после `git init` при живом демоне движок
писал бы lock в `<common-dir>/stepcast-backlog.lock`, а витрина до перезапуска
смотрела бы на прежний файл и занятую блокировку не видела.

### 5. Lock-файл входит в отпечаток очереди

К частям отпечатка проекта добавляется `lock:<mtime>:<size>:<abandoned>` при
существующем файле и `lock:-` без него. Без этого взятие и снятие блокировки,
не меняющие файлов очереди, не дошли бы до экрана; а снятие после записи меняет
и `backlog.md`, так что кадр в любом случае придёт. Признак брошенности в
отпечатке нужен потому, что смерть процесса-владельца файла не трогает:
`isAbandoned` зовётся только при существующем файле, то есть почти никогда.

### 6. Возраст считается в браузере от `acquiredAt`

Демон отдаёт момент взятия, экран показывает его (`fmtTime`) и возраст
относительно текущего времени на момент отрисовки. Возраст в кадре устаревал бы
вместе с кадром, а кадр без смены отпечатка не приходит.

По той же причине предупреждение перерисовывается по своему таймеру
(`lockNoticeRefreshMs`). Кадр с новой блокировкой приходит на ближайшем такте,
когда ей почти всегда меньше секунды, и без таймера повисшая блокировка так и
осталась бы скрытой порогом. Таймер ставится на переход порога, а у показанной
блокировки — на смену подписи возраста. Момент взятия, который не разбирается
как дата (`readOwner` проверяет только, что это строка), показывается как есть,
без возраста и без порога.

### 7. Что сказано о занятой блокировке

Предупреждение (не ошибка — запрос верен, очередь просто занята) называет
команду, pid, машину, момент и возраст. Дополнительно:

- брошенная — «the process is gone; the next writer will remove the lock»;
- чужая машина (`host` не совпадает с `hostname()` демона; сравнивает демон и
  отдаёт признак `foreignHost`, браузер имени машины демона не знает) —
  подсказка движка: если процесс-владелец мёртв на другой машине, lock-файл
  удаляется руками; путь файла показывается;
- нечитаемая — что содержимое lock-файла нечитаемо и запись будет ждать до
  предела.

Поэтому к виду из Решения 3 добавляются `path: string` у `held` и `unreadable`
и `foreignHost: boolean` у `held`.

### 8. Отказ записи — дословный текст демона

Обработчики «Scrum» уже показывают `cause.message`, а `json()` берёт его из
`error` ответа. Изменение закрепляет это тестом на `409` по обоим путям
(перенос и панель) и не подменяет текст своим: в нём владелец и путь, которых
у клиента нет.

## Risks / Trade-offs

- [Блокировка обычно живёт миллисекунды, кадр может показать её «мигнув»] →
  показ занятой блокировки откладывается, пока ей нет секунды по `acquiredAt`;
  нормальная запись этот порог не переходит, повисшая — переходит.
- [Часы машин расходятся, возраст чужого lock'а неточен] → рядом с возрастом
  показывается и абсолютный момент; решение о ручном удалении человек принимает
  по нему и по имени машины.
- [Кэш пути переживает перенос репозитория на ходу] → при смене пути проекта в
  `projects.json` ключ кэша другой; перенос самого `.git` при живом демоне не
  поддерживается и сейчас.
