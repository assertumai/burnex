## Context

Цикл по группе работ (`loops:` пайплайна, `job-group-loops`) исполняет
участников проходами. Что движок оставляет на диске:

- `status.json` → `loops[]` (`LoopRecordSchema`, `journal/schema.ts`): `id`,
  `jobs`, `iterations` — «проходов начато к этому моменту», `max_iterations`,
  `verdict` (`done` / `exhausted` / `canceled`, только у законченного),
  `status`, `reason`, `cause`. Запись пишется на границе прохода. Без
  объявленных циклов ключа нет.
- Запись работы в `status.json` описывает её **последний** проход (так сказано
  в комментарии к `LoopRecordSchema`): перед новым проходом `runner.ts`
  (`resetLoopParticipants`) снимает исход, данные, `outputs.env` и
  `artifacts/<job>.json` участника.
- Каталоги шагов участника лежат по проходам: `jobs/<job>/steps/pass-<n>/…`
  (`stepDir`, `passDirName`) — уровень прохода есть у каждого прохода,
  включая первый. Внутри — прежние уровни попытки работы и итерации `until`.
- `findStepDir(paths, job, step, iteration?, jobAttempt?, loopPass?)` уже
  умеет адресовать проход; без `loopPass` берёт последний.

Витрина сейчас: `buildSnapshot` строит `JobSnapshot` без сведений о цикле;
`layoutJobs` получает `id/needs/on/if/status/display`; `readStepOutput`
вызывает `findStepDir` без прохода; `StepOutput.tsx` переключает только
попытки шага (`stdout.<n>.log`). Граф на странице прогона — `JobGraph.tsx` с
подписью узла, которую задаёт `RunDetail.tsx`.

## Goals / Non-Goals

**Goals:**

- Узел участника цикла на графе прогона показывает число проходов и текущий
  проход (или вердикт законченного цикла).
- Вывод каждого шага участника читается по любому проходу, чей каталог есть на
  диске; по умолчанию — последний, как сейчас.
- Попытки шага (`attempts`) работают как прежде — внутри выбранного прохода.

**Non-Goals:**

- Выход работы (`artifacts/<job>.json`) прошлых проходов: движок его стирает,
  витрина не восстанавливает. Хранить его по проходам — изменение движка, не
  витрины.
- Список файлов шага по проходам (`prompt.txt`, `output.json`, `context.json`
  в снимке) — остаётся списком последнего прохода.
- Граф на экране «Pipelines» (по определению) и изменения движка, журнала,
  `status.json`.
- Рисование цикла рамкой или обратным ребром на графе.

## Decisions

### Решение 1. Сведения о цикле — поле `loop` в `JobSnapshot` и в узле графа

`buildSnapshot` уже читает `status.json`; запись цикла берётся из
`status.loops`, участник находится по `loop.jobs`. У работы появляется

```ts
readonly loop?: {
  readonly id: string;
  readonly iterations: number;      // начато проходов
  readonly maxIterations: number;
  readonly current?: number;        // только у цикла в статусе running
  readonly verdict?: 'done' | 'exhausted' | 'canceled';
  readonly status: StatusValue;
  readonly passes: readonly number[]; // pass-<n> этой работы на диске, по возрастанию
};
```

`current` равен `iterations`, пока цикл в статусе `running`, и отсутствует у
ожидающего и законченного: «текущий проход» законченного цикла читатель
спутал бы с идущим. `passes` — отдельно от `iterations`: участник, чей проход
не дошёл до шагов (отменён, пропущен по `if`), каталога прохода не имеет, а
возобновлённый прогон с переиспользованным циклом может нести `iterations`
без каталогов. Переключатель предлагает только то, что можно прочитать.

`GraphInput` и `GraphNode` получают то же поле без `passes` (узлу перечень не
нужен) — раскладка его только переносит, как `display`. Колонки и строки от
него не зависят.

Альтернатива — считать проходы в браузере по событиям `loop.*` журнала.
Отвергнута: снимок уже единственный источник для страницы прогона, а правила
в проекте проверяются тестами на стороне Node (тот же довод, что у раскладки
графа в `graph.ts`).

### Решение 2. Метка прохода в узле — без изменения высоты узла

Узел графа фиксированной высоты, общей на весь граф. Метка ставится в верхний
правый угол узла короткой строкой: `pass 2/5` у идущего цикла, `3 passes` с
вердиктом у законченного (`done` / `exhausted` / `canceled`; вердикт
`exhausted` выделен как неудача), `0/5` у ещё не начатого. Полное имя цикла и
предел — во всплывающей подсказке узла и в карточке работы. Подпись узла
(статус) остаётся как есть.

### Решение 3. Проход — параметр маршрута вывода шага, а не новый маршрут

`/api/step-output` получает необязательный `pass` (положительное целое, разбор
тем же `readNonNegativeInt`, `0` и мусор — `400`, как у `attempt`).
`readStepOutput` передаёт его в `findStepDir(..., loopPass)` и отвечает полем
`pass` — номером прочитанного прохода, когда раскладка работы проходовая.
Прохода, чьего каталога нет, — пустой ответ (`attempts: []`), как у шага без
каталога; молча подменять его последним нельзя — читатель увидел бы чужой
проход под выбранным номером.

Признак `done` учитывает проход так же, как попытку: запрошен не последний
проход — шаг уже не пишет. Иначе каталог шага прошлого прохода без
`step.json` (проход отменён посреди шага) держал бы опрос живым, пока жив
прогон.

### Решение 4. Переключатель проходов — в карточке работы, общий на её шаги

Проход — свойство работы, не шага: все шаги участника исполняются в каждом
проходе. Карточка работы-участника показывает строку «Loop `<id>`: pass n of
max, verdict» и переключатель по `loop.passes` (виден, когда проходов больше
одного); по умолчанию выбран последний. `RunDetail.tsx` передаёт выбранный
проход в `StepOutput` каждого шага пропом `pass`; смена прохода сбрасывает
накопленный вывод и выбранную попытку шага — номер попытки в другом проходе
означает другую попытку. Пока выбран последний проход, `StepOutput` не
передаёт `pass` вовсе — поведение для идущего прохода совпадает с нынешним.
Новый проход, пришедший живым потоком, переключает выбор на себя, только если
был выбран прежний последний.

## Risks / Trade-offs

- [Список файлов шага в карточке — от последнего прохода, а вывод — от
  выбранного] → карточка при выбранном не последнем проходе помечает список
  файлов «последний проход»; перенос списка файлов в ответ вывода шага —
  отдельный пункт, если понадобится.
- [Стоимость снимка: листинг `jobs/<job>/steps` у каждого участника на каждый
  кадр] → один `readdirSync` на участника, только у работ из `loops[].jobs`;
  работ вне цикла не касается.
- [Старый прогон без `loops` в `status.json`, но с каталогами `pass-<n>`] →
  поля `loop` нет, узел без метки; вывод по-прежнему читается последним
  проходом.
