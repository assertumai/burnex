## Context

После `review-strategies` шаг `review:` умеет режим `independent`: ревьюеры
параллельно дают находки, агрегатор сводит их. Сессии участников живут
внутри шага, адаптеры бэкендов умеют возобновлять сессию
(`resumeSession`, реестр сессий `agentStep.ts`).

## Goals / Non-Goals

**Goals:**

- Ревьюеры обмениваются доводами и приходят к согласию о результате ревью.
- Лимит реплик соблюдается движком, а не просьбой в промпте.
- Консенсус проверяем механически и виден в журнале.

**Non-Goals:**

- Участие агрегатора в обсуждении — он судья, а не сторона.
- Свободный выбор, кому адресовать реплику: все реплики видны всем.
- Настоящий транспорт A2A (см. решение 1).
- Показ обсуждения — изменение `ui-review-discussion`.

## Decisions

### 1. Движок — посредник, формат журнала — A2A Message

Пользователь выбрал посредничество движка. Каждый ревьюер — сессия
CLI-бэкенда, запускаемая на один ответ. Чтобы ревьюер «получил» реплики
остальных, движок возобновляет его сессию промптом с новыми репликами и
ждёт одну структурированную реплику в ответ.

Запись реплики в `discussion.ndjson`:

```json
{ "kind": "message", "messageId": "m7", "role": "agent",
  "from": "security", "round": 2, "seq": 3,
  "parts": [{ "kind": "text", "text": "…" }],
  "stance": "agree", "proposal": "p2", "replyTo": ["m5"] }
```

Поля `messageId`, `role` и `parts` — форма A2A `Message`; остальное —
метаданные движка. Предложение записывается отдельной записью
`{ "kind": "proposal", "id": "p2", "by": "architecture", "round": 2,
"content": { … } }`.

### 2. Структура реплики

Ревьюер отвечает по `schema/review-message.json`:

- `text` — довод;
- `stance` — `propose` | `agree` | `disagree`;
- `proposal` — при `propose`: предлагаемый итог ревью (находки с severity
  и решением) в форме схемы находок;
- `target` — при `agree`/`disagree`: id предложения;
- `reply_to` — необязательный список id реплик.

Невалидная реплика — один повтор с ошибкой схемы. Повтор тоже невалиден —
реплика засчитывается как `disagree` без текста с отметкой в журнале.
Лимит расходуется в обоих случаях: ошибка ревьюера не даёт ему лишних
реплик.

### 3. Раунды

- Раунд 0 — независимые ревью, как `independent`; находки становятся
  первыми репликами (`stance: propose`, предложение — свои находки). Они
  не расходуют лимит.
- Раунд N ≥ 1: каждый ревьюер с остатком лимита получает все реплики,
  появившиеся после его последней реплики, и отвечает одной репликой.
  Ревьюеры раунда работают параллельно; порядок записей в журнале — по
  ревьюеру в порядке стратегии, чтобы журнал был детерминирован.
- Ревьюер, исчерпавший лимит, в раундах больше не участвует, но его
  последняя позиция учитывается в консенсусе.

### 4. Консенсус

После каждого раунда движок вычисляет действующие позиции: для каждого
ревьюера — его последняя реплика. Консенсус есть, если существует
предложение P, для которого у каждого ревьюера позиция — `agree` на P
либо он автор P и не сменил позицию после него. Тогда обсуждение
заканчивается с P.

Обсуждение без консенсуса заканчивается, когда:
- у всех ревьюеров исчерпан лимит; или
- раунд не дал ни одной реплики, меняющей позиции (все повторили прежние
  позиции), — дальнейшие раунды бесполезны.

Ревьюер, не давший находок в раунде 0, в обсуждении не участвует и в
консенсусе не учитывается; если таких все, кроме одного, консенсуса быть
не может, и решение за агрегатором.

### 5. Агрегатор

- С консенсусом: агрегатор получает согласованное предложение и обязан
  оформить его по `output_schema` шага, не меняя решения. В промпте это
  сказано прямо. Движок проверяет обязательство так, как может проверить
  механически: схема выхода и `expect` шага. Пользователь выбрал вариант
  без права агрегатора отклонить консенсус.
- Без консенсуса: агрегатор получает всю ленту обсуждения и действующие
  позиции и выносит решение сам.
- В журнал записывается исход: `consensus` с id предложения или
  `no_consensus` с причиной (`limit` / `stalled`).

### 6. Повторы и бюджет

Повтор шага после провала агрегатора не перезапускает обсуждение — оно
переиспользуется целиком, как находки в `independent`. Каждая реплика
расходует бюджет шага; превышение бюджета посреди обсуждения завершает его
без консенсуса, после чего агрегатор всё равно запускается, если бюджет
позволяет, иначе шаг проваливается по бюджету.

## Risks / Trade-offs

- [Ревьюеры соглашаются из вежливости] → промпт реплики требует согласия
  только с конкретным предложением и называет цену ошибочного согласия;
  лента видна человеку, и ложный консенсус заметен.
- [Длинная лента раздувает контекст возобновляемой сессии] → ревьюер
  получает только новые реплики (остальное уже в его сессии), лимит
  ограничивает объём сверху.
- [Расход растёт с лимитом] → лимит обязателен для режима, общий бюджет
  шага ограничивает сверху, расход по участникам виден.

## Migration Plan

Стратегии без `mode: discussion` не меняются.
