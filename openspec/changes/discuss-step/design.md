## Context

Шаг `review` (`review-strategies`, `review-defend`) умеет:

- запускать нескольких агентов внутри одного шага, каждого как агентский шаг
  со своей сессией (`participants.ts`, `runOne` в `reviewStep.ts`);
- раскрывать участников стратегии по слоям и профилям
  (`reviewStrategy.ts`, `expand.ts`);
- вести раунды защиты с закрытием пунктов `accepted | withdrawn |
  contested` (`reviewDefense.ts`);
- отдавать выход агрегатора по `output_schema` шага.

Изменение `review-defend-shared-session` заменяет ветки защиты общими
раундами: защитник одним ходом отвечает на открытые пункты всех сторон.
Оно же выносит построители промптов и схемы ходов из `runDefense` в
параметры, а тип шага сужает до `{ id }`. Это изменение на нём строится и
реализуется после него.

Прежний режим `discussion` провалился по трём причинам:

- голосовали за итог целиком;
- у текста не было владельца;
- каждый держался за своё.

Схему согласовали в обсуждении двух агентов (Claude Opus 5.5 и Fable 5.2).

## Goals / Non-Goals

**Goals:**

- Несколько агентов независимо предлагают подход. Альтернативы появляются
  до того, как кто-то на чём-то заякорился.
- У документа один владелец, спор идёт по точкам решения, а не по
  документу целиком.
- Согласованность итога проверяется механически. Несогласованное не
  прячется в прозе, а называется полями, на которые опираются `if`, `until`
  и гейт.
- Максимум переиспользования механики `review`: участники, сессии, профили,
  раунды, бюджет, журнал.

**Non-Goals:**

- Витрина документа и ленты, рендер в HTML и OpenSpec, редактор стратегий —
  это изменение `render-design`.
- Вариант «один автор без предложений» (`proposals: false`). При одном
  дошедшем предложении путь A получается сам, без флага.
- Зависимости между точками решения (`depends_on`).
- Передача сессии автора следующим шагам. В ней остались бы решения,
  отменённые агрегатором. Документ идёт дальше обычным выходом шага.
- PlantUML и проверка синтаксиса Mermaid движком.

## Decisions

### 1. Отдельный вид шага и отдельный документ стратегии

Шаг `discuss:` вносится строкой встроенного слоя `step-discuss`, как
`review`. Стратегия — документ `kind: discussion-strategy`:

```yaml
version: 1
kind: discussion-strategy
name: design-panel
profiles:
  deep: { backend: claude, model_tier: deep }
participants:
  - id: pragmatist
    agent: codex
    focus: "Минимум новых сущностей, переиспользование движка"
  - id: skeptic
    agent: deep
    focus: file:./focus/skeptic.md
author: { agent: deep }
aggregator: { agent: claude, model_tier: deep, prompt: file:./aggregator.md }
rounds: 1
```

Слои те же, что у стратегий ревью: явный путь
(`./`, `../`, абсолютный) → `.burnex/discussion-strategies/<имя>.yml` →
`~/.burnex/discussion-strategies/<имя>.yml`. Файл, найденный по имени,
обязан объявлять тот же `name`. Отпечаток считается так же: текст плюс
файлы `file:` и `context` профилей.

Общие куски выносятся из `reviewStrategy.ts` и параметризуются по `kind` и
подкаталогу:

- формы выбора агента (`ParticipantChoiceShape`);
- профили;
- резолвер слоёв;
- отпечаток.

Отвергнутые варианты:

- **`mode: design` в стратегии ревью.** Шаги пришлось бы перекрёстно
  проверять («`review:` не берёт такую стратегию, `discuss:` — другую»), а
  роли назывались бы чужими словами (`reviewers`, `defender`).
- **Режим шага `review`.** Пользователь выбрал отдельный шаг: ревью
  проверяет сделанное, обсуждение — до реализации.

Обязательны `participants` (непустой) и `name`. `author` и `aggregator`
без объявления исполняются профилем `default`. Id `author` и
`aggregator` участникам запрещены, потому что каталоги журнала и адреса
`step_agents` у них общие.

### 2. Роли и фазы

```
participants ──► предложения ──► author: черновик (d1…, диаграммы)
                                          │
participants ◄──── черновик ──────────────┘
     │ возражения (blocking / preference)
     ▼
общие раунды: author отвечает на открытые blocking ─► participants maintain|withdraw
     │  (rounds раз или пока открытые не кончились)
     ▼
aggregator: решает contested, собирает документ по output_schema
```

Автор — отдельный участник, предложений он не подаёт. Если бы черновик
писал один из участников, он сводил бы к своему и защищал своё.

Число вызовов: `N` предложений + 1 черновик + `N` возражений +
`rounds·(1+N)` защиты + 1 агрегатор. При `N = 2` и `rounds = 1` это 9.

### 3. Предложения

Участник получает задание шага, контекст шага и свой `focus`. Отвечает по
схеме `discuss-proposal`:

- `summary`;
- `approach`;
- `decisions[{ question, choice, rationale }]`;
- `risks[]`;
- `diagrams[]` (форма та же, что у черновика, без ссылок на точки).

Невалидный ответ даёт один повтор с ошибкой схемы, как у ревьюера.

Сбой части участников терпим: их id и причины уходят автору и агрегатору.
Если не дошло ни одного предложения, шаг проваливается без автора. Отмена
и превышение бюджета останавливают шаг, как в `review`.

### 4. Черновик

Автор получает задание шага, контекст шага и предложения с подписью
участника (id, агент, модель, focus). Отвечает по схеме `discuss-draft`:

- `summary`;
- `decisions[{ id, question, options[{ by, summary }], choice, rationale }]`;
- `diagrams[{ id, title, kind: "mermaid", source, decisions[] }]`;
- `risks[{ risk, mitigation }]`.

Проверки движка поверх схемы (провал даёт повтор хода с текстом ошибки):

- id решений — `d1, d2, …`, id диаграмм — `g1, g2, …`, без повторов;
- `options[].by` — id участника, давшего предложение, либо `author`.
  Иначе автор мог бы приписать вариант не тому участнику, и отклонённые
  альтернативы в итоге были бы недостоверны;
- `diagrams[].decisions` ссылаются на существующие id решений.

Несовместимые архитектуры автор не смешивает. Корневая точка выбирает
одну, другая уходит в отклонённые варианты. Это сказано в промпте
автора.

Срыв черновика после повтора проваливает шаг: без владельца текста
обсуждать нечего.

### 5. Возражения

Каждый участник, давший предложение, получает черновик в своей сессии.
Своё предложение повторно ему не показывают: оно уже есть в сессии, а
повтор подталкивает защищать свой вариант вместо разбора черновика.

Ответ — по схеме `discuss-objections`:
`objections[{ target, weight, title, breaks, alternative }]`.

- `target` — id решения или диаграммы черновика;
- `weight` — `blocking | preference`;
- у `blocking` поля `breaks` («что сломается») и `alternative` обязаны
  быть не `null`. Это проверка движка, провал даёт повтор.

Id возражения — `<участник>.<n>`. Пустой список — тоже ответ.

`preference` в раунды не идут: они попадают к агрегатору заметками.
Иначе автор сдавался бы просто от числа замечаний, и документ
получался бы «по истощению».

Если `blocking` нет ни у кого, защита пропускается и сразу работает
агрегатор.

### 6. Защита — общие раунды `review-defend-shared-session`

`runDefense` вызывается с параметрами `discuss`: пункты — открытые
`blocking`, защитник — автор, стороны — участники, построители промптов и
схемы ходов — свои:

- **Автор** (`discuss-defense`): на каждое открытое возражение `accept`,
  `dispute` или `clarify` с `text` и `evidence`. У `accept` поле `change`
  `{ choice, rationale }` обязательно. Черновик не переписывается: id точек
  должны быть стабильны, поэтому принятая правка живёт как `change` у
  пункта.
- **Участник** (`discuss-rebuttal`): `maintain` или `withdraw` с `text`.
  `revise` нет: веса не пересматриваются.

Закрытия и сбои — как в общих раундах ревью:

- `accept` — пункт `accepted`;
- `withdraw` — `withdrawn`;
- открытый после `rounds` или по сбою — `contested`;
- последнее слово за участником.

Сессия автора своя (`<шаг>/author`) и возобновляется на месте. Выбирать
защитника, как в `review`, не нужно: автор — участник этого же шага.
Без сессий у бэкенда каждый ход несёт всю переписку заново, и журнал
пишет `backend.degraded`, как в `defend`.

`rounds` по умолчанию 1. В споре о дизайне второй раунд чаще повторяет
позиции, чем сдвигает их. Это оценка, а не замер. Задача живого прогона
меряет долю `contested`.

### 7. Агрегатор и контракт итога

Агрегатор получает:

- задание шага;
- черновик;
- по каждому `blocking`: статус, переписку и `change` у принятых;
- `preference`-заметки;
- список участников без предложений и причины;
- `aggregator.prompt` стратегии.

Он решает `contested` и пишет документ по `output_schema` шага.

Поля движка домешиваются в схему шага при разборе. Они входят в
`properties` и `required` корня, а не через `allOf`: так схема с
`additionalProperties: false` продолжает работать.

- `agreed: boolean`;
- `unresolved: [{ decision, reason }]`;
- `changed_by_aggregator: [<id решения>]`.

Разбор шага отказывает с названием поля, если корень схемы шага — не
объект или схема сама объявляет одно из этих полей.

Инварианты движка после проверки схемы (провал даёт повтор попытки, как
провал `expect`):

- `agreed: true` при непустом `unresolved` — невалидно;
- id в `unresolved[].decision` и `changed_by_aggregator` — существующие id
  решений черновика.

Промпт агрегатора запрещает сшивать. Если переворот спорной точки
затрагивает другие решения и пересобрать их согласованно не удаётся, он
ставит `agreed: false` и перечисляет несогласованное. Решения, которые
агрегатор изменил, хотя их никто не оспаривал и автор не принимал, он
перечисляет в `changed_by_aggregator`.

Встроенная схема `burnex:design-doc` (`schema/design-doc.schema.json`):

- `title`, `summary`;
- `decisions[{ id, question, choice, rationale, rejected[{ by, summary, reason }] }]`;
- `diagrams[{ id, title, kind: "mermaid", source, decisions[] }]`;
- `risks[{ risk, mitigation }]`;
- `open_questions[]`;
- поля движка.

Пользователь может дать свою схему: поля движка домешиваются в неё так же.

### 8. Сессии, адреса, ключ шага, повторы

- Псевдонимы сессий: `<шаг>/<участник>`, `<шаг>/author`,
  `<шаг>/aggregator`. Они живут внутри шага, исход шага сессии не несёт.
- `step_agents.<p>.<job>.<step>` выбирает агрегатора,
  `…/<участник>` — участника, `…/author` — автора.
- Ключ шага включает отпечаток стратегии, как у `review`.
- Попытки шага (`attempts`) повторяют только агрегатора с теми же
  фазами 1–4. Это дорогая часть, и её форма уже проверена.
- `expect` шага, в том числе `judge`, проверяет выход агрегатора.

### 9. Журнал и события

Каталоги в `steps/<шаг>/participants/`:

- `<участник>/` — предложение;
- `<участник>/objections/` — возражения;
- `<участник>/rounds/<r>/` — ответы в раундах;
- `author/draft/` — черновик;
- `author/rounds/<r>/` — ходы защиты;
- `aggregator/` — итог.

`discussion.ndjson` содержит записи:

- `proposal` (участник, статус);
- `draft`;
- `objection`;
- `message` (в форме A2A `Message`, как в `defense.ndjson`);
- `settled`;
- `outcome` (`accepted`, `withdrawn`, `contested`, `preference`,
  `agreed`).

События:

- `discuss.phase` (`proposals | draft | objections | defense | aggregate`,
  `started | finished`);
- `discuss.participant.started|finished` (участник, фаза, раунд);
- `discuss.message`;
- `discuss.settled`;
- `discuss.finished`.

Расход разложен по строкам участников, `author` и `aggregator` и идёт в
бюджет шага.

## Risks / Trade-offs

- **[Битая диаграмма Mermaid проходит проверку]** → Схема проверяет только
  форму. В Node синтаксис без DOM не разобрать. Рендер и витрина
  (`render-design`) показывают исходник блоком кода, если отрисовать не
  удалось. Проверку синтаксиса добавим, если битые диаграммы будут
  встречаться в прогонах.
- **[Угодливость автора]** → В раунды идут только `blocking` с «что
  сломается» и альтернативой. `accept` требует конкретного `change`.
  Агрегатор видит всю переписку.
- **[Агрегатор переписывает неоспоренное]** → `changed_by_aggregator`
  обязателен, промпт запрещает сшивать, `agreed: false` — законный исход.
- **[Стоимость]** → `rounds: 1` по умолчанию. Защита пропускается, если нет
  `blocking`. Бюджет шага общий и проверяется перед каждым ходом.
- **[Зависимость от `review-defend-shared-session`]** → Изменение
  реализуется только после него. Задачи этого изменения начинаются с
  проверки, что общие раунды и параметры `runDefense` на месте.

## Migration Plan

Новый вид шага и новый документ, прежние пайплайны не меняются. Откат —
удаление строки `step-discuss`.

## Open Questions

- Нужен ли участнику, чьё предложение сорвалось, ход возражений против
  черновика? Сейчас нет: у него нет позиции, и сессия пуста. Вернуться к
  этому, если сбои предложений будут частыми.
