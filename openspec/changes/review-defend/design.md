## Context

Шаг `review:` (`review-strategies`) запускает ревьюеров параллельно, каждого
в сессии `<шаг>/<ревьюер>`, затем агрегатора. Сессии ведёт реестр
`agentStep.ts`. Идентификатор сессии агентского шага записан в его
`step.json` (`session`). Claude Code умеет
`--resume <id> --fork-session --session-id <новый>` (проверено на 2.1.312):
форк помнит исходный диалог и получает заданный id. Codex CLI 0.160 умеет
`codex exec fork <id>` с теми же опциями, что `exec resume`. Cursor и
Copilot форка не дают.

Замечание о названии. В burnex «судья» (`judge`) уже занят проверкой
`expect` моделью (`judgePass.ts`). Поэтому сводящий участник остаётся
`aggregator`, хотя в режиме `defend` он решает спорное.

## Goals / Non-Goals

**Goals:**

- Возражает против замечания тот, кто знает, почему код такой.
- Спор идёт по каждой находке, а не за итог целиком. Ревьюер остаётся в
  своей области.
- Сессия имплементатора не меняется, ветки ревьюеров не мешают друг другу.
- Режим работает и без сессии имплементатора, с честной пометкой.
- Цена растёт линейно по числу ревьюеров.

**Non-Goals:**

- Новые находки от защитника: он не ревьюер, полнота за ревьюерами.
- Правка кода в ходе защиты: шаг `review` только читает, исправления — дело
  следующих шагов.
- Обсуждение ревьюеров между собой.

## Decisions

### 1. Режим `defend` заменяет `discussion`

`discussion` удаляется целиком: схема реплики, раунды, консенсус и лента. Два
режима с похожим смыслом путали бы пользователя, а старый показал себя
плохо. Стратегия с `mode: discussion` отклоняется разбором так:
`неизвестный режим: известны independent, defend (discussion заменён режимом defend)`.

```yaml
mode: defend
defend:
  rounds: 2            # 1–5, по умолчанию 2
defender:              # свежий защитник, когда форка нет
  agent: claude
  model_tier: max
  prompt: Защищай решения, опираясь на код; принимай доказанное.
```

Блоки `defend` и `defender` при другом режиме отклоняются. `id` ревьюера
`defender` занят, как `aggregator`.

### 2. Имплементатор — поле шага, не стратегии

Стратегия переносима между пайплайнами, а имплементатор — свой у каждого.
Поэтому `implementer` объявляет шаг `review`:

```yaml
- id: review-diff
  review: panel
  implementer: implement          # шаг этой работы
  # implementer: build.implement  # шаг работы, от которой зависит эта
```

Ссылка MUST указывать агентский шаг. Это либо шаг той же работы перед
`review`, либо шаг работы, от которой работа шага `review` зависит
(`needs`, транзитивно). Иначе разбор и линт отказывают. `implementer` при
режиме, отличном от `defend`, — ошибка линта: поле ничего бы не делало.

Ссылка входит в ключ шага. Id сессии в ключ не входит: новая сессия при той
же реализации не повод переисполнять ревью. Переисполнение имплементатора
меняет дерево и выходы выше по графу, и это уже сдвигает ключ.

### 3. Защитник: форк или свежий агент

Перед ветками движок один раз решает, кто защищает:

1. **Форк.** Он выбирается, когда есть `implementer`, в записи его шага есть
   `session`, а адаптер его агента объявляет `sessions` и `forkSessions`.
   - Агент, модель и effort защитника берутся у шага имплементатора.
   - Права (`permissions`) берутся у шага `review`, а не у имплементатора:
     защитник не правит файлы.
   - Запись имплементатора ищется в текущем прогоне. Для шага,
     переиспользованного при `resume`, она ищется в исходном прогоне.
2. **Свежий агент.** Он выбирается в остальных случаях.
   - Агент берётся из `defender` стратегии, а без него — из профиля
     `default`. Адрес `step_agents` — `<работа>.<шаг>/defender`.
   - Промпт несёт задание шага и контекст шага.
   - Если имплементатор есть, но форк невозможен, к промпту добавляется
     текстовый выход шага имплементатора, если он есть.

Решение записывается первой строкой `defense.ndjson` и событием
`review.defender`:
`{ mode: fork|fresh, implementer?, agent, model?, reason? }`. Значения
`reason`: `no_implementer`, `no_session`, `no_fork`.

Каждая ветка получает свою сессию защитника, псевдоним
`<шаг>/defender/<ревьюер>`. Первый вызов форкающей ветки передаёт
`forkFrom: <id сессии имплементатора>`. Последующие возобновляют форк
обычным `resume`.

### 4. Форк в адаптере

- `BackendCapabilities.forkSessions?: boolean` — по умолчанию нет.
- `AgentInvocation.forkFrom?: string` уходит только на первой попытке, пока
  сессия псевдонима не начата.
- Claude (`sessionIdSource: engine`):
  `--resume <forkFrom> --fork-session --session-id <выданный id>`.
- Codex (`sessionIdSource: backend`): `codex exec fork <forkFrom> …` с теми
  же опциями. Новый id приходит в `thread.started`.
- Неудачный форк (ненулевой код без `init`) — сбой попытки. Ветка
  засчитывает его как сбой защитника (решение 5). Тихого отката на свежего
  агента нет: журнал обязан показать, что форк не удался.

### 5. Ветка: раунды по находкам

Находки ревьюера получают id `<ревьюер>.<n>` в порядке его выхода. Ревьюер
с пустым списком ветки не получает. Ветки разных ревьюеров идут параллельно
в пределах `limits.concurrency`.

Раунд `r` (1…`rounds`):

1. **Защитник** отвечает на все открытые находки ветки по схеме
   `review-defense`:
   ```json
   { "text": "…",
     "responses": [{ "finding": "security.1", "stance": "accept|dispute|clarify",
                     "text": "…", "evidence": "src/x.ts:42 … | null" }] }
   ```
   Проверочная схема требует ровно открытые id. Невалидный ответ получает
   один повтор с ошибкой. `accept` закрывает находку как `accepted`.
2. Если открытых не осталось, ветка закончена. Иначе **ревьюер**, в своей
   возобновлённой сессии, отвечает на каждую открытую находку по схеме
   `review-rebuttal`:
   ```json
   { "text": "…",
     "responses": [{ "finding": "security.1", "stance": "maintain|withdraw|revise",
                     "text": "…", "severity": "critical|major|minor|info|null" }] }
   ```
   `withdraw` закрывает находку как `withdrawn`. `revise` требует
   `severity` и меняет её. `maintain` оставляет находку открытой.

После раунда `rounds` открытые находки закрываются как `contested`.
Последнее слово за ревьюером: возражение защитника без ответа ревьюера
судье было бы видно односторонне.

Сбои:

- Ход, не давший валидного ответа после повтора или упавший (таймаут, отказ
  бэкенда, неудачный форк), записывается репликой с `invalid: true` или
  `failure`. Ветка на этом кончается, её открытые находки — `contested`.
- Бюджет проверяется перед каждым ходом. Перейдённый бюджет обрывает все
  ветки, и шаг кончается `budget_exceeded` без агрегатора, как и прочие
  обрывы бюджетом.
- Отмена отменяет шаг.

Цена ветки — не больше `2·rounds` вызовов. Шага — N ревьюеров + ветки +
агрегатор.

### 6. Агрегатор

Промпт агрегатора в режиме `defend` состоит из:

- задачи шага;
- строки о защитнике (форк сессии `<implementer>` или свежий агент и
  причина);
- находок каждого ревьюера с `focus`, итоговой серьёзностью, статусом и
  перепиской по находке (доводы и доказательства обеих сторон);
- ревьюеров без находок с причинами;
- `aggregator.prompt` стратегии;
- роли:
  - `accepted` включить (повторы можно объединить, понизить серьёзность
    можно только с объяснением);
  - `withdrawn` не включать;
  - `contested` решить самому, взвесив доводы.

Выход — по `output_schema` шага. Попытки и `expect` шага — агрегатора. Повтор
шага повторяет только агрегатора с той же защитой.

### 7. Журнал и события

`participants/<ревьюер>/` — независимое ревью, как в `independent`.
`participants/<ревьюер>/rounds/<r>/` — ответ ревьюера в раунде `r`.
`participants/defender/<ревьюер>/rounds/<r>/` — ход защитника в ветке.
`participants/aggregator/` — агрегатор.

`defense.ndjson`, строки по порядку:

```json
{"kind":"defender","mode":"fork","implementer":"build.implement","agent":"claude","model":"opus"}
{"kind":"finding","id":"security.1","by":"security","severity":"critical","title":"…","location":"…","detail":"…","suggestion":null}
{"kind":"message","messageId":"m1","role":"agent","from":"defender","thread":"security","round":1,
 "parts":[{"kind":"text","text":"…"}],
 "responses":[{"finding":"security.1","stance":"dispute","text":"…","evidence":"…"}]}
{"kind":"message","messageId":"m2","role":"agent","from":"security","thread":"security","round":1,
 "parts":[{"kind":"text","text":"…"}],
 "responses":[{"finding":"security.1","stance":"revise","text":"…","severity":"major"}]}
{"kind":"settled","finding":"security.2","status":"accepted","severity":"major","round":1}
{"kind":"outcome","accepted":3,"withdrawn":1,"contested":1}
```

- Записи разных веток в файле перемежаются. Порядок внутри ветки строгий,
  `messageId` сквозной по шагу.
- Строка `settled` пишется в момент закрытия находки, для `contested` — в
  конце ветки.
- Невалидная реплика несёт `"invalid": true`, упавшая — `"failure": "<причина>"`;
  `responses` у обеих пусты.
- События:
  - `review.defender` — `mode`, `implementer?`, `agent`, `model?`, `reason?`;
  - `review.message` — `participant`, `thread`, `round`, `message_id`,
    `invalid?`, `failure?`;
  - `review.settled` — `finding`, `status`;
  - `review.defense.finished` — `accepted`, `withdrawn`, `contested`.
- `review.participant.started|finished` несут `thread` у защитника.
- Старые виды событий (`review.consensus`, `review.no_consensus`,
  `review.message` с позициями) остаются читаемыми схемой журнала, чтобы
  прежние прогоны открывались. Движок их больше не пишет.
- Расход защитника всех веток ведётся под участником `defender`.

### 8. Витрина

Лента шага `review` в режиме `defend` строится из `defense.ndjson`:

- системная строка о защитнике;
- сообщения ревьюеров с карточками их находок; у каждой карточки id и бейдж
  статуса (`open`, `accepted`, `withdrawn`, `contested`, серьёзность с
  отметкой пересмотра);
- реплики ветки под находками своего ревьюера. Защитник — на стороне,
  противоположной ревьюерам. Ответы — по находкам с метками
  (`accepts`, `disputes`, `clarifies` / `maintains`, `withdraws`,
  `revises → major`) и доказательством;
- вердикт агрегатора последним сообщением.

Боковая панель:

- находки со статусом и итоговой серьёзностью;
- раунды по ветке `r/rounds`;
- расход по участникам, включая `defender`.

Живое обновление идёт по `review.message`, `review.settled` и
`review.participant.*`. Режим `independent` — находки и вердикт, как
прежде. Журнал прежнего режима `discussion` показывается списком
участников и вердиктом.

Редактор стратегии:

- переключатель режима «Independent / Defend»;
- в режиме `defend` поле `rounds` (1–5) и блок выбора агента защитника с
  пояснением, что при сессии имплементатора защитник — её форк;
- схема хода: «Reviewers in parallel → Defend with implementer ≤ R rounds
  → Aggregator decides contested».

## Risks / Trade-offs

- **Угодливость защитника.** Защитник склонен соглашаться с любой критикой.
  Поэтому `accept` не проходит мимо агрегатора без следа: агрегатор видит
  переписку и может понизить серьёзность с объяснением. В промпте защитника
  прямо сказано, что принимать стоит только то, что подтверждается кодом.
- **Упрямство защитника.** Спорное решает агрегатор с доводами обеих
  сторон, а последнее слово в ветке за ревьюером.
- **Стоимость форка по токенам.** Контекст сессии имплементатора велик.
  Ревью обычно идёт сразу после реализации, и форк попадает в кеш промпта.
  Число вызовов ограничено `2·rounds` на ветку.
- **Форк ломается версией CLI.** Сбой форка виден в журнале как сбой хода
  защитника, находки ветки — `contested`. Шаг не падает.
