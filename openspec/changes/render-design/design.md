## Context

Шаг `discuss` пишет в каталог шага:

- `discuss.ndjson` — записи `proposal`, `draft`, `objection`, `message`,
  `settled`, `outcome`;
- `participants/<id>/` — предложение участника, а в нём `objections/` (ход
  возражений) и `rounds/<r>/` (ответы в раундах защиты);
- `participants/author/draft/` (черновик, при повторе `draft/retry/`) и
  `participants/author/rounds/<r>/` (ходы защиты);
- `participants/aggregator/` — итог;
- `output.json` — итоговый документ по `output_schema` шага с полями движка.

Замок хранит у шага блок `discuss` (ссылка на стратегию, `rounds`),
`participants`, `author`, `aggregator`.

У шага `review` уже есть лента: `src/parts/ui/reviewFeed.ts` (чтение) →
`GET /api/review-feed` → `ui/src/components/ReviewFeed.tsx`. В ней есть
помощники чтения вызова участника, `ndjson`, переиспользованного шага и
расхода. Лента discuss нуждается в тех же помощниках.

Чего пока нет: рендеров документа, команды `burnex render`, Mermaid в
витрине.

## Goals / Non-Goals

**Goals:**
- Детерминированный рендер `burnex:design-doc` в один офлайн-HTML и в
  OpenSpec `design.md`, доступный из CLI и витрины одним кодом.
- Лента шага `discuss` в деталях прогона с итоговым документом и
  отрисованными диаграммами.
- Вызов рендера из пайплайна обычным шагом `run:` по явному пути.

**Non-Goals:**
- Редактор стратегий обсуждения.
- Проверка синтаксиса Mermaid в Node (без DOM её нет).
- Другие форматы диаграмм.
- Новый вид шага или `uses: burnex:render-design`: такой формы встроенных
  шагов нет, а `run:` с командой покрывает случай.

## Decisions

### 1. Рендер — команда CLI, а не вид шага

`burnex render design <файл> --format html|openspec [--out <путь>]`.
Позиционный `<что>` сейчас один (`design`), он оставлен ради ясности
команды: `render` без вида ничего не говорит. Неизвестный вид — ошибка
конфигурации с перечнем видов.

Вызов из пайплайна:

```yaml
- id: html
  run: [sh, -c, 'burnex render design "$BURNEX_ARTIFACTS/design.json" --format html --out "$BURNEX_ARTIFACTS/design.html"']
```

Альтернатива — флаг `--job <id>`, который сам находит выход работы через
`BURNEX_RUN_DIR`. Отклонена: Fable 5.2 и мы согласились на явный путь (вход
виден в шаге, команда работает и вне прогона).

Команда не зависит от конфигурации (`{ independent: true }`, как `data`).

### 2. Проверка входа схемой `burnex:design-doc`

Вход разбирается как JSON и проверяется схемой
`schema/design-doc.schema.json` через `ajv` (уже зависимость движка). Поля
движка в схеме не объявлены и закрыты `additionalProperties: false`, поэтому
рендер снимает их до проверки, проверяет сами поля движка отдельно (типы:
`agreed` boolean, `unresolved` массив строк, `changed_by_aggregator` массив
строк) и возвращает их рядом с документом.

Своя `output_schema` шага, отличная от `burnex:design-doc`, рендеру не
подходит: команда отказывает с путём первой ошибки схемы. Расширять рендер
под произвольные схемы — не цель.

Отказ — ошибка конфигурации (`ExitCode` как у прочих отказов входа) с
файлом и путём ключа.

### 3. HTML: один файл, Mermaid встроен из пакета

- Разметка — шаблон строками в TS, без зависимостей. Весь текст документа
  экранируется (`& < > " '`). Ссылки и HTML из текста не исполняются.
- Стили встроены `<style>`, светлая и тёмная тема через
  `prefers-color-scheme`.
- Диаграммы — `<pre class="mermaid">` с экранированным исходником (Mermaid
  читает `textContent`). Под каждой — подпись с названием и ссылками на
  точки решения (`#d1`), у решений — якоря.
- Бандл `mermaid.min.js` встраивается `<script>` как есть, с заменой
  `</script` на `<\/script`. Затем инициализация:
  `mermaid.initialize({ startOnLoad: false, securityLevel: 'strict' })` и
  `mermaid.run({ suppressErrors: true })`. Блок, который отрисовать не
  удалось, остаётся исходником, к нему добавляется текст ошибки
  (обработчик `postRenderCallback` ловит отказ поблочно через
  `mermaid.parse`).
- Документ без диаграмм скрипт не встраивает.

Откуда бандл: `mermaid@12.2.0` — devDependency. Сборка (`build:node`)
копирует `node_modules/mermaid/dist/mermaid.min.js` в
`dist/vendor/mermaid.min.js` скриптом `scripts/copy-vendor.mjs`. Релиз
(`install.sh` копирует `dist`) и npm-пакет (`prepack` → `build`) несут файл
без рантайм-зависимости движка от `mermaid`. Рендер находит файл
относительно собственного модуля. Нет файла (сборка без шага копирования) —
отказ с подсказкой пересобрать, а не HTML без диаграмм.

Альтернативы:
- CDN — отклонена пользователем (офлайн).
- Серверная отрисовка SVG — нужен браузер (Puppeteer/Playwright), тяжело
  для CLI.
- Взять чанк из сборки витрины — имя чанка с хешем, связь хрупкая.

Цена: HTML с диаграммами около 5,5 МБ. Приемлемо для локального артефакта.

### 4. OpenSpec `design.md`

Порядок разделов — шаблон OpenSpec:

```
# <title>

> **Итог не согласован.** Несогласованные точки: d3, d5.   (только agreed: false)
> Изменено агрегатором: d9.                                  (если список не пуст)

## Context
<summary>

## Decisions
### d1. <question>
**Решение:** <choice>

<rationale>

**Отклонено:**
- <summary> (<by>) — <reason>

## Diagrams
### g1. <title>
Точки решения: d1, d4.
```mermaid
<source>
```

## Risks / Trade-offs
- **[<risk>]** → <mitigation>

## Open Questions
- <вопрос>
```

Разделы без содержимого (нет диаграмм, рисков, вопросов) не выводятся, кроме
`Context` и `Decisions`. Текст полей вставляется как есть: это Markdown,
который авторы документа и пишут. Исходник диаграммы с тройным бэктиком
внутри обрамляется более длинной оградой.

Подписи («Решение», «Отклонено», «Точки решения», пометки итога) —
по-русски, как и остальная проектная документация репозитория; заголовки
разделов — как в шаблоне OpenSpec.

### 5. Детерминизм

Рендеры — чистые функции документа (и для HTML — текста бандла). Нет
дат, путей, случайных id. Ключи и порядок — как в документе. Тест сверяет
два рендера одного входа побайтно.

### 6. Лента шага `discuss`: чтение журнала, общие помощники

`readDiscussFeed(paths, job, step, { pass })` в
`src/parts/ui/discussFeed.ts`. Помощники, которые уже есть в
`reviewFeed.ts` и нужны обеим лентам, переезжают в
`src/parts/ui/participantJournal.ts`: `readNdjson`, `readCall`, `fileRef`,
`listRounds`, `listDirs`, `reusedSource`, построитель расхода участника. Лента
review импортирует их оттуда, её поведение не меняется.

Состав ленты:

- `participants[]` — участники стратегии (порядок из замка), затем
  `author` и `aggregator`. У каждого: `role`, `agent`, `model`, `focus`,
  вызовы (`calls[]`: фаза, раунд, статус, причина, ссылка на `stdout.log`,
  `running`), расход из `usage.json`.
- `phases` — `proposals | draft | objections | defense | aggregate` со
  статусом `pending | running | done | skipped`. Выводятся из журнала и
  каталогов: запись `draft` есть — `draft` готов; есть `outcome` — защита
  кончилась; есть `output.json` шага — итог готов. Защита без `blocking` —
  `skipped`.
- `proposals[]` — по записям `proposal`: участник, статус, причина,
  `summary` из его `output.json`.
- `draft` — из записи `draft` (решения, диаграммы).
- `objections[]` — по записям `objection`, с итоговым статусом из
  `settled` (`accepted | withdrawn | contested | open`), у `preference` —
  `note`.
- `rounds[]` — реплики `message` по раундам: от кого, текст, ответы по
  возражениям (`responses`).
- `outcome` — счётчики из записи `outcome`.
- `document` — `output.json` шага, если он разобрался как документ рендера
  (решение 2); иначе `output` сырым значением и `documentError`.
- `done`, `reusedFrom` — как у ленты review.

Отказ разбора строки или файла — пропуск записи, не исключение: ленту
опрашивают раз в секунду, пока шаг идёт.

### 7. API демона

- `GET /api/discuss-feed?run=<project>/<run>&job=&step=[&pass=]` — лента.
  Параметры и коды ответа — как у `/api/review-feed`.
- `GET /api/design-render?run=&job=&step=&format=html|openspec[&pass=]` —
  рендер `output.json` шага тем же кодом, что у команды.
  `Content-Disposition: attachment; filename="<job>-<step>.html|design.md"`.
  Документ не той формы — 422 с текстом ошибки.

### 8. Витрина

- `RunDetail` ведёт шаг `discuss` в `DiscussFeedPanel` (по образцу
  `ReviewFeedPanel`: опрос раз в секунду, пока `done: false`).
- Панель: строка фаз, карточки участников, вкладки «Документ» и
  «Обсуждение». «Документ» — `DesignDoc`: заголовок, отметка согласия,
  `summary`, решения с отклонёнными вариантами и отметкой «изменено
  агрегатором», диаграммы, риски, вопросы, кнопки скачать HTML и
  `design.md`. «Обсуждение» — лента: предложения, черновик (решения
  свёрнуты), возражения по точкам с весом и исходом, реплики раундов
  пузырями от участников (цвет по позиции, как в ленте review).
- `Mermaid` — компонент, который лениво делает `import('mermaid')`
  (отдельный чанк Vite), инициализирует `securityLevel: 'strict'`, тему по
  теме витрины и рисует SVG `mermaid.render(id, source)`. Ошибка — исходник
  блоком кода и текст ошибки. Пока чанк грузится — исходник.
- Пока документа нет (шаг идёт), «Обсуждение» открыто по умолчанию.

## Risks / Trade-offs

- **[Тяжёлый HTML]** → 5,5 МБ из-за бандла. Скрипт встраивается только
  при наличии диаграмм. Если вес начнёт мешать, можно добавить
  `--mermaid none` (исходники без отрисовки) — сейчас не делаем.
- **[Бандл не попал в сборку]** → отказ рендера с подсказкой, тест
  проверяет наличие `dist/vendor/mermaid.min.js` после `build:node`.
- **[Несовместимость Mermaid витрины и HTML]** → оба берут один пакет одной
  версии.
- **[Своя `output_schema` у шага discuss]** → рендер и кнопки скачивания
  недоступны, лента показывает сырой вывод с причиной. Схема шага —
  выбор пользователя.
- **[XSS из текста документа]** → весь текст экранируется,
  `securityLevel: 'strict'` у Mermaid; витрина выводит текст узлами React.

## Migration Plan

Не нужна: формат журнала и шага прежний, новые маршруты и команда только
добавляются.
