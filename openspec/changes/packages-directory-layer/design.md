## Context

Каждый вид ресурса stepcast сегодня ищется своим обходом и своим набором
слоёв:

| Ресурс | Где ищется сейчас | Код |
|---|---|---|
| Пайплайн | путь от каталога запуска; `stepcast:<имя>` — поставка | `resolvePipelineTarget`, `src/parts/pipeline/domain/package-schema.ts` |
| Перечень пайплайнов витрины | `stepcast.yml` и `.stepcast/pipelines/*.yml` проекта | `listPipelineFiles`, `src/parts/pipeline/domain/project/pipelines.ts` |
| Шаг `uses` | проект → home → встроенное | `STEP_LAYERS`, `src/parts/pipeline/document/steps.ts` |
| Скрипт `script` | проект → home → встроенное | `ScriptRoots`, `src/parts/pipeline/document/expand.ts` |
| Плагин-каталог | home, затем проект — операции дерева; имя встроенной строки — отказ | `discoverPluginDirectories`, `src/kernel/tree/discover.ts`; сборка в `src/parts/pipeline/config/resolve.ts` |
| Виджет | только `.stepcast/widgets/` проекта; встроенные — каталог образцов | `src/parts/ui/widgets.ts` |
| Дашборд | home и проект, проект перекрывает | `src/parts/ui/dashboardsFile.ts` |
| Маршрут | встроенное ← home ← проект, слияние по `id` | `src/parts/ui/routesFile.ts` |

Слово «package» в коде уже занято npm-пакетом движка
(`package-schema.ts`, `findPackageRoot`, «пайплайн поставки»). Новое понятие
— пакет пользователя — живёт в своём модуле `src/parts/packages/`, и в его
API пакет движка называется «поставкой», как уже принято в комментариях.

Образец поведения — раздел 6 «Пакеты» `docs/burnex-after-stepcast.md`; из него
берётся раскладка и порядок поиска, но не поля маркетплейса (`owner`,
`private`, `pipeline_agents` и пр.).

## Goals / Non-Goals

**Goals:**

- один каталог переносит практику целиком, и движок знает, что это одно
  целое, его имя, версию и потребности;
- один порядок поиска для всех видов ресурсов, вписанный в существующие слои,
  без изменения поведения проектов, у которых пакетов нет;
- поломка одного пакета видна с причиной и не трогает остальное.

**Non-Goals:**

- установка, обновление, удаление и публикация пакетов, каталог-репозиторий,
  проверка `needs` с отказом в установке — `marketplace-catalog`;
- поля манифеста сверх названных в пункте очереди (`owner`, `private`,
  `plugins`, `integrations`, `pipeline_agents`) — добавятся вместе с
  маркетплейсом, строгая схема отклоняет их до тех пор;
- одиночные `.mjs` плагины пакета, подключаемые строкой `plugins:`, — пакет
  приносит только каталожные плагины с `plugin.json`;
- запись из витрины в пакет: дашборды и виджеты пакета только читаются;
- вложенные пакеты и пакеты внутри пакетов.

## Decisions

### Решение 1. Указатель пакетов — один обход на корень проекта и home

`src/parts/packages/index.ts` строит по паре корней (`projectRoot | undefined`,
`homeStepcastDir`) неизменяемый указатель: для каждого слоя (`project`,
`home`) — пакеты в порядке имён каталогов, у каждого — `name`, `layer`,
`dir`, `manifest` или `failure`. Потребитель спрашивает у указателя
упорядоченный список каталогов своего ресурса:

```
resourceLayers(index, 'steps') →
  [{ source: 'project', dir: <проект>/.stepcast/steps },
   { source: 'project-packages', dirs: [{ package: 'hello', dir: …/packages/hello/steps }, …] },
   { source: 'home', dir: ~/.stepcast/steps },
   { source: 'home-packages', dirs: […] },
   { source: 'builtin', dir: … }]
```

Свободный слой и слой пакетов разделены: внутри слоя пакетов имена ресурсов
обязаны быть уникальны (Решение 4), а свободный каталог законно перекрывает
пакет своего корня.

Альтернатива — дописать пакетные каталоги в каждый из семи обходов по
месту — отвергнута: семь копий правила затенения и конфликта разойдутся, как
уже разошлись сегодняшние наборы слоёв (у виджетов нет home, у дашбордов нет
встроенного). Указатель не выравнивает эти различия: ресурс, у которого нет
свободного слоя home, не получает его и сейчас, — пакетные слои добавляются к
тем, что есть.

Каталог пакетов home — `dirname(globalPath)/packages`, а не
`homedir()/.stepcast/packages`: сборка с подставным путём конфигурации
(запасное ядро демона) обязана остаться без пользовательских пакетов, тем же
доводом, что у `plugins/` (`src/kernel/tree/discover.ts`).

Указатель строится синхронно, без кеша в модуле: обходы, которые он заменяет,
синхронны, а демон пересобирает свои составы по отпечаткам каталогов, и
указатель — часть того, что отпечатывается (Решение 8).

### Решение 2. Манифест — zod, строгий, публикуемый

`PackageManifestSchema` (zod, `.strict()`): `version: 1`, `kind: 'package'`,
`name` — `^[a-z0-9]+(-[a-z0-9]+)*$`, `description` — непустая строка,
`package_version` — semver (`MAJOR.MINOR.PATCH` с необязательными пре-релизом и
сборкой), `needs` — необязательный строгий объект из четырёх необязательных
массивов уникальных непустых строк. Проверки вне схемы: `name` совпадает с
именем каталога; `name` не `stepcast` и не `builtin` — первое занято адресом
поставки (`stepcast:<имя>`), второе — ключом встроенных виджетов в адресе
модуля (`BUILTIN_WIDGETS_KEY`). JSON Schema `schema/package.schema.json`
порождается `npm run schema` из той же модели, как остальные файлы `schema/`.

Отказ называет файл и место тем же `describeSchemaFailure`, что и
дашборды и маршруты.

### Решение 3. Затенение пакета — целиком, по имени

Пакет проекта `hello` затеняет пакет home `hello` целиком: ни один ресурс
пакета home `hello` не участвует в поиске, даже тот, которого в пакете проекта
нет. Иначе обновлённый пакет проекта, в котором шаг переименовали, продолжал
бы тянуть старый шаг из копии home — смесь двух версий, которую никто не
собирал. Затенённый пакет виден в `package list` с пометкой, чем он затенён.
Сломанный пакет проекта затеняет одноимённый пакет home тоже: молча
подставить копию home вместо сломанной проектной значило бы скрыть поломку.

### Решение 4. Конфликт внутри слоя — отказ ресурса, а не пакета

Два пакета одного слоя, приносящие ресурс одного имени (шаг `lint`, виджет
`clock`, дашборд `ops`, плагин `board`, маршрут с `id: ops`), — ошибка,
называющая оба пакета и ресурс. Отказывает именно этот ресурс: он не
разрешается ни в один из двух пакетов и не проваливается в нижний слой
(провал дал бы молчаливую подмену). Остальные ресурсы обоих пакетов
работают. Для шага и скрипта отказ приходит значением `ScriptUnresolved` с
причиной — тем же путём, каким `stepcast lint` называет все промахи за проход;
для плагина — строкой дерева с заведомым отказом (`TreeRowFailure`); для
виджета и дашборда — записью с ошибкой в составе витрины; для маршрута —
отказом строки таблицы.

Альтернатива — побеждает первый по алфавиту — отвергнута: исход зависел бы от
имени каталога, а не от намерения автора.

Пайплайны конфликтовать не могут: адрес несёт имя пакета.

### Решение 5. Адрес пайплайна `<пакет>:<имя>`

`resolvePipelineTarget` получает третью ветвь: цель вида
`^[a-z0-9]+(-[a-z0-9]+)*:[A-Za-z0-9_-]+$`, не начинающаяся с `stepcast:`,
— адрес пайплайна пакета. Пакет ищется в слое проекта, затем home (с учётом
Решения 3); пайплайн — файл `pipelines/<имя>.yml` (или `.yaml`) с
`kind: pipeline`. Неизвестный пакет, сломанный пакет и отсутствующий пайплайн
— отказ с перечнем того, что есть. Всё, что под форму не подходит, —
по-прежнему путь от каталога запуска, так что `./foo:bar.yml` и любые пути с
`/` остаются путями.

Признак `isSupplyPipeline` обобщается до «пайплайн не из проекта»: и для
поставки, и для пакета слои `script`/`step` ищутся от каталога запуска
(`projectRoot: cwd`), а не от каталога пакета. Пайплайн пакета home, запущенный
в проекте, работает с этим проектом — ради этого им и делятся.

Журнал прогона записывает адрес так, как он был назван, и разрешённый путь:
`stepcast resume` идёт по разрешённому пути журнала, а не разрешает адрес
заново.

### Решение 6. Плагины пакетов — те же операции дерева с источником

`TreeOperation` каталожной строки сегодня несёт `layer: 'project' | 'home'`.
Он заменяется источником `{ layer: 'project' | 'home', package?: string }`:
ядро не знает, что такое пакет, но печатает источник строкой
(`project`, `home`, `package hello (project)`). Разрешение конфигурации
подаёт операции в порядке: встроенное → пакеты home → свободный home →
ключ и патч home → пакеты проекта → свободный проект → ключ и патч проекта.
Более поздняя операция с тем же `id` заменяет раннюю — существующее правило,
и оно даёт ровно порядок поиска из пункта очереди. Конфликт внутри слоя
пакетов (Решение 4) указатель превращает в одну операцию с `failure`,
называющей оба пакета. Каталог плагина пакета, названный идентификатором
встроенной строки, — тот же отказ, что у свободного каталога.

### Решение 7. Виджеты, дашборды, маршруты витрины

- **Виджет**: `resolveWidgetFile(projectPath, id)` ищет свободный каталог
  проекта → пакеты проекта → пакеты home. Проверка реального пути остаётся, но
  относительно каталога `widgets/` того слоя, где файл найден. Адрес модуля
  витрины не меняется (`/widgets/<projectKey>/<id>.js`): виджет пакета
  адресуется голым `id`, как и свободный. Перечень виджетов проекта несёт
  источник каждого.
- **Дашборд**: слои пакетов вставляются между имеющимися (пакеты home ниже
  home, пакеты проекта ниже проекта). Запись (`writableDashboardPath`) — только
  в свободные слои: правка дашборда пакета из витрины сохраняется копией в
  свободный слой проекта, затеняя пакетный, — ту же семантику уже даёт правка
  дашборда home из проекта.
- **Маршруты**: таблица собирается слиянием по `id` в порядке встроенное ←
  пакеты home ← home ← пакеты проекта ← проект. `routes.yml` пакета проходит ту
  же схему; его цель `widget:`/`dashboard:` разрешается обычным поиском, а не
  только внутри пакета.
- **Pipelines**: экран и запуск прогона получают пайплайны пакетов с адресом
  `<пакет>:<имя>` и запускают их этим адресом, а не путём файла: путь пакета
  home лежит вне проекта, и `runLaunch` отказал бы ему как пути наружу.

### Решение 8. Демон видит появление и правку пакетов

Наблюдатель демона, уже следящий за `widgets/`, `dashboards/`, `routes.yml` и
`plugins/` свободных слоёв, добавляет `packages/` обоих корней: появление,
удаление пакета и правка `package.yml` пересобирают затронутые составы тем же
путём, каким сегодня пересобирается правка свободного каталога. Отдельного
механизма перезагрузки пакет не получает.

### Решение 9. `stepcast package list|new`

Одна строка команды `package` с подкомандами, независимая от состава
плагинов (как `plugins` и `config`): она обязана работать, когда пакет сломал
состав. `list` печатает по строке на пакет — имя, слой, `package_version`,
каталог, что приносит (подкаталоги, где есть хоть один ресурс), статус
(`ok`, `сломан: <причина>`, `затенён пакетом проекта`) и незакрытые `needs`.
Проверка `needs` в этом изменении — справочная и мягкая: `packages` — по
указателю, `backends` — по реестру, если состав собран; `mcp` и `secrets`
печатаются как объявлены, без проверки. `--json` отдаёт ту же модель.
`new <имя> [--home]` проверяет имя схемой, отказывает при существующем
каталоге и создаёт `package.yml` (`package_version: 0.1.0`, описание-заглушка)
и пустые подкаталоги не создаёт: пустой каталог в git не живёт, а
документированная раскладка в `docs/packages.md` достаточна.

## Risks / Trade-offs

- [Порядок поиска растёт с трёх слоёв до пяти, и «откуда взялся этот шаг»
  становится труднее] → слой и пакет записываются в происхождение шага
  (`UsesOrigin`), строки дерева плагинов, перечни витрины и `package list`.
- [Затенение пакета целиком удивит того, кто ждал поресурсного слияния] →
  затенённый пакет назван в `package list`, а `docs/packages.md` говорит прямо.
- [Адрес `<пакет>:<имя>` перехватывает имя файла вида `foo:bar`] → форма узкая
  (без `/` и расширения), путь с `./` остаётся путём; описано в
  `docs/pipeline-format.md`.
- [Слой пакетов home применяется ко всем проектам машины] → это и есть смысл
  home; проект перекрывает и свободным каталогом, и одноимённым пакетом.
- [Сравнение журналов: прогон до изменения записывал слой шага `project|home`]
  → новое поле источника необязательно, старые записи читаются как прежде.

## Migration Plan

Проекты без `packages/` ведут себя как прежде: каждый слой пакетов пуст.
Отката не требуется — удаление каталога `packages/` возвращает прежнее
поведение. Перенос `.stepcast/` самого репозитория в пакет — отдельный пункт,
не это изменение.

## Open Questions

- Нужен ли пакету свой свободный от проекта корень для `scripts/` его шагов,
  если шаг пакета ссылается на скрипт пакета по имени, а проект перекрыл это
  имя? Сейчас — да, проект перекрывает (единый порядок поиска); если это
  окажется ловушкой на практике, решение — поиск сначала внутри своего пакета,
  отдельным изменением.
