## Context

Три места витрины правят или показывают одно и то же — кто и чем исполняет
агентские шаги:

| Место | Что показывает | Что пишет |
|---|---|---|
| `Settings.tsx` | `defaults.agent`, `defaults.model` с областью действия и счётом по `/api/pipelines`, список бэкендов | `PUT /api/settings` (`agent`, `model`) |
| `Agents.tsx` | `defaults.agent`, `defaults.effort`, общие tier, модель и tier/effort каждого бэкенда, исход перечисления моделей (`/api/models`) | `PUT /api/settings` (`agent`, `effort`, `connectCodex`, `backends`, `removeModelTiers`) |
| `Pipelines.tsx` + `PipelineAgents.tsx` | `agent_policy`, записи `pipeline_agents`/`step_agents` с подписями слоёв | `PUT /api/pipelines/agents` |

Обе страницы настроек читают один `GET /api/settings` (`src/parts/ui/settings.ts`)
и пишут один глобальный файл. Экран «Agents» уже содержит поле `agent` и
предупреждение «глобальный `model` сильнее tier — снимите его на Settings»:
дублирование не только внешнее, страница сама знает о расколе.

Ограничения, в которые упирается решение:

- **Экран — строка демона плюс браузерная половина** (`ui-screens`): объявление
  `declaration.ts` с `id`, `title`, `params`; `server.ts` регистрирует экран и
  свои маршруты API; `ui/src/screens/<id>.tsx` вносит компонент в слот `SCREEN`
  по тому же `id`; состав читается из `GET /api/screens`, и половина без
  строки не применяется. Маршрут API принадлежит ровно одной строке.
- **Адрес и меню — таблица маршрутов** (`ui-routes`, `docs/routes.md`): путь,
  `nav`, `values`, `params`, `active_for` — поля строки `routes.yml`; цель —
  `screen: <id>`; строки сливаются по `id` слоями. Компонент экрана получает
  `params` маршрута и `navigate` (как `ui/src/screens/usage.tsx` получает
  `period`). Понятия «редирект» в таблице нет.
- **Домашний патч дерева плагинов** может отключать строки поставки по `id`
  (`stepcast:screen-settings` в `test/ui-screens.test.ts`).
- **Браузерные тесты идут в Node без DOM** (`scripts/build-ui-tests.mjs`):
  проверяется либо чистая логика, либо `renderToStaticMarkup` без эффектов.
- Язык всего, что видит браузер, — английский (`ui-overhaul`).

## Goals / Non-Goals

**Goals:**

- Одно место для всех настроек агентов; `~/.stepcast/config.yml` правится с
  одного экрана.
- Прежние адреса и ссылки не ломаются: `/settings` открывает то, что нужно.
- Ни одна форма API не меняется: `/api/settings`, `/api/models`,
  `/api/pipelines`, `/api/pipelines/agents` остаются как есть.
- Вкладка адресуема ссылкой.

**Non-Goals:**

- Правка `agent_policy` с экрана: политика — поле документа пайплайна или
  проектной конфигурации, витрина пишет только глобальный файл. Вкладка Policy
  показывает политику и правит записи выбора — то, что уже умеет «Pipelines».
- Снятие селектора агента с карточки шага на «Pipelines».
- Новый экран «Settings» под расписание и автозапуск — отдельные пункты
  очереди (`docs/ui-proposals.md`, п. 2–4).
- Перенос общего механизма вкладок в маршруты (слот «вкладка»): хватает
  параметра пути.

## Decisions

### Решение 1. Вкладка — необязательный параметр пути с закрытым перечнем

Маршрут `screen-agents` получает `path: /agents/:tab?` и
`values: { tab: [default, backends, tiers, policy] }`. Объявление экрана
называет параметр `tab`. Компонент экрана читает `params.tab`, пустое значение
означает `default`; переключение вкладки — `navigate(hrefForTarget(...))`, а
не локальное состояние.

Почему так, а не состояние компонента: вкладка со ссылкой переживает
перезагрузку, открывается в новой вкладке браузера и годится для ссылки из
предупреждения («снимите глобальную модель» ведёт на `/agents/default`) и из
документации. Механизм — ровно тот, которым `/usage/:period?` выбирает период:
новых понятий у таблицы маршрутов не появляется, значение вне перечня остаётся
неразобранным адресом, как и везде.

Альтернатива — четыре строки маршрутов (`/agents`, `/agents/backends`, …) на
один экран с `params: { tab: backends }`: больше строк в таблице ради того же
результата, и `active_for` пришлось бы перечислять все четыре.

### Решение 2. `/settings` — строка маршрута с чужой целью, а не редирект

Строка `screen-settings` в `src/builtin/routes.yml` остаётся с тем же `id` и
путём `/settings`, но её `target` — `{ screen: screen-agents }` с
`params: { tab: default }`, а `nav` снят. У `screen-agents` появляется
`nav.active_for: [screen-settings]`, чтобы пункт меню подсвечивался и на
старом адресе.

`id` сохранён нарочно: домашний или проектный `routes.yml`, который перекрывал
`screen-settings` (другой `path`, `enabled: false`), продолжает сливаться по
тому же ключу и действует, как действовал. Редиректа (`301`, смена адреса в
строке браузера) в таблице маршрутов нет и заводить его ради одного адреса не
стоит: адрес открывает нужный экран, а это единственное, что обещалось.

### Решение 3. `/api/settings` переезжает в строку `screen-agents`

Строка `screen-settings` (`src/parts/ui/screens/settings/`) удаляется целиком,
а `GET`/`PUT /api/settings` регистрирует `screens/agents/server.ts` рядом с
`/api/models`. `readSettings`/`writeSettings` не трогаются.

Маршрут принадлежит одной строке (`ui-screens`), и строка без экрана — пустая
оболочка вокруг двух маршрутов; оставлять её ради обратной совместимости с
патчем, который её отключал, значило бы держать «экран», которого нет в
составе. Патч `enabled: false` на `stepcast:screen-settings` теперь получает
отказ на неизвестную строку поставки — тот же, что на любое опечатанное имя;
это и есть честный сигнал, что отключать больше нечего (Migration Plan).

Следствие: отключение `screen-agents` патчем теперь снимает и `/api/settings`,
а с ним — выбор агента на «Pipelines» (экран читает настройки ради вариантов и
без них остаётся читающим, как и сегодня при отказе запроса). Это согласуется с
назначением строки: нет экрана агентов — нет и правки агентов.

### Решение 4. Четыре вкладки собираются из существующих кусков, не переписываются

| Вкладка | Откуда | Что меняется |
|---|---|---|
| Default | карточка «Default agent» из `Agents.tsx` + поле `model` с областью действия и счётом `scopeOf` из `Settings.tsx` | предупреждение о глобальном `model` ссылается не на `/settings`, а остаётся рядом с полем, которое его снимает |
| Backends | список бэкендов из `Settings.tsx` + статусы перечисления моделей и чекбокс «Connect Codex» из `Agents.tsx` | карточка на бэкенд: команда, `disabled`/`plugin not connected`/`default`, модель бэкенда, `N models listed` или причина отказа; кнопка «Reload models» в шапке экрана |
| Tiers | «Shared tiers» и карточки агентов из `Agents.tsx` | без изменений по сути |
| Policy | `PipelineCard` → блок `pipeline-agents` и `JobCard` → `AgentSelector` агентских шагов | новая компоновка: по проекту → по пайплайну с именем: политика с файлом, селектор пайплайна, затем агентские шаги плоским списком `<job>/<step>` с подписями слоёв и селектором; пайплайн без `name` назван с причиной, как на «Pipelines» |

Черновик и запись остаются одним состоянием на весь экран: `dirty`, `Save`,
`Discard` — общие для Default, Backends и Tiers, поскольку все три пишут один
`PUT /api/settings` одним патчем. Переключение вкладки черновик не сбрасывает:
адрес меняется, компонент экрана — тот же, состояние живёт в нём. Policy
пишет другой маршрут и своим `Apply`/`Clear` на запись, как сегодня на
«Pipelines»; общая кнопка `Save` на ней не показывается.

Чистая логика — `scopeOf` (счёт области действия модели) и разбор параметра
вкладки — выносится в экспортируемые функции и проверяется тестами в Node;
компоновка вкладок тестом на разметку не проверяется (эффекты в
`renderToStaticMarkup` не идут, экран показал бы только «Loading…»).

### Решение 5. Селектор агента на «Pipelines» остаётся

Вкладка Policy и карточка шага отвечают на разные вопросы: «кто работает где по
всем пайплайнам» и «что делает этот шаг и почему именно этой моделью».
Убрать второй ради первого — потерять контекст (команда шага, `uses`, поля
плагина) там, где решение о модели принимается чаще всего. `AgentSelector`,
`agentChoices`, подписи слоёв и `entryMarkLabel` импортируются из
`PipelineAgents.tsx` в обе страницы — дублируется компоновка, не логика.

## Risks / Trade-offs

- [Строка `stepcast:screen-settings` в чужом патче даёт отказ сборки дерева] →
  отказ назван именем строки, как любой неизвестный `use`; в `docs/config.md`
  и предложении сказано, что строки нет. Иного пути нет: пустая строка без
  экрана была бы ложью о составе.
- [Экран стал длиннее: четыре вкладки в одном компоненте] → вкладки —
  отдельные функции-компоненты внутри `Agents.tsx` или соседних файлов
  (`AgentsPolicy.tsx`), общий черновик передаётся props; `agents.test.tsx`
  закрепляет чистую логику. Файл `Settings.tsx` при этом исчезает — суммарный
  объём кода витрины не растёт.
- [Policy дублирует данные `/api/pipelines`, которые уже тянет «Pipelines»] →
  один запрос на экран, общий для Default (счёт области действия модели, он
  был и у «Settings») и Policy; ответ записи заменяет его. «Pipelines» лишнего
  запроса не делает.
- [Пользователь привык искать модель по умолчанию на «Settings»] → `/settings`
  открывает вкладку Default, где это поле и стоит.

## Migration Plan

1. Патчи дерева плагинов с `use: stepcast:screen-settings` — строку убрать;
   отказ сборки называет её по имени.
2. `routes.yml` пользователя, перекрывавший `screen-settings`, продолжает
   действовать: `path` и `enabled` сливаются по `id`; `nav.title` перекрытия
   теперь даёт пункт меню на псевдоним — безвредно.
3. Откат — возврат коммита: формы API не менялись, файлы конфигурации не
   трогались.
