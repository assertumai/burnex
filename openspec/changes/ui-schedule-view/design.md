## Context

Из `schedule-trigger` сделано: разбор cron и ближайший момент
(`src/parts/pipeline/domain/trigger/cron.ts`: `parseCron`, `isKnownTimeZone`,
`isSatisfiable`, `nextOccurrence`), ключ `triggers.schedule` в документе
(`ScheduleTriggerEntrySchema` в `src/parts/pipeline/document/schema.ts`) с
линтом (`checkTriggers` в `src/parts/pipeline/domain/lint.ts`), `pid` в
манифесте. Решения о срабатывании, команды `stepcast schedule` и сервиса
триггеров в демоне нет; секции `ui.triggers` (`keep_awake`, `require_network`,
`max_catchup_hours`) в конфигурации тоже нет — она объявлена в
`schedule-catchup-and-keep-awake` машинной, только для домашнего конфига.

Витрина уже умеет обходить проекты корня прогонов и раскрывать их пайплайны
(`projectSection`, `listPipelineEntries`, `buildPipelines` в
`src/parts/ui/pipelines.ts`) — экран «Secrets» собран тем же путём. Список
прогонов строится из манифестов (`src/parts/ui/runsView.ts` → `RunOverview`) и
уже различает прогон по полю манифеста `mode: shadow`.

## Goals / Non-Goals

**Goals:**

- По каждому проекту видно, какие пайплайны стоят на расписании, с каким
  выражением и поясом и когда ближайший момент.
- Видно, когда пайплайн последний раз запускался по расписанию и был ли это
  догон.
- Прогон по расписанию отличим в списке прогонов, независимо от того, жив ли
  сервис, который его запустил.
- Экран честно показывает, что сервиса триггеров нет и флаги не действуют.

**Non-Goals:**

- Правка расписания с экрана — витрина не пишет документ пайплайна.
- Запуск прогонов по расписанию, решение о срабатывании, догон, `keep_awake`,
  проверка сети — это `schedule-trigger` (группа 4) и
  `schedule-catchup-and-keep-awake`.
- Заведение секции `ui.triggers` в конфигурации.
- Решения сервиса (пропуск, откладывание, поглощение) и сниппет sudoers на
  экране — их добавит `schedule-catchup-and-keep-awake` поверх этого экрана.

## Decisions

### 1. Источник — `triggers.schedule` раскрытого пайплайна

Экран читает расписание из раскрытого документа (`ExpandedPipeline.pipeline.
triggers.schedule`), а не из сырого YAML: подключённые работы, пакеты и слои
разрешаются так же, как при запуске, и расписание на экране — то, которое увидит
планировщик. Обход проектов, проектная конфигурация и список пайплайнов —
переиспользование `projectSection` и `listPipelineEntries`; пайплайн, который не
раскрылся, даёт строку с ошибкой (`toFailure`), как на «Pipelines».

Пункт очереди называет ключ `on.schedule` — это неточность пункта: `on:` в этом
формате — условие работы относительно зависимостей.

### 2. Ошибка записи — словами линта, без второго валидатора

Для каждой записи вычисление повторяет шаги `checkTriggers`: нет `cron` →
разбор → пояс → выполнимость → `nextOccurrence(mask, tz, now)`. Чтобы тексты
не разошлись, проверка одной записи выносится из `checkTriggers` в функцию
`src/parts/pipeline/domain/trigger/` с исходом `{ ok: true, mask, timezone } |
{ ok: false, reason }`; линт и экран вызывают её оба. Пояс по умолчанию — пояс
машины, как в `schedule-trigger`; на экране явный и умолчательный пояс
различимы. `now` передаётся в свёртку параметром — тесты не зависят от часов.

### 3. Происхождение прогона — поле манифеста, а не состояние сервиса

`run.json` получает необязательное
`trigger: { kind: 'schedule', entry, cron, timezone?, moment, catchup }`.
`kind` — закрытое перечисление с единственным значением, ключ оставлен под
будущий вид триггера (GitHub), как и `triggers` в документе.

Альтернатива — связь «решение сервиса → прогон» по `pid` из файла состояния
сервиса, как задумано в `schedule-catchup-and-keep-awake`, — отвергнута для
списка прогонов: файл состояния живёт рядом с `ui.pid` демона, теряется вместе
с ним, не существует для прогонов внешнего cron и не переносится с каталогом
прогона. Признак происхождения — свойство прогона, его место — манифест, рядом с
`mode` и `resumed_from`.

`cron` и `timezone` копируются в манифест, а не только номер записи: документ
правят, номера сдвигаются, и «последний запуск по этой записи» ищется по
совпадению файла пайплайна, выражения и пояса. `entry` оставлен для
диагностики.

### 4. Признак догона пишет запускающий

`catchup` — явный флаг запуска, а не вывод из `started_at − moment`: прогон,
запущенный вовремя, может стартовать позже момента на секунды-минуты (раскрытие,
снятие якоря), и порог «сколько считать догоном» пришлось бы выдумать. Решение
«это догон» принимает тот, кто выбирал момент из пропущенных, — сервис.

### 5. Флаги `run`: `--scheduled`, `--schedule-entry`, `--catchup`

`stepcast run --scheduled <ISO-момент> --schedule-entry <N> [--catchup]`.
`--scheduled` и `--schedule-entry` — только вместе; `--catchup` — только с
ними. До старта прогона проверяется: момент — разборчивая дата ISO 8601 с
поясом, запись `N` существует в `triggers.schedule` раскрытого пайплайна и
проходит проверку записи (Решение 2). Отказ — до создания каталога прогона, с
названной причиной. Флаги не проверяют, что момент — действительно момент
выражения: это знание запускающего, и прогон, запущенный вручную «как по
расписанию», останется честно помеченным своим аргументом.

`launchRun` (`src/parts/ui/runLaunch.ts`) получает
`scheduled?: { entry, moment, catchup }`; строка поставки
`runLaunch/row.ts` пробрасывает его тем же путём, что `shadow`. `POST /api/run`
не принимает его от формы — опция для сервиса в демоне.

`resume` поле не наследует: возобновление — действие человека, и
`resumed_from` уже говорит, откуда прогон взялся.

### 6. Блок сервиса — одна точка чтения, сегодня пустая

`buildSchedule` берёт сведения о сервисе из функции
`triggerServiceView(config)` в `src/parts/ui/schedule.ts`. Пока секции
`ui.triggers` нет, она возвращает `{ present: false }`. Тип ответа уже несёт
форму `{ present: true, enabled, keepAwake, requireNetwork, maxCatchupHours }`;
`schedule-catchup-and-keep-awake` наполнит её из конфигурации, не меняя экран.
Экран при `present: false` пишет, что расписания объявлены, но сами не
срабатывают, и флаги не показывает вовсе — показывать умолчания несуществующей
секции значило бы обещать поведение, которого нет. Разметку блока с флагами
проверяет тест экрана по фикстуре ответа.

### 7. Последний запуск по записи

Для каждой записи берутся прогоны проекта (`listRuns`), чьи манифесты читаются
мягко (`readManifestSoft`) и несут `trigger.kind === 'schedule'` с тем же
`pipeline_file`, `cron` и `timezone`; последний — по `started_at`. Ответ несёт
идентификатор (ссылка на экран прогона), момент расписания, `catchup`, статус.
Нечитаемый манифест пропускается. Сканирование манифестов — та же цена, что у
списка прогонов; кеш не заводится.

### 8. Маршрут и меню

`screen-schedule` на `/schedule`, `nav: { order: 9, group: system }` — рядом с
«Secrets»: оба — просмотр того, что задано вне витрины. Название пункта берётся
из заголовка экрана «Schedule».

## Risks / Trade-offs

- [Манифест с `trigger` не читается прежней версией движка] → тот же шаг, что
  у `mode` и `pid`; называется в `docs/run-layout.md`. Поле появляется только у
  прогонов, запущенных с флагами, а таких до сервиса триггеров нет.
- [Экран показывает расписание, которое ничто не исполняет] → блок сервиса
  говорит об этом прямо; это и есть текущее состояние, и экран не должен его
  скрывать.
- [Поиск последнего запуска сканирует все манифесты проекта] → терпимо при
  нынешних объёмах; при росте — индекс по `pipeline_file`, отдельным пунктом.
- [Совпадение по выражению и поясу склеит две одинаковые записи одного
  пайплайна] → две одинаковые записи бессмысленны; на экране они покажут один и
  тот же последний запуск, что верно.

## Migration Plan

Аддитивно: новое поле манифеста, новые флаги, новый маршрут. Откат — удалить
маршрут и экран; манифесты с `trigger` останутся нечитаемыми для отката движка,
как сказано выше.
