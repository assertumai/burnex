## ADDED Requirements

### Requirement: Экран «Schedule» показывает расписания пайплайнов и ближайшие моменты
Витрина SHALL отдавать `GET /api/schedule` и экран «Schedule» по маршруту `/schedule` в группе меню `system`: по каждому проекту корня прогонов — пайплайны, чей раскрытый документ объявляет непустой `triggers.schedule`, и по каждой записи — выражение `cron`, часовой пояс (явный или пояс машины, различимо), ближайший момент после текущего времени и последний прогон этого пайплайна, запущенный по этой записи, с моментом расписания, признаком догона и статусом. Запись, которую отклонил бы `stepcast lint`, MUST показываться с причиной теми же словами, что у линта, без ближайшего момента; пайплайн, который не раскрылся, MUST показываться строкой с ошибкой.

#### Scenario: Пайплайн с двумя записями расписания
- **WHEN** пайплайн проекта объявляет `triggers.schedule` с записями `0 3 * * *` в поясе `Europe/Berlin` и `*/30 * * * *` без пояса
- **THEN** ответ `GET /api/schedule` содержит обе записи, у первой — пояс `Europe/Berlin` и ближайший момент 3:00 по Берлину после текущего времени, у второй — пояс машины с признаком умолчания

#### Scenario: Ошибочная запись
- **WHEN** запись расписания содержит `cron: "0 0 30 2 *"`
- **THEN** запись в ответе не имеет ближайшего момента и несёт причину, совпадающую с текстом диагностики `stepcast lint` для этой записи

#### Scenario: Пайплайн без расписания
- **WHEN** пайплайн проекта не объявляет `triggers`
- **THEN** его нет в ответе `GET /api/schedule`

#### Scenario: Последний запуск по расписанию и догон
- **WHEN** у пайплайна есть прогоны, запущенные вручную, и два прогона с `trigger` по записи `0 3 * * *`, последний из которых — догон
- **THEN** запись показывает последний из двух прогонов по `started_at` с его моментом расписания, признаком догона и статусом, а ручные прогоны не учитываются

#### Scenario: Расписание правили после запуска
- **WHEN** последний прогон по расписанию записан с выражением `0 3 * * *`, а документ теперь объявляет `0 4 * * *`
- **THEN** запись `0 4 * * *` показывает, что запусков по ней не было

#### Scenario: Сервиса триггеров нет
- **WHEN** экран открыт на версии без сервиса триггеров
- **THEN** ответ несёт `service.present: false`, а экран сообщает, что расписания объявлены, но сами не срабатывают, и не показывает значений `keep_awake`, `require_network` и окна догона

#### Scenario: Флаги сервиса показаны, когда сервис есть
- **WHEN** экран отрисован по ответу с `service.present: true`, `keepAwake: true`, `requireNetwork: false` и `maxCatchupHours: 2`
- **THEN** экран показывает, включён ли сервис, и значения этих трёх флагов

#### Scenario: Экран только читает
- **WHEN** пользователь открывает экран «Schedule»
- **THEN** на экране нет элементов правки расписания, и ни один запрос экрана не меняет файлы проекта

#### Scenario: Пункт меню
- **WHEN** пользователь открывает витрину со встроенной таблицей маршрутов
- **THEN** в группе `system` есть пункт «Schedule», ведущий на `/schedule`

### Requirement: Прогон по расписанию помечен в списке прогонов
Обзор прогона в списке прогонов SHALL нести происхождение из поля манифеста `trigger`, а экран списка прогонов SHALL помечать прогон, запущенный по расписанию, бейджем `schedule`, а запущенный догоном — бейджем `catch-up`, с моментом расписания в подсказке. Прогон без поля `trigger` MUST NOT получать пометки.

#### Scenario: Прогон по расписанию
- **WHEN** манифест прогона несёт `trigger` с `catchup: false`
- **THEN** строка прогона в списке показывает бейдж `schedule` и момент расписания в подсказке

#### Scenario: Прогон догоном
- **WHEN** манифест прогона несёт `trigger` с `catchup: true`
- **THEN** строка прогона показывает бейдж `catch-up`

#### Scenario: Ручной прогон и прогон прежней версии
- **WHEN** манифест прогона не несёт поля `trigger`
- **THEN** строка прогона не имеет ни одного из этих бейджей
