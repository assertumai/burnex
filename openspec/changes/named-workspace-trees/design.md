## Context

`dependent-job-workspace` научил зависимую работу начинать с результата
предшественника, но вывел раскладку каталогов из формы графа: цепочка
продолжает каталог, развилка засевает новый якорем. В итоге каталог — свойство
работы, а одно дерево на прогон получается только у линейного графа. Это
расходится с тем, как автор думает о рабочем каталоге («прогон идёт в
worktree»), и ломает всё, что привязано к пути или к неотслеживаемому
содержимому: сессии агентов, установленные зависимости, сборку, кеши.

Решения согласованы с пользователем 2026-11-12:

- две оси: материал (`mode`) и область (`scope: run | job`), умолчание `run`;
- новое дерево отпочковывается от `needs` головы;
- новый каталог получает **всё** содержимое каталога источника, а не только
  якорь;
- независимые работы одного дерева сериализуются;
- деревья сами не сливаются;
- `lane` дерево не выбирает;
- `resume` восстанавливает только отслеживаемое (вариант «а»).

## Goals / Non-Goals

**Goals:**

- Материал и область каталога — независимые и явные ключи.
- Один каталог на прогон по умолчанию.
- Параллельность объявляется: `scope: job` целиком или именованными
  деревьями точечно.
- Работа продолжает полное состояние того, от кого зависит.
- Защитник `defend` и группы сессий не уходят в чужой каталог.

**Non-Goals:**

- Автоматическое слияние деревьев.
- Вывод деревьев из `lane`.
- Изменения режима `cwd`.
- Чистое восстановление игнорируемого при `resume` (вариант «б»). Его
  можно добавить позже флагом `burnex resume --clean`.

## Decisions

### 1. Две оси

```yaml
workspace:
  mode: worktree        # материал: cwd | worktree | copy
  scope: run            # область: run (умолчание) | job
  trees: [main, b]      # только при scope: run; первое — дерево по умолчанию

jobs:
  probe: { needs: [build], workspace: { tree: b } }   # параллельная ветка
  bench: { workspace: { tree: own } }                  # одна изолированная работа
```

| Материал | Что даёт | Чем платим |
|---|---|---|
| `cwd` | ничего не готовится, результат на месте, видно незакоммиченное | агент правит дерево пользователя |
| `worktree` | checkout защищён, быстрый старт, настоящий git, вложенные репозитории | нужен git, незакоммиченное не попадает, результат через `apply` |
| `copy` | защита checkout без git и с незакоммиченным | дорого по диску и старту, нет вложенных репозиториев |

| Область | Что даёт | Чем платим |
|---|---|---|
| `run` | один предсказуемый путь, зависимости и кеши живут весь прогон, сессии не теряют каталог, один `apply` | нет параллельности без объявленных деревьев, работы видят следы друг друга |
| `job` | параллельность без объявлений, каждая работа в своей среде (измерения) | подготовка и диск на каждую работу, сессии поперёк работ не форкаются, результат разбросан по каталогам |

Правила:

- `scope`, `trees` и `tree` при `mode: cwd` — ошибка линта: каталог там
  checkout.
- `scope` и `trees` объявляются только на уровне пайплайна. `trees` при
  `scope: job` — ошибка линта: там у каждой работы и так своё дерево.
- `workspace.tree` у работы при `scope: run` — объявленное дерево или `own`.
  Без него работа идёт в дереве по умолчанию; без `trees` подразумевается
  `[main]`. Опечатка в имени — ошибка, а не новое дерево.
- Работа, переопределившая `workspace.mode`, получает `own`, и явный `tree` у
  неё — ошибка. Так `finalize` в `cwd` у пайплайна в `worktree` работает как
  прежде.

Название `scope` выбрано потому, что область относится и к `worktree`, и к
`copy`. Вариант вроде `each-worktree` привязал бы её к одному материалу.

### 2. Новые каталоги и их источник

Каталог заводится:

- дереву по умолчанию при `scope: run` — в начале прогона, от исходного
  состояния (`HEAD` на начало прогона или копия каталога запуска);
- голове именованного дерева и работе с `own` — при `scope: run`;
- каждой работе — при `scope: job`.

Голова именованного дерева — его работа, от которой транзитивно зависят все
остальные работы дерева. Если таких несколько, это ошибка линта: точка
ветвления была бы недетерминированной. При `scope: job` и у `own` каждая
работа — голова своего дерева.

Источник головы выбирается прежними правилами наследования:

- единственная зависимость;
- при нескольких — обязательный `workspace.inherit`;
- `none` — исходное состояние;
- источник без зафиксированного дерева пропускается по цепочке.

`workspace.inherit` у работы, не являющейся головой, — ошибка линта: её
дерево уже заведено.

Почему не «от последней выполненной перед ней работы»: при параллельных
работах «последняя» зависит от того, кто раньше закончил, а `needs`
воспроизводимы между прогонами и при `resume`.

### 3. Полный перенос каталога источника

Новый каталог получает всё содержимое каталога источника на момент
завершения источника: отслеживаемое, неотслеживаемое и игнорируемое, включая
`node_modules`, сборку и кеши. Работа продолжает с того места, где источник
остановился, как если бы шла в его каталоге.

- **Когда.** Засев выполняется сразу по завершении источника, до того как его
  дерево получит следующая работа. При `scope: run` дерево источника
  продолжится другими работами, и позже снимать его состояние было бы уже
  поздно. Поэтому каталоги всех голов, ждущих этого источника, заводятся в этот
  момент. Отдельных каталогов-снимков нет. Если голова потом пропущена
  условием, её каталог снимается.
- **`copy`.** Каталог источника копируется целиком, кроме служебных каталогов
  движка. Фильтр игнорирования к засеву не применяется: он действует только при
  копировании каталога запуска. Где файловая система умеет клонировать файлы
  (APFS `clonefile`, reflink), копия делается клонированием.
- **`worktree`.** `git worktree add --detach` на коммит якоря источника, затем
  поверх — всё содержимое каталога источника, кроме `.git`. Индекс совпадает с
  отслеживаемым состоянием якоря, неотслеживаемое и игнорируемое лежит на
  месте. Вложенные репозитории (`project.nested_repos`) переносятся так же,
  каждый своим worktree.
- **Отступление к якорю.** Если каталога источника нет (после `burnex gc`, при
  `resume` с удалённым каталогом исходного прогона), дерево засевается якорем,
  как сейчас засевается развилка. Запись работы называет способ:
  `seed: anchor` и причину.

Альтернатива — переносить только якорь, как сейчас у развилки. Отвергнута:
работа, зависящая от сборки, получала бы дерево без сборки, а результат
зависел бы от формы графа.

### 4. Сериализация работ одного дерева

Планировщик считает дерево ресурсом: готовая работа ждёт, пока её дерево
занято. Среди ждущих первой идёт объявленная раньше. `limits.concurrency`
ограничивает общее число работ, а фактическая параллельность не превышает
числа одновременно занятых деревьев.

Линт предупреждает о паре работ одного дерева без пути между ними в графе: то,
что каждая увидит в дереве, задаёт порядок объявления, а не `needs`. Ошибкой
это не делается: две проверки или отчёт в общем дереве — обычный случай, и
требовать для них `needs` значило бы заставлять писать ложные зависимости.

### 5. Деревья не сливаются

Работа, зависящая от работы другого дерева, получает её выходы
(`jobs.<id>.output`), статус и артефакты, но не файлы. Код приносится явно:
`burnex merge-lanes`, `burnex apply` или шагом пайплайна.

### 6. Дорожки

`lane` остаётся учётной меткой. Пайплайн с параллельными дорожками объявляет
деревья дорожек сам (`trees: [main, lane-a, lane-b]`) или берёт `scope: job`.
`merge-lanes` и `apply --lane` читают каталог из записи работы.

### 7. Раскладка

`<base>/trees/<tree>/` — объявленные деревья, `<base>/jobs/<job>/` — `own` и
работы при `scope: job`. `<base>` — это `workspace.path` или
`<run_dir>/workspace`. `gc`, `apply` и витрина берут путь из записи работы.

### 8. Сессии

- **`defend`.** Форк сессии имплементатора допустим, только если работа
  имплементатора и работа шага `review` исполняются в одном дереве. Иначе
  защитник свежий с причиной `other_tree` — это обычный исход, а не сбой. Линт
  предупреждает, если деревья статически разные. При `scope: job` это любой
  имплементатор из другой работы.
- **`session_group`.** Все работы группы — в одном дереве. При `scope: job`
  группа из нескольких работ — ошибка линта.

### 9. Возобновление

Возобновление идёт по деревьям. Для каждого дерева берётся его каталог из
исходного прогона, а если каталога нет — каталог заводится заново от
источника. Затем каталог восстанавливается по якорю последнего
переиспользованного шага этого дерева, как сейчас по правилу «Рабочее дерево
восстанавливается по якорю».

При `scope: run` это одно восстановление на дерево, без сборки состояния из
каталогов разных работ. Восстанавливается только отслеживаемое (вариант «а»).
Игнорируемые и неотслеживаемые следы работ, шедших после точки возобновления,
остаются в каталоге и могут повлиять на переисполняемые работы. Это
документируется. Чистое восстановление — будущий флаг `--clean`.

### 10. Журнал

Запись работы в `status.json` получает:

- `tree` — идентификатор дерева или `own`;
- у работы, для которой заведён каталог, — `seed`: `{ from: <работа> | none, by: copy | anchor, reason? }`;
- у остальных — `continued: true`.

Прежнее `inherited_from` заменяется на `seed.from`. Версия формата журнала
поднимается, записи без `tree` читаются как раньше.

## Risks / Trade-offs

- **[Ломающее изменение умолчания]** → Пайплайны в `worktree` и `copy`, которые
  держались на изоляции развилки, начнут делить дерево и исполняться по
  очереди. Митигация: предупреждение линта о независимых работах в одном
  дереве; пайплайнам с изоляцией по замыслу достаточно `scope: job`.
- **[Диск и время засева]** → Полный перенос копирует `node_modules` и сборку
  в каждый новый каталог. Митигация: клонирование файлов там, где ФС умеет; при
  `scope: run` новые каталоги появляются только у объявленных деревьев.
- **[Следы при `resume`]** → Вариант «а» оставляет игнорируемое содержимое
  поздних работ. Это осознанный выбор ради скорости, документируется.
- **[Независимые работы видят изменения друг друга]** → В общем дереве вторая
  по объявлению работа видит правки первой. Предупреждение линта и
  документированный порядок.

## Migration Plan

1. Влить `dependent-job-workspace` и `review-defend` в основные спецификации.
2. Реализовать изменение одной поставкой.
3. В корневом репозитории: измерительные пайплайны — `scope: job`,
   `self-improve.yml` и `measure-improvement.yml` — деревья дорожек или
   `scope: job`; `burnex lint` по всем пайплайнам корня без ошибок.
4. Откат — возврат версии движка. Журналы нового формата старый движок не
   читает, поэтому `resume` прогонов нового движка после отката невозможен.
