## Context

Выбор агента шага сегодня — четыре независимых поля (`agent`, `model`,
`model_tier`, `effort`), разрешаемых по слоям: документ (шаг → работа →
корень пайплайна) и пользователь (`defaults.*` → `pipeline_agents` →
`step_agents`), с рангом по `agent_policy` (`pipeline-definition`, «Ранг
выбора пользователя задаётся политикой»). `agent` — всегда имя бэкенда.
Уровни модели (`model_tiers`) — у каждого бэкенда свои.

Изменение — первый из пяти этапов стратегий ревью (профили → стратегия и
режим `independent` → режим `discussion` → экран стратегий → чат обсуждения
в прогоне). Стратегия будет ссылаться на ревьюеров и агрегатора по профилю,
поэтому профиль должен быть понятием движка, а не витрины.

## Goals / Non-Goals

**Goals:**

- Именованная связка «бэкенд + модель/уровень + effort + контекст», на
  которую можно сослаться из любого слоя выбора.
- Нулевая разница для конфигураций без `agents:` — тот же шаг и тот же ключ.
- Происхождение выбора наблюдаемо так же, как сегодня, плюс имя профиля.

**Non-Goals:**

- Стратегии ревью, шаг `review:`, локальные профили внутри файла стратегии —
  следующие изменения. Формат записи профиля выбирается так, чтобы стратегия
  переиспользовала его без изменений.
- Наследование профилей друг от друга (`extends`). Не нужно ни одному
  известному сценарию.
- Права (`permissions`) и MCP-серверы в профиле. Это свойства шага, а не
  агента: ревьюер и исполнитель одного профиля нуждаются в разных правах.

## Decisions

### 1. Профиль — запись `agents.<имя>` конфигурации

```yaml
agents:
  reviewer-strict:
    backend: codex
    model_tier: max
    effort: high
    context:
      - text: "Ты строгий ревьюер безопасности."
      - path: guides/security.md
```

Поля: `backend` обязателен; `model` и `model_tier` взаимоисключающие (тот же
отказ, что у записи выбора); `effort` и `context` необязательны. `context`
принимает те же записи, что `context` шага (`path`, глоб, `text`,
`knowledge`), той же схемой.

Имя — `^[a-z][a-z0-9_-]*$`, как имя уровня модели. Слияние слоёв — по
профилю целиком, а не по листьям: проектный `agents.x` заменяет глобальный
`agents.x`. Альтернатива «по листьям», как у `pipeline_agents`, отвергнута:
склейка `backend` из одного файла с `context` из другого даёт агента,
которого не объявлял никто, а путь контекста к тому же разрешается от слоя
(решение 5).

### 2. `default` — единственный встроенный профиль, бэкенд — неявный профиль

`default` — представление `defaults.agent/model/effort`, хранение прежнее,
миграции нет. `agents.default` отклоняется разбором: два места объявления
одного значения рассогласуются.

Каждый подключённый бэкенд `B` — неявный профиль `{ backend: B }` без модели,
effort и контекста. Так `agent: claude` сохраняет смысл, а поле `agent` везде
означает «имя профиля» без второго пространства имён. Профиль с именем
бэкенда (подключённого или поставляемого) отклоняется разбором: иначе
`agent: claude` молча сменил бы смысл после чьей-то правки конфигурации.

Альтернатива — отдельное поле `profile:` рядом с `agent:` — отвергнута: два
поля об одном и том же и вопрос «кто главнее», который пришлось бы решать в
каждом слое.

### 3. Профиль раскрывается в том слое, который его назвал

Разрешение остаётся прежним по полям и рангам. Меняется одно: слой, чьё
`agent` названо профилем, считается объявившим также `model` / `model_tier` /
`effort` профиля — в тех полях, которые он не объявил сам. Агент шага —
`backend` профиля.

Пример: `step_agents.p.review.check: { agent: reviewer-strict }` при
`agent_policy: force`, шаг объявляет `model: opus`. Агент — `codex` от
`step_agents`; модель — по существующему правилу «выбор модели слоя
пользователя заменяет выбор документа целиком»: `step_agents` слабее шага при
`force`, поэтому модель из шага — `opus`, а она чужая codex и отбрасывается
существующим правилом, после чего берётся `model_tier: max` профиля. То есть
новых правил старшинства нет: профиль лишь «дописывает» слой.

Почему не отдельный слой «profile» с собственным рангом: ранг пришлось бы
вписать в обе последовательности политики, и пользователь объяснял бы себе
три вида слоёв вместо двух. Привязка к назвавшему слою сохраняет простое
правило «значение пришло оттуда, где назван профиль».

Неизвестное имя в поле `agent` — тот же отказ, что сегодня для неизвестного
бэкенда, с перечнем профилей и бэкендов в подсказке.

### 4. Контекст профиля — уровень «профиль» перед пайплайном

Порядок сборки: профиль → пайплайн → работа → шаг → блок предшественников.
Уровень профиля:

- не снимается `context_inherit: false` и не фильтруется `context_exclude` —
  пользователь просил «всегда при старте этого агента», а наследование
  описывает иерархию документа, к которой профиль не относится;
- подчиняется `context.deny` и `context.max_tokens` — это границы
  безопасности и бюджета, не вкуса;
- в `context.json` записи имеют источник `profile:<имя>`;
- в сессии, продолжающей диалог, отправляется один раз, как общий контекст.

### 5. Пути контекста профиля разрешаются от слоя

Относительный путь в профиле проектного файла — от корня репозитория (как
пути секции знания). В профиле глобального файла — от `~/.burnex/`;
абсолютные пути и `~/` принимаются в обоих. Файлы глобального профиля обычно
лежат вне рабочего дерева, поэтому их содержимое не входит в отпечаток
входов работы: ключ шага MUST включать отпечаток содержимого файлов контекста
профиля, лежащих вне дерева, иначе правка `~/.burnex/guides/security.md` не
инвалидирует переиспользуемый шаг.

### 6. Происхождение и замок

Происхождение агента/модели/effort получает необязательное имя профиля рядом
со слоем: «агент — `step_agents` через профиль `reviewer-strict`, модель —
`tier` через профиль». `pipeline.lock` печатает имя профиля шага и итоговые
значения. Имя профиля в ключ шага не входит — ключ уже содержит итоговых
агента, модель и контекст; переименование профиля без смены содержимого
переиспользования не ломает.

### 7. Витрина: вкладка Profiles

Пятая вкладка `profiles` экрана «Agents» (`/agents/profiles`). Список: `default`
сверху ссылкой на вкладку Default, затем профили по имени с пометкой файла
(глобальный / проектный) и строкой «используется в: …» по данным вкладки
Policy. Правка — форма: имя, бэкенд, модель или уровень (переключатель),
effort, редактор записей контекста (текст / путь). Сохраняет витрина только
глобальные профили — тем же путём, что Default/Backends/Tiers; проектные
показаны только для чтения, как проектные значения на других вкладках.
Комбобоксы выбора агента (Policy, диалог запуска) перечисляют профили
группой над бэкендами.

### 7a. Наперёд: адресация участников стратегии

Для этапа 2 зафиксировано: `step_agents.<p>.<job>.<step>` у шага `review:`
выбирает агента агрегатору (его вердикт — выход шага), а участник-ревьюер
адресуется ключом `step_agents.<p>.<job>.<step>/<reviewer>`. В этом
изменении не реализуется; упомянуто, чтобы формат ключей `step_agents` здесь
не закрыл эту возможность (символ `/` в ключе записи шага сейчас допустим).

## Risks / Trade-offs

- [Контекст профиля незаметно раздувает каждый шаг] → источник
  `profile:<имя>` в `context.json` и в превью контекста; `max_tokens` шага
  считает и его.
- [Профиль, удалённый из конфигурации, ломает пайплайны, которые на него
  ссылаются] → отказ раскрытия называет имя, файл и путь ключа; вкладка
  Profiles предупреждает об использовании перед удалением.
- [Глобальный профиль с путями вне дерева непереносим между машинами] →
  осознанно: глобальный файл и так машинный; проектный профиль для
  командного использования разрешает пути от корня репозитория.
- [`agent` теперь может значить профиль — старые сообщения «известны:
  бэкенды» вводят в заблуждение] → все тексты отказов перечисляют профили и
  бэкенды раздельно.

## Migration Plan

Миграции нет: `agents:` новый необязательный ключ, `default` хранится там же.
Откат — удаление ключа `agents:`; пайплайны, ссылающиеся на профили, тогда
отказывают на раскрытии названно.
