# workspace-modes Specification

## Purpose
Режимы рабочей директории `cwd`, `worktree` и `copy`, правила их выбора и переопределения работой, жизненный цикл изолированных деревьев после прогона, возврат результата командой `burnex apply`.
## Requirements
### Requirement: Режим рабочей директории объявляется и переопределяется

Пайплайн SHALL объявлять режим рабочей директории значением `cwd`, `worktree`
или `copy` с умолчанием `cwd`. Работа MAY переопределить режим для себя. Режим
MUST разрешаться до начала работы, а разрешённый режим и путь рабочей
директории MUST записываться в манифест и состояние прогона.

#### Scenario: Умолчание

- **WHEN** пайплайн не объявляет режим рабочей директории
- **THEN** работы исполняются в каталоге запуска

#### Scenario: Переопределение работой

- **WHEN** пайплайн объявляет `cwd`, а работа объявляет `worktree`
- **THEN** эта работа исполняется в отдельном git worktree, а остальные — в каталоге запуска

#### Scenario: Режим виден в состоянии

- **WHEN** прогон начался
- **THEN** состояние прогона содержит режим и путь рабочей директории каждой работы

### Requirement: Режим worktree изолирует работу от текущего дерева

В режиме `worktree` система SHALL создавать на каждую работу отдельный git
worktree, ответвлённый от текущей позиции `HEAD`. Незакоммиченные изменения
рабочего дерева проекта MUST NOT попадать в него. Работы MUST NOT видеть
изменения друг друга через файловую систему. Режим MUST отклоняться до начала
прогона, если проект не является репозиторием git, — с указанием причины и
предложением режима `copy`.

#### Scenario: Ответвление от HEAD

- **WHEN** работа исполняется в режиме `worktree`
- **THEN** её рабочая директория содержит состояние проекта на текущей позиции `HEAD`

#### Scenario: Незакоммиченные изменения не переносятся

- **WHEN** в дереве проекта есть незакоммиченные изменения, а работа исполняется в режиме `worktree`
- **THEN** в её рабочей директории этих изменений нет

#### Scenario: Изоляция работ друг от друга

- **WHEN** две работы исполняются в режиме `worktree` и первая изменила файл
- **THEN** рабочая директория второй этого изменения не содержит

#### Scenario: Проект не под git

- **WHEN** объявлен режим `worktree`, а проект не является репозиторием git
- **THEN** прогон завершается ошибкой конфигурации до запуска работ
- **AND** сообщение называет причину и предлагает режим `copy`

### Requirement: Режим copy работает вне git и с незакоммиченным

В режиме `copy` система SHALL копировать рабочее дерево проекта в директорию
работы, пропуская пути, подпадающие под правила игнорирования, и служебный
каталог git. Копия MUST включать незакоммиченные изменения. Расположение копий
по умолчанию MUST находиться внутри директории прогона и MAY переопределяться
объявленным путём.

#### Scenario: Незакоммиченные изменения попадают в копию

- **WHEN** в дереве проекта есть незакоммиченные изменения, а работа исполняется в режиме `copy`
- **THEN** её рабочая директория содержит эти изменения

#### Scenario: Игнорируемые пути не копируются

- **WHEN** дерево содержит каталог, подпадающий под правила игнорирования
- **THEN** в копии его нет

#### Scenario: Копия вне git

- **WHEN** проект не является репозиторием git, а объявлен режим `copy`
- **THEN** прогон исполняется, а состояние дерева фиксируется хеш-манифестом

#### Scenario: Явный путь размещения копий

- **WHEN** объявлен путь размещения рабочих копий
- **THEN** копии создаются по нему, а не внутри директории прогона

### Requirement: Пригодность режима проверяется до первой работы

Возможность подготовить рабочую директорию в объявленном режиме SHALL
проверяться один раз до запуска первой работы: наличие репозитория git для
режима `worktree`, доступность на запись места размещения для режима `copy`.
Непригодность режима MUST быть ошибкой конфигурации до исполнения шагов, а не
отказом работы посреди прогона.

#### Scenario: Непригодность обнаружена заранее

- **WHEN** объявленный режим невозможно подготовить в текущем окружении
- **THEN** прогон завершается ошибкой конфигурации до запуска первой работы
- **AND** ни один шаг не исполнен

#### Scenario: Проверка выполняется однократно

- **WHEN** пайплайн содержит несколько работ в изолированном режиме
- **THEN** пригодность режима проверена до первой из них, а не при подготовке каждой

### Requirement: Журнал прогона отделён от рабочей директории

Директория прогона SHALL располагаться вне рабочей директории работы при любом
режиме. Шаги MUST NOT видеть журнал прогона как часть своего рабочего дерева, и
запись журнала MUST NOT изменять `tree_id` работы.

#### Scenario: Журнал не попадает в дерево

- **WHEN** работа исполняется в режиме `copy` с копией внутри директории прогона
- **THEN** файлы журнала прогона не входят в фиксируемое состояние рабочего дерева

### Requirement: Изолированные деревья сохраняются после прогона

Рабочие деревья режимов `worktree` и `copy` SHALL сохраняться после завершения
прогона. Их пути MUST записываться в состояние прогона. По завершении прогона в
изолированном режиме система MUST сообщать путь рабочего дерева и команду
возврата результата.

#### Scenario: Дерево доступно после прогона

- **WHEN** прогон в изолированном режиме завершился
- **THEN** рабочая директория каждой работы существует, а её путь есть в состоянии прогона

#### Scenario: Подсказка о возврате результата

- **WHEN** прогон в изолированном режиме завершился
- **THEN** вывод содержит путь рабочего дерева и команду наложения результата на текущее дерево

### Requirement: Команда apply возвращает результат в текущее дерево

Команда `stepcast apply <run-id>` SHALL накладывать изменения, произведённые
прогоном, на текущее рабочее дерево проекта. Ключ `--job` MUST ограничивать
наложение одной работой. Изменение MUST вычисляться из якорей дерева, а не из
состояния каталога на момент вызова. При конфликте наложения команда MUST
завершаться ошибкой, не оставляя частично наложенных изменений, и называть
конфликтующие пути.

Наложение результата прогона, снятого составным способом, MUST отклоняться с
причиной, называющей этот способ: изменение такого прогона складывается из
частей, снятых в разных базах объектов, и наложение по репозиторию — отдельная
возможность. Отказ MUST NOT называть отсутствие git: дерево составного прогона
целиком принадлежит репозиториям. Итог прогона в изолированном режиме MUST
называть пути рабочих деревьев и MUST NOT предлагать наложение там, где оно
отклоняется.

#### Scenario: Наложение результата прогона

- **WHEN** пользователь вызывает наложение для завершившегося прогона в режиме `worktree`
- **THEN** изменения прогона появляются в текущем рабочем дереве проекта

#### Scenario: Наложение одной работы

- **WHEN** вызов ограничен одной работой
- **THEN** накладываются только изменения этой работы

#### Scenario: Конфликт

- **WHEN** текущее дерево изменено так, что наложение невозможно
- **THEN** команда завершается ненулевым кодом и перечисляет конфликтующие пути
- **AND** текущее дерево остаётся неизменным

#### Scenario: Наложение в режиме cwd

- **WHEN** прогон исполнялся в режиме `cwd`
- **THEN** команда сообщает, что результат уже на месте, и ничего не изменяет

#### Scenario: Наложение составного прогона

- **WHEN** пользователь вызывает наложение для прогона, снятого составным способом
- **THEN** команда отказывает с причиной, называющей составной способ фиксации, и не трогает текущее дерево

#### Scenario: Итог составного прогона не предлагает наложения

- **WHEN** составной прогон в изолированном режиме завершился
- **THEN** вывод содержит пути рабочих деревьев и не содержит команды наложения

### Requirement: Отказ подготовки изолированной директории снимает заведённое

При отказе подготовки рабочей директории в режимах `worktree` и `copy` система SHALL снять всё, что подготовка успела завести, в порядке, обратном заведению: части вложенных репозиториев в обратном порядке, затем корень. Отказ самого снятия MUST записываться событием `bookkeeping.failed` с именем операции и MUST NOT подменять причину отказа подготовки. При успешной подготовке зарегистрированные операции снятия MUST NOT исполняться ни при каком исходе работы: изолированное дерево сохраняется после прогона.

#### Scenario: Отказ на второй части

- **WHEN** корень и первая часть заведены, а заведение второй части отказало
- **THEN** первая часть и корень сняты в этом порядке, а работа отказала причиной заведения второй части

#### Scenario: Отказ снятия записан

- **WHEN** при откате подготовки снятие части отказало
- **THEN** в журнале событие `bookkeeping.failed` с именем операции и работой, а причина отказа работы — исходная

#### Scenario: Успешная подготовка ничего не снимает

- **WHEN** подготовка прошла, а работа затем отказала
- **THEN** её рабочее дерево на месте

### Requirement: Объявленный состав вложенных репозиториев проверяется до первой работы

Пригодность объявленного состава вложенных репозиториев SHALL проверяться один раз до запуска первой работы, а непригодность MUST быть ошибкой конфигурации, а не отказом бухгалтерии посреди прогона.

Проверка MUST убеждаться, что корень рабочего дерева — репозиторий git, что
каждый объявленный каталог существует, что он является рабочим деревом git и
что он является деревом собственного репозитория, а не подкаталогом корневого.
Сообщение MUST называть каталог и причину: три случая — несуществующий
каталог, каталог вне git и обычный подкаталог корня — MUST различаться, потому
что чинятся они по-разному, а последний иначе означал бы двойной учёт
содержимого корня.

Проверка MUST отклонять и объявленный каталог, который корневой репозиторий
не сможет обойти при снятии якоря: вложенный репозиторий без единого коммита
корневой git ссылкой на коммит не встраивает, а отказывает целиком, и якорь
не снялся бы вовсе. Отказ MUST относиться только к тем частям, до которых
корень действительно доходит: часть, которую он игнорирует, в его обход не
попадает и своим репозиторием снимается без коммита — отклонять её MUST NOT.

#### Scenario: Объявленный каталог без единого коммита

- **WHEN** объявленный каталог является репозиторием git без единого коммита и корневым репозиторием не игнорируется
- **THEN** прогон завершается ошибкой конфигурации до запуска первой работы, называющей каталог и причину

#### Scenario: Игнорируемая корнем часть без коммита допустима

- **WHEN** объявленный каталог является репозиторием git без единого коммита, но игнорируется корневым репозиторием
- **THEN** прогон начинается обычным порядком

#### Scenario: Объявленный каталог отсутствует

- **WHEN** объявлен вложенный репозиторий, каталога которого в дереве нет
- **THEN** прогон завершается ошибкой конфигурации до запуска первой работы, называющей каталог

#### Scenario: Объявленный каталог не репозиторий

- **WHEN** объявленный каталог существует, но рабочим деревом git не является
- **THEN** прогон завершается ошибкой конфигурации, называющей каталог и причину

#### Scenario: Объявлен подкаталог корневого репозитория

- **WHEN** объявленный каталог принадлежит корневому репозиторию, а не собственному
- **THEN** прогон завершается ошибкой конфигурации, называющей каталог и его репозиторий

#### Scenario: Корень вне git

- **WHEN** состав объявлен в дереве, которое само репозиторием git не является
- **THEN** прогон завершается ошибкой конфигурации до запуска первой работы

#### Scenario: Пригодный состав не мешает прогону

- **WHEN** все объявленные каталоги существуют и являются отдельными репозиториями
- **THEN** прогон начинается обычным порядком

### Requirement: Наложение составного результата идёт по репозиториям

`stepcast apply` SHALL накладывать результат составного прогона по репозиториям — по вызову на корень и на каждый объявленный вложенный репозиторий, состояние которого прогон изменил, — вместо отказа «накладывать нужно по репозиторию».

Правило MUST быть одним для всех входов команды: прогон целиком, `--job` и
ограничение дорожкой, которым пользуется сведение, — разница между ними лишь в
том, между какой парой состояний считается дифф. Патч каждой части MUST
считаться и накладываться в её собственном каталоге, путями от её корня.
Конфликт на любом репозитории MUST возвращать все затронутые к состоянию до
наложения и MUST называть конфликтующие пути — частично наложенного составного
результата MUST NOT оставаться. Форма идентификатора составного состояния MUST
разбираться единственным местом движка — тем же, которое её порождает, — и
принадлежность разобранного состояния действующему составу MUST проверяться:
состояние, снятое на другом составе, MUST быть отказом, называющим
расхождение, а не наложением чужой части в сегодняшнюю. Итог `stepcast run`
для составного прогона MUST снова предлагать команду наложения.

#### Scenario: Наложение составного прогона

- **WHEN** пользователь вызывает наложение для завершившегося составного прогона в режиме `worktree`
- **THEN** изменения появляются и в корне, и в каждом объявленном вложенном репозитории дерева проекта

#### Scenario: Конфликт в одном из репозиториев

- **WHEN** патч одного из затронутых репозиториев не лёг
- **THEN** команда завершается ошибкой, называя конфликтующие пути, а все затронутые репозитории остаются в состоянии до наложения

#### Scenario: Состав изменился после прогона

- **WHEN** состояния сняты на одном составе вложенных репозиториев, а наложение идёт при другом
- **THEN** команда отказывает, называя расхождение составов, и дерева не касается

#### Scenario: Итог прогона предлагает наложение

- **WHEN** составной прогон завершился в изолированном режиме
- **THEN** итог печатает пути рабочих деревьев и команду наложения, а не причину, по которой наложение недоступно

### Requirement: Изолированное дерево получает объявленные вложенные репозитории

Рабочее дерево работы в изолированном режиме `worktree` при объявленном составе вложенных репозиториев SHALL содержать каждый объявленный каталог, а каждый такой каталог MUST быть отдельным рабочим деревом собственного репозитория этой части.

Состоянием части MUST быть `HEAD` её собственного репозитория: незакоммиченные
изменения рабочего дерева части в дереве работы MUST NOT появляться — то же
правило, что у корня. Состояние части MUST NOT выводиться из ссылки на коммит,
которую хранит корневой репозиторий: у части, которую корень игнорирует, такой
ссылки нет вовсе.

Заведение частей MUST NOT изменять ни рабочее дерево части в проекте, ни
рабочее дерево корневого репозитория: ни его файлы, ни его индекс, ни его
`HEAD`.

Части MUST быть готовы до первого шага работы — шаг MUST NOT заставать дерево
без объявленной части.

Порядок заведения MUST определяться самим составом, а не тем, в каком порядке
его перечислили: часть, объявленная внутри другой объявленной части, MUST
заводиться после объемлющей — иначе объемлющая выкладывалась бы в непустой
каталог.

#### Scenario: Объявленная часть материализована

- **WHEN** объявлен вложенный репозиторий `public-site`, а работа исполняется в режиме `worktree`
- **THEN** каталог `public-site` в рабочем дереве работы содержит состояние этого репозитория на его `HEAD`
- **AND** является рабочим деревом git собственного репозитория этой части

#### Scenario: Незакоммиченное части не переносится

- **WHEN** в рабочем дереве объявленной части есть незакоммиченные изменения, а работа исполняется в режиме `worktree`
- **THEN** в её каталоге в дереве работы этих изменений нет

#### Scenario: Деревья проекта не тронуты

- **WHEN** работа в режиме `worktree` подготовила дерево с объявленными частями
- **THEN** рабочее дерево каждой части в проекте и рабочее дерево корневого репозитория остались в прежнем состоянии

#### Scenario: Правка внутри части видна границам правок

- **WHEN** шаг работы изменил файл `src/api.ts` внутри объявленной части `public-site`
- **THEN** сравнение якорей шага даёт путь `public-site/src/api.ts`

#### Scenario: Дорожки не видят правок друг друга и внутри частей

- **WHEN** две работы в режиме `worktree` исполняются одновременно и первая изменила файл внутри объявленной части
- **THEN** дерево второй этого изменения не содержит

#### Scenario: Порядок объявления состава не влияет на заведение

- **WHEN** объявлены каталоги `a` и `a/b`, причём `a/b` назван в составе первым
- **THEN** обе части материализованы, и каждая является рабочим деревом своего репозитория

### Requirement: Подготовка изолированного дерева атомарна

Отказ при заведении любой части SHALL снимать всё, что эта подготовка успела завести, а работа MUST отказывать прежней причиной невозможности подготовить рабочую директорию.

Снятие MUST охватывать и заведённые части, и корневое дерево работы, и учётные
записи всех заведённых рабочих деревьев. Наполовину составленного дерева
MUST NOT оставаться ни на диске, ни в учёте репозиториев, которым части
принадлежат.

#### Scenario: Отказ на второй части

- **WHEN** первая объявленная часть заведена, а заведение второй отказало
- **THEN** работа отказывает с названной причиной, а каталога работы и учётных записей обеих частей не остаётся

#### Scenario: Отказ не мешает остальным работам

- **WHEN** подготовка дерева одной работы отказала
- **THEN** деревья остальных работ прогона и их части не тронуты

### Requirement: Наследование дерева переносит объявленные части

Наследование дерева зависимой работой при объявленном составе SHALL переносить объявленные части наравне с корнем.

Работа, продолжающая каталог предшественника, MUST получать заведённые в нём
части как есть и MUST NOT заводить их заново. Работа, которой каталог
заводится заново (развилка), MUST получать полное дерево — корень и все
объявленные части, — приведённое к состоянию источника; приведение каждой
части MUST выполняться средствами её собственного репозитория.

#### Scenario: Продолжение цепочки

- **WHEN** работа продолжает каталог предшественника в дереве с объявленными частями
- **THEN** части на месте, а их содержимое — результат предшественника

#### Scenario: Развилка приводит части к состоянию источника

- **WHEN** работе заводится собственное дерево, наследующее состояние работы, изменившей файл внутри объявленной части
- **THEN** этот файл в её дереве содержит изменение источника

### Requirement: Пригодность изолированного режима при объявленном составе проверяется до первой работы

Пригодность объявленного состава для изолированного режима SHALL проверяться один раз до запуска первой работы, а непригодность MUST быть ошибкой конфигурации с указанием работы, режима и причины.

Отдельными сообщениями MUST различаться: режим `copy` при объявленном составе
(копия не содержит служебного каталога git, и часть в ней была бы каталогом без
репозитория), объявленная часть без единого коммита (отделить рабочее дерево от
несуществующего `HEAD` нечем) и объявленная часть, по чьему пути корневой
репозиторий отслеживает файлы (выкладка корня займёт каталог).

Требование коммита в изолированном режиме MUST относиться к каждой объявленной
части независимо от того, игнорирует ли её корневой репозиторий.

Тот же случай MUST выявляться статической проверкой пайплайна: прогон,
минующий её, MUST отказывать до первой работы, а не при подготовке директории.

#### Scenario: Режим copy при объявленном составе

- **WHEN** объявлены вложенные репозитории, а работа объявляет `workspace.mode: copy`
- **THEN** прогон завершается ошибкой конфигурации до первой работы, называющей работу, режим `copy` и его собственную причину

#### Scenario: Часть без коммита в изолированном режиме

- **WHEN** объявленная часть не имеет ни одного коммита, а работа объявляет режим `worktree`
- **THEN** прогон завершается ошибкой конфигурации до первой работы, называющей каталог и причину
- **AND** отказ наступает и тогда, когда корневой репозиторий эту часть игнорирует

#### Scenario: Корень отслеживает файлы по пути части

- **WHEN** корневой репозиторий отслеживает файлы внутри каталога объявленной части, а работа объявляет режим `worktree`
- **THEN** прогон завершается ошибкой конфигурации до первой работы, называющей каталог и причину

#### Scenario: Статическая проверка называет то же самое

- **WHEN** `stepcast lint` разбирает пайплайн с режимом `copy` при объявленном составе
- **THEN** он сообщает об ошибке, называя работу и её режим

#### Scenario: Пригодный состав в изолированном режиме прогону не мешает

- **WHEN** все объявленные части существуют, имеют коммиты и являются отдельными репозиториями, а работы объявляют режим `worktree`
- **THEN** прогон начинается обычным порядком

#### Scenario: Режим каталога запуска не меняется

- **WHEN** объявлены вложенные репозитории, а работа исполняется в каталоге запуска
- **THEN** поведение прогона совпадает с прежним во всём, включая допустимость части без коммита, игнорируемой корнем
