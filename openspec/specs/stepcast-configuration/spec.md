## Purpose

Разрешение конфигурации из глобального и проектного файлов, флагов и встроенных умолчаний; складывающиеся снизу запреты `env_deny` и `context.deny`; потолки `limits`; отчёт о происхождении значений.
## Requirements
### Requirement: Разрешение конфигурации из двух файлов

Система SHALL собирать действующую конфигурацию из встроенных умолчаний,
глобального файла `~/.burnex/config.yml`, проектного файла `.burnex/config.yml` и
флагов командной строки. Каждый следующий источник MUST перекрывать
предыдущий. Отсутствие любого из файлов MUST NOT быть ошибкой.

#### Scenario: Проектный конфиг перекрывает глобальный

- **WHEN** в глобальном конфиге `defaults.model: sonnet`, а в проектном `defaults.model: opus`
- **THEN** действующее значение `defaults.model` равно `opus`

#### Scenario: Флаг перекрывает оба файла

- **WHEN** оба конфига задают `defaults.model`, а запуск выполнен с `--model haiku`
- **THEN** действующее значение `defaults.model` равно `haiku`

#### Scenario: Конфигов нет

- **WHEN** ни `~/.burnex/config.yml`, ни `.burnex/config.yml` не существуют
- **THEN** система работает на встроенных умолчаниях без ошибки

### Requirement: Запреты складываются и не отменяются снизу

Списки `env_deny` и `context.deny` SHALL объединяться со всех уровней —
глобального конфига, проектного конфига и пайплайна. Нижний уровень MUST NOT
иметь возможности удалить шаблон, объявленный выше.

#### Scenario: Пайплайн добавляет запрет

- **WHEN** глобальный конфиг задаёт `env_deny: ["AWS_*"]`, а пайплайн `env_deny: ["FOO_*"]`
- **THEN** действуют оба шаблона

#### Scenario: Пайплайн не может снять запрет

- **WHEN** глобальный конфиг задаёт `env_deny: ["AWS_*"]`, а пайплайн задаёт пустой `env_deny: []`
- **THEN** шаблон `AWS_*` остаётся действующим

### Requirement: Потолки limits ограничивают пайплайн

Значения `limits` из конфигурации SHALL задавать верхнюю границу для
соответствующих значений пайплайна, включая денежный потолок `limits.cost`.
Пайплайн, превышающий потолок, MUST отклоняться с ошибкой, а не урезаться
молча. Значения `limits` MUST оставаться границей для объявляемого и MUST NOT
применяться как самостоятельный потолок прогона.

#### Scenario: Бюджет пайплайна выше потолка

- **WHEN** конфиг задаёт `limits.tokens: 5M`, а пайплайн `budget.tokens: 8M`
- **THEN** `stepcast lint` завершается ошибкой с указанием обоих значений
- **AND** `stepcast run` не начинает прогон

#### Scenario: Число попыток выше потолка

- **WHEN** конфиг задаёт `limits.attempts: 5`, а шаг `attempts.max: 9`
- **THEN** `stepcast lint` завершается ошибкой

#### Scenario: Денежный потолок выше потолка проекта

- **WHEN** конфиг задаёт `limits.cost: "$50"`, а пайплайн `budget.cost: 200`
- **THEN** `stepcast lint` завершается ошибкой с указанием обоих значений
- **AND** `stepcast run` не начинает прогон

#### Scenario: Денежный потолок проекта не ограничивает прогон сам по себе

- **WHEN** пайплайн не объявляет `budget.cost`, а конфиг задаёт `limits.cost`
- **THEN** прогон исполняется без денежного потолка

### Requirement: Проектный конфиг не содержит машинно-зависимых значений

Ключи `runs.root` и `backends.*.command` SHALL приниматься только в глобальном
конфиге. Их присутствие в проектном конфиге MUST быть ошибкой.

#### Scenario: Путь к бэкенду в проектном конфиге

- **WHEN** `.burnex/config.yml` содержит `backends.claude.command`
- **THEN** система завершается с ошибкой конфигурации и называет запрещённый ключ

### Requirement: Происхождение значений наблюдаемо

Команда `burnex config` SHALL печатать действующую конфигурацию, указывая для
каждого значения источник, из которого оно получено. Для складывающихся списков
вывод MUST показывать вклад каждого источника.

#### Scenario: Отчёт о конфигурации

- **WHEN** пользователь выполняет `burnex config`
- **THEN** для каждого ключа выводится значение и источник — встроенное умолчание, путь к файлу конфигурации или имя флага
- **AND** для `env_deny` выводится число шаблонов из каждого источника

### Requirement: Практика памяти объявляется секцией project.knowledge

Система SHALL принимать секцию `project.knowledge` с ключами `provider`, `command`, `dir`, `rules`, `index_max_tokens`, `stale_after` и `timeout`. Каждый ключ MAY объявляться отдельно, слои сливаются по листьям, и встроенных умолчаний у `provider`, `command`, `dir` и `rules` не MUST быть.

#### Scenario: Объявлен встроенный источник

- **WHEN** проектный конфиг объявляет `provider: fs` и `dir: knowledge`
- **THEN** записи `knowledge:` разрешаются встроенным источником по этому каталогу

#### Scenario: Объявлен собственный источник

- **WHEN** проектный конфиг объявляет `provider: cmd` и `command: node scripts/knowledge.mjs`
- **THEN** записи `knowledge:` разрешаются запуском этой команды, а ключ `dir` источнику не передаётся

#### Scenario: Провайдер cmd без команды

- **WHEN** объявлено `provider: cmd` без ключа `command`
- **THEN** разбор конфигурации отклоняет секцию с диагностикой о недостающей команде

### Requirement: Знание принадлежит репозиторию, а не машине

Система SHALL допускать секцию `project.knowledge` только в `.burnex/config.yml` и отклонять её в `~/.burnex/config.yml` — тем же правилом, каким отклоняются `project.check`, `project.tools` и `project.spec`.

#### Scenario: Объявление в глобальном конфиге

- **WHEN** `~/.burnex/config.yml` содержит секцию `project.knowledge`
- **THEN** разбор конфигурации отклоняет её с диагностикой о недопустимой области объявления

### Requirement: Пути секции знания относительны корню репозитория

Система SHALL проверять `dir` и `rules` той же моделью, что `project.spec.dir` и `project.spec.rules`: непустой относительный путь без сегмента `..`. Пустая строка, строка из пробелов, абсолютный путь и путь с `..` MUST отклоняться разбором конфигурации.

#### Scenario: Абсолютный путь отклонён

- **WHEN** объявлено `dir: /var/knowledge`
- **THEN** разбор конфигурации отклоняет значение

### Requirement: Значения секции знания доступны подстановкой

Система SHALL публиковать значения секции подстановками `${project.knowledge.dir}`, `${project.knowledge.rules}` и `${project.knowledge.provider}` в пайплайне, файлах работ и файлах промптов — тем же правилом, каким публикуются `${project.spec.*}`.

#### Scenario: Правила письма приходят контекстом

- **WHEN** работа объявляет `- path: ${project.knowledge.rules}`
- **THEN** в контекст шага попадает объявленный файл правил

### Requirement: Пайплайн может объявить практику памяти сам

Система SHALL принимать секцию `project.knowledge` верхним ключом `project` документа пайплайна, перекрывающим проектный конфиг полистовым слиянием, — тем же порядком слоёв, каким пайплайн перекрывает `project.check` и `project.spec`.

#### Scenario: Пайплайн переопределяет каталог знания

- **WHEN** конфиг объявляет `dir: knowledge`, а пайплайн — `dir: knowledge/experimental`
- **THEN** записи `knowledge:` этого пайплайна разрешаются по каталогу пайплайна, а прочие ключи секции берутся из конфига

### Requirement: Ключи `pipeline_agents` и `step_agents` задают выбор пользователя по пайплайну и по шагу
Конфигурация SHALL принимать ключ `pipeline_agents.<имя пайплайна>` и ключ `step_agents.<имя пайплайна>.<работа>.<шаг>`, где значение — запись с необязательными полями `agent`, `model`, `model_tier`, `effort` и хотя бы одним из них. Имя пайплайна — поле `name` его документа, работа — идентификатор в карте `jobs:` документа до раскрытия дорожек, шаг — `id` шага. Запись, объявившая одновременно `model` и `model_tier`, и запись с неизвестным полем отклоняются разбором конфигурации с указанием файла и пути ключа. Оба ключа допустимы в глобальном и в проектном файле и сливаются между слоями по листьям.

#### Scenario: Запись пайплайна принимается
- **WHEN** `~/.stepcast/config.yml` содержит `pipeline_agents: { self-improve: { agent: codex, model_tier: deep } }`
- **THEN** конфигурация разрешается без ошибки, и отчёт `stepcast config` называет этот файл источником `pipeline_agents.self-improve.agent`

#### Scenario: Модель и tier в одной записи
- **WHEN** запись `step_agents.p.implement.code` объявляет и `model: sonnet`, и `model_tier: fast`
- **THEN** разбор конфигурации отклоняется с указанием файла и пути `step_agents.p.implement.code`

#### Scenario: Проектный файл перекрывает поле глобальной записи
- **WHEN** глобальный файл объявляет `pipeline_agents.p: { agent: codex, effort: high }`, а проектный — `pipeline_agents.p: { agent: claude }`
- **THEN** действующая запись — `{ agent: claude, effort: high }`, у `agent` источник — проектный файл, у `effort` — глобальный

### Requirement: Политика `agent_policy` выбирает, кто сильнее — документ или пользователь
Конфигурация SHALL принимать ключ верхнего уровня `agent_policy` со значением `force` или `fallback` и SHALL считать его равным `force`, когда он не объявлен ни одним слоем. Ключ допустим в обоих файлах, и ближний слой побеждает. Порядок слоёв, который задаёт каждое значение, определяет требование «Ранг выбора пользователя задаётся политикой `agent_policy`» возможности `pipeline-definition`.

#### Scenario: Умолчание
- **WHEN** ни один файл не объявляет `agent_policy`
- **THEN** отчёт `stepcast config` показывает `agent_policy` равной `force` со встроенным умолчанием в качестве источника

#### Scenario: Неизвестное значение
- **WHEN** файл объявляет `agent_policy: always`
- **THEN** разбор конфигурации отклоняется с указанием файла и ключа `agent_policy`

### Requirement: Запись выбора пользователя не роняет чужие пайплайны
Движок SHALL считать предупреждением, а не ошибкой, запись `step_agents`, которая называет работу или шаг, отсутствующие в пайплайне, или шаг не агентского вида. Запись `pipeline_agents` или `step_agents`, чей `agent` не назван среди бэкендов, SHALL отклонять раскрытие только того пайплайна, к которому запись относится, с указанием файла и пути ключа.

#### Scenario: Запись исчезнувшего шага
- **WHEN** `step_agents.p.old.gone` объявлена, а в пайплайне `p` нет работы `old`
- **THEN** `stepcast run` пайплайна `p` исполняется, а `stepcast config --pipeline` называет запись в списке записей без действия с причиной «шага нет в пайплайне»

#### Scenario: Неизвестный агент в записи другого пайплайна
- **WHEN** `pipeline_agents.other` объявляет `agent: nosuch`, а запускается пайплайн `p`
- **THEN** раскрытие пайплайна `p` проходит без ошибки

#### Scenario: Неизвестный агент в записи своего пайплайна
- **WHEN** `pipeline_agents.p` объявляет `agent: nosuch`, а запускается пайплайн `p`
- **THEN** раскрытие отклоняется с указанием файла конфигурации и пути `pipeline_agents.p.agent`

### Requirement: `stepcast config --pipeline` показывает итоговый выбор и его источник
Команда `stepcast config --pipeline <p>` SHALL раскрыть пайплайн `<p>` (путь к файлу или `stepcast:<имя>`) с действующей конфигурацией и вывести вслед за обычным отчётом действующую политику с её источником и, для каждого агентского шага, агента, модель и effort вместе с источником каждого. Обязательные входы без умолчаний подставляются заглушками. Отброшенная чужая модель выводится вместе со слоем, из которого пришла. Отдельным списком выводятся записи `pipeline_agents` и `step_agents` этого пайплайна, которые не повлияли ни на один шаг, с причиной: проиграли документу при названной политике либо называют отсутствующий шаг.

#### Scenario: Источник у каждого значения
- **WHEN** при `agent_policy: fallback` агента шага `implement/code` дал `pipeline_agents.p`, а модель — `step_agents.p.implement.code`
- **THEN** строка шага `implement/code` называет агента с источником `pipeline_agents` и файлом и модель с источником `step_agents` и файлом

#### Scenario: Проигравшая запись названа
- **WHEN** при `agent_policy: force` запись `step_agents.p.review.check` объявляет `model: sonnet`, а шаг `review/check` объявляет `model: opus`
- **THEN** запись перечислена среди записей без действия с причиной «проиграла шагу (политика force)»

#### Scenario: Поставляемый пайплайн
- **WHEN** выполняется `stepcast config --pipeline stepcast:self-improve` в проекте без файла этого пайплайна
- **THEN** команда раскрывает поставляемый пайплайн и выводит его агентские шаги

### Requirement: Экран Pipelines записывает выбор пользователя в глобальный файл
Экран Pipelines SHALL позволять выбрать для пайплайна и для его агентского шага агента, модель или tier и effort, а также снять выбор, и SHALL записывать результат в `pipeline_agents` или `step_agents` файла `~/.stepcast/config.yml`, сохраняя комментарии, проверяя результат схемой конфигурации и подменяя файл атомарно. Выбор tier снимает `model` той же записи, выбор модели снимает `model_tier`. Опустевшая запись удаляется вместе с опустевшими родительскими ключами. После записи экран показывает заново раскрытый пайплайн, действующую политику и отметку у записи, которая не влияет на шаг: проигрывает документу либо перекрыта проектным файлом.

#### Scenario: Выбор модели для шага
- **WHEN** пользователь на карточке шага `implement/code` пайплайна `p` выбирает модель `sonnet`
- **THEN** `~/.stepcast/config.yml` содержит `step_agents.p.implement.code.model: sonnet`, прежние комментарии файла сохранены, а карточка показывает модель шага с источником `step_agents`

#### Scenario: Снятие выбора
- **WHEN** пользователь снимает единственное поле записи `step_agents.p.implement.code`
- **THEN** в файле не остаётся ни этой записи, ни опустевших `step_agents.p.implement` и `step_agents.p`

#### Scenario: Запись без действия помечена
- **WHEN** при `agent_policy: force` пользователь выбирает модель для шага, объявившего `model` сам
- **THEN** запись сохраняется, а карточка шага помечает её как проигрывающую документу и показывает прежнюю модель шага

### Requirement: Учётные данные бэкенда объявляются только глобальной конфигурацией

Ключ `backends.<id>.credentials` SHALL быть допустим только в `~/.stepcast/config.yml`, а проектный конфиг и слой умолчаний вклада плагина MUST его отклонять.
Отказ MUST называть путь ключа и файл, в котором он найден.

#### Scenario: credentials в проектном конфиге

- **WHEN** `.stepcast/config.yml` содержит `backends.claude.credentials.ANTHROPIC_API_KEY`
- **THEN** разбор конфигурации отклоняет её с указанием, что ключ допустим только в глобальной конфигурации

#### Scenario: credentials в умолчаниях плагина

- **WHEN** вклад плагина бэкенда приносит в умолчаниях запись `credentials`
- **THEN** загрузка плагина отклоняет умолчания с путём ключа

### Requirement: Поставляемое пакетом разрешается именем, а не прежним путём

Файл, поставляемый пакетом и называемый в документе именем формы `stepcast:<имя>` — схема, пайплайн поставки, обёртка раннера, — SHALL разрешаться в свой файл после любой перестановки модулей внутри пакета: имя MUST оставаться прежним, а разрешение MUST идти от корня пакета, найденного подъёмом, а не от глубины вызывающего модуля. Отказ на незнакомом имени MUST сохранить прежний текст и прежний перечень поставляемого. Прогон, снятый снимком движка прежней раскладки, MUST продолжать исполняться своим снимком: записанный в лок путь указывает внутрь снимка, и переезд в рабочем дереве его не задевает.

#### Scenario: Обёртка раннера поставки разрешается после переезда

- **WHEN** конфигурация объявляет обёртку раннера именем поставки
- **THEN** она разрешается в файл собранного пакета, и шаг исполняется тем же argv, что и до переезда

#### Scenario: Незнакомое имя отказывает прежним текстом

- **WHEN** документ называет схему, пайплайн поставки или обёртку именем, которого пакет не несёт
- **THEN** отказ приходит прежним текстом с прежним перечнем поставляемого

#### Scenario: Прогон прежнего снимка движка продолжается

- **WHEN** возобновляется прогон, снятый снимком движка до переезда
- **THEN** он исполняется своим снимком, и записанные в лок пути остаются верными

### Requirement: Режим доставки правки кабинета объявляется ключом project.proposals

Конфигурация SHALL принимать ключ `project.proposals` со значением `queue` либо `direct`, где `queue` — умолчание, ставящее предложенную правку файла кабинета в очередь, а `direct` — разрешение записать её немедленно. Ключ MUST приниматься только в `.stepcast/config.yml` и MUST отклоняться в `~/.stepcast/config.yml` тем же правилом, что `project.check`, `project.tools` и `project.edit_paths`: режим доставки принадлежит репозиторию, а не машине. Сверх того ключ MUST отклоняться в документе пайплайна — в отличие от `project.edit_paths`, который пайплайн объявлять вправе, — потому что пайплайн и есть тот, кого настройка ограничивает. Значение вне двух названных MUST быть отказом разбора с перечнем допустимых.

#### Scenario: Проект объявил прямую запись

- **WHEN** `.stepcast/config.yml` несёт `project.proposals: direct`
- **THEN** конфигурация разрешается, и действующим режимом доставки значится прямая запись

#### Scenario: Умолчание

- **WHEN** ключ не объявлен ни одним слоем
- **THEN** действующим режимом значится очередь

#### Scenario: Ключ в машинном конфиге

- **WHEN** `~/.stepcast/config.yml` объявляет `project.proposals`
- **THEN** разрешение конфигурации отказывает, называя ключ и место, где он допустим

#### Scenario: Ключ в пайплайне

- **WHEN** документ пайплайна объявляет `project.proposals` верхним ключом `project`
- **THEN** разбор отказывает, называя, что режим доставки объявляет только конфигурация репозитория

#### Scenario: Негодное значение

- **WHEN** объявлено значение вне `queue` и `direct`
- **THEN** разбор отказывает, перечисляя допустимые значения

### Requirement: Перечень команд, независимых от конфигурации

Система SHALL объявлять перечень встроенных команд, независимых от конфигурации, по правилу: команда независима тогда и только тогда, когда её исполнение не читает ни одного значения действующей конфигурации и ни одного вклада реестра. Перечень MUST состоять из имён встроенных команд: сегодня это `data`, `down` и `init`. Команда плагина MUST NOT попадать в перечень — её собственное имя приходит из конфигурации. Каждая встроенная команда MUST принадлежать ровно одной стороне границы: либо перечню, либо множеству команд, отказывающих при неразбираемой конфигурации.

#### Scenario: Граница покрывает весь состав встроенных команд

- **WHEN** к встроенным командам добавлена новая, не названная в перечне
- **THEN** она отказывает при неразбираемой конфигурации наравне с прочими зависимыми, а не исполняется молча

#### Scenario: Команда плагина независимой не бывает

- **WHEN** плагин объявляет команду `hello`, а `.stepcast/config.yml` не разбирается
- **THEN** `stepcast hello` завершается ошибкой конфигурации, потому что состав команд при неразобранной конфигурации неизвестен

### Requirement: Независимая команда исполняется, не читая конфигурацию

Система SHALL исполнять команду из перечня независимых, не разрешая конфигурацию и не загружая плагины вовсе. Состояние файлов `~/.stepcast/config.yml` и `<проект>/.stepcast/config.yml` MUST NOT влиять на исход такой команды — ни нечитаемый файл, ни неразбираемый YAML, ни несоответствие схеме, ни ключ, недопустимый в своём слое. Разбор аргументов такой команды MUST выполняться описанием этой же команды, а её код возврата MUST быть кодом возврата процесса.

#### Scenario: Публикация данных работы при неразбираемом проектном конфиге

- **WHEN** `.stepcast/config.yml` не разбирается как YAML, а шаг прогона вызывает `stepcast data set итог готово`
- **THEN** данные работы записаны, команда завершается кодом `0`, и диагностика конфигурации не печатается

#### Scenario: Неразбираемый глобальный конфиг

- **WHEN** `~/.stepcast/config.yml` не соответствует схеме, а вызвана `stepcast down`
- **THEN** команда исполняется и сообщает об исходе остановки витрины

#### Scenario: Заведение пайплайна поверх сломанной конфигурации

- **WHEN** `.stepcast/config.yml` содержит ключ, недопустимый в проектном слое, а вызвана `stepcast init`
- **THEN** `stepcast.yml` и пример работы созданы, команда завершается кодом `0`

#### Scenario: Объявленный плагин не существует

- **WHEN** конфигурация разбирается, но объявляет модуль плагина, которого нет, а вызвана `stepcast data get`
- **THEN** команда исполняется: модуль не импортируется, потому что независимая команда плагинов не загружает

### Requirement: Команда, читающая конфигурацию, отказывает вместо подстановки умолчаний

Система SHALL прекращать команду, не входящую в перечень независимых, при любой ошибке разрешения конфигурации, кодом ошибки конфигурации. Сообщение MUST называть файл и, если известно, место внутри документа и способ починки. Система MUST NOT подставлять вместо непрочитанного объявления встроенные умолчания и MUST NOT разрешать конфигурацию из части слоёв, пропустив сломанный.

#### Scenario: Состояние прогонов при сломанной конфигурации

- **WHEN** `.stepcast/config.yml` не разбирается, а вызвана `stepcast status`
- **THEN** команда завершается кодом ошибки конфигурации, называя файл и причину, и не читает каталог прогонов по умолчаемому `runs.root`

#### Scenario: Уборка при сломанной конфигурации

- **WHEN** `.stepcast/config.yml` не разбирается, а вызвана `stepcast gc --older-than 30d`
- **THEN** команда завершается кодом ошибки конфигурации и не удаляет ничего

#### Scenario: Отчёт о конфигурации при сломанной конфигурации

- **WHEN** `.stepcast/config.yml` не разбирается, а вызвана `stepcast config`
- **THEN** команда завершается кодом ошибки конфигурации, и отчёт не печатается вовсе

### Requirement: Команда перечня, обратившаяся к конфигурации, отказывает внятно

Система SHALL отказывать сообщением о нарушенном объявлении, если команда, названная независимой, обращается к действующей конфигурации или к реестру вкладов. Сообщение MUST называть имя команды и то, что она объявлена независимой от конфигурации. Система MUST NOT отдавать такой команде конфигурацию, собранную из одних встроенных умолчаний.

#### Scenario: Команда перечня читает конфигурацию

- **WHEN** команда из перечня независимых обращается к действующей конфигурации своего окружения
- **THEN** вызов завершается ошибкой, называющей команду и её объявленную независимость, а не значением умолчания

### Requirement: Справка при неразбираемой конфигурации остаётся отказом разбора

Система SHALL отвечать ошибкой конфигурации на вызов без команды, на `--help` и на неизвестную команду, если конфигурация не разрешается. Перечень команд в этом случае MUST NOT печататься: собранный без плагинов, он умолчал бы о командах, объявленных конфигурацией.

#### Scenario: Справка при сломанной конфигурации

- **WHEN** `.stepcast/config.yml` не разбирается, а вызвано `stepcast --help`
- **THEN** печатается диагностика конфигурации с именем файла и причиной, а перечень команд не печатается

#### Scenario: Неизвестная команда при сломанной конфигурации

- **WHEN** `.stepcast/config.yml` не разбирается, а вызвана несуществующая команда
- **THEN** ответом остаётся диагностика конфигурации, а не сообщение о неизвестной команде

### Requirement: Команда проверки документов изменения объявляется в конфигурации

Конфигурация SHALL принимать в секции `project.spec` ключ `check` — полную команду, которой репозиторий проверяет документы изменения.

Значение — строка целиком, а не имя инструмента с дописанными движком
подкомандой и флагами: устройство команды знает только объявивший её, и
движок MUST передавать её оболочке не разбирая — тем же правилом, каким он
передаёт `project.check`.

Ключ MUST проверяться той же моделью, что `project.check` и
`project.spec.tool`: непустая строка, строка из одних пробельных символов
отклоняется разбором конфигурации. Требование непустоты MUST быть выражено и
в публикуемой JSON Schema, а не только в модели.

Встроенного умолчания у ключа MUST NOT быть: команда, подставленная за автора,
была бы верна ровно для того репозитория, из которого её списали. Ключ MUST
оставаться необязательным сам по себе — его отсутствие не ошибка, пока на него
никто не сослался.

Ключ MUST быть допустим только в `.stepcast/config.yml` и отклоняться в
`~/.stepcast/config.yml` тем же правилом, что остальные ключи секции
`project`: практика спецификации принадлежит репозиторию, а не машине.

Слияние секции по листьям MUST сохраняться: объявить `check` в одном слое, а
`dir`, `rules` или `tool` в другом можно, и одно другого не затирает.

Ключ MUST приниматься и объектной формой элемента `project.nested_repos` — той
же моделью объявления практики, что у корня, а не отдельной.

#### Scenario: Ключ объявлен в проектном конфиге

- **WHEN** `.stepcast/config.yml` содержит `project: { spec: { check: 'openspec validate "$SPEC_CHANGE" --strict' } }`
- **THEN** действующее значение `project.spec.check` равно объявленной строке целиком
- **AND** отчёт `stepcast config` называет источником этот файл

#### Scenario: Ключ не объявлен

- **WHEN** ни один слой конфигурации не задаёт `project.spec.check`
- **THEN** конфигурация разрешается без ошибки, а значение отсутствует

#### Scenario: Пустая команда

- **WHEN** конфигурация содержит `project: { spec: { check: "   " } }`
- **THEN** чтение конфигурации завершается ошибкой, называющей файл и ключ

#### Scenario: Ключ в глобальном конфиге

- **WHEN** `~/.stepcast/config.yml` содержит `project: { spec: { check: "make spec-check" } }`
- **THEN** чтение конфигурации завершается ошибкой, называющей файл и предлагающей `.stepcast/config.yml`

#### Scenario: Соседний ключ группы не затирается

- **WHEN** `.stepcast/config.yml` объявляет `project.spec.dir`, `project.spec.rules` и `project.spec.tool`, а документ пайплайна — только `project.spec.check`
- **THEN** действуют все четыре значения: три из конфигурации, `check` из пайплайна

#### Scenario: Вложенный репозиторий объявляет свою команду

- **WHEN** элемент `project.nested_repos` объявлен объектом `{ dir: backend, check: "make test", spec: { dir: docs/changes, rules: docs/rules.md, tool: make, check: "make spec-check" } }`
- **THEN** конфигурация разрешается без ошибки, а объявление этого репозитория несёт свою команду проверки документов изменения

#### Scenario: Публикуемая схема повторяет требование

- **WHEN** `schema/config.schema.json` описывает `project.spec.check`
- **THEN** описание требует строку с непустой длиной и образцом непробельного символа — тем же, что у `project.check`

### Requirement: Вложенный репозиторий объявляет свою проверку и практику спецификации

Элемент списка `project.nested_repos` SHALL допускать вторую, объектную форму — каталог репозитория вместе с его командой проверки и его практикой спецификации — наравне с прежней формой одной строки.

Объектная форма MUST состоять из обязательного `dir` и необязательных `check`
и `spec` (`dir`, `rules`, `tool`) — тех же моделей, что и одноимённые ключи
секции `project`: непустая строка у команды и имени инструмента,
относительный путь без сегмента `..` у каталогов, отказ символам шаблона
глоба у `dir`. Строковая форма MUST означать тот же элемент без объявлений.
Обе формы MUST давать читателям состава (составной якорь, проверка чистоты,
изоляция дорожки) прежний перечень каталогов — приведение форм MUST быть
одно на движок, а не по читателю. Повтор одного каталога в составе MUST быть
отказом разбора конфигурации. Объявления вложенных, как и сам состав, MUST
NOT публиковаться подстановкой `${project.*}`: значений тут по числу
репозиториев, и выбрать из них нечем, пока не выбран пункт.

#### Scenario: Объектная форма элемента

- **WHEN** элемент `nested_repos` объявлен объектом с `dir`, `check` и `spec`
- **THEN** конфигурация разбирается, а состав дерева содержит этот каталог наравне с объявленными строкой

#### Scenario: Строковая форма сохраняется

- **WHEN** элементы `nested_repos` объявлены строками, как прежде
- **THEN** поведение состава не меняется ни в одном читателе

#### Scenario: Элемент без каталога

- **WHEN** объектная форма не называет `dir` либо называет его пустой строкой
- **THEN** разбор конфигурации отказывает, называя ключ

#### Scenario: Недопустимые значения объявлений

- **WHEN** `check` пуста или состоит из пробелов, либо путь практики абсолютен или содержит `..`
- **THEN** разбор конфигурации отказывает той же диагностикой, что и у одноимённых ключей секции `project`

#### Scenario: Повтор каталога в составе

- **WHEN** один и тот же каталог назван в составе дважды — в любых формах
- **THEN** разбор конфигурации отказывает, называя каталог

#### Scenario: Объявления вложенных не подставляются

- **WHEN** документ ссылается на `${project.nested_repos}` либо на объявление вложенного репозитория
- **THEN** раскрытие отказывает как на имени вне состава пространства `project`

### Requirement: Объявление, читаемое командой, живёт в конфигурации проекта

Секция `project` конфигурации SHALL быть единственным местом, откуда команды движка читают объявления репозитория: слой документа пайплайна командам не виден.

Ключ `project.**` MUST оставаться допустимым только в проектной
конфигурации. Документ пайплайна MUST сохранять право объявлять `project`
для подстановки `${project.*}` — этот слой не отменяется, — но объявление,
которое обязано быть видно и команде, MUST жить в `.stepcast/config.yml`.
Нехватка объявления в конфигурации MUST называться отказом команды с именем
файла, а не толковаться умолчанием: молчаливая подмена вернула бы проверку
не того репозитория.

#### Scenario: Команда читает конфигурацию

- **WHEN** объявления репозитория лежат в `.stepcast/config.yml`
- **THEN** команда движка получает те же значения, что и подстановка `${project.*}` документа

#### Scenario: Объявление только в пайплайне

- **WHEN** значение объявлено верхним ключом `project` документа пайплайна и не объявлено в конфигурации
- **THEN** подстановка `${project.*}` продолжает раскрываться этим значением, а команда движка отказывает, называя `.stepcast/config.yml`

#### Scenario: Секция project в глобальной конфигурации

- **WHEN** объявления вложенного репозитория написаны в `~/.stepcast/config.yml`
- **THEN** разбор отказывает тем же правилом, что и для прочих ключей `project.**`

### Requirement: Секция project объявляет вложенные репозитории дерева

Секция `project` SHALL принимать ключ `nested_repos` — непустой список каталогов рабочего дерева, каждый из которых является отдельным репозиторием git.

Каждый элемент MUST быть относительным путём от корня репозитория без сегмента
`..` — той же моделью, что `project.spec.dir` и `project.edit_paths`. Сверх неё
элемент MUST NOT содержать символов шаблона глоба: значение называет конкретный
каталог, по которому заводится отдельное частное состояние и чьим именем
префиксуются пути, — шаблон нечем ни открыть, ни приписать к пути. Завершающий
разделитель MUST отбрасываться, повторы MUST отбрасываться, а сам состав MUST
приводиться к одному порядку независимо от порядка объявления.

Пустой список MUST отклоняться разбором — той же причиной, что `project.tools:
[]` и `project.edit_paths: []`: объявление, не называющее ни одного каталога,
почти наверняка забытая правка, а не «вложенных репозиториев нет». Отсутствие
ключа MUST NOT быть ошибкой и MUST означать однорепозиторное дерево.

Ключ MUST приниматься только в проектном конфиге: в глобальном он MUST
отклоняться тем же правилом и тем же сообщением, что остальные ключи секции.
В отличие от остальных ключей секции, документ пайплайна MUST NOT принимать его
верхним ключом `project` — состав вложенных репозиториев описывает форму
состояния дерева, а она обязана быть одна на дерево: два пайплайна одного
проекта с разным составом снимали бы в одном каталоге несравнимые между собой
якоря. Отказ MUST называть ключ.

Пространство подстановки `${project.*}` MUST NOT пополняться этим именем:
значение читает движок, а не документы. Обращение к нему MUST отказывать
действующим сообщением о составе пространства.

#### Scenario: Объявление в проектном конфиге

- **WHEN** `.stepcast/config.yml` содержит `project.nested_repos: [public-site, vendor/sdk]`
- **THEN** действующая конфигурация несёт оба каталога

#### Scenario: Ключ не объявлен

- **WHEN** `.stepcast/config.yml` не содержит `project.nested_repos`
- **THEN** разбор конфигурации проходит, а состав вложенных репозиториев пуст

#### Scenario: Пустой список

- **WHEN** `.stepcast/config.yml` содержит `project.nested_repos: []`
- **THEN** разбор завершается ошибкой, называющей файл и ключ

#### Scenario: Непригодное значение элемента

- **WHEN** элемент списка — пустая строка, абсолютный путь, путь с сегментом `..` или путь с символом шаблона глоба
- **THEN** разбор завершается ошибкой, называющей файл и ключ

#### Scenario: Объявление в глобальном конфиге

- **WHEN** `~/.stepcast/config.yml` содержит `project.nested_repos`
- **THEN** разбор завершается ошибкой о ключе, недопустимом в глобальном конфиге

#### Scenario: Объявление в документе пайплайна

- **WHEN** документ пайплайна содержит `project: { nested_repos: [public-site] }`
- **THEN** разбор документа завершается ошибкой, называющей ключ

#### Scenario: Обращение подстановкой

- **WHEN** документ содержит `${project.nested_repos}`
- **THEN** разбор завершается ошибкой с перечнем имён пространства `project`, среди которых этого имени нет

#### Scenario: Отчёт о конфигурации

- **WHEN** пользователь выполняет `stepcast config` в дереве с объявленным составом
- **THEN** объявленные каталоги напечатаны именами и с указанием источника, а не счётчиком

### Requirement: Границы правок объявляются в конфигурации

Конфигурация SHALL принимать в секции `project` ключ `edit_paths` — список путей и шаблонов от корня репозитория, правка которых в этом репозитории и есть работа над ним.

Значение — список путей, а не готовый предикат: форму предиката собирает файл
работы, потому что работа добавляет к объявленному свои записи, а список между
слоями заменяется целиком и дописать к нему было бы нечем.

Каждый элемент MUST проверяться тем же правилом, что `project.spec.dir`:
пустая строка, строка из пробельных символов, абсолютный путь и путь с
сегментом `..` отклоняются разбором конфигурации. Правило MUST быть тем же
самым, а не повторённым: пути в предикат границ приходят относительно корня
рабочего дерева, и запись, которой ни один из них не может соответствовать, —
не расширенная граница, а тихо бесполезное объявление. Шаблоны глоба
(`src/**`, `*.md`) MUST приниматься: граница правок из них и состоит.

Пустой список MUST отклоняться там же и по той же причине, что `project.tools`:
объявление, не называющее ни одного пути, — забытая правка, а не «править
нечего».

Требование непустоты — и строки, и списка — MUST быть выражено в публикуемой
JSON Schema, а не только в модели: обрезку пробелов схема не переносит.

Встроенного умолчания у ключа MUST NOT быть: раскладка, подставленная за
автора, была бы верна ровно для того репозитория, из которого её списали. Ключ

### Requirement: Инструменты репозитория объявляются в конфигурации

Конфигурация SHALL принимать в секции `project` ключ `tools` — список имён команд, которыми в этом репозитории собирают, проверяют и запускают код.

принадлежит бэкенду, а не репозиторию. Пробел внутри значения MUST

сужение права.

Каждый элемент MUST быть непустым по тому же правилу, что `project.check` и

JSON Schema, а не только в модели: обрезку пробелов схема не переносит, и без

подставленный за автора, был бы верен ровно для того репозитория, из которого
его списали. Ключ MUST оставаться необязательным: его отсутствие — не ошибка,
пока на него никто не сослался.

`~/.stepcast/config.yml` тем же правилом, что остальные ключи секции

свои, называет их вместо, а не вдобавок. Слияние секции `project` по листьям
MUST сохраняться: объявить `tools` в одном слое, а `check` в другом можно, и
одно другого не затирает.

### Requirement: Практика спецификации проекта объявляется в конфигурации

Конфигурация SHALL принимать в секции `project` группу `spec` с ключами `dir`, `rules` и `tool` — объявлением того, где живут документы изменения, по каким правилам они пишутся и каким инструментом заводятся.

`dir` — каталог документов изменения; документы изменения `<слаг>` лежат в
`<dir>/<слаг>/`. `rules` — путь к файлу правил репозитория, который читает
работа, заводящая описание изменения. `tool` — имя команды инструмента
спецификации; значение открывает право на её запуск и не несёт аргументов.

Каждый ключ MUST быть необязательным сам по себе: слои конфигурации сливаются
по листьям, и объявить можно часть группы. Встроенных умолчаний у ключей MUST
NOT быть — путь, подставленный за автора, указывал бы в чужом репозитории на
несуществующий каталог.

Значения `dir` и `rules` MUST быть относительными путями от корня
репозитория: пустая строка, строка из пробельных символов, абсолютный путь и
путь, выходящий за корень сегментом `..`, отклоняются разбором конфигурации.
Причина в потребителе: `dir` раскрывается в границу правок `<dir>/**`, и
пустое значение превратило бы её в разрешение на всё дерево, а `..` вывело бы
границу за пределы проверяемого дерева. Значение `tool` MUST быть непустым по
той же причине, по какой непуста команда проверки: право, собранное из пустого
имени, либо расширяет разрешённое молча, либо отказывает без причины.

Требование непустоты MUST быть выражено и в публикуемой JSON Schema, а не
только в модели: обрезку пробелов схема не переносит, и редактор принимал бы
значение, которое движок отвергает.

#### Scenario: Группа объявлена в проектном конфиге

- **WHEN** `.stepcast/config.yml` содержит `project: { spec: { dir: "openspec/changes", rules: ".stepcast/prompts/spec-rules.md", tool: "openspec" } }`
- **THEN** действующие значения `project.spec.dir`, `project.spec.rules` и `project.spec.tool` равны объявленным
- **AND** отчёт `stepcast config` называет источником этот файл

#### Scenario: Часть группы

- **WHEN** конфигурация объявляет только `project.spec.dir`
- **THEN** конфигурация разрешается без ошибки, а `project.spec.rules` и `project.spec.tool` отсутствуют

#### Scenario: Группа не объявлена

- **WHEN** ни один слой конфигурации не задаёт `project.spec`
- **THEN** конфигурация разрешается без ошибки, а значения группы отсутствуют

#### Scenario: Пустой каталог документов

- **WHEN** конфигурация содержит `project: { spec: { dir: "   " } }`
- **THEN** чтение конфигурации завершается ошибкой, называющей файл и ключ

#### Scenario: Абсолютный путь

- **WHEN** конфигурация содержит `project: { spec: { dir: "/tmp/changes" } }`
- **THEN** чтение конфигурации завершается ошибкой, называющей ключ и требование относительного пути

#### Scenario: Выход за корень репозитория

- **WHEN** конфигурация содержит `project: { spec: { rules: "../rules.md" } }`
- **THEN** чтение конфигурации завершается ошибкой, называющей ключ

#### Scenario: Неизвестный ключ группы

- **WHEN** конфигурация содержит `project: { spec: { folder: "openspec/changes" } }`
- **THEN** чтение конфигурации завершается ошибкой о неизвестном ключе

### Requirement: Проектный-только запрет действует на вложенные ключи секции project

Запрет объявлять секцию `project` в глобальной конфигурации SHALL действовать на все ключи под ней, а не только на ключи первого уровня.

Шаблон ключей MUST допускать хвостовую форму `**` — «названный ключ и всё под
ним». Перечисление уровней вместо неё (`project.*`, `project.*.*`) MUST NOT
использоваться: сопоставление требует равного числа сегментов, и каждое
углубление секции открывало бы дыру, о которой ничто не сообщает.

Хвостовая форма MUST быть единственной допустимой формой `**` в шаблоне
ключей: в середине пути у неё нет потребителя, а сопоставление с откатом ради
неё избыточно.

#### Scenario: Вложенный ключ в глобальном конфиге

- **WHEN** `~/.stepcast/config.yml` содержит `project: { spec: { dir: "openspec/changes" } }`
- **THEN** любая команда, читающая конфигурацию, завершается ошибкой с указанием ключа `project.spec.dir`
- **AND** подсказка называет `.stepcast/config.yml` как верное место объявления

#### Scenario: Ключ первого уровня по-прежнему отклоняется

- **WHEN** `~/.stepcast/config.yml` содержит `project: { check: "npm run check" }`
- **THEN** чтение конфигурации завершается ошибкой с указанием ключа `project.check`

#### Scenario: Проектный конфиг не ограничен запретом

- **WHEN** `.stepcast/config.yml` содержит `project: { spec: { dir: "docs/changes" } }`, а глобальный конфиг секции `project` не содержит
- **THEN** конфигурация разрешается без ошибки

#### Scenario: Соседняя секция не задета шаблоном

- **WHEN** `~/.stepcast/config.yml` содержит `defaults: { model: "sonnet" }`
- **THEN** конфигурация разрешается без ошибки

### Requirement: Команда проверки проекта объявляется в конфигурации

Конфигурация SHALL принимать секцию `project` с ключом `check` — строкой,
несущей команду проверки репозитория. Значение MUST быть непустым: пустая
строка и строка из одних пробельных символов отклоняются разбором
конфигурации, потому что пустая команда даёт нулевой код возврата и превращает
проверку в тихое согласие. Ключ MUST быть необязательным: репозиторий, которому
проверять нечем, конфигурацию с этой секцией не заводит, и отсутствие ключа
само по себе MUST NOT быть ошибкой.

Встроенного умолчания у `project.check` MUST NOT быть: команда, подставленная
за автора, исполнялась бы в чужом репозитории.

#### Scenario: Команда объявлена в проектном конфиге

- **WHEN** `.stepcast/config.yml` содержит `project: { check: "npm run check" }`
- **THEN** действующее значение `project.check` равно `npm run check`
- **AND** отчёт `stepcast config` называет источником этот файл

#### Scenario: Команда не объявлена

- **WHEN** ни один слой конфигурации не задаёт `project.check`
- **THEN** конфигурация разрешается без ошибки, а значение `project.check` отсутствует

#### Scenario: Пустая команда

- **WHEN** конфигурация содержит `project: { check: "   " }`
- **THEN** чтение конфигурации завершается ошибкой, называющей файл и ключ

#### Scenario: Неизвестный ключ секции

- **WHEN** конфигурация содержит `project: { chek: "npm run check" }`
- **THEN** чтение конфигурации завершается ошибкой о неизвестном ключе

### Requirement: Секция project допустима только в проектной конфигурации

Ключи секции `project` SHALL приниматься только из `.stepcast/config.yml` и
MUST отклоняться с ошибкой при чтении `~/.stepcast/config.yml`. Сообщение MUST
называть ключ и предлагать перенести значение в проектный конфиг.

Правило зеркалит запрет машинно-зависимых ключей (`runs.root`,
`backends.*.command`) в проектном конфиге: у каждого вида ключей есть
единственный верный слой, и слой, общий всем репозиториям машины, не может
объявлять команду одного из них.

#### Scenario: Команда проверки в глобальном конфиге

- **WHEN** `~/.stepcast/config.yml` содержит `project: { check: "npm run check" }`
- **THEN** любая команда, читающая конфигурацию, завершается ошибкой с указанием ключа `project.check`
- **AND** подсказка называет `.stepcast/config.yml` как верное место объявления

#### Scenario: Проектный конфиг не ограничен этим правилом

- **WHEN** `.stepcast/config.yml` содержит `project: { check: "./gradlew check" }`, а глобальный конфиг секции `project` не содержит
- **THEN** конфигурация разрешается без ошибки

### Requirement: Вложенный репозиторий объявляет свои инструменты

Объектная форма элемента `project.nested_repos` SHALL принимать необязательный ключ `tools` — перечень имён инструментов этого репозитория, той же моделью, что и `project.tools`: непустой список непустых строк.

Значение MUST складываться с корневым `project.tools`, а не замещать его, — в
отличие от `check` и `spec`, которые репозиторий объявляет вместо корневых.
Причина в смысле величины: `check` описывает репозиторий целиком, и корневая
команда в его каталоге была бы просто неверной, тогда как инструменты
накапливаются — `git` и `npm` корневого перечня верны в любом дереве, а
`./gradlew` верен только там, где лежит обёртка.

Порядок MUST быть объявленным, корневые впереди; повтор имени между
перечнями MUST схлопываться в одну запись — две одинаковые записи политики
доступа означают то же, что одна, и различить их нечем.

Репозиторий, не объявивший ключ, MUST получать ровно корневой перечень —
поведение, бывшее до появления ключа. Дерево, не объявившее инструментов ни
корнем, ни репозиторием, MUST оставаться деревом без объявленных
инструментов, а не деревом с пустым перечнем.

#### Scenario: Репозиторий добавляет свой инструмент

- **WHEN** корень объявляет `tools: [npm, git]`, а элемент состава — `dir: mobile` с `tools: ["./gradlew"]`
- **THEN** действующий перечень репозитория `mobile` — `npm`, `git`, `./gradlew` в этом порядке

#### Scenario: Повтор между перечнями

- **WHEN** репозиторий объявляет инструмент, уже названный корнем
- **THEN** в действующем перечне он встречается один раз, на корневом месте

#### Scenario: Репозиторий своих инструментов не объявляет

- **WHEN** элемент состава несёт `check` и `spec`, но не `tools`
- **THEN** действующий перечень репозитория совпадает с корневым

#### Scenario: Пустой перечень репозитория

- **WHEN** элемент состава объявляет `tools: []`
- **THEN** разбор конфигурации отказывает — той же причиной, что и `project.tools: []`

### Requirement: Ключ plugins складывается между слоями

Конфигурация SHALL принимать ключ `plugins` — список строк — в глобальном и проектном слоях. Значения слоёв MUST объединяться в порядке «глобальный, затем проектный» с сохранением порядка внутри слоя; повтор строки MUST схлопываться в одно вхождение. Пустой список MUST отклоняться разбором как объявление, не объявляющее ничего. Требование MUST быть выражено в публикуемой JSON Schema конфигурации. Каждая строка ключа MUST быть сокращённой формой строки дерева плагинов (возможность `plugin-tree`), то есть вставкой в конец своего слоя, и MUST быть доступна для замены и отключения патчем вышестоящего слоя.

#### Scenario: Объединение слоёв

- **WHEN** глобальный слой объявляет `plugins: ["a"]`, проектный — `plugins: ["b", "a"]`
- **THEN** действующий список — `["a", "b"]`

#### Scenario: Пустой список

- **WHEN** конфигурация содержит `plugins: []`
- **THEN** чтение конфигурации завершается ошибкой, называющей файл и ключ

#### Scenario: Строка ключа отключается патчем

- **WHEN** глобальный конфиг объявляет `plugins: ["a"]`, а проектный патч объявляет строку `a` с `enabled: false`
- **THEN** модуль `a` не загружается

### Requirement: Отчёт о конфигурации показывает плагины и их умолчания

Отчёт `stepcast config` SHALL показывать вклад каждого слоя в список `plugins` по образцу складывающихся списков и SHALL печатать раздел о загруженных плагинах. Значение, полученное из умолчаний плагина, MUST показываться с источником `plugin:<имя плагина>`. Действующее значение ключа `plugins` в отчёте MUST быть проекцией итогового дерева — модулями действующих строк в порядке дерева, — а не объединением объявленных списков: состав, который отчёт называет действующим, MUST совпадать с составом, который загружается. Строки встроенного слоя в это значение MUST NOT входить: их `use` (`stepcast:<имя>`) модулем не является. Строка, принесённая одним лишь патчем, MUST быть в нём названа, даже если ключ `plugins` не объявлял ни один слой.

#### Scenario: Источник умолчания плагина

- **WHEN** `backends.codex.sessions` получено из умолчаний плагина `codex-adapter`
- **THEN** отчёт показывает значение с источником `plugin:codex-adapter`

#### Scenario: Отключённая патчем строка не числится действующей

- **WHEN** патч отключил строку, объявленную ключом `plugins`
- **THEN** отчёт не показывает её модуль среди действующих, а вклад слоя в ключ `plugins` показывает как объявленный

#### Scenario: Строка, объявленная одним лишь патчем

- **WHEN** ключ `plugins` не объявлен ни одним слоем, а патч вставляет строку с модулем
- **THEN** отчёт называет этот модуль действующим значением ключа `plugins`

### Requirement: Слой конфигурации включает файл патча дерева плагинов

Слой конфигурации SHALL состоять из двух документов: `config.yml` и `plugins.patch.yml` того же каталога. Домашний слой MUST читаться из `~/.stepcast/`, проектный — из `.stepcast/` корня проекта. Патч MUST участвовать только в сборке дерева плагинов и MUST NOT сливаться с прочими значениями конфигурации по точечным путям. Отсутствие файла патча MUST быть обычным состоянием, а не отказом. Чтение конфигурации, у которой патч не разбирается или не проходит схему, MUST отказывать так же, как отказывает неразбираемый `config.yml`: с именем файла, местом и подсказкой.

#### Scenario: Патч читается вместе со слоем

- **WHEN** в `.stepcast/` лежат `config.yml` и `plugins.patch.yml`
- **THEN** значения конфигурации берутся из первого, состав плагинов — из обоих

#### Scenario: Патча нет

- **WHEN** файла `plugins.patch.yml` нет ни в одном слое
- **THEN** конфигурация разрешается без ошибок, а дерево плагинов собирается из встроенных строк и ключа `plugins`

#### Scenario: Патч не разбирается

- **WHEN** `plugins.patch.yml` содержит неверный YAML
- **THEN** любая команда, разрешающая конфигурацию, завершается ошибкой, называющей файл и место

### Requirement: Таблица раннеров объявляется секцией runners

Конфигурация SHALL содержать секцию `runners` — записи вида «имя → argv-префикс `command` и необязательный список расширений `extensions`», пополняемые и глобальным, и проектным конфигом.

Встроенный слой MUST поставлять записи `node` (`.js`, `.mjs`, `.cjs`),
`node-ts` (`.ts`, `.mts`, с `--experimental-strip-types`), `python3` (`.py`) и
`sh` (`.sh`) — на тех же правах, что прочие встроенные умолчания, с
происхождением «встроенное умолчание» в `stepcast config`. Имя записи MUST
состоять из букв, цифр, дефиса и подчёркивания; `command`, названный слоем,
MUST быть непустым списком непустых строк — строковой формы у него нет, потому
что правил разбиения строки на слова у движка нет; каждое расширение MUST
начинаться с точки. Слои MUST сливаться по листьям, как `backends`, в обе
стороны: запись вправе назвать одни `extensions` либо один `command`,
перекрывая одноимённую поле за полем, а не отменяя её целиком. Запись,
действующая после слияния всех слоёв, `command` иметь MUST: раннер, ни в одном
слое её не назвавший, — отказ разбора конфигурации с его именем, потому что
пустая команда дала бы argv из одного пути скрипта, то есть запуск файла
напрямую.

Отчёт `stepcast config` MUST печатать действующие `command` и `extensions`
записи значениями, а не их количеством: это единственный отчёт, отвечающий на
вопрос «чем исполнится файл этого расширения» и показывающий, какой слой
перехватил расширение.

Секция MUST быть допустима в обоих конфигах: в отличие от команды бэкенда,
раннер — обычно имя в `PATH`, и зависимость репозитория от него принадлежит
репозиторию.

#### Scenario: Встроенная таблица есть без всякой конфигурации

- **WHEN** ни один файл конфигурации секции `runners` не содержит
- **THEN** действующая таблица содержит `node`, `node-ts`, `python3` и `sh`, и `stepcast config` называет их источником встроенное умолчание

#### Scenario: Проект пополняет таблицу

- **WHEN** проектный конфиг объявляет `runners.uv.command: [uv, run, --script]`
- **THEN** действующая таблица содержит и встроенные записи, и `uv`, а происхождение `uv` называет файл проектного конфига

#### Scenario: Слияние по листьям

- **WHEN** домашний конфиг объявляет только `runners.python3.command: [python3.12]`
- **THEN** запись `python3` сохраняет встроенный список расширений и получает новую команду

#### Scenario: Слияние по листьям в обратную сторону

- **WHEN** домашний конфиг объявляет только `runners.python3.extensions: ['.py', '.py3']`
- **THEN** запись `python3` сохраняет встроенную команду и закрепляет за собой оба расширения

#### Scenario: Запись без команды

- **WHEN** ни один слой не назвал `command` объявленного раннера
- **THEN** разбор конфигурации отказывает, называя раннер и ключ `command`

#### Scenario: Форма записи проверяется

- **WHEN** конфигурация объявляет `runners.uv.command: "uv run"` либо расширение без точки
- **THEN** разбор конфигурации отклоняет значение, называя файл и ключ

#### Scenario: Отчёт называет команду и расширения

- **WHEN** проектный конфиг объявил `runners.uv` с расширением `.py`, и напечатан `stepcast config`
- **THEN** отчёт показывает команду `uv` и её расширения значениями, называя рядом слой, который их дал

### Requirement: Расширение, названное дважды, разрешается слоем или отказом

Расширение, закреплённое за разными раннерами в разных слоях конфигурации, SHALL принадлежать записи ближайшего слоя: проектный конфиг важнее домашнего, домашний — встроенной таблицы.

Два раннера **одного** слоя, назвавшие одно расширение, MUST быть ошибкой
конфигурации с именами обоих: между собой они несравнимы, и выбор по порядку
ключей документа был бы решением случая. Явный `runner` на шаге MUST оставаться
сильнее любого закрепления расширения.

#### Scenario: Проект перехватывает расширение

- **WHEN** проектный конфиг объявляет `runners.uv` с расширением `.py`, а встроенная таблица держит `.py` за `python3`
- **THEN** скрипт `.py` без явного `runner` исполняется раннером `uv`

#### Scenario: Спор внутри одного слоя

- **WHEN** проектный конфиг объявляет два раннера с расширением `.py`
- **THEN** разбор конфигурации отказывает, называя оба имени и расширение

#### Scenario: Явное имя сильнее закрепления

- **WHEN** расширение `.py` закреплено за `uv`, а шаг объявляет `runner: python3`
- **THEN** исполняется раннер `python3`
