# run-cleanup Specification

## Purpose
Команда `burnex gc`, отбор прогонов по возрасту, минимальный набор файлов, переживающих уборку, отчёт без действия при отсутствии `--older-than`.
## Requirements
### Requirement: Уборка без порога возраста только отчитывается

Команда `burnex gc` SHALL без ключа `--older-than` перечислять прогоны
текущего проекта как кандидатов на удаление вместе с датой завершения и
оценкой занимаемого места, показывать суммарную оценку и завершаться кодом 0,
не удаляя ничего. Вывод MUST называть флаг, которым удаление выполняется.

#### Scenario: Отчёт без действия

- **WHEN** `burnex gc` вызвана без `--older-than`
- **THEN** команда печатает список прогонов с их размером и итоговую сумму
- **AND** ни один файл прогона не удалён

#### Scenario: Подсказка о флаге удаления

- **WHEN** `burnex gc` вызвана без `--older-than`
- **THEN** вывод называет `--older-than` как способ выполнить удаление

#### Scenario: Нет прогонов

- **WHEN** у проекта ещё нет ни одного прогона
- **THEN** команда сообщает об этом и завершается кодом 0

### Requirement: Уборка по возрасту удаляет прогоны старше порога

Команда `burnex gc --older-than <длительность>` SHALL удалять прогоны
текущего проекта, чей возраст превышает указанную длительность, и оставлять
остальные нетронутыми. Возраст прогона SHALL вычисляться от `finished_at` из
его `run.json`; если `finished_at` отсутствует — от `started_at`. Формат
длительности MUST совпадать с форматом `timeout` и `budget.wallclock`.

#### Scenario: Удаление прогонов старше порога

- **WHEN** вызвана `burnex gc --older-than 30d`, а прогон завершился 40 дней назад
- **THEN** директория этого прогона больше не содержит `workspace/`, `jobs/`, `artifacts/`, `anchors/`, `pipeline.lock.yml` и `events.ndjson`

#### Scenario: Прогоны младше порога не трогаются

- **WHEN** вызвана `burnex gc --older-than 30d`, а прогон завершился 10 дней назад
- **THEN** его директория остаётся без изменений

#### Scenario: Возраст прерванного прогона

- **WHEN** прогон не содержит `finished_at` в `run.json`
- **THEN** его возраст вычисляется от `started_at`

#### Scenario: Отчёт об удалённом

- **WHEN** уборка по порогу возраста завершилась
- **THEN** вывод перечисляет удалённые прогоны и суммарно освобождённое место

### Requirement: Уборка сохраняет минимум и работает без подтверждения

Уборка SHALL сохранять `run.json`, `status.json` и `usage.json` каждого
удаляемого прогона и удалять остальное содержимое его директории. Команда
MUST NOT запрашивать интерактивное подтверждение: решение об удалении
принимается наличием и значением `--older-than`, а не диалогом в терминале.

#### Scenario: Минимум остаётся

- **WHEN** прогон подвергся уборке
- **THEN** `run.json`, `status.json` и `usage.json` этого прогона читаются как прежде

#### Scenario: Без интерактивного ввода

- **WHEN** `burnex gc --older-than <длительность>` вызвана в неинтерактивном окружении без доступного stdin
- **THEN** команда выполняет удаление и завершается, не ожидая ввода

### Requirement: Срок сужает исход в снятии записей командой

`stepcast gc --stats` SHALL применять `--older-than` к признаку `--failed` по «и»: при обоих ключах MUST сниматься только записи отказавших прогонов старше срока. Один `--older-than` MUST снимать все записи старше срока, один `--failed` — все записи отказавших прогонов. Отбор записей командой MUST совпадать с отбором витрины при тех же условиях.

#### Scenario: Отказавшие старше срока

- **WHEN** вызвана `stepcast gc --stats --failed --older-than 2d`, а в хранилище есть запись отказавшего вчера прогона, запись отказавшего десять дней назад и запись успешного десять дней назад
- **THEN** снята только запись отказавшего десять дней назад

#### Scenario: Срок без исхода

- **WHEN** вызвана `stepcast gc --stats --older-than 2d`
- **THEN** сняты все записи старше двух дней независимо от исхода

### Requirement: Перенос накопленного в хранилище годен к вызову перед отбором

Перенос прогонов, лежащих на диске корня, в хранилище расхода SHALL быть доступен в виде, не ограниченном одним вызовом за время жизни процесса, и MUST допускать сужение обхода до одного проекта либо до явного списка прогонов. Защита от повторного переноса MUST оставаться у того входа, который зовут при открытии хранилища, и MUST NOT распространяться на догон, который зовут перед отбором. Догон MUST дописывать записи только тех прогонов, каталоги которых лежат на диске и чья сводка расхода уже подведена, MUST NOT переписывать и MUST NOT удалять ни одной уже существующей строки хранилища и MUST NOT изменять ни одного каталога прогона. Повторный догон при неизменном диске MUST не дописывать ничего. Отказ дозаписи — корень только для чтения, кончилось место, чужой файл хранилища — MUST вырождать догон в отсутствие свежих записей и MUST NOT доходить до вызывающего исключением: догон пополняет производное, а зовут его пути, которые сами по себе только читают.

#### Scenario: Прогон появился после первого переноса

- **WHEN** перенос уже выполнялся в этом процессе, а затем на диске появился прогон со сводкой расхода и без записи в хранилище
- **THEN** догон дописывает его запись, и отбор по хранилищу его называет

#### Scenario: Догон сужен проектом

- **WHEN** догон запрошен с указанием проекта, а прогоны без записи есть в двух проектах корня
- **THEN** дописаны записи прогонов названного проекта, и ни одной записи прогона чужого проекта не появилось

#### Scenario: Догон ничего не портит

- **WHEN** догон выполняется на хранилище, где уже есть записи
- **THEN** прежние строки остались как были, ни одна не удалена и не переписана, а каталоги прогонов не изменились

#### Scenario: Повторный догон впустую

- **WHEN** догон выполнен дважды подряд, а диск между вызовами не менялся
- **THEN** второй вызов не дописал ни одной строки

#### Scenario: Догон сужен списком прогонов

- **WHEN** догон запрошен с явным списком прогонов, а в корне есть и другие прогоны без записи
- **THEN** дописаны записи названных прогонов, и ни одного из остальных догон не обходил

#### Scenario: Дозапись отказала

- **WHEN** догон выполняется на корне, в который писать нельзя, а прогон без записи на диске есть
- **THEN** догон завершается без исключения, отбор идёт дальше и отвечает по тому, что в хранилище уже было

### Requirement: Отбор по признаку называет прогоны, которых не смог проверить

Отбор кандидатов на уборку по признакам SHALL сообщать вместе с отобранными число прогонов области отбора, статус которых не удалось прочитать ни из состояния, ни из манифеста и которые в отбор поэтому не попали. Такой прогон MUST NOT считаться ни оборванным, ни отказавшим: признак «оборванные» утверждает, что состояние осталось `running`, а процесс мёртв, и прогон, о котором ничего не известно, ему не отвечает. Такой прогон MUST по-прежнему попадать в отбор по сроку, возраст которого считается по времени его каталога, и, попав в него, MUST NOT входить в число непроверенных: он уже назван списком, и счёт его вторым разом прибавлял бы к итогу отбора то, что в итоге уже посчитано. Число непроверенных MUST считаться по той же области, что и отбор: по одному проекту, если проект назван, и по всем проектам корня, если не назван.

#### Scenario: Прогон с испорченным состоянием при отборе по признаку

- **WHEN** запрошен отбор по признакам «оборванные» и «отказавшие», а в корне лежит прогон, чьи `status.json` и `run.json` не проходят разбор
- **THEN** он не назван отобранным, и отбор сообщает, что один прогон проверить не удалось

#### Scenario: Тот же прогон при отборе по сроку

- **WHEN** запрошен отбор прогонов старше срока, которому отвечает время каталога этого прогона
- **THEN** он назван отобранным, и число непроверенных прогонов при этом нулевое

#### Scenario: Читаемые прогоны непроверенными не считаются

- **WHEN** запрошен отбор по признаку в корне, где все журналы читаются
- **THEN** число непроверенных прогонов нулевое

### Requirement: Удаление файлов прогона не удаляет его статистику

Удаление прогона SHALL снимать его файлы и MUST NOT снимать его записи в хранилище расхода как побочный эффект.
Это относится и к уборке по возрасту, и к полному снятию прогона, и к снятию
группы прогонов. Удаление, которому велено сохранить статистику, MUST
убедиться, что запись прогона в хранилище есть, — дописав её из каталога, если
её ещё нет, — и только затем снимать файлы. Удаление, которому велено снять и
статистику, MUST снимать её отдельным действием после того, как файлы сняты
успешно. Исход удаления MUST называть судьбу записи отдельно от судьбы файлов и
MUST NOT называть снятой или сохранённой запись, которой у прогона не было.

#### Scenario: Уборка по возрасту не трогает хранилища

- **WHEN** выполнена `stepcast gc --older-than <длительность>`
- **THEN** записи убранных прогонов остались в хранилище расхода

#### Scenario: Полное снятие прогона сохраняет его запись

- **WHEN** прогон снят целиком, а снятия статистики не просили
- **THEN** каталога прогона нет, а его запись в хранилище читается

#### Scenario: Оборванный прогон получает запись перед снятием файлов

- **WHEN** снимаются файлы прогона, который никогда не завершался и записи в хранилище не имеет, а статистику велено сохранить
- **THEN** его запись дописывается из каталога до снятия файлов и переживает его

#### Scenario: Прогон, записи которому не было

- **WHEN** снимаются файлы прогона, у которого нет и не появилось записи в хранилище
- **THEN** исход этого адреса говорит, что записи не было, а не что она снята

#### Scenario: Снятие файлов не удалось — статистика не снимается

- **WHEN** удалению велено снять и файлы, и статистику, но снятие файлов отказало
- **THEN** запись прогона в хранилище остаётся

### Requirement: Снятие статистики — отдельная цель команды уборки

Команда `stepcast gc --stats` SHALL снимать записи хранилища расхода и MUST NOT трогать файлов прогонов.
Отбор записей MUST задаваться теми же признаками, что и отбор файлов: возраст,
исход и проект. Область снятия записей MUST совпадать с областью снятия
файлов — проектом рабочего каталога, — а чужой проект MUST адресоваться явно,
своим ключом. Названный явно проект MUST сам по себе быть признаком отбора:
без возраста и исхода он снимает записи своей области целиком. Без единого
признака команда MUST только отчитываться, ничего не снимая. Один вызов команды
MUST снимать либо файлы, либо записи, но не то и другое сразу. Отчёт
`stepcast gc` без ключей MUST называть и каталоги прогонов с их объёмом, и
число записей хранилища, и MUST называть способ снять каждое из двух.

#### Scenario: Снятие записей не трогает файлов

- **WHEN** вызвана `stepcast gc --stats --older-than 1y`
- **THEN** записи старше года сняты, а каталоги прогонов остались нетронутыми

#### Scenario: Отчёт называет обе величины

- **WHEN** `stepcast gc` вызвана без ключей
- **THEN** вывод называет прогоны с их объёмом, число записей хранилища и флаги, которыми снимается каждое из двух

#### Scenario: Снятие записей не выходит за пределы проекта

- **WHEN** `stepcast gc --stats --older-than <срок>` вызвана внутри одного проекта, а в корне прогонов есть записи и других проектов
- **THEN** сняты только записи этого проекта, а записи остальных остались

#### Scenario: Названный проект снимает свою область целиком

- **WHEN** вызвана `stepcast gc --stats --project <ключ>` без возраста и исхода
- **THEN** сняты записи названного проекта, а записи прочих проектов остались

#### Scenario: Снятие записей без признаков ничего не снимает

- **WHEN** вызвана `stepcast gc --stats` без единого признака отбора
- **THEN** команда перечисляет записи-кандидаты и завершается кодом 0, не сняв ни одной

#### Scenario: Две цели не совмещаются в одном вызове

- **WHEN** один вызов просит снять и файлы, и записи
- **THEN** команда отказывает и называет, что за вызов делается ровно одна из двух операций

### Requirement: Уборка не снимает каталог, перенятый другим прогоном

Уборка прогона SHALL оставлять на месте каталог рабочего дерева, перенятый другим, ещё не убранным прогоном.
Это касается и удаления директории прогона, и снятия учётной записи рабочего
дерева репозитория: каталог, в котором идёт или шло продолжение, MUST NOT
исчезать из-под прогона, которому он теперь принадлежит. Владельцем каталога
MUST считаться последний перенявший его прогон из уцелевших — тот, чьё
перенимание не перехвачено следующим звеном цепочки продолжений. Остальное
содержимое убираемого прогона MUST удаляться как обычно, а отчёт MUST называть
сохранённый каталог и прогон, ради которого он сохранён.

#### Scenario: Каталог сохранён ради продолжения

- **WHEN** уборка удаляет прогон, каталог работы которого перенят другим, ещё не убранным прогоном
- **THEN** этот каталог и его учётная запись рабочего дерева остаются на месте
- **AND** отчёт называет сохранённый каталог и прогон, который его перенял

#### Scenario: Обычный каталог удаляется

- **WHEN** уборка удаляет прогон, каталоги работ которого никем не переняты
- **THEN** каталоги удаляются, а их учётные записи рабочих деревьев снимаются

### Requirement: Перенятый каталог снимает тот прогон, который им владеет

Уборка прогона SHALL снимать каталог, перенятый этим прогоном у другого, — и сам каталог, и его учётную запись рабочего дерева.
Перенятый каталог лежит в раскладке прогона-источника, поэтому уборка MUST
сверять путь с директорией того прогона, в которой каталог физически лежит, а
не с директорией убираемого. Каталог, перенятый ещё более поздним прогоном,
MUST оставаться на месте по требованию «Уборка не снимает каталог, перенятый
другим прогоном». Уборка MUST NOT сообщать о неснятой учётной записи там, где
она снята или сохранена намеренно.

#### Scenario: Перенявший прогон снимает свой каталог

- **WHEN** убирается прогон, перенявший каталог работы у прогона-источника, и более поздних перенявших нет
- **THEN** каталог и его учётная запись рабочего дерева сняты
- **AND** отчёт не называет неснятых записей

#### Scenario: Источник снимается целиком, когда каталог освободился

- **WHEN** прогон-источник убирается повторно после того, как перенявший его прогон убран
- **THEN** каталог снят, а прогон-источник удаляется целиком

### Requirement: Удаление прогона с сохранённым каталогом оставляет его читаемым

Удаление прогона, чья директория хранит сохранённый каталог, SHALL оставлять его читаемой записью истории, а не пустым каталогом.
Директория такого прогона переживает удаление ради каталога, который в ней
лежит, поэтому удаление MUST вырождаться в уборку: содержимое снимается, а
`run.json`, `status.json` и `usage.json` остаются. Прогон MUST оставаться
разбираемым для перечня прогонов, разрешения идентификатора и обзора, а
повторное удаление после ухода перенявшего прогона MUST снимать его целиком.

#### Scenario: Прогон с сохранённым каталогом остаётся разбираемым

- **WHEN** удаляется прогон, каталог работы которого перенят другим прогоном
- **THEN** его `run.json`, `status.json` и `usage.json` остаются на месте, а остальное содержимое снято
- **AND** перечень прогонов проекта по-прежнему его называет

### Requirement: Полное снятие прогона отличается от уборки по возрасту

Движок SHALL различать два вида удаления: уборку (`stepcast gc`), которая сохраняет `run.json`, `status.json` и `usage.json` и оставляет прогон видимым в истории, и полное снятие прогона, которое удаляет его каталог целиком вместе с этим минимумом. Полное снятие MUST убирать и следы прогона в раскладке: ярлык `latest` проекта SHALL переставляться на новейший оставшийся прогон, а при отсутствии оставшихся — сниматься; проект, у которого не осталось ни одного прогона, SHALL терять свою запись в указателе `projects.json` вместе с каталогом проекта. Платформа без символических ссылок MUST NOT приводить к отказу снятия: прогон адресуется идентификатором, и отсутствие ярлыка работе не мешает.

#### Scenario: Каталог снят целиком

- **WHEN** прогон снят полностью
- **THEN** его каталога нет, включая `run.json`, `status.json` и `usage.json`

#### Scenario: Ярлык latest переставлен

- **WHEN** снят прогон, на который указывал `latest`, а у проекта остались другие прогоны
- **THEN** `latest` указывает на новейший оставшийся прогон

#### Scenario: Последний прогон проекта

- **WHEN** снят единственный прогон проекта
- **THEN** запись этого проекта исчезла из `projects.json`, а его каталог в корне прогонов снят

#### Scenario: Уборка остаётся уборкой

- **WHEN** прогон подвергся `stepcast gc --older-than`
- **THEN** он по-прежнему виден в истории со своим `run.json`, `status.json` и `usage.json`

### Requirement: Прогоны отбираются к снятию по признаку

Движок SHALL отбирать прогоны к полному снятию по признакам — оборванные, отказавшие, старше указанного срока — по всем проектам корня прогонов либо по одному проекту. По каждому отобранному прогону отбор SHALL отдавать его адрес `<ключ проекта>/<идентификатор>`, момент, от которого считается возраст, сам возраст и размер каталога на диске. Возраст и размер MUST вычисляться тем же кодом, каким их вычисляет отбор кандидатов `stepcast gc`: два ответа на вопрос «сколько прогону лет и сколько он занимает» разошлись бы при первой же правке. Отбор MUST NOT изменять ничего на диске.

Прогон с испорченным журналом MUST NOT выпадать из отбора молча: статус SHALL браться из манифеста, когда состояние не читается, а возраст прогона, чей манифест не читается, SHALL считаться по времени его каталога, и такой прогон SHALL быть помечен нечитаемым.

#### Scenario: Отбор по всем проектам

- **WHEN** отбор запрошен без указания проекта, а в корне есть прогоны двух проектов
- **THEN** в отбор попали подходящие прогоны обоих проектов, названные адресами с ключом проекта

#### Scenario: Возраст прерванного прогона

- **WHEN** отбирается прогон, чей `run.json` не содержит `finished_at`
- **THEN** его возраст посчитан от `started_at`

#### Scenario: Размер отобранного прогона

- **WHEN** прогон попал в отбор
- **THEN** назван размер его каталога, посчитанный обходом содержимого

#### Scenario: Прогон с нечитаемым манифестом

- **WHEN** отбирается прогон, чей `run.json` не разбирается
- **THEN** он назван в отборе с возрастом по времени каталога и помечен нечитаемым

#### Scenario: Отказ у прогона с нечитаемым состоянием

- **WHEN** отбирается по признаку «отказавшие» прогон, чей `status.json` не разбирается, а манифест несёт статус `failed`
- **THEN** он попал в отбор

#### Scenario: Отбор ничего не трогает

- **WHEN** отбор выполнен по любому набору признаков
- **THEN** все каталоги прогонов остались нетронутыми

### Requirement: Уборка снимает учётные записи рабочих деревьев, заведённых прогоном

Уборка прогона SHALL снимать учётные записи рабочих деревьев, заведённых этим прогоном, — каждую в том репозитории, которому она принадлежит, — до того как удалит каталоги прогона.

Снятие MUST охватывать и корневые деревья работ, и деревья объявленных
вложенных репозиториев внутри них. Перечень снимаемого MUST браться из
состояния прогона, записанного при заведении деревьев, — то есть уборка MUST
быть полной и после отказа прогона, отмены сигналом и остановки по бюджету, а
не только после успешного завершения.

Снятие MUST быть адресным: удаляется учётная запись названного рабочего дерева
и только она. Осиротевшие записи, заведённые не этим прогоном, MUST оставаться
нетронутыми — уборка MUST NOT снимать записи чужого репозитория списком по
признаку осиротелости.

Отказ снятия MUST NOT останавливать удаление прогона и MUST называться в исходе
по этому адресу: неснятая запись, о которой не сказано, — та самая цена, ради
которой ведётся учёт.

Названа MUST быть только запись, которая действительно осталась. Уборка, у
которой снимать уже нечего — тот же прогон убирается повторно, — MUST молчать:
выдуманная утечка обесценивает канал, заведённый ради настоящих.

#### Scenario: Записи прогона сняты

- **WHEN** удаляется прогон, заводивший рабочие деревья с объявленными вложенными репозиториями
- **THEN** учётных записей этих деревьев не остаётся ни в корневом репозитории, ни в репозиториях частей

#### Scenario: Чужие записи не тронуты

- **WHEN** в репозитории объявленной части есть учётная запись рабочего дерева, заведённая не этим прогоном
- **THEN** после уборки прогона она на месте

#### Scenario: Уборка после отказавшего прогона

- **WHEN** удаляется прогон, остановленный отказом, отменой или бюджетом
- **THEN** учётные записи всех заведённых им рабочих деревьев сняты

#### Scenario: Неснятая запись названа

- **WHEN** снятие учётной записи отказало
- **THEN** каталог прогона всё равно удалён, а исход по этому адресу называет неснятую запись

#### Scenario: Повторная уборка не выдумывает неснятых записей

- **WHEN** уже убранный прогон убирается второй раз
- **THEN** исход не называет ни одной неснятой записи
